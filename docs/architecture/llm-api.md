# LLM / agent API

Status: implemented ([below](#implementation-task-310)); the [hardening amendment](#amendment-hardening-a1-a2-a5-a7-agent-friction) (A1, A2, A5, A7) is accepted (user 2026-11-25, TG #331 "go", Q123) · Task: 1.6 of the [v0.1 plan](../plans/v0.1.md#1-docs-and-decisions-accepted-before-implementation) (implementation: 3.10, end-to-end: 3.11) · Principle: [principles.md §1](../principles.md#1-llm-first) · Decision: [ADR 0011](../decisions/0011-mcp-and-cli-agent-api.md) · Commands: [commands.md](commands.md)

How agents reach DFYOM: an **MCP server** (stdio for a headless instance, local HTTP for attaching to a running app) and a **CLI**, both thin adapters over the [command layer](commands.md). This doc maps commands, queries, jobs, errors and the action log onto MCP and the CLI, and defines agent sessions, project binding, coexistence with the GUI and safety. The [decisions](#decisions) were settled with the user; the sections after them specify them.

## Decisions

Settled with the user when this doc was accepted; the sections below specify them.

1. **One MCP tool per command and query**, input schemas with shared `$ref` definitions, a size-budget test and an `--areas` filter ([Exposure](#exposure-commands-and-queries-as-mcp-tools)).
2. **Output schemas are not listed** in `tools/list`; they are served by `dfyom://schema/{name}` and `dfyom tools` ([Schemas](#schemas)).
3. **App-scope dispatcher** (same pipeline, empty document) holding `library.*`, `feedsSpeeds.*` and the new `project.*` lifecycle commands ([App scope](#app-scope-and-project-scope)).
4. **One bound project per session** (`project.bind`; open, create and restore bind) ([Sessions](#sessions-and-sources)).
5. **Explicit attach** to the instance that owns a project: local HTTP or `dfyom mcp --connect`; a headless open of a locked project fails with a connect hint ([Coexistence](#coexistence-with-a-running-gui)).
6. **Agent-opened projects in the GUI** open a window and stay open after the session ends ([Sessions](#sessions-and-sources)).
7. **Local HTTP is on by default**, with every protection: `127.0.0.1` only, a bearer token in an owner-only discovery file, `Host`/`Origin` checks, a visible "agent connected" indicator, and a setting to turn it off ([Local HTTP](#local-http)).
8. **Jobs:** job tools return `{ jobId }`; `job.wait` blocks with a timeout and MCP progress; the CLI waits by default ([Jobs](#jobs)).
9. **User actions reach agents** as a digest line in every tool result plus `project.log.list`; the subscribable log resource is an extra ([Action log](#action-log-and-user-actions)).
10. **Undo:** the shared linear history under the stale-write rule, plus a `history.list` query ([Undo](#undo-and-history)).
11. **Real machines** (not v0.1, input to [run.md#safety](../modes/run.md#safety)): an explicit grant by the user at the GUI, per agent session and connection, revoked on disconnect, never for headless instances ([Permissions](#permissions)).
12. **`expectedRevision`** is a reserved optional top-level arg of every project-scope command, stripped by the adapter; like `apply` it is explained once in the primer, not listed in each tool schema ([Schemas](#schemas)).
13. **CLI:** `dfyom <name> <json>` one-shot (open → call → save on change → close), `dfyom batch` (JSON lines), `dfyom mcp`, `dfyom tools` ([CLI](#cli)).
14. **No job follow-up commands in v0.1**; adapters never dispatch them. When a job needs one, its definition declares it and the dispatcher dispatches it with `startRevision` ([Jobs](#jobs)).
15. **Headless runtime:** the CLI/MCP entry is a separate build output with no Electron import, run by the app's own binary with `ELECTRON_RUN_AS_NODE` when packaged (the `runAsNode` fuse stays enabled) and by `node` in tests ([Processes](#processes-and-hosting)).

## Requirements

- **Parity:** every user action is available to agents; the tool list is derived from the registry, never hand-written ([ADR 0005](../decisions/0005-shared-command-layer.md)).
- **Headless** operation (no window) and **multiple app instances** on one computer.
- **Multi-agent** workflows: several agents (and the user) on one project at once.
- An agent attached to a visible window **receives the user's actions**.
- Later (not v0.1): agent-authored run-mode automation scripts and live run supervision ([modes/run.md](../modes/run.md)).

### App scope and project scope

Today every command runs on a project dispatcher, so the library is unusable without an open project and project lifecycle is not a command (plan known issues: "app-level dispatcher", "no project opens via IPC/MCP/CLI"). Therefore ([decision 3](#decisions)):

- An **app-scope dispatcher** per instance: the same `createDispatcher` pipeline (lookup, `parseArgs`, FIFO, permission, one action-log event per call) over an empty `ProjectDoc` and an app registry. It holds `library.*`, `feedsSpeeds.*` and the project lifecycle below; these move out of `APP_COMMANDS`/`APP_QUERIES`. Names stay unique across both registries (registry test).
- **Project lifecycle commands** (all `effect`, app scope; handlers call the app host through a new `services.host` port):

| Name                       | Args                       | Result / notes                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| -------------------------- | -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `project.create`           | `{ name, unitSystem }`     | `{ key, revision }`; untitled until `project.save { target }`.                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| `project.open`             | `{ file, reset? }`         | `{ key, revision, alreadyOpen }`. A file already open **in this instance** returns its key instead of `persist.locked` (the storage rule is unchanged; the host checks its open map first). Recovery case → `persist.recovery` (new code, added to `ERROR_CODES` in 3.10) with the key in `data`. Incompatible pre-alpha data → the load error with a `project.incompatible` frame; `reset: true` (only after the user confirmed) replaces the file with an empty project ([persistence.md § Open](persistence.md#open)). |
| `project.close`            | `{ key?, confirm?: true }` | `key` defaults to the session's bound project ([A5](#amendment-hardening-a1-a2-a5-a7-agent-friction)). Unsaved changes need `confirm: true` (else `input.malformed`, rule `unsavedChanges`); the working folder then stays recoverable ([persistence.md](persistence.md#crash-recovery)). `run.busy` while a run job runs.                                                                                                                                                                                                |
| `project.list`             | `{}` (query)               | Open projects: `key`, file, name, `dirty`, `revision`, bound sources.                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| `project.recovery.list`    | `{}` (read-only effect)    | Wraps `listRecovery` ([persistence.md](persistence.md#crash-recovery)); an effect, since queries are synchronous ([implementation](#implementation-task-310)).                                                                                                                                                                                                                                                                                                                                                            |
| `project.recovery.resolve` | `{ key, action, confirm }` | Wraps `resolveRecovery`; `restore` opens the project.                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |

### Machine scope (DF80)

The instance has one machine connection ([run-v0.1.md](../modes/run-v0.1.md#processes)), and manual machine control needs no document ([run.md § Run without a project](../modes/run.md#run-without-a-project-df80)). So the host keeps a third dispatcher, the **machine-scope dispatcher**: the same pipeline (permission policy included) over an empty `ProjectDoc` with `services.machine` and `services.library`, and a registry (`createMachineScopeRegistry`, `MACHINE_SCOPE_COMMANDS` / `MACHINE_SCOPE_QUERIES` in `src/core/commands/registry.ts`) of the run commands that read no document: `run.connection.open` (with `machineId`), `run.connection.close`, `run.ports.scan`, `run.machine.home` / `unlock` / `jog` / `jogCancel` / `reset` / `probeZ`, `run.workZero.set`, `run.override.set`, `run.timeScale.set`, `run.job.continue`, `run.status.get`, `run.settings.check` (DF87), and the job built-ins `job.get`, `job.list`, `job.pause`, `job.resume`, `job.abort` (no history, no Apply).

- **Routing** (`AgentSession`): a session **without a bound project** sends those names (and `job.wait`) to the machine-scope dispatcher instead of answering `noProject`; `run.connection.open` with `planId` still answers `noProject`, and so do the plan-reading run commands (`run.job.start`, `run.job.check`, `run.align.*`). A bound session is unchanged: everything goes to its project's dispatcher.
- **Names are not new tools:** the commands are the project registry's own definitions, so the tool list and its budget ([DF79](#result-size)) do not change; the registry test checks the machine scope is a subset of the project scope.
- **Jobs of the machine scope from a bound session:** `job.get`, `job.pause`, `job.resume`, `job.abort` and `job.wait` with a job id the bound project does not know but the machine scope does run in the machine scope (`AgentSession`), so a project window or a bound agent stops (and follows) a homing or probing job started without a project. `job.list` stays per scope.
- **Pausing machine-scope jobs (DF82):** `job.pause` of a homing job (`run.machine.home`) fails `job.notPausable` (GRBL ignores a feed hold while homing; `job.abort` or `run.machine.reset` stop it with a reset), and `job.get`/`job.list` show it with `pausable: false`. `job.pause` of a Probe Z job (`run.machine.probeZ`) sends a feed hold and answers `{ state: 'paused' }` only once the controller reports `Hold:0`; `job.resume` sends cycle start and the probe goes on to its result; `job.abort` still resets. A job state never says paused while the machine moves ([commands.md](commands.md#pausing-a-job), [run.md](../modes/run.md#1-emergency-stop-stop-and-reset)).
- **Stop from any window:** a window's `job.abort` refused by its own session is tried in every other open project (`abortElsewhere`, `src/main/host/stop.ts`, called by `src/main/ipc.ts`), so a window without a project stops a project window's job. Agents are not windows: an unbound agent reaches only the machine scope's jobs with `job.abort`; `run.machine.reset` and `run.machine.jogCancel` act on the one connection from any scope. Tests: `src/main/host/machine-scope-stop.test.ts`.

### Session tools

A few tools are not registry entries because they depend on the session, not on a dispatcher (`history.list`, which shows whose step is on top, is a built-in query of every project dispatcher, [Undo](#undo-and-history)). They live in the shared session core (`src/core/agent/`), so MCP and CLI offer the same set, and they follow the [naming](commands.md#naming) rules:

| Name               | Args                                       | Result                                                                                                                                                                                                |
| ------------------ | ------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `project.bind`     | `{ key }`                                  | Binds the session to an open project (`project.open`/`create`/`recovery.resolve` bind automatically).                                                                                                 |
| `project.log.list` | `{ afterSeq?, sources?, names?, limit? }`  | Action-log events of the bound project ([Action log](#action-log-and-user-actions)); `gap: true` if evicted.                                                                                          |
| `job.wait`         | `{ jobId, timeoutSeconds?: 30 }` (max 300) | The `job.get` value once finished, at an operator wait of a run (`waiting`, [A2](#amendment-hardening-a1-a2-a5-a7-agent-friction)), or the current one on timeout (`timedOut: true`) ([Jobs](#jobs)). |

## Exposure: commands and queries as MCP tools

### Which

- **Every** command and query of both registries is a tool, plus the session tools. Nothing is hidden from agents; [Safety](#safety) gates what may run. Test fixtures (`commands.fixture.ts`) are never registered. Measured on 2026-11-18: 63 registry entries (43 commands, 20 queries); about 85 with run mode (3.9) and the tools above.
- Queries are **tools**, not MCP resources: models call tools; resources are application-driven in most clients. Resources are used only for streams and catalogs ([Resources](#resources)).

### Names

- MCP name = registry name with `.` → `_`: `design.pocket.add` → `design_pocket_add`. Registry names contain no `_` (`NAME_PATTERN`), so the mapping is bijective; it is the only transport-specific renaming ([commands.md](commands.md#naming)). Underscored names fit every common client and LLM tool-name rule (`^[a-zA-Z0-9_-]{1,64}$`); the server name `dfyom` is the client's prefix.
- No tool `title` (`CommandMeta.title` needs args). `description` = `summary` plus the kind line: "Undoable." / "Not undoable; writes app data." / "Starts a job; returns { jobId }, wait with job_wait." / "Affects a machine."

### Schemas

- `inputSchema` = `toolDescriptor(def).inputSchema` from [`json-schema.ts`](../../src/core/commands/json-schema.ts) ([commands.md](commands.md#json-schema-for-agent-tools)), without the **reserved keys**: `expectedRevision` (integer, every command of project scope, [decision 12](#decisions)) and `apply` (boolean, project-scope document commands, [apply.md](apply.md#agents-mcp-and-cli)); at the MCP and `batch` boundary also `detail` (`plan.get`, `plan.toolpath.get`, `design.shape.get`; since DF38 `plan.warning.list`, `design.operation.list`, `design.clones.preview`) with `from`/`count` (`plan.toolpath.get`, [Result size](#result-size)). They are not listed in any tool schema (on 47 tools they cost 3 K chars of the [size budget](#implementation-task-310)); the primer names them and which tools take them, and `apply` on a tool that does not take it fails with `input.malformed` naming the tools that do. The adapter removes them before `dispatch(…, { expectedRevision, apply })`; tests assert no command arg and no tool schema has either name.
- **Validation-only keywords are not listed** (hardening A8, [size budget](#implementation-task-310)): record-id patterns, `minLength: 1` and `maxLength` from 120 up are dropped from the listed schemas; the command still validates them and names the field. The quantity forms are explained once in the primer, not per field.
- **Compact emission** ([headroom work](#implementation-task-310)): `compactSchema` writes every listed schema in the shortest **equivalent** form, which accepts exactly the values the generated one accepts: a `$defs` entry only where its `$ref`s are shorter than the copies (`{"type":"string"}` is never shared, it is shorter than `{"$ref":"#/$defs/d1"}`); `const` without the `type` it already fixes; a nullable simple type as a type array (`"type": ["string", "null"]`, with an enum `null` joins it; JSON Schema 2020-12, MCP's default dialect); no allow-all keywords (`additionalProperties: {}`, and `properties: {}` below the root). A test expands every compact schema and compares it with the generated one in these forms.
- **Ids and names are not described per field**: `partId`, `planId`, the library ids and `name` have no field description; the primer says once that ids come from results and `name` is a display label. Field descriptions that say more (`"Shape id, e.g. shape1"`, an operation id that becomes a surface prefix, a name used in G-code comments) stay.
- **Listed sketches ("As <tool> <arg>")**: a long arg that another tool lists in full is listed as a sketch, an object or array of objects described "As design.shape.add items", from the definition's `listedArgs` ([commands.md](commands.md#json-schema-for-agent-tools)). Only the listing changes: the dispatcher validates the full `args` as before (same refusals, issue paths and unknown-key hints), `dfyom://schema/{name}` and `dfyom tools --json` serve the full input schema, and the primer explains the convention once. It is the F6 "as add" sketch ([v0.4 F6](#implementation-task-310)) made general. Used where the full arg is listed on the matching add tool and means the same there: `design.shape.update` `items`, `design.shape.item.update` `segments`/`fillets` (as a path item's), `library.{tool,machine,stock}.update` `values` (the update replaces all values), `design.clones.update`/`.preview` `source`/`rows`. Not used for args that differ from the add's or have no add (`plan.operation.update`, `plan.design.operation.update`), nor to hide arg names: every top-level arg stays listed by name.
- **Output schemas are not listed** in `tools/list` ([decision 2](#decisions)): they are 80 % of the size (470 K of 585 K chars; `plan.get` alone 148 K). They are served by the `dfyom://schema/{name}` resource and `dfyom tools --json`.
- Size: input schemas of all 63 entries are about 111 K chars (~28 K tokens), dominated by `library.{tool,machine}.{add,update}` (~13 K each, repeated quantity sub-schemas; since v0.2 they take quantity strings, [library.md](library.md#command-input)). 3.10 generates with shared definitions (`$defs`/`$ref` for reused schemas) and a test enforces a budget on the serialized `tools/list` (target: under 60 K chars), so growth is noticed when a command is added. Clients with deferred tool loading handle the rest.
- **Granularity:** ([decision 1](#decisions)) one tool per command/query (structural parity, client-side validation, no extra round trip). Server option `--areas design,plan,…` (MCP) restricts the list for small-context models; session tools and `history`/`job` are always listed.

### Annotations and server instructions

- MCP tool annotations are derived, never hand-set: query → `readOnlyHint: true`; `document` → `destructiveHint: false` (undoable); `effect`/`job` → `destructiveHint: true` when the args require `confirm` or the command is `machine`, else `false`; `machine: true` → `openWorldHint: true`; queries and `job.wait` → `idempotentHint: true`. `tools/list` leaves `idempotentHint` and `destructiveHint` out beside `readOnlyHint: true`: the MCP spec gives them meaning only when a tool is not read-only (`dfyom://schema/{name}` keeps the derived set).
- The `initialize` result's `instructions` is a short primer generated from one source file (`src/core/agent/primer.ts`, linking here): open or create a project first; quantities are strings as entered (`"6 mm"`, `"1/4\""`, a tolerance, a formula in design parameters; [quantities.md](quantities.md)); ids come from results, `name` is a display label, an arg described "As <tool> <arg>" takes what that arg takes ([Schemas](#schemas)); the reserved keys (`expectedRevision` on project commands, `apply` on tools described "Undoable.", `detail` on the summarized reads); compact results ([Result size](#result-size)); query before editing or pass `expectedRevision`; job tools return a `jobId`, wait with `job_wait`; `confirm: true` means the user agreed; the part, face and shape frames and the work zero ([A3](#a3-frames-in-the-primer-placed-bounds)).

### Library

The adapter uses the SDK's **low-level `Server`** of `@modelcontextprotocol/sdk` (MIT, GPL-compatible) with our JSON Schemas and own Zod parsing (`parseArgs`), not `McpServer.registerTool` with Zod shapes: it avoids coupling our Zod 4 schemas to the SDK's Zod version and keeps `parseArgs`' unknown-key rule.

## Data flow

### Results

Every tool call goes through `atBoundary` with `EntryPoint { kind: 'agent', name }` ([boundaries.md](../conventions/error-handling/boundaries.md#entry-points-ui-agent-cli-automation)) and returns a `CallToolResult`:

| Outcome         | `isError` | `structuredContent`                      | `content` (text, for clients without structured output)                                                                           |
| --------------- | --------- | ---------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| Command `Ok`    | `false`   | `{ value, revision }` (`CommandOutcome`) | Same JSON up to 32,000 chars, else an outline ([Result size](#result-size)), then the [digest](#action-log-and-user-actions) line |
| Query `Ok`      | `false`   | `{ value, revision }` (`QueryOutcome`)   | Same                                                                                                                              |
| Job started     | `false`   | `{ value: { jobId }, revision }`         | Same, plus "wait with job_wait"                                                                                                   |
| `Err(AppError)` | `true`    | `{ error: AppErrorData, retryable }`     | `code: message` and the issues, one per line                                                                                      |

- Errors are **tool execution errors** (`isError: true`), never JSON-RPC errors, so the model sees `code`, `issues` with `params` and frames and can self-correct ([app-error.md](../conventions/error-handling/app-error.md#serialization)). `retryable` comes from `ERROR_CODES`. JSON-RPC errors are only for protocol faults (unknown tool name, malformed request) – an unknown tool cannot be a known command, since the list equals the registry.
- `command.conflict` text says to re-query and retry ([commands.md](commands.md#stale-writes)); `permission.denied` names the command and source kind.
- **Explanations are data:** the calculator's derivation (formula, inputs and result per step) comes back verbatim, from `feedsSpeeds.suggest` outside a plan and `plan.operation.feeds.get` for a plan operation (with the values at use), so an agent can explain a number the same way the inspector's "Show calculation" does ([plan-v0.1.md](../modes/plan-v0.1.md#feeds-explanation-v02)).
- Results are `ResultWire` DTOs, shaped for agents at the MCP and `batch` boundary ([Result size](#result-size)); meshes are not exposed ([workers.md](workers.md#jobs-for-agents)).

### Result size

The black-box LLM test of 2026-11-22 (`.continuous/research/2026-11-22-llm-first-test.md`, F5) found results far too large for a model: every design edit carried all of the part's DFM warnings twice (`value.warnings` and `applied.warnings`, 23–30 KB for a one-field change), `plan_get` was 674 KB and `plan_toolpath_get` 7.45 MB, every quantity was a four-field object, and every result came twice (text and `structuredContent`). Since then the agent boundary shapes results; the command layer, the GUI's IPC and one-shot CLI calls (`dfyom <name>`) keep the full results. Implementation: [`src/core/agent/shape.ts`](../../src/core/agent/shape.ts) (`ResultShaper`, one per MCP session or `batch` run), [`results.ts`](../../src/core/agent/results.ts) (text).

Rules, applied to MCP results and `dfyom batch` lines:

1. **Summaries of the large reads.** `plan.get` returns a summary: plan id, name, status, design snapshot (part id, time, hash, operation count, `planEdits`), machine and stock names, and per setup its `direction` and `rotation` (always, also a top setup's `+z` and `0`, which the record leaves out; DF58), heights, `overreach` (DF59: how far the tool reaches past the stock sides on the machine, `{ xMin, xMax, yMin, yMax }` = left, right, front, back, in the project's units (mm, or inches in an inch project) rounded up to 0.1 mm / 0.01 in, 0 = within the outline; `null` while a toolpath of the setup is missing or stale; [plan-v0.2.md](../modes/plan-v0.2.md#tool-reach-past-the-stock-and-clamps-hardening-df59-interim)) and operations (id, kind, design operations, tool name, the five feeds values, `seconds` and `toolpath`: `current`/`stale`/`none` from the toolpath cache, finding counts by severity), with setup and plan `seconds` (`null` while a toolpath is missing or stale), per setup (hardening DF66) `toolChanges` (tool changes the operator makes, the one at the setup start included, none there when the tool stays in the spindle from the setup before) and `toolRuns` (`[{ tool, operations, seconds }]`: tool name, plan operation ids, seconds or `null`; [plan-v0.4.md](../modes/plan-v0.4.md#tool-changes-per-setup-hardening-df66)), and the plan's finding counts. `plan.toolpath.get` returns the toolpath's envelope: move count, moves per pass, the bounds of the move end points (drills: top and bottom), `stats` (cut and rapid length, estimated seconds), and its `overreach` (mm, as the query; DF59). Both carry a `detail` hint.
2. **Detail on request: reserved args** (like `expectedRevision` and `apply`, not listed in the tool schemas, so `tools/list` does not grow; the primer and the `detail` hint name them): `detail: "full"` on `plan.get` returns the whole record; on `plan.toolpath.get` it returns a range of the moves across passes, `from` (default 0) and `count` (default 500, max 5,000), each pass with the index of its `first` move in the range, plus `moves: { from, count, total, next }`. The whole program is `plan_export`. On other tools these keys are unknown arguments (`input.malformed`).
3. **DFM warnings as changes.** A result whose schema carries the part's DFM warnings (design edit commands) and every `applied.warnings` entry list only what changed against the warnings this session last received for that part: `{ count, added?, changed?, removed? }` (`added`/`changed` in full, `removed` as `{ code, operation, parameter? }`; empty lists left out). A warning's identity is code, operation and parameter (and its index among equal ones); `changed` = same identity, other content. The first time a part's warnings reach the session they are all `added`; `design.warning.list` stays complete and becomes the baseline. Only the part's warnings (the shared `Warnings` schema) are shaped: a query's own warnings, such as a Clones draft's in `design.clones.preview`, pass as they are and leave the baseline alone (X1). The baseline is per session and starts over when the session binds another project.
4. **Compact quantities.** A quantity DTO becomes the plain number when its source is a decimal literal equal to its value in the canonical unit (mm, deg, mm/min, rpm, W, bare scalar; `"6 mm"`, `"89"`), else `{ source, value }` (value in the canonical unit; `tolerance: { upper, lower }` when it has one), e.g. `{ "source": "1/4\"", "value": 6.35 }`. Inputs stay quantity strings. The exact rational is in the project file and the GUI; agents that need it read `{ source }` and re-enter it.
5. **Rounded floats.** Every non-integer number is rounded to 10 significant digits (`2.4000000000000004` → `2.4`; 0.1 µm or better on any part dimension).
6. **Text content is short.** `structuredContent` holds the result; the text block repeats it when its JSON is at most 32,000 chars (every summary and most reads; set high so text-only clients such as some agent hosts still see the result), else gives an outline (nested objects and lists after their first three items elided) with "the full result is in structuredContent". The MCP spec asks for the serialized JSON in a text block for backward compatibility (a SHOULD); the outline is the deliberate exception for large results. Clients that show only text see small results in full.

### Jobs

- A `job` command's tool returns `{ jobId }` at once, as the dispatcher does ([commands.md](commands.md#long-running-commands-jobs)). `job_get`, `job_list`, `job_pause`, `job_resume`, `job_abort` are the registry entries.
- **`job.wait`** ([decision 8](#decisions)) blocks until the job finishes, a run reaches an operator wait ([A2](#amendment-hardening-a1-a2-a5-a7-agent-friction)) or `timeoutSeconds` passes and returns the `job.get` value. If the call carries `_meta.progressToken`, the server sends `notifications/progress` from `JobHandle.onProgress` (`progress` = `done`, `total`, `message` = `label`; already throttled by the dispatcher). Cancelling the MCP request (`notifications/cancelled`) ends the wait, **not** the job (`job_abort` does that).
- A job's completion is also an action-log `job` event, so it shows up in the [digest](#action-log-and-user-actions) of the agent's next call.
- **Follow-up document commands:** ([decision 14](#decisions)) no v0.1 job needs one (toolpaths are derived, [plan-v0.1.md](../modes/plan-v0.1.md); evaluation and runs change no document). Adapters never dispatch follow-ups; this closes the plan known issue for v0.1.

### Action log and user actions

The [action log](commands.md#action-log) is how an agent sees what the user and other agents did. Most MCP clients do not show server notifications to the model, so the primary channel is pull plus piggyback ([decision 9](#decisions)):

- **Digest:** each session keeps a cursor (last seen `seq`). Every tool result of a bound session ends with one text line (and `_meta["dfyom/actions"]`) summarizing events **by other sources** since the cursor, e.g. `Since your last call: 3 actions by ui:win-1 (design.pocket.update ×2, history.undo), revision 41 → 44.` Then the cursor advances. Patches are never included.
- **Pull:** `project.log.list { afterSeq }` returns the events (args summarized, `withPatches: false`); a `gap` means the ring buffer dropped events and the agent should re-query what it needs.
- **Push (optional):** resource `dfyom://project/{key}/log` supports `resources/subscribe`; the server sends `notifications/resources/updated` (debounced 250 ms) and the client reads the resource with `?after=<seq>`. For clients and harnesses that act on notifications.

The reserved key `apply: false` batches several edits for one `project_apply`; `project.pending.get` lists what is pending. ## Sessions and sources

- **Source:** each MCP session is one [source](commands.md#stale-writes) `{ kind: 'agent', id }`: `stdio-<n>` or `http-<n>` (per `Mcp-Session-Id`), unique per instance. The client's `clientInfo.name` is logged with it and shown in the GUI ("Claude Code · http-2"). A CLI invocation or `dfyom batch` run is `{ kind: 'cli', id: 'cli-<pid>' }`. A `--connect` bridge keeps its client's identity (the HTTP session is the source).
- **Binding:** ([decision 4](#decisions)) a session is bound to at most one project; project-scope tools run on the bound project's dispatcher and fail with `input.malformed` (rule `noProject`, hint: open, create or bind) when none is bound. App-scope tools work unbound. Several projects = several sessions (cheap over HTTP; one headless process per project over stdio).
- **Concurrency:** the adapters never serialize a session's calls; every call goes straight to `dispatch`/`query`, so ordering is the project queue's ([commands.md](commands.md#concurrency)). **Urgent** commands – `run.machine.reset`, `run.machine.jogCancel` and `job.pause`/`job.resume`/`job.abort` – skip that queue ([run-v0.1.md](../modes/run-v0.1.md#safety-v01)), so an agent can stop a run or a job while another call (its own `job.wait`, or an effect waiting for the machine) is still pending. Their tool descriptions say "Runs immediately, even while other commands wait." The CLI reaches them on a running instance with `--connect`.
- **Stale writes** apply per source unchanged: an agent edits after a query or with `expectedRevision`; a user's edit in between gives `command.conflict` ([commands.md](commands.md#stale-writes)).
- **Lifecycle:**
  - Headless stdio: the process is the instance. On end of stdin: abort running jobs, close every project it opened (unsaved changes stay recoverable, as on `project.close { confirm: true }`), flush logs, terminate workers, exit 0.
  - HTTP session end (DELETE, or 30 min idle): unbind; projects stay open. Its running jobs keep running (they belong to the dispatcher).
  - Agent-opened projects in the GUI instance open a window and stay open after the session ends ([decision 6](#decisions)).

### Coexistence with a running GUI

One project has exactly one owner instance: the [lock](persistence.md#lock) holder, whose dispatcher is the only authoritative `ProjectDoc` ([commands.md](commands.md#project-state)). There is no shared-file editing between instances.

| Situation                                                   | Behaviour                                                                                                                                                         |
| ----------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Agent wants the project the user has open                   | Attach to that GUI: HTTP directly, or stdio via `dfyom mcp --connect`; then `project.list` / `project.bind`. Same dispatcher, queue, history and log as the user. |
| Headless `dfyom mcp` opens a file locked by a live instance | `persist.locked` as today; `data` adds the holder's instance id and, if it serves HTTP, the hint `dfyom mcp --connect <instance>` ([decision 5](#decisions)).     |
| GUI opens a file a headless instance holds                  | `persist.locked`; the GUI shows which agent instance holds it.                                                                                                    |
| Several GUIs / headless instances                           | Independent; each owns different projects; the library is shared ([library.md](library.md#storage), cross-instance revision check).                               |

**Discovery:** an instance serving HTTP writes `<appData>/instances/<instanceId>.json` `{ instanceId, pid, port, token, startedAt, appVersion }` (owner-only permissions: mode `0600`; Windows: user-profile ACL) and deletes it on quit; stale files (dead PID) are ignored and removed. `--connect` without an id picks the only live instance, else fails listing them. The lock's instance id names the file.

## Safety

### Permissions

- The dispatcher's `PermissionPolicy` stays the single gate ([commands.md](commands.md#dispatcher-pipeline) step 5); adapters add none. The default policy **denies by default**: UI sources are allowed; agent and CLI sources only on a connection the machine host reported as virtual, or to open a virtual connection when none is open. Unknown or real targets, a connection still opening and a missing machine port are denied ([commands.md](commands.md#dispatcher-pipeline), [grbl.md](grbl.md#transport-and-sender), [run-v0.1.md](../modes/run-v0.1.md#safety-v01)). Only virtual exists in v0.1, so an agent opens the virtual connection itself (`run_connection_open { target: 'virtual' }`) before any other `run.*` command. On a real (serial) connection agents may read the status, scan ports (`run.ports.scan`), wait and stop (`job.pause`, `job.abort`, `run.machine.jogCancel`, `run.machine.reset`), nothing that moves the machine (Q50, [run.md § Safety](../modes/run.md#2-who-may-command-a-real-connection-q50)).
- Real machines are specified in [run.md#safety](../modes/run.md#safety) before any serial connection exists; the direction for agents ([decision 11](#decisions)) is an explicit grant by the user at the GUI, per agent session and connection, revoked on disconnect, never available to headless instances.
- Destructive non-machine commands already need `confirm: true` in their args (library `remove`, recovery `discard`, replacing files in `project.save`/`plan.export`, `project.close` with unsaved changes). For agents `confirm: true` asserts the user agreed; the primer says so; it is logged with the source.
- No path sandbox in v0.1: a local agent already has the user's file access. HTTP hardening (below) keeps web pages out.

### Local HTTP

**On by default** in the GUI ([decision 7](#decisions)), with all of the protections below; none of them can be turned off.

- **Setting:** "Allow local agents to connect" (app setting, default on; persisted in the [settings store](../conventions/ui.md#settings) since 3.3b). Turning it off stops the server at once, ends every HTTP session (their running jobs keep running in their dispatchers) and deletes the discovery file; turning it on starts a new server with a new token. `--mcp-http=off|<port>` overrides the setting for one run. A headless `dfyom mcp` instance serves stdio only, HTTP only with `--mcp-http`.
- **Indicator:** while at least one agent session is attached, every window shows a visible "agent connected" indicator naming the sessions (client name and source id, [Sessions](#sessions-and-sources)); it links to the setting.
- Binds `127.0.0.1` only (never `0.0.0.0`/`::`); port random unless given. Streamable HTTP at `/mcp` (not the deprecated HTTP+SSE transport).
- **Bearer token:** 256 random bits per instance start, in the discovery file; every request needs `Authorization: Bearer <token>` (else 401). Compared in constant time; redacted in logs ([logging.md](../conventions/logging.md#redaction) already covers `authorization`, `token`).
- **DNS-rebinding guard:** reject requests whose `Host` is not `127.0.0.1:<port>`/`localhost:<port>`, and any request with an `Origin` header (browsers) – 403.
- Limits: request body 4 MB; at most 16 concurrent sessions.

**What on-by-default means for a fresh install.** The first launch, with no configuration, starts the server on a random loopback port and writes the discovery file with a new token. From then on:

- Any program running **as the same OS user** can read the discovery file and drive the app with the full tool set: open, edit, save and export projects, edit the shared library, and run the virtual machine. This is the same trust a local agent already has through the user's files (it could edit project files or run the CLI); the indicator makes an attached session visible.
- **Other OS users** on the computer cannot read the owner-only file and get 401. **Other computers** cannot reach a loopback socket. **Web pages** in a browser are rejected by the `Origin`/`Host` checks, including DNS rebinding.
- **No real machine** can be driven: v0.1 has only the virtual machine, and the permission policy denies agents on anything else ([Permissions](#permissions)). Before real machines exist, the explicit per-session grant ([decision 11](#decisions)) is what keeps an on-by-default endpoint from reaching hardware; real-machine work must re-check this default with [run.md#safety](../modes/run.md#safety).
- Users who do not want agents turn the setting off once; it stays off.

### Undo and history

- Agents use `history_undo`/`history_redo` on the one linear, shared history ([commands.md](commands.md#undo--redo)) ([decision 10](#decisions)). The stale-write rule makes an agent's undo safe by default: without a fresh read it may undo only while nobody else committed, i.e. its own step; after a query it undoes the top entry, whoever made it.
- `history.list` shows whose step is on top before undoing; undo/redo events name the entry in the log and the digest.
- **Live edits by the user** ([gestures](commands.md#gestures-live-edits)): a field's adjust panel in the GUI commits every −/+ step as its own command, so agents see each intermediate commit in the action log and the digest (`design.pocket.update ×5`), each with its own revision, and each `command` event carries the `gesture` id. The steps share one undo entry: after the session, `history.list` shows one step and one `history_undo` reverts the whole session. While the user is still adjusting, the entry grows; an agent commit in between ends the merge (the next step starts a new entry), so an agent never has its change folded into the user's. When the user cancels with Escape, the GUI sends `history.undo { gesture }`: logged as an `undo` event, the entry is discarded rather than kept for redo. The `gesture` arg of `history_undo` is for the GUI; an agent has no gestures (the option is not offered to agents), so it never needs it.
- Library edits (`effect`) are not undoable; the tool description says so.

## Amendment (hardening A1, A2, A5, A7): agent friction

Status: **accepted** (user 2026-11-25, TG #331 "go", Q123; implemented on the hardening branch; the user reviews it with the [hardening plan](../plans/hardening.md) task 1.3) · Source: the LLM-first black-box test of 2026-11-22 (`.continuous/research/2026-11-22-llm-first-test.md`, findings F3, F5, F8, F13) · Tasks: [hardening.md § 4](../plans/hardening.md) A1, A2, A5, A7 (the follow-up's A2, A3, A6 in [v0.4-llm-first.md](../plans/v0.4-llm-first.md))

No new tools ([A8](../plans/hardening.md)): every change is a default, a reserved arg, a field in an existing result or message text. The size of `tools/list` is logged under [Implementation](#implementation-task-310).

### A1: compact results

Most of F5 was fixed in v0.4 ([Result size](#result-size)); this closes the rest.

- **No stack, anywhere.** Errors already reach agents without `stack` ([Errors for agents](#implementation-task-310)). The shaper also drops a string `stack` key at any depth of a shaped value and of `applied` (an error kept as data inside a result, e.g. a toolpath failure in a job outcome), so no agent result carries one, whatever produced it. Stacks stay in the log.
- **Warnings as a delta plus a count:** as in [rule 3](#result-size). Within one result a part's warnings are listed once: `applied.warnings` of the part an edit's `value.warnings` already listed is `{ partId, count }` only.
- **One copy per result.** `structuredContent` and the text block hold the same result, as the MCP spec asks (a SHOULD for clients without structured output). That is one copy for the model: clients pass one of them to it (Claude Code passes `content`). Large results are outlined in text ([rule 6](#result-size)); the result itself never repeats an item.
- **`detail` on `design.shape.get`.** The reserved `detail` arg extends to `design.shape.get`, whose default stays `"full"` (agents read a shape's resolved loops to place features). `detail: "summary"` returns the shape's id, name, `source` and per item its kind and scalar fields (lists as their lengths: `points: 84`), `usedBy`, and `resolved` without `pieces` and `path` (kind, loop and hole counts, `elements`, `area`, `bounds`, `length`, `smallestInsideRadius`), or the `issues`. `plan.get` and `plan.toolpath.get` keep `"summary"` as their default ([rule 2](#result-size)); `detail: "summary"` is accepted on all three.

### A2: `job.wait` at operator waits

- **Returns at a wait.** While a run job (`run.job.start`) waits for the operator at a tool change or a program pause (M0), `job.wait` returns at once (`timedOut: false`, `state` still `running`) with `waiting`: `{ kind: 'toolChange', toolChange: { n, name } }` or `{ kind: 'programPause', pause }`, plus `next: { name: 'run.job.continue', args: { jobId, toolChange | pause } }`, the call that ends the wait after the operator's step (zero the new tool, or the step the M0 message asks for). A wait ended by a `run.job.continue` already logged is not reported again, so a `job_wait` right after a continue does not return the same wait while the machine leaves it.
- **Setup change.** A run job ends after its setup; when the plan has another one its outcome has `next` ([run-v0.1.md](../modes/run-v0.1.md#amendment-v02-task-e2-one-program-per-setup)). `job.wait` then adds `waiting: { kind: 'setupChange', setup: next, next: { name: 'run.job.start', args: { planId, setupId } } }` (the run result gains `planId`): re-fixture, set the work zero, then start that setup.
- **`run.job.continue` defaults.** `jobId` defaults to the run job of the connection; `toolChange` / `pause` default to the wait the run is at. Naming them stays the safe form: a retried call that names its wait never ends the next one, an unnamed retry may ([run-v0.1.md decision 9](../modes/run-v0.1.md#decisions)). The GUI always names the wait. `run.state` as before when the run waits at nothing.
- How: `job.wait` checks the machine status (`run.status.get`) when it starts, on each progress tick and every 250 ms while it waits on a `run.job.start` job; other jobs are unchanged.

### A5: unknown arguments and `project.close`

- **Unknown-argument hints.** `parseArgs` names the closest valid key of the same object when one is close (edit distance with transpositions at most a third of the longer name, one name inside the other, or a common prefix of at least 60 % of the shorter one): `unknown argument "timeout"; did you mean "timeoutSeconds"?`. The issue keeps rule `unrecognized_keys` and gains `params: { key, suggestion?, valid }` (`valid`: the object's keys, at most 20). It applies to every caller of `parseArgs` (agents, CLI, GUI); the GUI never sends unknown keys. Only schema keys are suggested; the reserved keys are named by the primer.
- **`project.close` without `key`** closes the session's bound project; with no bound project it fails with `input.malformed` (rule `noProject`, the usual hint). The session fills the key before dispatch, so the action log shows it.

### A7: refusals that say what to do

Every agent-facing refusal names the **field** (the issue `path`, or the arg in the message), the **rule** (the issue `rule`, or a code that names it) and a **next step** (a tool to call, a value to pass, or a value range). The general paths:

- `parseArgs`/`parseWith` (`input.malformed`) and the `model.invariant` refusals of the design, plan, shape and Clones commands: the message names the first issue (`job.wait: jobId: expected string, received undefined`, then `(+ n more)`; helper `issueSummary`), not only a count ("2 invalid value(s)"); each issue line keeps path, message and rule.
- The text of an `AppError` result (`errorText`) ends with a `Next:` line for codes whose next step is generic: `command.conflict` (re-query and retry, as before), `run.notConnected` (`run_connection_open { target: "virtual" }`), `persist.locked` (the `--connect` hint), `op.timeout` (`job_get`; the job may still run). ### A6: `design.measure`, headless snap and measure

`design.measure { partId, near?, radius?, points? }` – a query on the design part in the part frame (mm numbers), exactly one of `near` and `points` (else `input.malformed`, rule `nearOrPoints`). It reuses the viewport's snap rules: the snap engine moved from the renderer to core (`src/core/geometry/snap.ts`, the renderer's `viewport/snap.ts` re-exports it) and the distance maths with it (`src/core/geometry/measure.ts`), so the UI and agents rank and measure the same way ([ui.md § Snap and measure](../conventions/ui.md#snap-and-measure)).

- **Snap** (`near: [x, y, z]`, `radius` mm, default 2, at most 50): `{ evaluation, candidates: [{ kind, at, distance, ref? }], more? }`, the targets within `radius` of `near`, ranked as the engine ranks them (`SNAP_PRIORITY`, then the nearest), at most 10 (`more`: how many were cut).   - `edge` (the nearest point on a feature edge, the 30° edges the viewport draws, `featureEdges`), priority 3; only the nearest one, as the engine treats curves.
  - Instead of the viewport's 8 screen px, the reach is `radius` in mm. The mesh targets (`vertex`, `faceCentre`, `edge`) need the part's evaluation of its current input: while it is `pending` or `failed` (`evaluation` says which, as in `design.warning.list`) they are left out; `design_part_evaluate` waits for it.
- **Measure** (`points`): two points give `{ evaluation, points, distance, delta }` (`delta` = b − a per axis, as the viewport's chip shows ΔX, ΔY, ΔZ); three give the angle at the middle one, `{ evaluation, points, angle, distances }` (degrees, 0–180; `distances` from the middle point to the others). A point is `[x, y, z]` or a `ref` string: `partZero`, an operation id with a `holeCentre`, or a surface id (its `faceCentre`). An unknown ref is `input.malformed` (rule `unknownRef`, next step: the snap form lists refs near a point); a surface ref while the evaluation is not `done` is rule `notEvaluated` (next step `design_part_evaluate`).
- Rounded to 0.001 mm and 0.001°. Nothing is stored; the query does not wait for the worker.

- **Reads at open.** A `project.open`, `project.create` or `project.recovery.resolve` that started the project's runtime shows the document at the returned revision, so the session records that revision as its stale-write baseline (`Dispatcher.markRead(source, revision)`, [commands.md](commands.md#stale-writes)); a CLI one-shot edits right after its own open. `project.bind` and an open that returns `alreadyOpen: true` are **not** reads: the project is someone else's (the GUI user's), so an agent must query (or pass `expectedRevision`) before an edit or `history_undo`, as [Undo](#undo-and-history) requires; binding again never clears a conflict.

- **Closing.** `project.close` checks run jobs and unsaved changes, then suspends the project dispatcher (new dispatches fail with `input.malformed`, rule `projectClosing`; urgent job controls still run), drains its queue and checks again, so an edit queued meanwhile cannot bypass the confirmation; a refused close resumes the project.
- **`job.wait` progress** first sends the job's latest progress (a wait on a job past its last tick, or finished, still reports one), then the throttled ticks.

- **Local HTTP sessions.** A host session is kept only for an initialize the transport accepted (a rejected one, e.g. `406` for a missing `text/event-stream` accept, ends it at once); initializations in progress count against the 16-session limit. A `--connect` one-shot maps transport failures to `external.failure` (exit 6) and always ends its HTTP session.
- **CLI details.** `--new <name>` creates an untitled project; it is saved only with the added option `--save-as <file>`, otherwise its changes are discarded at the end. `--no-save` closes, then discards through `project.recovery.resolve { action: 'discard' }` (the file is unchanged). `batch` answers each line with `{ ok: true, value, revision }` or `{ ok: false, error, retryable }` and exits with the first failing line's code (0 if none; 6 if projects kept unsaved changes). The default `--data-dir` is Electron's `userData` path computed without Electron (`defaultAppData`), so the CLI and the app share projects, the library and discovery files. A `--connect` one-shot reaches a running instance over HTTP; with `--project` it opens (or re-uses) the file there and never saves or closes it. Stderr carries only the `code: message` lines (and the unsaved-projects notice); the JSON log goes to the log file, and to stderr too only with `--log-level` ([logging.md](../conventions/logging.md#port-and-helpers)).
- **Headless build.** electron-vite builds `out/main/cli.js` as a second main entry; it shares chunks with `index.js`, none of which imports Electron. The packaged `dfyom` launcher is `DFYOM.app/Contents/Resources/bin/dfyom` (the app binary with `ELECTRON_RUN_AS_NODE`, [amendment A4](#amendment-hardening-a4-launcher-and-connect-an-agent)); in development `node out/main/cli.js`. Tests bundle `src/main/cli/test-entry.ts` (worker entries from `DFYOM_TEST_*`) in the Vitest global setup into `node_modules/.cache`, so its external dependencies resolve.
- **GUI.** Each window is an `AgentSession` with source `ui:win-<id>` (`window.dfyom.call`, `project.onEvent` with patches, `agents.*` in [preload-api.ts](../../src/shared/preload-api.ts)). A project an agent opens (a new runtime) gets a new window bound to it; one already open (`alreadyOpen`) gets none, and the user's New / Open route to a window by the same rule: one window per project, an empty window reused only by the user ([ui.md](../conventions/ui.md#project-files)). Agents address projects by key, never windows. The UI shell (task 3.3b, [ui.md](../conventions/ui.md#app-shell)) renders the indicator (main pushes `dfyom:agents.sessions` and answers `agents.list`), persists the setting (`window.dfyom.settings`; the one-run IPC switch `agents.setLocalHttp` is gone, `--mcp-http` still overrides at start) and closes a project with its last window (`project.close` through the window's session; refusals are shown in the window).
- **Library follow.** Since v0.2 P2 a library change is pending in every open project with an affected `draft` plan and followed by its next Apply; an agent's library write auto-applies its bound project ([apply.md § Implementation (task P2)](apply.md#implementation-task-p2)). v0.1's host-side `followLibraryChanges` is gone.
- **Tests.** `src/core/agent/*.test.ts` (mapping, results, exit codes, session; `session-run.test.ts`: `job.wait` at operator waits), `src/core/commands/args.test.ts` (unknown-argument hints), `src/main/mcp/server.test.ts` (in-memory transport), `http.test.ts` (real loopback), `src/main/host/*.test.ts` (host, coexistence and the `--connect` bridge), `src/main/cli/cli.test.ts` (spawned CLI) and the end-to-end flow, which became the 3.11 exit-criteria tests (`src/main/cli/exit-criteria.*`, over MCP and `batch`, [testing.md](../conventions/testing.md#end-to-end)).
