## Post-processor (task 2.11)

### Input boundary

Two pure, synchronous steps in `src/core/post/`, composed by `exportGrbl` (the [`plan.export` command](#plan-export-command) calls it):

1. **Export** (`toMachiningProgram(input, machine): AppResult<MachiningProgram>`) takes plan mode's [export boundary](../modes/plan-v0.1.md#export-boundary-tasks-110-and-211): the ordered `Toolpath[]` of one setup ([toolpath data model](../modes/plan-v0.1.md#toolpath-data-model), float64 mm in the setup's WCS), each with its tool copy (`ProgramTool`: name, diameter) and a label, the setup (name, `clearanceHeight`) and the machine snapshot. It expands `drill` moves, converts arc centers to `I`/`J` offsets and inserts tool-change and spindle blocks.
2. **Post** (`postGrbl(program: MachiningProgram, opts: PostOptions): AppResult<string>`; `postGrblLines` returns the lines) turns that program into gCode text. It never sees design, geometry or the plan.

```ts
// src/core/post/export.ts
exportGrbl(input: ExportInput, opts: PostOptions): AppResult<GrblExport>
ExportInput = { name, setup: { name, clearanceHeight, header? }, operations: { toolpath, tool, label, positions? }[],
                machine: Option<Machine>, workZero?: Vec3 }
GrblExport  = { program, lines, text, stats, warnings }   // warnings: plan.machine findings
PostOptions = { generator: string, spinUpSeconds?: number /* 3 */, firstToolLoaded?: boolean /* true */ }
```

`lines` are the gCode lines without line ends (what a sender streams, progress `total`), `text` the file (LF, final newline). `stats` = `{ cutLength, rapidLength, estimatedSeconds, dwellSeconds, toolChanges }`: lengths and time as the [toolpath stats](../modes/plan-v0.1.md#toolpath-generators-task-210) (no acceleration, rapids at the slowest axis) over the whole program incl. the moves between operations, plus the spin-up dwells; moves from an unknown position (program start, after a tool change's `M0`) are not counted. One file per setup, i.e. one per plan in v0.1.

| `MachiningProgram` field  | Content                                                                                                                                                                |
| ------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `name`, `setupName`       | Plain text for the header comment.                                                                                                                                     |
| `units`, `spindleControl` | From the machine snapshot (`programUnits`, `spindle.control`); coordinates stay mm, the post converts to inch (÷ 25.4).                                                |
| `clearanceZ`              | Stock top in the WCS + `clearanceHeight`: rapids between operations, tool changes, start and end.                                                                      |
| `blocks`                  | `toolChange` (tool snapshot: name, diameter), `spindle` (rpm or off), `rapid { to }`, `feed { to, feed }`, `arc { to, i, j, cw, feed }` (Z change = helix), `comment`. |

**Drill expansion** (GRBL 1.1 has no `G81–G83`): `simple` = rapid to `retract`, feed to `bottom`, rapid to `retract`; `peck` = feed by `peck`, rapid up to `retract`, rapid back to 0.5 mm / 0.02″ above the last depth, repeat; `chipBreak` = after each peck rapid up by `back` only. Implemented once, as `expandDrill` in `src/core/toolpath/stats.ts`; the export passes 0.508 mm (0.02″) for inch programs.

**Tools and spindle blocks:** a `toolChange` block whenever the toolpath's tool copy (`Toolpath.tool`) differs from the previous one, tools numbered 1, 2, … by first use (a tool used again keeps its number); a `spindle` block after every tool change and whenever the speed changes; a `comment` block with the operation's label before each operation, and a position comment (`positions`, by design operation id) before each pass whose `operationId` names a new position: the clone positions of [plan-v0.4.md P-E](../modes/plan-v0.4.md#implementation-p1), e.g. `(Clones 1 #3)`.

### Output dialect

| Item           | Emitted                                                                                                                                                                                                                                                                                        | Why                                                                         |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| Motion         | `G0`, `G1`, `G2`/`G3` with `I`/`J` (never `R`)                                                                                                                                                                                                                                                 | IJK is unambiguous for near-180° arcs; all in GRBL's supported list.        |
| Modes          | `G17`, `G21`/`G20`, `G90`, `G94`, `G54`                                                                                                                                                                                                                                                        | Explicit state; never rely on controller defaults.                          |
| Spindle        | `M3 S<rpm>`, `M5`; spin-up `G4 P<s>` after `M3` (`opts.spinUpSeconds`, default 3)                                                                                                                                                                                                              | GRBL does not wait for spindle speed. `M4` (CCW) not emitted.               |
| Pause          | `M0 ;<message>` preceded by the comment `(<message>)` ([pause messages](#pause-messages-hardening-df63))                                                                                                                                                                                       | GRBL pauses in `Hold:0`; `~` resumes. Senders show the `M0` line's comment. |
| Tool change    | No `M6`, no `T` word: `(Tool change to Tn: spindle off, retract)`, `M5`, `G0 Z<clearanceZ>`, marker comment `(DFYOM TOOL CHANGE n: tool)`, `M0 ;Install Tn tool, then zero Z`, `G90 G94 G17 G21\|G20`, `G54`, `G0 Z<clearanceZ>`, then `M3 S…` + dwell                                         | `M6` is not in GRBL 1.1's supported list; GRBL has no tool table or ATC.    |
| Manual spindle | `spindle.control = 'manual'`: `M3 S<rpm>`, `(Set spindle to N rpm)`, `M0 ;Set spindle to N rpm` before cutting; no dwell; `(Stop the spindle)` before a tool change's marker (its `M0` message starts `Stop spindle, install …`) and `(Stop the spindle)`, `M0 ;Stop the spindle` before `M30` | [library.md](library.md#machine).                                           |
| Never emitted  | `G28`/`G30`, `G53`, `G92`, `G43.1`, coolant, `N` line numbers, `%`                                                                                                                                                                                                                             | Depend on stored or machine state the export cannot know; not needed.       |

- **Modal suppression:** a word is emitted only when it changes (motion code, unchanged axis words, `F`). "Unchanged" compares the written text, so a move whose every axis word is unchanged after rounding is dropped (its `F` stays pending for the next feed move). The first `G1`/`G2`/`G3` after any `F` change always carries `F` (GRBL has no default feed: `error:22`). An arc needs at least one axis word in the plane (GRBL `error:32` otherwise): a full circle in the program (end = start in X and Y) writes both `X` and `Y`. `I` and `J` are always written.
- **Arcs as GRBL reads them:** `I`/`J` = center − the _written_ start, so GRBL's center is the intended one within rounding. Toolpath arcs sweep at most 180°, so an arc whose written chord is under 10 resolution steps (0.01 mm, 0.001″) is written as `G1`: GRBL would read near-equal ends as a full circle. An arc (not a full circle) whose sagitta is at most half a resolution step is written as one `G1` too (it is a line in the text), and an arc of radius over 10 m (`ARC_HUGE_RADIUS`; GRBL computes in float32 and `I`/`J` would leave the 5-digit range) as `G1` chords within 0.001 mm, Z interpolated (v0.3 T3, [plan-v0.3.md § Arcs](../modes/plan-v0.3.md#arcs-in-g2g3-out)). If GRBL's end-on-circle check (`error:33`: 0.005 mm and 0.1 % of the radius) would fail after rounding (possible with 4 inch decimals at radii under ~5 mm), the post takes the neighbouring `I`/`J` (± one step) closest to the end; an arc that still fails fails the export with `model.invariant`. A second guard compares the sweep GRBL computes from the text with the intended one: it fails the export only when the difference times the radius exceeds 0.005 mm + 4 resolution steps (0.009 mm in mm, 0.0152 mm in inch), i.e. a wrap-around or direction flip, not rounding (a 162° inch arc of r 8.1 mm differs by 0.0055 mm, and its written end lies 0.0016 mm from the intended one). Random-toolpath fuzzing (300 inch programs) exports without failures.
- **Header:** comment lines (`Program:`, `Setup:`, `Units:`, `Tool n: name, dia D mm|in` in order of use, `Generator:` from `opts`), then `G90 G94 G17 G21|G20`, `G54`, `G0 Z<clearanceZ>`. With `MachiningProgram.setup` (every plan export since DF58) the `Setup:` line becomes the [setup instructions](#setup-header-hardening-df58).
- **First tool:** treated like a tool change without the `M0` when `opts.firstToolLoaded` (default true): the marker comment (informational: no `M0` follows, so no sender stops), `M3 S…`, dwell. With `firstToolLoaded: false` it pauses like any tool change.
- **After a tool change's `M0`** the user has jogged and re-zeroed Z, so the post forgets the position, motion code and `F`: it states the modes again (`G90 G94 G17 G21|G20`, `G54`, in case the user ran MDI in another mode), writes `G0 Z<clearanceZ>` (in the new WCS, before the spindle starts) and the next move carries `X`, `Y` and `F` again. The retracts before a tool change and in the footer are suppressed like any move when Z is already at clearance (toolpaths end there); the header's and the post-`M0` retract are always written.
- **Validation:** non-finite values or magnitudes over 99 999 as written (lengths and feeds in text units, `S` in rpm), a feed that rounds to 0, an `S` that rounds to 0, a feed move with the spindle off, an arc without a radius or from an unknown position, a non-finite or oversized tool diameter, and `spinUpSeconds` outside 0–3600 fail with `model.invariant` (issues name the block; after a failed arc the post continues from its end, so each bad block is reported once). `toMachiningProgram` requires `clearanceHeight` > 0 and ≥ the highest Z of every toolpath (`model.invariant`, rule `clearance`): the tool-change and footer retracts must never move down.
- **Tool change in DFYOM:** one file per setup. GRBL accepts no jog or zeroing while paused by `M0` (it reads no lines in Hold:0), so DFYOM's sender stops streaming before the marker comment, waits for Idle, guides the user (jog, change tool, zero Z with `G10 L20 P1 Z0`), sends the marker, skips the `M0` and continues. Other senders pause at `M0`.
- **Marker rule for the sender (task 3.9, DF63):** a tool change is a whole line matching exactly `(DFYOM TOOL CHANGE n: name)` (`n` digits, `name` without parentheses: since DF63 the [tool description](#pause-messages-hardening-df63)) whose next line is exactly `M0` or `M0 ;` followed by a message. Anything else (a malformed marker, a marker inside a longer line, a next line other than that) is streamed unchanged, so GRBL's plain `M0` pause applies. `GrblSender` implements this rule ([run-v0.1.md](../modes/run-v0.1.md#sender)).
- **Footer:** `G0 Z<clearanceZ>`, `M5`, (manual spindle: `(Stop the spindle)`, `M0 ;Stop the spindle`), `M30`. No park move: the safe XY position is machine-specific and unknown in v0.1.

### Export checks

`exportGrbl` fails with **`post.noMachine`** when the plan has no machine copy. Every other machine check is a warning (`plan.machine` findings in the shape of `plan.warning.list`, [plan-v0.1.md](../modes/plan-v0.1.md#plan-record)); the program is still written:

| Rule               | Check                                                                                                                                                                                                                                                                                                                                                                                                                     |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `maxFeedRate`      | Per operation, the worst move: its speed along each axis (feed × that axis' share of the direction; an arc counts its full XY speed on X and Y) ≤ the axis' `maxFeedRate` – where GRBL starts to slow it down.                                                                                                                                                                                                            |
| `spindleRange`     | Each operation's spindle speed within `spindle.minSpeed..maxSpeed` (GRBL clamps silently).                                                                                                                                                                                                                                                                                                                                |
| `travel`           | The program's extent per axis (all visited points incl. arc bulges and `clearanceZ`) ≤ the travel; the work zero on the table is unknown.                                                                                                                                                                                                                                                                                 |
| `softLimit`        | Only with `workZero` (MPos of the work zero, e.g. from a connected controller): every point in machine coordinates within [−travel, 0] (GRBL's soft-limit rule for every homing direction, [below](#homing-and-machine-coordinates)). Z only up to the first tool change that pauses: the user re-zeroes Z for each new tool, so later Z positions in MPos are unknown (with `firstToolLoaded: false`, none are checked). |
| `zHeadroom`        | Only with the setup's stock thickness (`exportPlan`) and the machine's `noseToTable`: per tool (name and stickout), the clearance height + 1 mm ≤ the tool tip's height above Z0 with Z homed ([Z headroom](#z-headroom-hardening-df68)). Without `spoilboardThickness` checked as if there were none.                                                                                                                    |
| `zReach`           | Same, with `spoilboardThickness` too: per tool, its lowest toolpath Z ≥ the tip's height at the end of the Z travel ([Z headroom](#z-headroom-hardening-df68)).                                                                                                                                                                                                                                                           |
| `zHeadroomUnknown` | Info, once: the machine lacks `noseToTable` and/or `spoilboardThickness` (`params.missing`), so the Z headroom was not (or only partly) checked.                                                                                                                                                                                                                                                                          |

### Numbers, lines and comments

- **Precision:** mm 3 decimals, inch 4 decimals for coordinates and `I`/`J`; `F` 1 decimal (also in inch: 0.1 in/min = 2.54 mm/min steps, enough for v0.1 feeds); `S` integer; `P` 2 decimals. Round half away from zero from the decimal value, strip trailing zeros and a trailing `.`, normalize `-0` to `0`, no exponent, keep the leading `0` (`0.5`). `F` must be > 0 after rounding, else `Err('model.invariant')`.
- **Line length:** GRBL's line buffer is 80 chars (`LINE_BUFFER_SIZE`, overflow = `error:11`); the 128-byte RX buffer counts every byte sent. DFYOM rule: every line ≤ 70 bytes including comments; longer comments are truncated, code lines never exceed it.
- **Character set (safety):** GRBL picks realtime commands out of the stream at any position, including inside comments: `?`, `!`, `~` and every byte ≥ 0x80 (overrides, door, jog cancel). The post therefore emits **printable ASCII only**, and comment text drops `?!~()`, `;` and non-ASCII (`″` → `in`, `ø` → `dia`, `°` → ` deg` for chamfer mill names, `·` → `-` and `×` → `x` for feature labels, others → `_`).
- **Comments:** `(text)` on their own line, no nesting; the only `;` comment is a pause's message on its `M0` line (`M0 ;text`, same character rules, the whole line ≤ 70 bytes; GRBL 1.1 ignores everything after `;`), because senders show that comment ([pause messages](#pause-messages-hardening-df63)).

### Determinism and tests

Same input and options → byte-identical output: LF line endings, final newline, no dates; the app version only in the `Generator:` line (the generator string is passed in; post tests use a fixed one, and the end-to-end goldens are compared with that line reduced to `DFYOM`, `withoutAppVersion`, so they survive version bumps), fixed word order `G M X Y Z I J F S P`. Golden files: `src/core/post/grbl/__golden__/*.nc` (`facing`, `pocket-circle-helix`, `drilling-peck-chipBreak`, `profile-tabs`, `multi-tool`, `multi-tool-inch-manual-spindle`); update with `vitest -u`. Each golden file is also streamed through the virtual machine in tests (no `error:` lines, ends `Idle`). The whole test project's program is a golden file of the end-to-end tests ([testing.md](../conventions/testing.md#end-to-end)).

- **Properties** (`post.test.ts`, on the golden programs, the test part and 40 random toolpaths per unit with tiny, 180° and helical arcs): every line ≤ 70 bytes of printable ASCII, every word in its precision (no `-0`, exponent or trailing zero), fixed word order, nothing from the never-emitted list (no `G81`–`G83`), every arc line with an in-plane axis word; and the text re-parsed with the virtual machine's `parseBlock` makes exactly the intended moves (targets within half a resolution step, rapid/feed mode, feed, arc circle, direction and sweep), so modal suppression never loses state.
- **End to end** (`emulator-run.test.ts`): the [geometry test part](geometry.md#testing)'s program (5 tools, the drill twice) streamed by `GrblSender` with character counting through the virtual machine after `$H` and a `G54` 750/750/50 mm into the table: no `error:` and no alarm, no protocol violation, the final position as programmed (mm and inch); with the DFYOM tool-change rule the sender stops at all 5 markers, the test jogs and re-zeroes Z, and each resumes with the modes, `G54` and `G0 Z<clearanceZ>` before `M3`; another sender's run (the markers turned into plain comments) pauses at each `M0` (Hold:0) and resumes with `~`; a machine with too little Z travel for the first tool gets the `softLimit` warning and `ALARM:2`.
- **Time:** with 400/400/200 mm/s² acceleration the virtual machine needs 626.6 s for the test part (without the tool-change pauses) against 591.4 s estimated (`stats.estimatedSeconds`, incl. 18 s of dwells): **ratio 1.06** (1.09 against the sum of the toolpath estimates, 572.5 s, which leave out dwells and the moves between operations). The test asserts 1 < ratio < 1.5.

### Setup header (hardening DF58)

The agent test of 2026-11-23 (TG #232) exported a bottom and a top setup whose headers named only the program, setup and tools: nothing said how to turn the stock, where the work zero is or which face Z0 is on. Since DF58 `exportPlan` passes `setup.header` (`SetupHeader` in [`program.ts`](../../src/core/post/program.ts), built by `setupHeader` in [`src/core/plan/setup-header.ts`](../../src/core/plan/setup-header.ts)) and the post writes, in place of `(Setup: name)`:

```text
(Program: Enclosure)
(Setup 2 of 2: Top)
(Stock X 250 Y 100 Z 20 mm on the machine)
(Faces: top up, front towards you, right on the right)
(From setup 1: flip about X)
(Work zero G54 X0 Y0: front-left corner of the top face)
(That corner sits front left on the machine)
(Z0 on the top face: the stock surface facing up)
(Tool reaches past stock: left 7, right 7, front 1, back 1 mm)
(Keep clamps clear of those sides, below clearance Z 10 mm)
(Units: mm)
(Tool 1: …)
```

- **Number** in machining order and the plan's setup count.
- **Stock:** its extents along machine X, Y, Z in this setup's orientation (`setupOrientation`, a 90°/270° turn swaps X and Y), in program units. Not its name: the library name differs between flows that build the same stock (the UI's "Block 255 x 185 x 40", the headless "Walnut board"), and the same part must give the same file; the sizes are what the operator checks.
- **Faces:** the part faces up, towards the operator (−Y) and on the right (+X), as the run-mode setup-change picture names them ([plan-v0.2.md § Implementation (task E2)](../modes/plan-v0.2.md#implementation-task-e2)).
- **From setup 1** (setups 2 and later): the move from setup 1's orientation, from the two setups' machine axes (`R = A_k · A_1ᵀ`, rows of `setupFrame`). First the side that comes up: none, `flip about X` (the up face goes down) or `tip its front|back|right|left side up` (sides as they sat in setup 1, front = towards the operator); then the rest as a turn about the spindle axis: `turn 90 deg CCW`, `turn 180 deg`, `turn 90 deg CW` (seen from above). A flip about X followed by a half turn is written `flip about Y`; no change is `same orientation`. A test checks every pair of directions and rotations: the described moves, applied in order, give the second setup's orientation.
- **Work zero:** the part corner at G54 X0 Y0, named by the faces that meet there besides the up face (`setupCorner`, the setup panel's corner name, now in core): on the machine it is always the front-left corner of the up face. Z0 is on the up face. Since DF78 a setup may move its zero ([alignment.md § Setup work zero](../modes/alignment.md#setup-work-zero-q61)): the corner line names the corner it is measured from, `(Corner: front-left corner of the top face)`, and the zero line where it is, `(Work zero G54 X0 Y0: X 40 Y 25 mm from that corner)`, plus `(Work zero on <point>)` when it is on an alignment point. A setup with alignment points adds `(Align n points after zeroing, spindle off:)` and one `(Align i: <name> at X <x> Y <y>)` per point (WCS). A setup at the corner without points keeps the lines above byte for byte. Alignment aids (DF78 slice 2) are operations of their setup: in machining order, labelled with the aid's name (`(Registration hole 1)`, `(Witness mark 2)`), a hole as a peck drilling through into the spoilboard, a mark as a V-bit plunge or one straight cut at the mark depth.
- **Tool reach past the stock** (hardening DF59, interim until workholding): how far the tool reaches beyond each side of the stock outline on the machine, from the moves below the stock top of this program's toolpaths (`setupOverreach`, [plan-v0.2.md § Tool reach past the stock](../modes/plan-v0.2.md#tool-reach-past-the-stock-and-clamps-hardening-df59-interim)): `Tool reaches past stock:` with the sides that reach (left = X−, right = X+, front = Y−, back = Y+), each rounded up to 0.1 mm (0.01 in), then `Keep clamps clear of those sides, below clearance Z <h> <unit>`. Within the outline: `Tool stays within the stock outline` and `Keep clamps below clearance Z <h> <unit>`. A line longer than 70 bytes (four sides with large values) is split into an X line and a Y line. Absent without `overreach` in the header data (post unit tests). **With a clamp height and no workholding items** ([safe links](../modes/safe-links.md#clamps), DF64: minimum retraction, a `clampHeight`, and clampHeight + retract height below the clearance height; `SetupHeader.clamp`) the clamp sentence names it instead: `Keep clamps below Z <clampHeight> <unit>: links pass <margin> <unit> above them` (within the outline), or `Keep clamps clear of those sides` followed by that line.
- **Workholding** ([workholding.md § Program and Run](../modes/workholding.md#program-and-run), DF59): with workholding items in the setup, one line per item after the reach lines, `Workholding: <name>: <summary>` (`Workholding: Toe clamp 1: left Y50 grip 10 top Z12`, in program units; positions in the WCS, the setup-frame values less the setup's work zero, like every other coordinate of the program, DF81), then `Every move checked: <margin> <unit> clear of the workholding`; the `Keep clamps …` line of the reach is then left out (the clamps are modelled). Without items the reach lines stay as above. Exported programs of a setup with a workholding error (`plan.workholding.*`) are refused (`plan.check`).
- **GRBL-safe:** each a comment line through `commentLine` (printable ASCII, no `()`, `;` or realtime characters, at most 70 bytes); the words are fixed English like the other header comments. Programs without `setup` (post unit tests) keep `(Setup: name)`.
- **Goldens:** every exit-criteria program and the per-setup goldens gained these lines; nothing below the header changed.

### Pause messages (hardening DF63)

The user's cut of 2026-11-24 (TG #242) with gSender stopped at each tool change's `M0` without saying which tool to put in: the tool was only named in the marker comment on the line before. What gSender shows (source: [`GrblController.js`](https://github.com/Sienci-Labs/gsender/blob/master/src/server/controllers/Grbl/GrblController.js), sender `dataFilter`, and the `sender:M0M1` dialog in [`controllerSagas.tsx`](https://github.com/Sienci-Labs/gsender/blob/master/src/app/src/store/redux/sagas/controllerSagas.tsx), checked at v1.6.5):

- At a line whose words contain `M0` (or `M1`) it pauses and opens an "M0/M1 Pause" dialog with a fixed text and, when the line has one, `Comment: <comment>`. Only **the `M0` line's own comment** counts; a comment on the line before is never shown.
- gSender up to 1.6.1 reads only a `;` comment (`/\s*;.*/`, the first `;` removed); since 1.6.2 (May 2026) both `(…)` and `;…` comments on that line, joined with a space. A `;` comment works in every version. There is no length limit (the dialog wraps).
- An `M0` within the first 10 lines sent does not pause (a workaround for Carbide Create files); DFYOM's header is longer.
- `M6` with a `T` word triggers gSender's own tool-change flow; DFYOM emits neither (above).

DFYOM rule: every `M0` carries its message twice, as the comment line before it (what DFYOM's sender and file readers see) and as a `;` comment on the `M0` line (what gSender and other senders show). GRBL 1.1 ignores the rest of a line after `;`. Both go through the comment rules (printable ASCII, no `()`, `;` or realtime characters) and every line stays ≤ 70 bytes. Since the marker must stay directly before a tool change's `M0`, the marker itself carries the tool description:

```text
(Tool change to T3: spindle off, retract)
M5
G0 Z20
(DFYOM TOOL CHANGE 3: Wexme 1/4" 1F, 6.22 mm flat)
M0 ;Install T3 Wexme 1/4" 1F, 6.22 mm flat, then zero Z
```

- **Tool description:** the tool copy's name, its diameter in program units (as the header's `Tool n:` line) and a type word (`flat`, `bull nose`, `ball`, `drill`, `chamfer`): `ProgramTool.type`. A name too long for a 70-byte line is cut so the diameter, type and `then zero Z` survive.
- **Words:** `Install Tn …, then zero Z` (`T` + the program's tool number; no `T` word in code). "Zero Z" covers a touch plate, a probe or a paper touch-off; DFYOM's own sender guides it with `G10 L20 P1 Z0`. A manual spindle starts the message with `Stop spindle, install …`.
- **Before `M5`:** the comment `(Tool change to Tn: spindle off, retract)` labels the stop and retract, so a reader stepping through the file sees why the spindle stops.
- **Other pauses:** manual spindle `M0 ;Set spindle to N rpm` and the footer's `M0 ;Stop the spindle`. The first tool (already loaded, no `M0`) gets only the marker with the description.
- **Z reference (hardening DF69):** before the marker of every pausing tool change the program rapids to the tool run's touch-off spot at the clearance height (`X Y` after `M5` and the retract). When the run touches off on a surface other than the up face, two comment lines follow (`(Z0 for tool 2: Facing 1 floor, 0.50 below the stock top)`, `(Touch off Z here, X120 Y45: set Z0 on that surface)`), the `M0` comment ends `, then zero Z on Facing 1 floor` when that fits in 70 bytes, and the run's Z words are shifted by −`s` (the program Z0 is that surface). The header's Z0 line and tool lines say so. A first tool whose reference is not the up face pauses even with `firstToolLoaded`. Rules and examples: [z-reference.md § Exported gCode](../modes/z-reference.md#exported-gcode) and its [implementation notes](../modes/z-reference.md#implementation-notes-df69).
- **Setup changes** have no `M0`: each setup is its own file ("one file per setup"), and the [setup header](#setup-header-hardening-df58) says how to turn the stock (`From setup 1: flip about X`). DFYOM's run mode guides the change between files ([run-v0.1.md](../modes/run-v0.1.md)); other senders show the header only in the file.
- **DFYOM's sender** shows the `M0` line's `;` message at a plain `M0` pause (`programPause`), else the comment line before it.

### Z headroom (hardening DF68)

The user's real cut (TG #244, a program exported for gSender): retracts to the clearance height hit the Z+ limit switch with a long 1/4" tool (62 mm stickout) and the spoilboard not entered, and the machine locked. An export for another sender has no live work zero, so `softLimit` did not run (`softLimitChecked: false`). The Z headroom check estimates the tool tip's machine Z from the machine and the setup instead, with no controller (`zHeadroomFindings` in [`src/core/plan/z-headroom.ts`](../../src/core/plan/z-headroom.ts)):

- **Tip at Z home**, above the setup's Z0 (the stock top, [plan-v0.2.md](../modes/plan-v0.2.md#setups-from-face-directions)): `noseToTable − spoilboardThickness − stock thickness − stickout`. `noseToTable` is measured with Z homed (MPos −pull-off), from the spindle nose (the collet nut face, where stickout is measured) to the table; the stock thickness is its extent along this setup's spindle axis (`setupStockSize`); the stickout is the plan operation's resolved one ([plan-v0.1.md](../modes/plan-v0.1.md#tool-assignment-and-checks)).
- **Top (`zHeadroom`):** the program's highest Z is the clearance height (the post requires every toolpath below it; retracts, tool changes and the footer go there). It must be at most the tip at Z home − 1 mm (`Z_HEADROOM_MARGIN`). The message names the tool and stickout, the needed and available mm and the fixes: lower the clearance height, use a shorter stickout (or enter the spoilboard).
- **Bottom (`zReach`):** the tool's lowest toolpath Z must be at least the tip at Z home − (Z travel − pull-off), the end of the travel. Needs the toolpath, so only the export checks it; `plan.warning.list` checks the top only.
- **Missing fields:** without `noseToTable` nothing is estimated; without `spoilboardThickness` the top is checked as if there were none (a spoilboard only lowers the headroom, so a warning is certain) and the bottom is skipped. Either way one info `zHeadroomUnknown` names the fields to enter.
- **Per setup and tool:** one finding per tool name and stickout, naming its first plan operation, `params.setupId` always set (the setup inspector filters on it). Same findings in `plan.warning.list` (top only, from the plan) and in `plan.export`'s `warnings` (top and bottom, from the program); neither blocks.
- **Live work zero:** when the soft-limit check runs (a homed connection to the plan's machine, [run-v0.1.md](../modes/run-v0.1.md#work-zero-and-the-soft-limit-check)), it is authoritative: it uses the real G54 instead of measured distances, so a `zHeadroom` warning it contradicts is the estimate's error (check `noseToTable`). The estimate covers every tool; the soft-limit check covers Z only up to the first tool change that pauses (the user re-zeroes Z).
- **Tests:** [`z-headroom.test.ts`](../../src/core/plan/z-headroom.test.ts) with the user's case (62 mm stickout, clearance 20 mm, stock 40 mm, a 90 mm Z travel desktop machine: warns; a 25 mm stickout or a 4 mm clearance clears it), the missing fields, the reach; `plan-export.test.ts` and the plan warning list through the commands.

### Plan export command

Stats count the linked program. `full` writes today's bytes.

The same plan gives the same file within one app version.
5. **Write** (command only): `text` goes to `target` through the `ExportFiles` port (`services.exportFiles`), so `src/core` stays headless. `src/main/persistence/export-file.ts` follows the user-folder protocol of [Save As](persistence.md#save): it writes `<file>.tmp-<8 hex>` next to the target (created exclusively, so no existing entry is touched), fsyncs it and renames it over the target; on a failure it unlinks only that temp file (never recursively) and the target is untouched. Errors carry `target` (and `plan.export` adds `planId`).
   - **Folder target** (DF62): a `target` ending in `/` or `\\` is a folder; the file is `<folder><file name>.nc` with the [file name](#file-name-hardening-df62) below, so an agent need not invent one.
   - **Target:** an absolute, normalized path (on Windows with a drive or UNC root: no drive-relative `\out\a.nc` or `C:out`, no `:` after the root, i.e. no alternate data streams) whose file name has a stem and ends in `.nc`, `.gcode` or `.ngc` (any case).
   - **Existing entries** (checked with `lstat`, so a symlink counts, dangling or not) are replaced only with `confirm: true` (`input.malformed`, rule `confirmOverwrite`, as Save As); a folder never (`notAFile`). As Save As, the path is resolved with `canonicalPath`: through a symlink the real file is written and the link kept; `filePath` in the result is that real path. A dangling link is never replaced (`danglingLink`).
   - Nothing is written when the export fails.

- **Effect, not job:** export holds the project queue like `project.save`, so the program matches one revision; regenerating the test part's toolpaths takes well under a second ([workers.md](workers.md#performance-budgets)). Effects are not subject to the stale-write baseline ([commands.md](commands.md#stale-writes)) and change no document (toolpaths are derived data).
- **Soft limits:** `plan.export` passes no `workZero` until run mode supplies the connected G54 ([run-v0.1.md](../modes/run-v0.1.md#work-zero-and-the-soft-limit-check)); `softLimitChecked` says whether the check ran; when it did not, `softLimitNote` (DF58) says how to check before running: set the work zero, then `run.job.check` or the Run pre-flight (`run.job.start` checks too). The GUI's export dialog has its own sentence. The result does not carry the text: the file is the output (agents and run mode use `exportPlan`).

#### File name (hardening DF62)

The user's cut (TG #242) had files named `enclosure-hardwood-250x100x40_setup1-underside.nc`: too long for a sender's file list. `gcodeFileStem(doc, planId, setupId)` (`src/core/post/file-name.ts`) gives the suggested file name without extension, for the Export gCode dialog ([ui.md](../conventions/ui.md#plan-mode-task-37)) and a folder `target`:

- **Slug** of the project name: lower-case ASCII letters and digits (accents dropped, `″`/`"` after a digit → `in`: `1/4"` → `1-4in`), every other run of characters one `-`, none at the ends; empty → `program`.
- **Suffixes**, only where needed to tell files apart: `-p<k>` when the project has several plans (k: the plan's position in the project, 1-based), then `-s<n>` when the plan has several setups (n: machining order, as the header's `Setup n of N`).
- **At most 24 characters:** the slug is cut to leave room for the suffixes, at its last `-` when that keeps at least half the room, else hard; a trailing `-` goes.

Examples: "enclosure-hardwood-250x100x40-two-setups" (one plan, two setups) → `enclosure-hardwood-s1`, `enclosure-hardwood-s2`; "Bracket" (one plan, one setup) → `bracket`. Unique per setup within a project; two projects with the same name prefix can share names (the folder tells them apart).

## Virtual machine (task 3.8)

A GRBL 1.1 emulator: a pure, deterministic state machine in `src/core` fed bytes and a clock, producing bytes. It answers **exactly like GRBL** for the subset below so the same sender works against it and a real controller. Banner after reset: `Grbl 1.1h ['$' for help]`.

### Protocol subset

| Area          | Emulated                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Responses     | `ok`, `error:N`, `ALARM:N`, `[MSG:…]` (`'$H'\|'$X' to unlock`, `Reset to continue`, `Caution: Unlocked`, `Enabled`/`Disabled`, `Pgm End`, `Check Door`, `Restoring spindle`), `[HLP:…]`, settings, `$G`/`$#`/`$I` lines.                                                                                                                                                                                                                                                                                                                                      |
| Buffers       | RX 128 bytes (`RX_BUFFER_SIZE`, all usable: GRBL's ring has `RX_BUFFER_SIZE + 1` slots; `Bf` reports 128 − used), line 80 chars (`error:11` once 79 characters remain after stripping spaces and comments, like GRBL), planner 15 free blocks (`BLOCK_BUFFER_SIZE` 16; `Bf:15,128` when idle). Bytes beyond the RX buffer are dropped and recorded. Both `\r` and `\n` end a line, so CRLF gets two `ok`s.                                                                                                                                                    |
| Realtime      | `?` status, `!` feed hold, `~` cycle start/resume, `0x18` soft reset, `0x84` safety door, `0x85` jog cancel, `0x90–0x97` feed/rapid overrides (applied to timing), `0x99–0x9E` spindle (state only); the sender sends them for `run.override.set` (M6, [run-machine.md](../modes/run-machine.md#overrides-m6)).                                                                                                                                                                                                                                               |
| Status report | `<State\|MPos:x,y,z\|Bf:b,r\|FS:f,s\|WCO:x,y,z\|Ov:f,r,s\|A:S>`; `$10` selects MPos/WPos and `Bf`; `WCO` every 10 reports (30 while busy) and `Ov` (with the accessory field `A:S`/`A:C` while the spindle runs) every 10 (20) as in GRBL's report counters, and on the next report after a change. Positions in mm with 3 decimals (`$13=1`: inch, 4 decimals); `FS` is the current speed in mm/min (no decimals) and the running spindle rpm after override and `$30/$31` clamping. No reports while waiting for a reset after `ALARM:2` (GRBL busy-waits). |
| `$` commands  | `$`, `$$`, `$x=val` (session only), `$G`, `$I` (`[VER:1.1h.20190830:]`, `[OPT:V,15,128]`), `$#` (G54 from `G10`, PRB from the last probe; G55–G59, G28, G30, G92 and TLO printed as zero), `$H`, `$X`, `$C` (check mode), `$J=` (G20/G21, G90/G91, G53, X/Y/Z, F required; the jog's modes do not persist). `$N`, `$SLP`, `$RST` and `$I=` are not emulated → `error:3`.                                                                                                                                                                                      |
| gCode         | `G0–G3` (IJ or R arcs, G17 only), `G38.2–G38.5` (probing, [below](#probing)), `G4`, `G10 L2/L20 P0\|P1` (missing `P` = 0, the active system), `G17`, `G20/G21`, `G53`, `G54`, `G90/G91`, `G94`, `M0`, `M2`, `M30`, `M3/M4/M5`, `S`, `F`, `T` (accepted, ignored), `N` (ignored), comments. Anything else → `error:20` (including `G81–G83`, which the post expands). `S`/`M3–M5`, `G4`, `G10`, `M0`, `M2`/`M30` wait for the planner to empty (GRBL's buffer synchronization), so they end look-ahead.                                                        |
| Errors        | GRBL's codes for the checks of this subset: 1–5, 8–11, 15, 16, 20–26, 28, 30, 32–36, 38 with GRBL's meanings and precedence (e.g. `G0 G1` and `G0 G1.5` are 24; in R mode `I`/`J` are unused words, 36; `G10 L2 R…` is 20; `T` > 255 is 38). 6, 7, 12–14, 17, 27, 29, 31, 37 are not produced.                                                                                                                                                                                                                                                                |
| Alarms        | 2 soft limit (then `[MSG:Reset to continue]`), 3 reset during motion, 4 and 5 probe fail, 6 reset during homing, plus homing-lock at startup when `$22=1`; 1 hard limit only through the fault hook ([below](#fault-injection)).                                                                                                                                                                                                                                                                                                                              |

Settings: `$110–$132` and `$30/$31` come from the machine snapshot ([library.md](library.md#machine)), and so do `$11`, `$12` and `$100–$102` when the machine sets them, `$20` (soft limits), `$23` (homing direction mask from the homing corner) and `$27` (pull-off) always (defaults: on, `backRight` = 0, 1 mm); otherwise DFYOM defaults `$10=1`, `$11=0.010`, `$12=0.002`, `$20=1`, others GRBL defaults. Steps/mm are reported but not used.

Emulator option `homing` (sets `$22`): `true` (default in the app) starts in Alarm with `[MSG:'$H'|'$X' to unlock]` and needs `$H`; `false` starts Idle, already homed at MPos `0,0,0`, for tests and demos. Without homing `$20` is 0, as GRBL forces it (`$20=1` → `error:10`).

`$H` plays GRBL's homing cycle in time ([below](#homing-and-machine-coordinates)); its `ok` comes when it is done. Emulator option `position` (MPos at power-up, default 0,0,0): the app starts the virtual machine at the centre of its travel.

### State machine

| State           | Entered by                                               | Left by                                                            |
| --------------- | -------------------------------------------------------- | ------------------------------------------------------------------ |
| Alarm           | startup with `homing`; `ALARM:N`                         | `$H` → Home; `$X` → Idle; reset after ALARM:2/3 → Alarm (lock)     |
| Home            | `$H` (Idle or Alarm)                                     | done → Idle at the homed position (`$23`, `$27`)                   |
| Idle            | homing done, motion done, `$X`, jog cancel, reset        | first planned block → Run; `$J=` → Jog                             |
| Run             | blocks in the planner                                    | buffer empty → Idle; `!` or `M0` → Hold                            |
| Hold:1 / Hold:0 | `!` (decelerating / stopped); `M0` (Hold:0 once stopped) | `~` → Run; `0x18` → Idle, or ALARM:3 if still moving               |
| Jog             | `$J=` from Idle or Jog                                   | done or `0x85` → Idle; `!` cancels the jog                         |
| Door:0–3        | `0x84`, door pin (test hook)                             | `~` once stopped and closed (no pin: at once) → resume; no parking |
| Check           | `$C`                                                     | `$C` again → soft reset → Idle                                     |

`M0` waits for the planner to empty, enters Hold:0 and sends its `ok` only after `~`. While a feed hold decelerates (Hold:1) GRBL keeps reading, planning and acknowledging lines; once stopped (Hold:0) and in Door it reads none, so the RX buffer fills. Door details: decelerating Door:2, restoring Door:3; once stopped, `0x84` alone (no door pin) counts as closed, Door:0, and `~` resumes; the test hook `setDoorPin(open)` emulates GRBL's door switch (open: Door:1 until closed). A door during a jog stays Jog until the jog cancel completes, then enters Door. The spindle stops once motion has, and `~` restarts it with GRBL's 4 s `SAFETY_DOOR_SPINDLE_DELAY` before motion resumes. `M2`/`M30` also restore the feed, rapid and spindle overrides to 100 % (`RESTORE_OVERRIDES_AFTER_PROGRAM_END`). `0x9E` stops and restores the spindle in Hold:0 (`[MSG:Restoring spindle]`).

Soft limits as in GRBL (`system_check_travel_limits`): machine coordinates span `[-$13x, 0]` per axis for every homing direction. A gCode target outside → `ALARM:2` with feed hold; a jog target outside → `error:15`, no alarm.

### Homing and machine coordinates

Facts from GRBL 1.1h `limits.c` (`limits_go_home`), `system.c` (`system_check_travel_limits`) and `settings.c` (`max_travel` is stored negative), default build (no `HOMING_FORCE_SET_ORIGIN`):

- **Travel in negative space:** a target is outside the soft limits when an axis is `> 0` or `< −$13x`. This does not depend on `$23`.
- **Position after homing**, per homed axis: `$23` bit clear (homes towards +) → MPos = −`$27`; bit set (homes towards −) → MPos = −`$13x` + `$27`. Bits: 0 = X, 1 = Y, 2 = Z. So the physical box is the same for every corner; only the corner the machine rests in after `$H` differs.
- **Cycle:** `HOMING_CYCLE_0` = Z, then `HOMING_CYCLE_1` = X and Y together. Per cycle: approach at `$25` (search up to 1.5 × travel, `HOMING_AXIS_SEARCH_SCALAR`), pull off `$27` at `$25`, locate at `$24` (up to 5 × `$27`), pull off `$27` at `$25` (`N_HOMING_LOCATE_CYCLE` = 1). Several axes move together, each at `$25`.
- GRBL runs no realtime protocol inside the homing loop, so a real controller sends no status report until homing ends.

DFYOM's virtual machine:

| Topic         | Emulated                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| ------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Switches      | Physical, in the homed frame: + switch at MPos 0, − switch at −`$13x`. Before homing the virtual machine reports its physical position (real GRBL counts from 0 at power-up; the position is untrusted until homed either way).                                                                                                                                                                                                                                                                                                                                              |
| Path and time | Z cycle, then XY: approach from the current position to the switch at `$25`, pull-off at `$25`, locate at `$24`, pull-off at `$25`; X and Y each at `$25`, the XY cycle lasting for the longer approach. With GRBL defaults (`$24=25`, `$25=500`, `$27=1`) from the switches: 2 × 2.64 s = 5.28 s.                                                                                                                                                                                                                                                                           |
| End           | MPos per the rule above, `Idle`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| Reports       | **Deviation:** status reports answer during homing with state `Home` and the moving position (grblHAL does this; GRBL 1.1 is silent), so the view can animate the cycle. Option `silentHoming: true` is GRBL-exact: no report until the cycle ends, then the `?`s that came in are answered once; tests of the real-machine path use it ([run-machine.md](../modes/run-machine.md#homing-on-a-real-controller)); the sender suspends its status watchdog while `$H` is in flight either way. A soft reset during homing (`ALARM:6`) leaves the position where the cycle was. |

DFYOM's `softLimit` export check and the host's jog check (`run.travel`, [run.md](../modes/run.md#machine-coordinates-and-the-homing-corner-df33)) use the same `[−travel, 0]` rule.

### Motion timing

Motion follows GRBL's planner: a trapezoidal velocity profile per block from `$110–$112` (max rate, also for G0) and `$120–$122` (acceleration), with **junction-deviation look-ahead** (`$11`) over the 15-block planner buffer for corner speeds. `G2`/`G3` (incl. helices) are split into chords within `$12` like GRBL, since plan mode emits arcs in v0.1. Overrides scale feed (and rapid) rates. Time comes from an injected `Clock` (`src/core/run/clock.ts`: `now()`, `schedule(at, fn)`): tests step a `VirtualClock` in virtual time (`advance(ms)`, as fast as the CPU allows); the machine host runs it on a `ScaledClock`: real time, 1–100× or `max` ([run-v0.1.md](../modes/run-v0.1.md#clocks)).

Model details (from GRBL planner.c and stepper.c, in mm and seconds instead of steps): block acceleration and rapid rate are limited per axis along the move; the junction speed is `√(a·$11·sin(θ/2)/(1 − sin(θ/2)))` with `a` limited along the junction vector, and at most the smaller neighbouring nominal speed; reverse and forward passes run over the whole buffer whenever a block is added or an override changes, with the executing block re-planned from its current speed. A feed hold decelerates at each block's acceleration, across block boundaries; `~` restarts from rest. Feed overrides do not apply to jogs. Arc chords follow mc_arc()'s segment count, with exact points on the arc.

### Transport and sender

```ts
// src/core/run/transport.ts – byte stream, same for serial and emulator
interface ControllerTransport {
  write(bytes: Uint8Array): AsyncAppResult<void>
  onData(listener: (bytes: Uint8Array) => void): () => void
  close(): AsyncAppResult<void>
  /** Serial only: the port closed without being asked (cable pulled) → the sender fails at once. */
  onClose?(listener: (reason: string) => void): () => void
}
```

- `GrblSender` (`src/core/run/grbl/sender.ts`, headless) owns the protocol: line framing, **character counting** against the 128-byte RX buffer, `?` polling (5 Hz), mapping `job.pause`/`job.resume`/`job.abort` to `!`/`~`/`!`+`0x18`, and `error:N`/`ALARM:N` to `AppError`s (`machine.error`, `machine.alarm`, `machine.connection`). On the first `error:N` it stops sending, feed-holds and resets ([run-v0.1.md](../modes/run-v0.1.md#stop-errors-and-alarms)). Send-response mode is a sender option for debugging.
- Implementations: `VirtualGrblTransport` (wraps the emulator and a `Clock`, schedules the emulator's next event, delivers output by a clock timer at the current time, never inside `write()`, so a sender can book a line after awaiting `write()` as over serial; in-process in unit tests, in the machine host elsewhere: a utility process in the app, a `worker_threads` worker headless). `SerialTransport` (`serialport`, in the machine host only: utility process or headless worker) over a USB serial port ([run-machine.md](../modes/run-machine.md#serial-transport), hardening M1).
- v0.1 connected to the virtual machine only ([run-v0.1.md decision 1](../modes/run-v0.1.md#decisions)); hardening M1 adds `target: 'serial'` under the [real-machine safety rules](../modes/run.md#safety).
- Run commands (`run.connection.open { target: 'virtual' | 'serial' }`, `run.job.start` as a `job`, [commands.md](commands.md#long-running-commands-jobs)) are `machine: true`.
- **Permission rule** (for the `PermissionPolicy`, [commands.md](commands.md#dispatcher-pipeline) step 5): deny by default. A machine command on a connection the host reported as virtual is allowed for every source (UI, agent, CLI, automation, system), since no real machine is affected, and so is opening a virtual connection when none is open. On a real connection, other sources may only stop (jog cancel, reset; `job.pause`/`job.abort` are not machine commands); everything else, a connection still opening, or a process without a machine port is UI only ([run.md § Safety](../modes/run.md#2-who-may-command-a-real-connection-q50)). This makes the headless MCP exit criterion possible.
- Progress: `done` = lines acknowledged with `ok`, `total` = program lines; the position from status reports drives the 3D view.
- Run-mode design for task 3.9 (sender behaviour, clocks, machine host and protocol, run commands and job, safety): [run-v0.1.md](../modes/run-v0.1.md).

### Probing

`G38.2` (toward the workpiece, alarm on no contact), `G38.3` (toward, no alarm), `G38.4` (away, alarm when contact is never lost), `G38.5` (away, no alarm), as GRBL's mc_probe_cycle() (hardening M4, [run-machine.md](../modes/run-machine.md#probing-and-re-zero-m4)):

- Motion group: needs axis words (`error:26`) and a feed (`error:22`), a target other than the current position (`error:33`); `G53` with it is `error:30`. It waits for the planner to empty, then probes alone; the next line is read only after the probe.
- The probe input is a **simulated plate**: an infinite horizontal plane at MPos Z (emulator option `probePlate`, hook `setProbePlate(z | undefined)`); the input is closed while the tool tip is at or below it. Toward: closed before moving → `ALARM:4` (no motion, no `[PRB]`). The move runs at its feed with the planner's acceleration; on contact the position is latched and the machine decelerates to a stop (a few µm past the plate at probe feeds), like GRBL's motion cancel. Then the planner is flushed, the parser takes the stopped position, `[PRB:x,y,z:1]` (the latched contact, machine coordinates, report units) and the line's `ok`.
- No contact by the end of the move: `G38.2`/`G38.4` → `ALARM:5` (Alarm state, not critical: `$X` or `$H` clears it), then `[PRB:…:0]` (the end position) and `ok`; `G38.3`/`G38.5` → `[PRB:…:0]` and `ok`, no alarm. Away (`G38.4`/`G38.5`) mirrors it: the input must be closed at the start (else `ALARM:4`) and the probe stops when it opens.
- Check mode (`$C`) parses the line and does not probe. A soft reset during a probe is `ALARM:3` as any motion. A probe target outside the travel with soft limits on is `ALARM:2` before it moves, as GRBL's mc_line() check.
- `$#` reports the last probe as `[PRB:x,y,z:flag]` (zero and `0` before the first).

### Fault injection

Test hooks on `GrblEmulator` for failures hardware produces and the protocol cannot (hardening M8, [run-machine.md](../modes/run-machine.md#fault-injection-m8)): `setProbePlate(z | undefined)` (above), `triggerHardLimit()` (a limit pin closes: motion stops at once, `ALARM:1` and `[MSG:Reset to continue]`, critical like `ALARM:2`; the position counts as lost) and `setSilent(silent)` (a hung controller: input is still consumed but nothing is answered, no `ok`, no report, no realtime reply). The loopback serial port adds `unplug()` ([run-machine.md § Testing](../modes/run-machine.md#testing)).

### Observability for tests

The emulator records a trace readable in-process (`GrblEmulator.trace`): executed lines (text with comments, received/acknowledged time and response, start/end time of the line's motion or dwell), position samples (time, MPos, state, speed) at block boundaries and stops, every response sent, every state transition, and protocol violations (RX overflow, a byte ≥ 0x80 inside a line, a line over 80 bytes as sent). The trace is unbounded; `trace: false` records nothing, and the machine host always runs with `trace: false` ([run-v0.1.md decision 10](../modes/run-v0.1.md#decisions)). Material removal against the stock comes later, via plan-mode simulation.

### Not emulated in v0.1

Limit pins (hard limits only through `triggerHardLimit()`), probe inputs other than the plate, `G28`/`G30`/`G92`/`G93`, `G55–G59`, coolant effect, laser mode (`$32`), parking, sleep (`$SLP`), startup lines (`$N`), EEPROM persistence, `$RST`, step pulses and step-rate limits, backlash and missed steps, spindle physics, grblHAL/FluidNC extensions. Fault injection: [above](#fault-injection) (M8).
