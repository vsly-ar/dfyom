# Plan mode v0.2: setups from face directions, tools from design

Status: implemented (v0.2 closed 2026-11-22; follows from user decisions D10 and D11 of 2026-11-21; details confirmed with the v0.2 review, D18; visuals approved, D25 of 2026-11-22; the design ghost toggle is [later](#later)) · Vision: [plan.md](plan.md) · v0.1 subset: [plan-v0.1.md](plan-v0.1.md) · Design input: [design-v0.2.md](design-v0.2.md) · Apply (D13): [apply.md](../architecture/apply.md) · UI rules: [ui.md § Design and plan controls (v0.2)](../conventions/ui.md#design-and-plan-controls-v02) · Terms: [glossary.md](../glossary.md)

Plan consequences of [design-v0.2.md](design-v0.2.md): several setups, one per approach direction, and tool assignment from the design's tool field; plus plan-only edits of the design snapshot in the UI (strategy editing phase 2, [roadmap.md](../roadmap.md)). Everything not mentioned here stays as in [plan-v0.1.md](plan-v0.1.md). Tasks: [plans/v0.2.md](../plans/v0.2.md#3-plan-and-run).

## Decisions

Settled with the user when this doc was accepted (D18, 2026-11-22: Q15 as taken by D16, K–N as recommended by D12, O as drafted); the sections below specify them.

1. **No workholding, no in-process stock (Q15):** toolpaths of later setups use the design's analytic levels, so they may air-cut where an earlier setup already removed material, like the known facing/profile air-cutting. Amended by hardening DF50: a through profile cuts only the material earlier setups left under its slot ([§ Material removed by earlier setups](#material-removed-by-earlier-setups)); DF61 adds through holes and drops the passes of facings, pockets and profiles that lie wholly in air ([§ Material left for later cuts](#material-left-for-later-cuts-df61)); everything else is unchanged.
2. **Setup rotation (K):** 0/90/180/270° about the spindle axis per setup if it is cheap (decided in task E1: built, see [§ Implementation (task E1)](#implementation-task-e1)): a long side face may only fit the travel rotated. If not, the orientation stays fixed by the face frame and the travel check warns ([§ Setups](#setups-from-face-directions)).
3. **Default setup order (L):** the bottom (`−z`) first, as a datum, then the sides, the top (`+z`) last, so through profiles with tabs run last ([§ Merge, split, reorder](#merge-split-reorder)).
4. **A design tool locked after a plan assignment (M):** the plan assignment wins and the stale flag `designToolChanged` shows; plans are snapshots and are tuned on their own ([§ Tool resolution](#tool-resolution-from-the-design-tool-field)).
5. **Through features (N):** one approach direction per operation, the design's. Machining a through hole or profile from the opposite face ("access directions") is later; it changes the setup derivation.
6. **Plan-only edits on rebuild (O):** a rebuild discards all plan edits, as in v0.1; the confirmation names what is lost. Keeping edits the design change did not touch is later, if users ask ([§ Plan-only edits](#plan-only-edits-and-the-snapshot-scene)).

## Setups from face directions

- **Derivation:** `plan.create` and every rebuild group the plan operations by the [approach direction](design-v0.2.md#face) of their design operation's `on` face: **one setup per direction** in use. A part with only top operations keeps exactly one setup, as in v0.1.
- **Setup record** (extends [plan-v0.1.md § Plan record](plan-v0.1.md#plan-record)): `{ id, name, direction, rotation?, workOffset, clearanceHeight, retractHeight, operations[] }` (`rotation` only if task E1 finds it cheap; absent = 0°). `direction` is the part direction that points up to the spindle (machine +Z). Default name: "Top", "Bottom", "Front", "Right", "Back", "Left" (a second setup of one direction: "Top 2").
- **Orientation:** the setup's machine axes are the [face frame](design-v0.2.md#face-frame) of its direction: `u` → machine +X, `v` → machine +Y, `n` → machine +Z. For `+z` this is v0.1's fixed orientation ([plan-v0.1.md § Setup](plan-v0.1.md#setup-orientation-work-zero-safe-heights)). A setup may be rotated 0/90/180/270° about the spindle axis if cheap ([decision 2](#decisions)): the rotation turns `u` and `v` about machine +Z, and the work zero moves to the lower-left corner of the rotated face (`plan.setup.update { rotation }`).
- **Work zero:** `G54` at the setup's zero, by default the face frame origin (the lower-left corner of the up-facing stock face, seen from above on the machine), Z0 on that stock face. Since alignment phase 1 the X/Y zero is the user's free choice, negative work X/Y included ([§ Alignment (phase 1)](#alignment-phase-1)). Each setup is re-zeroed by the operator after re-fixturing; each exports its own program. The stock's thickness tolerance after a flip absorbs into `breakthrough` for through cuts, as in v0.1.
- **Safe heights** per setup as in v0.1, measured from the setup's up-facing stock face and the operation's `on` face.
- **Machine checks per setup:** the stock size in the setup's orientation (extent along `u`, `v`, `n`) + `clearanceHeight` must fit the travel.

### Merge, split, reorder

| Action  | Rule                                                                                                                                                                                     |
| ------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Split   | Move chosen plan operations of a setup into a new setup of the **same direction** (e.g. rough the top, flip, machine the bottom, flip back to finish the top).                           |
| Merge   | Join setups of the **same direction**. Merging different directions fails with `plan.setup` (new code): a 3-axis setup has one approach direction. (4th/5th axis and user planes later.) |
| Reorder | Setups in any order and plan operations across setups of the same direction, subject to the order checks below.                                                                          |

- **Default order** ([decision 3](#decisions)): `−z`, then the sides 0–3, then `+z` last, then repaired so every operation follows the operations its `on` references (as `repairOrder` in [plan-v0.1.md § Implementation](plan-v0.1.md#implementation-task-213)).
- **Order checks across setups:** `plan.order` (error) when an operation's `on` face is made in a later setup; warning `plan.cutoutBeforeSetup` when a through profile runs in a setup before another setup (the part is held only by its tabs while re-fixtured).
- **Rebuild keeps the user's structure:** a new operation of an existing direction joins the last setup of that direction; a new direction gets a new setup at its default position; a setup left empty by a rebuild is removed. An operation whose `on` changed direction moves to a setup of its new direction.

### Toolpaths per setup

Generators stay top-down ([plan-v0.1.md § Toolpath generators](plan-v0.1.md#toolpath-generators-task-210)): the seam (`planOperationInputs`) passes each operation in its face frame (`[u, v]` positions, levels along `n` relative to the setup's Z0, the stock extent along `n` as the thickness for through cuts). Toolpaths come out in the setup's WCS directly. Export and run work per setup: [`plan.export`](../architecture/grbl.md#plan-export-command) gains `setupId` (required when the plan has more than one setup) and writes one program per setup; run mode's setup-change prompt between programs is the [run-v0.1.md amendment](run-v0.1.md#amendment-v02-task-e2-one-program-per-setup) ([§ Implementation (task E2)](#implementation-task-e2)).

### Material removed by earlier setups

Status: implemented (hardening DF50, from the agent's two-setup enclosure test: the underside relief and steps of setup 1 cleared 9.5 mm under the outline, yet setup 2 cut the outline 40.5 mm deep with 7 passes in air, refused a 1/8″ tool that reached the 33 mm really left, needed 11.5 mm tabs for 2 mm of real tab, and warned that the underside pockets cut the tabs away). Not an in-process stock model: one number per through profile, the smallest model that makes "through" mean the material that is there.

- **Through depth.** A through profile (`inside`, `outside`, or `on` without a depth) and, since DF61, a **through hole** (drilling with `bottom: 'through'`) cut their **through depth**: the stock extent along the normal less the depth that **facings, pockets and blind profiles of the opposite direction, machined in an earlier setup,** cleared under the **whole slot** (a hole: its disc). Cleared depth: a facing clears from the opposite face down its depth; a pocket clears its region down to its floor, but only when its `on` level is already cleared there (stacked pockets add up: a relief pocket 7.2 deep and a step pocket 2.3 deep on its floor clear 9.5); a pocket with a floor fillet counts only its region inset by the fillet radius; a blind profile (a step or groove, DF61) clears its slot from the face down to its depth. A pocket or blind profile counts only when its region or slot covers the whole slot or hole (the slot swept by the profile, clipped to the stock face; less than 0.001 mm² uncovered counts as covered). Other operations (drillings, chamfers, through profiles, side faces) and partial coverage leave the full extent: the cut then goes deeper than needed in places (air), never shallower. Opposite cuts that leave less than 0.01 mm leave the full extent too (the cut goes through air where they went through).
- **What follows it.** Toolpaths cut to the through depth + `breakthrough` (a drilling cycle: its full diameter there, the drill tip below); **tabs stand on the material left** (their `thickness` is measured up from the through depth, not from the raw stock face); the plan's flute and stickout checks, Design's `dfm.reach` and the tool fit, the design's auto tool choice, the geometry evaluation (tab solids, the nominal tab for `dfm.retainedRemoved`, so an underside pocket below a tab no longer "cuts it away") and `placed.box` all read it; for a through hole the drilling toolpath, the plan's flute and stickout checks, `dfm.reach`, the tool fit, `dfm.holeDeep` and `placed.box` (DF61). `plan.operation.list` returns a profile's as `throughDepth` (the Cut depth field shows it as the material); a hole's is not listed (one plan operation drills several holes).
- **Order.** The plan uses its own setup order: an opposite operation counts when its setup comes before the profile's. Design has no setups and reads the [default setup order](#merge-split-reorder) (`SETUP_ORDER`: the bottom first, so a top profile counts the bottom's cuts and a bottom profile counts none). A plan whose setups run the top first therefore cuts the full extent, as it must.
- **Check.** `dfm.tabsThick` (warning, `tabs.thickness`): the tabs are as thick as the material left or thicker, so the slot leaves nothing to cut at them ("an earlier setup leaves only 33.3 mm of material under the slot"); suggestion: at most that. Validation keeps `tabs.thickness` < the stock extent.
- **Not covered.** `SurfaceTable`'s `profileN.tab[i].top` levels stay measured from the opposite stock face (as `on` targets; nothing in the shipped flows places operations on tab tops); the drilling solid still reaches the far face (it only removes air there); air above later cuts: [§ Material left for later cuts](#material-left-for-later-cuts-df61) (workholding and in-process stock stay [later](#later)).
- **Code.** `throughDepths` in [`src/core/geometry/through-depth.ts`](../../src/core/geometry/through-depth.ts) (2D port for the coverage test; without it only facings count), applied by `toGeometryInput` (design, default order) as the profile's or drilling's `throughDepth`; the plan's [`planThroughDepths`](../../src/core/plan/through.ts) recomputes it in the plan's setup order for `PlanOperationInput.throughDepths` (by design operation id; `toGeneratorInputs` replaces the design's value), the tool checks and `plan.operation.list`. The input hash already chains every earlier operation and setup, so a change of an earlier setup marks the profile's toolpath stale.
- **Tests:** `src/core/geometry/through-depth.test.ts` (facing, covering pocket, stacked pockets, a pocket on a level not yet cleared, partial coverage, floor fillet, default and plan order, reach), `checks.test.ts` (tabs over a relief no longer `retainedRemoved`), `src/core/plan/through.test.ts` (toolpath depth and tab lift, stickout check, `plan.operation.list`, setups reordered top first, `dfm.tabsThick`). Checked against the agent's saved enclosure project: the outline's through depth is 30.543 mm (40 − 7.185 relief − 2.272 step), not 40.

### Material left for later cuts (DF61)

Status: implemented (hardening DF61, the follow-up of DF50/DF53: a blind step below an earlier facing or pocket floor started its passes at the raw stock face, and a ring pocket on a floor an earlier ring already lowered re-cut that level). The same coverage model as the through depth, one **material band** per cut, not an in-process stock model: Follow-ups (DF61 follow-ups): partial coverage of pockets, holes on cleared material and openings of earlier setups as removals, below.

- **Band.** For every facing, pocket, profile and (top only) drilling, the material over its **whole region** (the face rectangle for a facing, the pocket region, the profile's slot, the hole's disc; clipped to the stock face) that earlier cuts left: **top** = the depth that facings, pockets and blind profiles **of its own direction, machined before it** (machining order: earlier setups, then earlier in its setup) cleared over the whole region, chained as above, when that is below the cut's start level (the stock face; a pocket's `on` level); **bottom** (blind cuts only: a facing, a pocket, a step or groove) = where the material ends when cuts **of the opposite direction in an earlier setup** cleared up into its depth over the whole region. A through profile gets a top but no bottom (its through depth is that). Partial coverage gives no band (conservative: a pass that may touch material is never skipped); pockets handle it by area (**Partial coverage** below).
- **Passes.** Milling generators (facing, v0.1 and region pocket, v0.1 and region profile) compute their levels with `cutLevels`: from the band's top (equal steps of at most the stepdown down to the floor, so the passes above it, wholly in air, are gone; the entry helix or ramp starts there), and a level whose slab (from the level above down to it) lies wholly below the band's bottom is skipped. The **floor stays the operation's** (its depth, surfaces and checks are unchanged); at least one level is kept, so a cut wholly in air keeps one pass. Finishing levels (pocket walls; profiles since [DF76](plan-v0.1.md#finishing-defaults-hardening-df75-df76)) follow the same rule. Retract, clearance and the rapids above the stock stay as they are. **Drillings** (follow-up) start their cycle at the band's top: the pecks count from there and the retract plane is that top + the setup's retract height (the hole's whole disc is cleared above it, so the rapids down to it stay in air); the flute and stickout checks keep the full depth. **Chamfers** keep their levels: a chamfer's `onZ` is the face of the edge it breaks (the drilling's or pocket's `on` surface), so a chamfer on a cleared floor already starts there; a chamfer whose edge's `on` face an earlier cut cleared away is a design matter and its geometry is not moved.
- **Partial coverage (pockets, follow-up).** When earlier cuts of its own direction clear only part of a pocket's region below its band's top, the band carries `partial`: the level L and the part cleared down to it (per clearing the part of the region it clears where the material above its own top is already gone – stacked pockets chain as above, by area – and L the level with the largest (L − top) × area). The wiring (`toGeneratorInputs`) then cuts the pocket as two region-generator inputs joined into one toolpath: first the **rest** – the uncovered part grown by `reach` into the cleared part and clipped to the region, so the cleared part acts as an [open side](plan-v0.3.md#open-sides-df61) (real walls keep their offset, the corners where they meet the cleared part are cut) – from the band's top down to L, then the whole region (or its open region) from L to the floor. A v0.1 rectangle or circle with partial coverage goes to the region generator too. Never skip material: the split is used only when every point of the uncovered part the tool reaches in the whole region (its opening by r) it also reaches in the rest, up to 0.01 mm² of boolean slivers (`uncoveredRegion`), and only when levels × area drop by at least 5 % (two parts in equal steps can add a level, and a rest grown into a small cleared part covers most of the region: the enclosure's cavity under the notch and rebate keeps one part). A wholly covered region (several clearings together) starts at L. Facings and profiles get no partial coverage (their generators cannot clip passes by area).
- **Openings as removals (follow-up).** An **opening** – an inside through profile without tabs – clears its loop's interior (slot and slug) through the whole stock for the operations of **later setups** on the same axis (either face): for their bands it counts like a clearing from the face to the stock extent. In its own setup the slug may still sit in its slot, so it does not count there; with tabs the slug and tabs stay, so it does not count at all; the outer release profile does not matter (the part is cut out). Through depths ignore openings (a through cut over an opening is a design error the through-depth rule already leaves at the full extent).
- **Plan only.** The band needs a machining order: the design has none, so its checks are unchanged (the tool checks measure the full depth, the safe side). `PlanOperationInput.material` (`planMaterialBands`, [`plan/through.ts`](../../src/core/plan/through.ts), in the machining order and, for openings, the setup order) carries it to `GeneratorInput.material` (the band; `partial` is resolved by the wiring), a drilling's per hole in `PlanOperationInput.materials`; the input hash already chains every earlier operation, so reordering marks the toolpath stale.
- **Code.** `materialBands` in [`src/core/geometry/through-depth.ts`](../../src/core/geometry/through-depth.ts), `cutLevels` / `cutTop` in [`src/core/toolpath/common.ts`](../../src/core/toolpath/common.ts); `uncoveredRegion` and the split in [`src/core/geometry/open-sides.ts`](../../src/core/geometry/open-sides.ts) and [`src/core/toolpath/inputs.ts`](../../src/core/toolpath/inputs.ts) (`splitSaves`), the joined `regionPocket` request in [`request.ts`](../../src/core/toolpath/request.ts).
- **Tests:** `through-depth.test.ts` (through holes, blind profiles as removals, bands: facing above a pocket, a step under a facing, a through profile, pocket coverage, a bottom under a blind pocket), [`toolpath/material.test.ts`](../../src/core/toolpath/material.test.ts) (`cutLevels`; facing, v0.1 pocket, region pocket, v0.1 profile over a band), `plan/through.test.ts` (a through hole over a bottom relief, a step below a facing). Checked against the agent's enclosure project: the outer rebate ring (on the relief floor, inside the foot rebate ring cut before it) starts at −8.145 instead of −7.185 (2 → 1 roughing passes, 126 → 83 s with its open sides, [plan-v0.3.md](plan-v0.3.md#open-sides-df61)); with the two steps modelled as blind outside profiles from the bottom face (DF53) they start at the relief floor (4 → 1 and 5 → 2 roughing passes, 308 → 119 s) and their slots, as blind profiles, count for the outline's through depth (30.543 mm instead of 32.815: 32 → 30 passes, 706 → 664 s); that variant drops from 99 passes / 65.1 min to 91 / 61.4 min. Follow-ups: `through-depth.test.ts` (partial coverage, chained, the best level; a hole's band; openings of an earlier setup, not in their own, not with tabs, not the release profile), `open-sides.test.ts` (`uncoveredRegion`: whole, partial, refused when the rest is narrower than the tool), `material.test.ts` (a peck cycle from the band's top), `plan/through.test.ts` (a pocket round a deeper earlier one: two inputs, faster, and the heightmap after both pockets equals the unsplit cut's; a hole in it bores from the pocket floor). Checked against the agent's saved enclosure project (as saved now: 111 passes, 84.5 min): unchanged – the cavity's partial coverage by the notch and rim rebate does not pay (refused by the 5 % rule; without it the split cost 82 s more), its holes and countersinks already sit on the relief floor and it has no opening.
- **Not covered.** Partial coverage of facings and profiles (a step whose slot runs past the relief's walls still cuts from the stock face); a partial bottom (opposite cuts under part of a region); a drilling's bottom band (a blind hole into a relief from the other side) and chamfers below a cleared level; openings with tabs, openings in their own setup, and openings for through depths.

### Implementation (task E1)

Core only (`src/core/plan/setups.ts`, `build.ts`, `order.ts`); the setup panel is F6, toolpaths per setup C3, export per setup E2.

- **Record:** `direction` and `rotation` are optional and left out for `+z` and 0°, so v0.1 records load unchanged (no `schemaVersion` change); `setups` has no upper bound. New setups get the direction names ("Top", not v0.1's "Setup 1"; stored names stay).
- **Direction of a plan operation:** the stock face its first design operation's `on` chain starts from (surfaces inherit their `on` direction, so every `on` dependency lies within one direction). Drillings are grouped into one plan operation only within one direction.
- **Rotation is built** (decision 2): `plan.setup.update { rotation }` stores it and the machine check swaps the `u`/`v` extents for 90°/270°; turning the toolpaths and the work-zero corner is C3 ([below](#implementation-task-c3)).
- **Split / merge / move** (and `plan.operation.move` with `toSetupId`) refuse with `plan.order` when they add an order violation the plan did not have, like `plan.operation.move` in v0.1. A split must leave at least one operation in its setup (`input.malformed`, rule `allOperations`); the new setup keeps the source's heights and rotation. Merge joins into the first of the setups in machining order (operations concatenated in that order). A setup emptied by `plan.operation.move` is removed, like one emptied by a rebuild.
- **Findings:** `plan.order` runs over the machining order of all setups; `plan.loosePiece` compares only operations of one direction (face-frame positions); `plan.cutoutBeforeSetup` (warning, rule `cutoutLast`) is attached to every profile's plan operation in a setup followed by another setup (every v0.2 profile is through); `plan.machine` runs per setup and carries `params.setupId` when the plan has several setups.
- **Until E2,** `plan.export` of a plan with several setups failed with `plan.setup` (rule `severalSetups`) rather than writing one program across a re-fixture; E2 replaced it with export per setup ([below](#implementation-task-e2)).

### Implementation (task C3)

Core only (`src/core/plan/inputs.ts`, `src/core/toolpath/inputs.ts`, `request.ts`, `wcs.ts`); per-setup export is E2, the setup panel and per-setup preview F6.

- **Seam:** `PlanOperationInput.setup` carries the setup's `direction` and `rotation`. `toGeneratorInputs` passes each operation as geometry already reads it ([geometry.md § Non-top faces](../architecture/geometry.md#non-top-faces-v02)): positions in `[u, v]`, `onZ` relative to the setup's Z0, without `direction`; the stock as `localStock(direction)` (the face rectangle on X/Y, the extent along `n` as the thickness for through cuts and tabs). Generators are unchanged. The `faceNotSupported` stub of A1 is gone.
- **Direction check:** an operation whose face is not its setup's direction (possible after a plan-only edit of `on`, until a rebuild regroups it) fails with `plan.setup`, rule `setupDirection`.
- **Rotation:** turning the inputs instead would move the tabs (they start at the middle of `wall[0]`, as in geometry), so generators run in the face frame and the toolpath is turned afterwards: the `GeneratorRequest` gains `wcs { rotation, size }` (absent for 0°, so unrotated setups, every v0.1 plan, generate byte-identical toolpaths and gCode) and the worker applies the quarter turn about machine +Z, counter-clockwise seen from above (`turnToolpath`: positions and arc centers turn, Z, feeds and arc senses stay; stats are recomputed, since rapids are timed per axis). A face point `(u, v)` of a face `L × W` lands at `(W − v, u)` for 90°, `(L − u, W − v)` for 180°, `(v, L − u)` for 270°: the work zero is the lower-left corner of the turned face, as the machine check's swapped extents assume. The strategy's facing `axis` stays along the part (`x` = along `u`) and turns with it.
- **Drilling order** starts from the hole nearest the work zero of the turned WCS.
- **Preview data:** `setupFrame(direction, rotation, stock)` (`wcs.ts`) is the setup's WCS as a placement in the part frame (identity for an unrotated top setup), for drawing a setup's toolpaths on the part (F6) and run mode's work zero (E2).
- **Cache:** `inputHash` already covered the whole setup record, so a changed rotation regenerates.
- **Tests** (`src/core/toolpath/setups.test.ts`): quarter turns and their inverse, `setupFrame` against the face frame for every direction and rotation, side and bottom toolpaths landing on the part where the geometry has the hole and the pocket, rotated setups placing back onto the same path, drilling order in a turned WCS, the direction check; golden toolpaths of the bottom and right setups (and the bottom turned 90°) and the gCode of a bottom-only plan and of a right-side plan turned 90° (`src/core/toolpath/__golden__/setup-*`). The exit-criteria golden is unchanged.

### Implementation (task F6)

Plan-mode UI only (`modes/plan/SetupList.tsx`, `SetupInspector.tsx`, `DirectionIcon.tsx`, setup helpers in `model.ts`); the commands are E1's, `plan.export { setupId }` E2's. UI rules as built: [ui.md § Design and plan controls (v0.2)](../conventions/ui.md#design-and-plan-controls-v02).

- **Every setup is shown:** the navigator lists all setups with their operations nested; the inspector finds a plan operation in any setup and shows a selected setup (name, rotation, safe heights); the plan summary counts every operation. Closes E1's "only the first setup" issue.
- **The window's setup** (selected setup, else the selected operation's, else the last selected, else the first) is the one previewed and exported. The plan scene draws only its toolpaths, through `setupFrame` (closes C3's preview issue for Plan); the export sends its `setupId` when the plan has several setups (closes E2's Export dialog issue). A one-setup plan sends no `setupId`, so v0.1 flows are unchanged.
- **WCS corner as text:** the part corner at the work zero, named by the faces that meet there besides the up face ("front left" on the top, "back left" on the bottom, "bottom front" on the right face; a 90° top setup "back left"), from `setupFrame`'s origin. On the machine it is the front-left corner of the up face (the setup-change prompt's wording); a setup whose zero is moved (DF78, [alignment.md § Setup work zero](alignment.md#setup-work-zero-q61)) names the zero as "X 40 Y 25 mm from the front-left corner of the top" or "on Witness mark 1" and the corner as the one it is measured from.
- **Moves across setups:** an operation's move up / move down (and `Alt+↑/↓`; a drag stays within its setup, hardening U3, [ui.md](../conventions/ui.md#reordering-lists-d45)) continue into the neighbouring setup when it has the same direction (`plan.operation.move { toSetupId }`); a split moves one operation ("Move to new setup"; multi-select later); merge joins two setups from the setup's menu. The core refuses order violations (`plan.order`), shown like any refused move (the row stays).
- **Export blocking per setup:** the panel disables the export on the window's setup's own errors and plan-wide errors without another setup's `params.setupId`, as the core blocks only that setup's program.

### Tool reach past the stock and clamps (hardening DF59, interim)

> Since DF59's workholding build (2026-11-24) a setup can list its clamps ([workholding.md](workholding.md#implementation-notes-df59)); with items the clamp note and the header's `Keep clamps …` line give way to the items. The reach stays.

No workholding model exists yet ([decision 1](#decisions); clamps come with workholding, v0.4 follow-up W1). Until then the setup says where the tool leaves the stock outline, so the operator clamps elsewhere: a facing's overshoot (the rows start and end with the tool fully outside, its flat edge `overshoot` past the edge), open pocket sides ([plan-v0.3.md § Open sides](plan-v0.3.md#open-sides-df61): the edge up to r (1 + √½) + allowance past it), outside profile slots and lead-ins.

- **Reach** ([`overreach.ts`](../../src/core/toolpath/overreach.ts), `toolpathOverreach`): per side of the stock rectangle as it sits on the machine in this setup (`setupOrientation(...).size`, the setup WCS spans X 0…length, Y 0…width), how far the tool's circle (centre ± D/2, the tool's largest diameter: conservative for chamfer mills and drills) reaches beyond that side: `{ xMin, xMax, yMin, yMax }` (left, right, front, back), mm, ≥ 0, 0 = within the outline. Only the parts of moves below the stock top (Z < 0) count: cutting moves, plunges and ramps, helices and arcs (their XY bounds when either end is below the top), drill cycles (the hole's centre and the tool radius when the bottom is below the top), and rapids below the top (rare); a line that crosses Z 0 counts from the crossing. Rapids and links at retract and clearance height do not count: clamps must stay below the clearance height instead (below). A setup's reach is the per-side maximum over its plan operations.
- **Where:** `plan.toolpath.get` returns `overreach` for a current toolpath (`null` when the toolpath is stale, missing or its inputs have errors); the export computes it from the toolpaths it writes ([grbl.md § Setup header](../architecture/grbl.md#setup-header-hardening-df58)); the setup inspector and the agent's `plan_get` summary combine the operations' values and show nothing (`null`) until every toolpath of the setup is current ([ui.md](../conventions/ui.md#design-and-plan-controls-v02), [llm-api.md § Result size](../architecture/llm-api.md#result-size)).
- **Clearance height:** clamps must stay lower than the setup's clearance height above the stock top, where the tool travels at tool changes, the start and the end. Without a clamp model nothing checks this unless the user enters the setup's clamp height (hardening DF64, [safe-links.md § Clamps](safe-links.md#clamps)): then a `plan.check` warning (rule `clampsAboveClearance`, field `setup.clearanceHeight`) says when the clearance height is below the clamp height + the retract height. The setup inspector shows the note on the clamp height field.
- **Tests:** [`overreach.test.ts`](../../src/core/toolpath/overreach.test.ts) (lines clipped at Z 0, arcs, drills, rapids above the top ignored; a facing's overshoot on every side; per-side maximum), `plan/shape-checks.test.ts` (an open pocket on the stock edge reaches past it, a closed pocket 0, both through `plan.toolpath.get`), the export header (`plan-export.test.ts`), the setup inspector (`Setups.test.tsx`) and the `plan.get` summary (`shape.test.ts`).

## Tool resolution from the design tool field

The design's [tool field](design-v0.2.md#operation-tool) is an input to Plan's [tool assignment](plan-v0.1.md#tool-assignment-and-checks). It replaces "the design's tool requirement" as the only input to `plan.tool.suggest`; the plan check table itself is unchanged.

| Design tool         | Locked | `plan.create` / rebuild assigns                                                                                                                                                                                                                                                                |
| ------------------- | ------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Specific            | no     | That tool (a plan copy of the design's snapshot) if it passes the plan checks for the plan's machine; else the first `plan.tool.suggest`, with info `plan.designToolReplaced` naming the failed check.                                                                                         |
| Specific            | yes    | That tool, **always**. If it fails a plan check, it stays assigned and `plan.designToolFailed` (error, fails generation for that operation) names the check and lists the fitting alternatives. Never swapped.                                                                                 |
| Generalized         | no     | The first `plan.tool.suggest`, where library tools matching the generalized type and diameter (and RE) within 0.01 mm rank first.                                                                                                                                                              |
| Generalized         | yes    | The best matching library tool (type and diameter, and RE, within 0.01 mm) that passes the checks, ranked as `plan.tool.suggest`. None: no tool, `plan.toolUnresolved` (error) naming the generalized tool and the fitting non-matching alternatives. Never a different size or type silently. |
| None (v0.1 project) | –      | As v0.1: the first `plan.tool.suggest`.                                                                                                                                                                                                                                                        |

- **A locked tool failing in a plan warns, it never swaps.** The user resolves it explicitly: assign another tool in the plan (`plan.tool.assign`, a deliberate plan decision), change the machine, extend the stickout, or change the design. The fix list in `plan.warning.list` offers these.
- **Plan assignment wins inside the plan.** `plan.tool.assign` marks the plan operation `toolSource: 'plan'` (new optional field, no `schemaVersion` change); create and rebuild set `toolSource: 'design'`. A rebuild re-resolves the tool only for `toolSource: 'design'` operations whose design tool field changed (by value) since the snapshot; `plan` ones keep their tool and show the stale flag `designToolChanged` in `plan.stale.list`. A later design lock does not override a plan assignment ([decision 4](#decisions)).
- **Draft plans** follow the design tool field through the rebuild like any design change, on Apply ([below](#draft-plans-follow-on-apply)); a locked specific tool that fails reports `plan.designToolFailed`, never a blocked rebuild.
- `plan.tool.suggest` gains a reason per candidate for the design tool (`matchesDesign`, `designTool`), so the UI and agents see why a tool ranks first.

### Implementation (task E4)

Core only: [`design-tool.ts`](../../src/core/plan/design-tool.ts) (the field as the plan sees it, matching), [`tool-resolution.ts`](../../src/core/plan/tool-resolution.ts) (the table, the findings), [`suggest.ts`](../../src/core/plan/suggest.ts), `build.ts`, `snapshot.ts`, `commands.ts`; the tool field in the inspector is F5 (which also added the renderer texts of the findings below and shows `toolSource` and `designToolChanged` in the plan inspector, [design-v0.2.md § Implementation (task F5)](design-v0.2.md#implementation-task-f5)). Choices made with the implementation:

- **The plan copies the design's tool snapshots** with the design's ids, like the stock copy: `takeDesignSnapshot` copies every tool snapshot a specific tool field of the part references, so the plan's part resolves in its own snapshots and every finding is derived from the plan record alone. "That tool" in the table is that copy (`tool` = the design's snapshot id). A rebuild adds copies of new ids and keeps an existing copy (it follows the library on its own, as a library copy: `libraryChanged`, re-import); `pruneSnapshots` keeps copies the part references. Plan copies taken by the plan get an id not used in the plan (`nextSnapshotId`). Plans taken before E4 have no such copy: their operations resolve as v0.1.
- **"Passes the plan checks"** is `plan.tool.suggest`'s filter (the `tool`, `stickout` and `stepdown` errors with the tool's own default stickout and preset, `failedCheck`), not the design's `toolFit`: the plan checks include the plan-only rows (point angle, flute length, stepdown, the plan's breakthrough). The first failing check names the rule (`params.check`, `checkField`).
- **Ranking** of `plan.tool.suggest`: `designTool` (the library item the design's specific tool was taken from) → `matchesDesign` (type and DC, and RE for a bull nose, within 0.01 mm of the design's tool, generalized or specific) → preset → used in plan → size (diameters within 6 % are one size) → shortest stickout (else flute length) → diameter (since hardening DF55, as the design's [auto choice](design-v0.2.md#tool-choice-fixes-df51-df52-df54-df55); was diameter alone); both flags are in each candidate with a reason ("the design's tool", "matches the design's 1/4″ flat end mill"). Without a design tool the order is v0.1's.
- **No fit at all:** an unlocked specific tool that fails while no library tool passes stays assigned (its `plan.check` errors say why) rather than leaving the operation without a tool; an unlocked generalized tool or none without a suggestion leaves a new operation without a tool (v0.1's "no tool") and keeps an existing one's tool.
- **Findings** (`plan.warning.list` only, derived per call for `toolSource: 'design'` operations): `plan.designToolReplaced` (info), `plan.designToolFailed` (error; judged with the operation's own stickout and preset, since the design's tool is the assigned one) and `plan.toolUnresolved` (error, rule `noMatchingTool`), each with `field: 'tool'`, `params.designTool` (label) and, for the errors, `alternatives` / `alternativeIds` (the current suggestions, comma-separated) and the fix list in the message. Generation is blocked by the operation's own `plan.check` / `noTool` error that comes with each error finding, so `planFindings` (and the toolpath seam) stay library-free.
- **Rebuild:** a kept plan operation is re-resolved when its first design operation's field (`tool` and `toolLocked`, by value; a specific tool by snapshot id: in-place `design.snapshot.update`s reach plans through the library copy) differs between the old and the new snapshot and its `toolSource` is `design`; otherwise it gets the stored marker `designToolChanged: true` (cleared by `plan.tool.assign`). A record without `toolSource` (taken before E4) counts as `plan`: never swapped. A re-resolution that lands on the same copy keeps `presetName`. New and re-resolved operations get `toolSource: 'design'`; `plan.tool.assign` sets `plan`.
- **Stale flag:** `plan.stale.list` operations gain `designToolChanged` (true when the design's field differs from the snapshot's, i.e. before a rebuild, or the plan operation carries the marker).
- **Drillings with different tool fields** are separate plan operations (the field is part of the drill grouping key); a changed field splits a group on rebuild.
- **Tests** (`src/core/plan/tool-resolution.test.ts`): every row of the table, the findings with alternatives, the suggest flags and reasons, rebuild re-resolution vs. the kept plan assignment and its marker (undo/redo of `plan.create`, `plan.rebuild`, `plan.tool.assign`), the preset kept, a record without `toolSource`, a draft plan following a tool change on Apply (undo/redo), drill groups split by tool. The exit-criteria golden gCode is unchanged; the C3 golden toolpaths changed only in the tool copy id of their header (`snapshot-9` instead of a plan-taken `snapshot-24`).

## Plan-only edits and the snapshot scene

Strategy editing phase 2 ([roadmap.md](../roadmap.md); phase 1 shipped the Strategy group and the feeds derivation). The core already has [plan-only edits](plan-v0.1.md#plans-are-snapshots) (`plan.design.operation.update` in `settledDesign`, the `editedInPlan` stale indicator, `discardPlanEdits` on rebuild); this section adds what the UI needs. No new data: the plan's design snapshot `{ taken, part }` already holds both versions.

- **New command `plan.design.operation.revert`** `{ planId, planOperationId }`: copies the `taken` version back into `part` for that operation (one undo step); allowed where `plan.design.operation.update` is. Agents and the CLI get it from the command layer.
- **Inspector:** in a `settledDesign` plan, a "Part (plan copy)" group under Tool shows the operation's design fields, reusing the Design inspector's per-kind field components (factored out of the Design inspector, not copied). An edited operation shows an "Edited in plan" badge and "Revert to design". In `draft` the group is read-only with the hint "This plan follows the design while it is a draft. To edit this operation for this plan only, set the plan status to settled design." (DF48) (the status by its glossary name, not "settle"); in `finalized` and later it is read-only.
- **Rebuild with plan edits** asks first ([ui.md § Confirmations](../conventions/ui.md#confirmations)): "Rebuild discards 2 plan-only edits" with Rebuild and Cancel; agents still pass `discardPlanEdits: true`.
- **Snapshot scene:** the plan scene draws the **plan's** part (`design.part` of the plan), not the design's current mesh. The geometry worker evaluates a part DTO passed in (cached by the snapshot's hash, [workers.md](../architecture/workers.md)); edited operations are tinted. Showing the design's current part as a ghost for comparison is [later](#later).
- **A rebuild discards all plan edits**, also those the design change did not touch ([decision 6](#decisions)).

**Implementation (task E3a, core):** `plan.design.operation.revert` returns `{ reverted }`, the design operation ids whose edits it reverted (empty, and no undo step, when the plan operation had none); it checks the reverted part against the plan's stock copy like `plan.libraryItem.update` (a copy updated since the snapshot can make the taken version not fit: `model.invariant`, the edit stays). The scene evaluation runs in the `EvaluationScheduler` as the plan's own subject ([workers.md](../architecture/workers.md#automatic-evaluation-after-design-edits)); the window push and drawing are task E3b.

**Implementation (task E3b, UI):** the per-kind design fields live in `modes/design/OperationFields.tsx`, used by the Design inspector and by `PlanCopyGroup` (each commit one `plan.design.operation.update`; read-only outside `settledDesign`, with the draft hint). The rebuild and the status change back to draft confirm when the plan has plan-only edits (the count is the design operations that differ from `taken`) and then pass `discardPlanEdits: true`. The app host pushes each plan's part evaluation to windows (`PartEvaluationView.planId`, `evaluation.getPlan` on bind, [overview.md § IPC](../architecture/overview.md#ipc)); the plan scene draws it on the plan's stock copy with edited operations tinted (`--info`, light). The plan copy has no pick mode (references from the field's list), and the design ghost toggle is deferred ([§ Later](#later)).

## Setup change in Run

Run mode loads **one program per setup** ([§ Toolpaths per setup](#toolpaths-per-setup)). Between programs it shows a setup-change prompt, styled like the tool-change dialog ([run-v0.1.md](run-v0.1.md)): the next setup's name and direction, a picture of the stock in its new orientation, "Set the work zero on the new top" with the WCS corner, then Start. The virtual machine needs nothing new (a setup change is a pause with a new program). The [run-v0.1.md amendment](run-v0.1.md#amendment-v02-task-e2-one-program-per-setup) is part of plan task E2 ([plans/v0.2.md](../plans/v0.2.md#3-plan-and-run)); as built: [§ Implementation (task E2)](#implementation-task-e2).

### Implementation (task E2)

Core (`src/core/plan/setups.ts` `chooseSetup`, `src/core/post/plan-export.ts`, `src/core/run/job.ts`, `src/core/toolpath/wcs.ts` `setupOrientation`) and run-mode UI (`modes/run/`); Plan mode's per-setup export and preview stay F6.

- **One setup per call:** `plan.export { planId, setupId?, target }` and `run.job.start { planId, setupId? }` work on one setup; `exportPlan` takes `setupId` in its options. `setupId` may be left out only when the plan has one setup (every v0.1 plan, so single-setup flows and the exit-criteria golden are unchanged); with several it fails with `plan.setup`, rule `setupRequired` (`params.setupIds` in machining order), an unknown id with `input.malformed`, rule `unknownSetup`. The E1 guard (rule `severalSetups`) is gone. Both results carry `setupId`. An optional argument rather than new tools keeps the agent `tools/list` budget (D21).
- **Z headroom (hardening DF68):** each setup's program is checked against the machine's Z height: the tool tip at Z home above this setup's Z0 (spindle nose to table − spoilboard − the stock extent along this setup's spindle axis − stickout) must clear the setup's clearance height by 1 mm, and each tool's lowest Z must be within the Z travel. Warnings in `plan.export`'s `warnings` and (top only) `plan.warning.list`, always with `params.setupId`; rules and the relation to the live soft-limit check in [grbl.md § Z headroom](../architecture/grbl.md#z-headroom-hardening-df68).
- **Program:** the header names the setup (`(Setup: Bottom)`; since hardening DF58 `(Setup 1 of 2: Bottom)` with the [setup instructions](../architecture/grbl.md#setup-header-hardening-df58)), the operations are the setup's in machining order, `clearanceHeight` is the setup's. Only the exported setup's error findings block it (as `plan.toolpath.generate` per operation): setup 1 can run while setup 3 still has a missing tool. The toolpath hash chain still runs over the whole machining order (a conservative cache key).
- **Setup change between run jobs:** a setup change is the gap between two run jobs, not a phase inside one: the operator re-fixtures, jogs and sets the new work zero with the machine idle and no job reserving the connection, and the next job's soft-limit check runs at the new G54 ([run-v0.1.md amendment](run-v0.1.md#amendment-v02-task-e2-one-program-per-setup)). `run.job.start`'s result adds `next` `{ setupId, name, direction, rotation }`, the setup after it in machining order (absent after the last), so agents chain the setups and the UI opens its prompt. The machine host, the sender and the emulator are unchanged.
- **Prompt (UI):** `SetupChangeDialog` (`modes/run/`) opens when the window's followed run ends `done` with a `next`: title "Setup change: setup 2, Top", the picture (`SetupPicture`: the stock as it sits on the machine in isometric view, extents from `setupOrientation`, the top face marked `--info`, the work zero ring at the front-left corner of the top, a legend of the part faces up, in front and on the right), the steps (raise, turn and clamp, set X/Y at the front-left corner, or where the setup moved the zero (DF78), and Z on the top, start), a setup with alignment points the [alignment step](alignment.md#run-the-alignment-step) (DF78), the jog pad, "Zero X/Y/Z" and "Zero X Y Z", the live G54, "Later", "Start setup 2" (the only primary, gated like Start run) and the run dialogs' Stop. "Later" leaves a note in the inspector with "Show instructions"; the inspector's "Start run" opens the prompt instead of the pre-flight while a setup change is pending. The badge shows "Setup change" with the tool-change token and shape while the machine is idle; the change is announced assertively. It never starts by itself; choosing another plan or setup or closing the connection drops it.
- **Navigator and pre-flight:** a plan with several setups shows a "Setup" select ("1. Bottom", "2. Top"; the first by default), the pre-flight a "Setup" row ("Bottom (1 of 2)"); the run starts the chosen setup.
- **Run scene placed per setup** (fixes C3's known issue for Run): toolpaths, the tool marker (`wpos`) and the work-zero ring stay in the setup's WCS and are drawn through `setupFrame` (`RunScene.frame`, a group matrix in `RunLayer`; framing bounds through `placeBox`), so a bottom or side setup's program lands on the part. Only the chosen setup's toolpaths are drawn (one program).
- **`prepare: true`** centres the stock of the **first** setup in its orientation (extents along the setup's X/Y, `setupStockSize`); the same as before for a top setup. Later setups set their work zero by jog and `run.workZero.set` (agents may pass `values`).
- **Tests:** `src/core/toolpath/setups.test.ts` (`setupOrientation` for every direction and rotation; `setupRequired`, `unknownSetup`, each setup's program with its own operations and header, findings of another setup not blocking, a single-setup plan unchanged with or without `setupId`), `src/core/run/commands.test.ts` (a Bottom + Top plan run setup by setup on the in-process host, `next` naming the top setup, none after it), `modes/run/RunMode.test.tsx` (setup select, pre-flight row, the prompt after a done run with picture, steps, controls, badge, Later and Show instructions, Start setup 2 naming the setup, axe), `machine-state.test.ts` (badge), `viewport/toolpath-lines.test.ts` (`placeBox`, `frameMatrix`). No e2e yet: a multi-face design is not yet buildable through the design UI (F1/F2); the headless multi-setup flow is X1.
