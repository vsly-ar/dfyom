# Run mode

Status: draft · Terms: [glossary.md](../glossary.md)

**Goal:** interact with the CNC machine. The baseline is running gCode; the mode goes far beyond that by integrating external devices.

The v0.1 subset (streaming to the virtual machine, utility process, run commands, progress) is specified in [run-v0.1.md](run-v0.1.md); the real machine over a serial port in [run-machine.md](run-machine.md), under the [safety rules](#safety).

## Devices

- **Sensors:** cameras, vibration, temperature, weight/pressure, distance, power consumption, flow meters, encoders, external RPM monitor (when the spindle doesn't report RPM).
- **Actuators:** servos, solenoids, relays, alarms, …
- Usually reached through **external controllers (MCUs)** the app communicates with.

## What this enables

1. **Detection of things going wrong** – chatter, loose parts, air-cutting where the tool should be engaging, collisions; machine vision for humans and other foreign objects.
2. **Extended machine capabilities** – external tool-changer automation; coolant / mist / compressed air / vacuum cleaning / vacuum table / ventilation / temperature automations.
3. **Lights-out cycles** – automatic setup changes, collecting finished parts, replacing stock and restarting the cycle.
4. **Calibration, measurement, testing, troubleshooting** – (semi-)automatic: resonant frequencies, motor load, thermal behaviour, tolerances/precision.

## Automation and LLMs

Automations can be scripts (JS/TS/Python/Lua) authored by users or LLMs, and/or an active LLM session watching the run via hooks and periodic checks. → [architecture/llm-api.md](../architecture/llm-api.md)

## Machine frame and manual control (hardening DF31–DF35)

Status: implemented (hardening, dogfood batch 1: DF31–DF35) · Spec of the v0.1 flow: [run-v0.1.md](run-v0.1.md) · GRBL facts and the virtual machine: [grbl.md](../architecture/grbl.md#homing-and-machine-coordinates) · Machine fields: [library.md](../architecture/library.md#machine) · UI: [ui.md](../conventions/ui.md#run-mode-safety-ui)

Manual control (position read-out, homing, jog, work zero) must work before and without a plan, and the 3D view must show where the spindle, the travel and the stock really are.

### Connect without a plan (DF31)

- `run.connection.open` takes **either** `planId` (the plan's machine copy, as in v0.1) **or** `machineId` (a library machine), exactly one (`input.malformed`, rule `oneOf`). The machine key of a library machine is the hash of its values, the same hash a plan's unchanged snapshot of it has ([run-v0.1.md decision 6](run-v0.1.md#decisions)), so a plan whose machine copy equals the connected library machine can be run on that connection; any other plan fails with `machineMismatch` as before.
- **Navigator:** the plan list has "No plan (manual control)" first; the first runnable plan stays the default when one exists. With no plan, a "Machine" select lists the library machines and "Connect" uses it. Home, unlock, jog, work zero, Stop, Reset and the DRO work without a plan; only "Start run" needs one ("Choose a plan first.").

### Run without a project (DF80)

Status: implemented (hardening DF80, user TG #280: "the run mode shouldn't be blocked by no project open to connect to machine and do basic machine controls") · Scope routing: [llm-api.md § Machine scope](../architecture/llm-api.md#machine-scope-df80) · UI: [ui.md § Mode switching](../conventions/ui.md#mode-switching)

Connecting to the machine and the basic machine controls need no project: only a plan run does. Before DF80, Run mode without a project showed the start panel (New / Open) and every `run.*` command answered `noProject`.

- **One machine connection per app instance** (unchanged, [run-v0.1.md](run-v0.1.md#processes)). Every window shows it, with or without a project: the toolbar's machine group, Stop and the DRO follow the same status push. A window without a project can connect, and it can control a connection another window opened (and the other way round); the connection is not tied to a project and survives closing one.
- **Without a project the navigator is manual control** ([DF31](#connect-without-a-plan-df31)) with nothing to choose between: no Plan select, the "Machine" select (library machines; the machine profile gives the travel and soft limits, the settings check of a serial connection and the probe plate thickness), the connection (virtual machine with its time scale, or a serial port), homing and unlock (confirmed as before), jog, work zero and Probe Z. The inspector keeps the DRO, overrides and Reset; its run section is an empty state, **"Open a project to run a plan"**, with "Open project" (the same handler as File → Open).
- **Lengths without a project** are shown in the unit system the Library window uses without a project (`libraryUnits` in the settings, [ui-library-window.md](../conventions/ui-library-window.md)); commands still take mm.
- **A run started elsewhere** ([M7](run-machine.md#run-status-and-the-zero-to-set-m7)): a window without a project shows it from the status (badge, "Plan 1 · setup 2 of 2", Feed hold, Stop, the tool-change and pause dialogs with Continue) but cannot start, check or resume a run.
- **Commands:** a session without a bound project (a window without a project, an unbound agent or CLI run) runs the manual-control commands on the instance's machine-scope dispatcher ([llm-api.md](../architecture/llm-api.md#machine-scope-df80)). `run.connection.open` there takes `machineId` only (`planId` → `noProject`); `run.job.start`, `run.job.check` and `run.align.*` need a project. A bound session is unchanged.
- **Safety is unchanged:** the permission policy ([Q50](#2-who-may-command-a-real-connection-q50)) runs in that dispatcher too (on a real connection agents get the stop paths only), and every stop path ([§ 1](#1-emergency-stop-stop-and-reset)) works from every window: Stop aborts a homing or probing job of the machine scope from a project window, as it aborts another project's run.

### Machine coordinates and the homing corner (DF33)

GRBL 1.1 without `HOMING_FORCE_SET_ORIGIN` (the default build) always puts the travel in **negative space**: machine coordinates span `[−travel, 0]` on every axis, whatever the homing direction ([grbl.md](../architecture/grbl.md#homing-and-machine-coordinates)). Where the machine homes only decides the machine position after `$H`:

| Axis homes towards      | `$23` bit | Switch at MPos | MPos after `$H`    |
| ----------------------- | --------- | -------------- | ------------------ |
| + (right, back, top)    | clear     | 0              | −pull-off (`$27`)  |
| − (left, front, bottom) | set       | −travel        | −travel + pull-off |

- The machine profile names the **homing corner** in XY (`backRight` = GRBL's default `$23=0`, `backLeft`, `frontRight`, `frontLeft`; Z always homes up), the **pull-off** (`$27`) and **soft limits** (`$20`), next to the travel (`$130–$132`) it already had ([library.md](../architecture/library.md#machine)). They configure the virtual machine; for a real controller they must match its `$$` (checked on connect with the real-machine lane, [hardening M1](../plans/hardening.md#5-real-machine)).
- Example (the dogfood machine, top-right homing, i.e. `backRight`, pull-off 1 mm): after homing the DRO reads −1/−1/−1. +X can move 1 mm (to 0); a further +X jog would leave the travel. That is correct; what was wrong was the view and the message.
- **Soft-limit refusals in words:** before sending a jog, the host computes its target (relative jogs from the last report, or from the end of the jogs it already queued while jogging) and, with soft limits on, refuses one outside `[−travel, 0]` with `run.travel` (`data: { axis, target, min, max }`), e.g. "X would leave the travel: max 0 mm, the jog would end at 1 mm." If GRBL still answers `error:15` (the estimate can lag a queued jog), the reply becomes the same `run.travel`. The navigator words it with the project's units.
- **3D view:** the run scene draws the **machine travel** (the work envelope `[−travel, 0]`, as a box outline) and the home position (a marker at the homing corner), placed through the work zero: in work coordinates the travel is `[−travel, 0] − G54`, so the travel, the stock at its work zero and the spindle at `wpos` are consistent with machine coordinates. A stock outside the travel shows where it is; with G54 still at 0 (never set) the Work zero section's G54 line adds "The work zero is at machine 0, the home corner: jog to the stock's zero corner and set it." The travel box widens the framing bounds.
- The travel, homing mask, pull-off and soft-limit flag come from the controller's `$$` at connect (`RunStatus.envelope`), never from the plan, so the view shows what the controller enforces.

### Homing on the virtual machine moves (DF32)

The virtual machine plays GRBL's homing cycle in time (Z, then X and Y together; seek, pull-off, locate, pull-off at `$25`/`$24`) and reports the moving position in `Home` state, so the tool marker travels to the home corner. It powers up at the centre of its travel (the app passes the start position; real GRBL reports 0,0,0 until homed, and the position is unknown either way). Details and the deviation from GRBL (which sends no status reports during homing) in [grbl.md](../architecture/grbl.md#homing-and-machine-coordinates).

### Messages never move controls; repeated jog clicks (DF34)

- The navigator's notice of why controls are disabled sits between the connection and homing sections in a **reserved status line** (two lines high, always present, `role="status"`; with nothing disabled it says "Ready to jog." — short texts only, so it never grows), so a reason appearing while the machine jogs or homes never shifts the jog pad.
- A refused action (`ErrorMessage`) shows **at the end of the navigator**, below the work-zero section, never above the controls.
- The navigator (and inspector) panel **reserves its scroll-bar gutter** (`scrollbar-gutter: stable`): with always-visible scroll bars (macOS "Show scroll bars: Always", or automatic with a mouse attached) a refusal overflowing the panel would otherwise add a scroll bar, narrow the panel, wrap "Unlock" under "Home" and drop the jog pad a row (hardening P6). The e2e forces classic scroll bars so the check runs the same on every machine.
- **Repeated step jogs queue:** jog stays enabled while jogging (GRBL plans `$J=` lines behind each other); every click sends one `$J=G91 …` that GRBL appends; a click whose target leaves the travel is refused in words (above) and the earlier jogs continue. "Stop jog" (`0x85`) cancels them all. Holding a jog button past the hold delay jogs to the travel edge and cancels on release ([run-machine.md § Machine readiness](run-machine.md#machine-readiness-m3), M3; DF88 made it click = step, hold = continuous, without a mode).

### Stop only when something can be stopped (DF35)

Stop is enabled while there is something to stop: a run job (any phase, including waits), or the machine moving or held without one (`Jog` → jog cancel; `Home` → reset, `ALARM:6`; `Run`, `Hold`, `Door` without a job → reset). Otherwise (Idle, Alarm, Check, not connected) it is disabled and says why ("Nothing to stop: the machine is not moving."). Feed hold (while streaming), Resume (while held) and "Reset (immediate)" (always, while connected) keep the other paths reachable.

### External holds (DF82)

Status: implemented (hardening DF82 follow-up) · Pause policy: [commands.md](../architecture/commands.md#pausing-a-job) · Stop paths: [§ 1](#1-emergency-stop-stop-and-reset)

A hold DFYOM did not send – the machine's **feed-hold button** (GRBL's feed-hold pin), or its **safety door** – acts like the app's own feed hold. Before, the sender went `held` while the run job stayed `running`, so the toolbar's Resume sent `job.resume`, which did nothing.

- **The job adopts the hold.** The sender marks a run `held` by the `machine` once motion has stopped (a report requested after the last `~` says `Hold:0`, or a door's `Door:1`/`Door:0`; never during `Hold:1`/`Door:2`, which still decelerate; an `M0` stop is still the program's pause). The run job (`handled` pause policy) is then **paused** with its `paused` lifecycle event, as after `job.pause`. A Probe Z job is paused when the machine comes to a standstill in a hold it did not ask for (`Hold:0`, `Door:0`/`Door:1`, entered from another state). Neither adopts a phase change while its own `job.pause`/`job.resume` is in flight, so the dispatch event still comes first.
- **Resume works as for the app's hold:** the toolbar's Resume and `job.resume` (on a real connection from the UI only, [§ 2](#2-who-may-command-a-real-connection-q50); agents read the hold and may stop) send `~`.
- **The machine's own cycle start** (GRBL's cycle-start pin): a report requested after the hold that says `Run` (or `Idle`) puts the run back to `streaming` and the sender streams on; the job is `running` again (`resumed` event), whoever held it. A Probe Z job is running again once the status says `Run`.
- **Safety door** (GRBL semantics): the door stops motion (`Door:2`), stays `Door:1` while ajar, and `Door:0` once closed; GRBL ignores `~` until then and never resumes by itself. While the door is open (`Door:1`/`Door:2`) `job.resume` and the Probe Z resume fail `run.state` (rule `doorOpen`, "the safety door is open: close it, then resume"), decided on a fresh status report; once closed, Resume sends `~` and GRBL restores the spindle (`Door:3`) before moving on.
- **Status:** `RunStatus.holdBy` (`app` | `machine`) says who holds while the state is `Hold` (absent at an `M0` pause). The badge says "Held (machine button)" for a `machine` hold at `Hold:0`, "Door open" for `Door:1`/`Door:2`, "Held (door closed)" for `Door:0` and "Resuming…" for `Door:3`; Resume is disabled while decelerating or while the door is open ([ui.md](../conventions/ui.md#run-mode-safety-ui)).
- **Tests:** the sender on the virtual machine (`sender.test.ts`, "holds the sender did not send"), the run and Probe Z jobs end to end on the loopback controller with its hold, cycle-start and door hooks (`commands.test.ts`, "fault injection on a real run"), the policy (`jobs.test.ts`, adopted holds), the badge and toolbar (`machine-state.test.ts`, `RunMode.test.tsx`).

### Run mode presentation (DF46)

Status: implemented (hardening DF46, UX audit 2026-11-23 items 7–9 and 23) · UI rules: [ui.md](../conventions/ui.md#run-mode-safety-ui)

What a first-timer sees from Connect to the first run. Only the presentation changes: every gate, refusal, confirmation and the Stop rules stay as they are.

- **The toolbar never changes height.** The main toolbar always reserves the height of the 44 px run controls (Stop, Feed hold, Resume), so connecting or disconnecting never moves the window content. The run controls stay 44 px.
- **Position unknown until homed.** While the machine is not homed (or not connected), the DRO shows "—" for every work and machine coordinate, with "Position unknown until homed." under the table. The numbers come back after a successful `$H` (or at once on a machine without homing, which counts as homed). After "Unlock" without homing the position stays unknown, as the unlock confirmation says. The tool marker in the 3D view is unchanged.
- **Needs homing, not an error.** GRBL with homing enabled starts locked in `Alarm` without an alarm code, because the position is unknown. While the state is `Alarm`, there is no alarm code and the machine is not homed, the badge says **"Needs homing"** (its own shape: a house in the hold colour, not the red octagon) and the navigator's Home is the primary action, with "Home the machine first." in the notice. Any `ALARM:n` (soft or hard limit, reset while moving, homing fail) stays the red "Alarm n: …" badge, and every control is gated exactly as in Alarm.
- **Connect** reads just "Connect", on one line (the audit saw "Connect to virtual machine" wrap in the 16 rem navigator); the "Connect to" select above it (Virtual machine / Serial port, [run-machine.md](run-machine.md#ports-and-the-port-picker)) names the target, the one hint under it says what connecting does ("To a virtual machine that simulates …", or "To a real GRBL controller on this port. …"), and the "Virtual machine · 10×" (or "Serial · port") chip says it once connected. "Connect to a machine first." shows once, in the navigator's notice; the inspector's disabled "Start run" is described by its "No run yet. Connect, home, …" line instead of repeating it.
- **Program pause** (`M0`): the badge says "Paused by program"; the dialog says the program paused the run, then names `M0` in a small details line. "Later" becomes **"Close (stay paused)"** in the program-pause and tool-change dialogs (the run waits; the inspector's "Show instructions" reopens the dialog). The setup-change prompt keeps "Later": no run is paused there.
- **Stop jog** uses the default button look (bordered when enabled, dimmed when disabled), like the jog buttons.
- **Pre-flight shows the soft-limit result.** Opening "Start run?" runs `run.job.check` ([run-v0.1.md](run-v0.1.md#commands-and-queries)): the same checks and export as `run.job.start` up to the soft-limit check, without streaming. The Soft limits row says "Checking…", then "Inside the travel at this work zero." or, per axis, "X leaves the travel: the program spans −812.000 to −12.000 mm, the travel is −800 to 0 mm." "Start run" is enabled only when the check passed; with findings the dialog focuses Cancel and says to move the work zero. The check runs again when the work zero changes while the dialog is open. A failed check (e.g. the program cannot be exported) shows its error in the row and keeps "Start run" disabled, since the start would fail the same way; `run.job.start` still runs every check itself.

### gCode panel (DF84)

Status: implemented (hardening DF84, user TG #286) · UI rules: [ui.md](../conventions/ui.md#run-mode-safety-ui) · Status: [run-v0.1.md](run-v0.1.md#status) · Sender: [run-v0.1.md](run-v0.1.md#sender)

The program as it streams, in a collapsible panel under the 3D view, following the line the machine executes. Read-only: nothing here changes what or how the sender streams.

- **The program streamed, not the exported file.** A resumed run streams its own program (the re-entry lines, then the operations from the chosen one; [run-machine.md § Section resume](run-machine.md#section-resume-m5)), so the panel shows what the run job handed the sender: main's `MachineClient` keeps the lines, the section starts (`SenderProgram.sections`, the progress labels) and the operations' first lines (`JobAbout.operations`) from `startJob` until the next run starts. A finished, stopped or failed run's program stays readable.
- **Renderer only** (decided in DF84): `window.dfyom.run.program(jobId)` (IPC `dfyom:run.program`, any DFYOM window) → `{ jobId, lines, sections, operations } | null` (null when that job's program is no longer kept). No command or agent tool: the tool list is near its budget (≈103 K of 120 K characters), the full program can be 100 k+ lines, and an agent has it already (`plan.export` writes the same program for a full run). The line indices below are in the status, for agents too.
- **Status (read-only additions):** `RunStatus.job.sent` (lines written to the controller so far) and `RunStatus.job.executing` (the 1-based line the machine is estimated to execute; absent until estimated). `job.line` stays the line being acknowledged (last acknowledged + 1). The host's status gains `job.sent` and `job.ackedAtReport` (lines acknowledged when the last status report arrived: the report's `Bf` and position belong to that count, while `line` may have moved on before the throttled status is posted); the sender only gains the getters `sent` and `acknowledged`, its streaming and timing are unchanged.
- **Executing line estimate** (`src/core/run/executing.ts`, computed in main on every host status of a run): GRBL answers `ok` once a line's motion is in its planner, so the line moving lags the acknowledged one by up to the planner's blocks (15 on an Uno build). GRBL reports the executing block's line (`Ln:`) only when built with `USE_LINE_NUMBERS` and sent `N` words, so DFYOM estimates it:
  1. **Planner blocks per line**, once at the start: each line through the emulator's gCode parser (`parseBlock`, the controller's `$12` arc tolerance, [grbl.md](../architecture/grbl.md)): a linear move is one block, an arc as many as GRBL's `mc_arc` splits it into, a zero-length move and a line without motion (spindle, dwell, a comment) none; each block keeps its end point (work coordinates).
  2. **With `Bf`** in the status report (`$10` with the buffer bit, e.g. `$10=3`): blocks in the planner = capacity − free blocks (capacity: the largest free count seen on this connection, 15 until one is seen). Counted back over the acknowledged lines' blocks, that many from the last, is the oldest block in the planner: the one executing. While GRBL splits an arc longer than the planner, the arc's line is not acknowledged yet and the newest planner blocks are its, so the oldest block may lie up to the next sent line's blocks later: within that window the block that best fits the reported work position is taken (the distance to its segment, plus 0.5 mm when the machine moved against the block's direction since the last report).
  3. **Without `Bf`** (GRBL's default `$10=1`, the virtual machine's too; DFYOM never changes `$10`): the window is the last capacity blocks of the acknowledged lines and the next sent line's blocks; the best-fitting block as above, the earliest on a tie.
  - **Sync floor** (both): GRBL runs a line without motion (spindle, dwell, a work offset, a program pause) only with an empty planner, so no block before the last such line up to the acknowledged one can still be executing; the window starts there.
  4. **Nothing in the planner** (`Bf` = capacity): the next line when one is sent and unanswered (GRBL is in it: a dwell, a spindle start waiting for the planner), else the last acknowledged one.
  5. **Never back** during one run: the estimate is at least the last one (a floor per job).
  - Limits: as fresh as the status (5 Hz); the program is traced in slices of 5,000 lines (≈0.5 s per 100 k lines in all) so main stays responsive, and the estimate waits for the trace to reach the lines in play; without `Bf`, on a segment retraced at the same point and direction the estimate may stay on the first until the tool leaves it. Against the emulator it is exact in more than 95 % of reports with `Bf`, more than 90 % without, and never more than a line off.
- **Before a run:** the panel says "The program shows here once a run starts." The setup's program is exported at the start (stale toolpaths regenerated, the live work zero); a preview before it would need its own command (tool budget) or an export per setup choice; left out (DF84 open).
- **Tests:** `src/core/run/executing.test.ts` (blocks per line, the `Bf` walk, arcs split past the planner, no `Bf`, the floor; against the emulator: the estimate equals the line the emulator's planner executes at nearly every report of a program with arcs, with and without `Bf`), `host/client` (the program kept, `sent` and `executing` in the status), `GcodePanel.test.tsx` (rows, the executing row, follow and pause on scroll, collapse, axe), `e2e/gcode-panel.e2e.ts` (a run on the virtual machine: the highlighted line advances and the list follows it; renders `df84-gcode-panel-{light,dark}.png`).

## Safety

Status: draft (hardening 1.1, 2026-11-23; awaits the user's answers to [Q49–Q52](../plans/hardening.md#questions-for-the-user)) · Real-machine lane: [run-machine.md](run-machine.md) · Virtual-machine rules: [run-v0.1.md § Safety (v0.1)](run-v0.1.md#safety-v01) · Protocol facts: [grbl.md](../architecture/grbl.md#transport-and-sender)

The rules every connection to a **real machine** (a controller on a serial port) follows, for every source and every window. The [virtual machine](run-v0.1.md#safety-v01) keeps its looser rules (no hardware moves). Each rule names where it is implemented: M1 (done on this branch) or the [hardening task](../plans/hardening.md#5-real-machine) that still implements it.

**Assumptions until Q49–Q52 are answered** (a different answer reopens this section):

- **A1 (Q49):** a GRBL 1.1–compatible controller (banner `Grbl 1.1…`, `$I` `1.1…`) on USB serial, with homing switches (`$22=1`), on a fixed-gantry machine that homes to the back right with Z up (`$23=0`); a spindle switched by hand or by `M3 S`. grblHAL extras and FluidNC are out.
- **A2:** the machine has a **hardware emergency stop** within the operator's reach that removes power from the spindle and the stepper drivers (at least the spindle) without software. DFYOM's Stop is not an emergency stop.
- **A3 (Q50):** machine-moving commands on a real connection come **from the UI only**; agents read, wait, hold and stop.
- **A4 (Q51):** the first cuts happen in two steps: DFYOM's exported program through the user's existing sender first, then through DFYOM's sender.
- **A5 (Q52):** the real-machine lane has the scope Q52 recommends ([run-machine.md § Scope](run-machine.md#scope)).

### 1. Emergency stop, stop and reset

| Control                                       | What it does                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            | Who may use it on a real connection |
| --------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------- |
| **Hardware e-stop** (A2)                      | Cuts power outside DFYOM; works when the app, the USB link or the controller hangs. The only stop the operator can rely on once DFYOM has lost the connection.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          | The operator                        |
| **Stop** (`job.abort`, toolbar, every dialog) | Controlled stop: feed hold `!`, wait for `Hold:0` (≤ 5 s), then soft reset `0x18`; the position survives, the spindle stops, GRBL's buffers are flushed ([run-v0.1.md](run-v0.1.md#stop-errors-and-alarms)). Without a job: jog cancel, or a reset while homing (DF35). A homing or Probe Z job's `job.abort` resets at once (as Stop without a run job; GRBL stops homing only by a reset).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            | Every source                        |
| **Feed hold** (`job.pause`, `Esc`)            | `!`: decelerates and holds; the **spindle keeps turning** (GRBL). Resume (`~`) is motion and follows the motion rules of § 2. The run job is paused only once the controller reports `Hold:0` (DF82; `Hold:1` is still decelerating, a door's `Door:0`/`Door:1` count as standing still; no `Hold:0` within 5 s machine time, or the run ending meanwhile: `job.pause` fails `run.state` and the job stays `running`); at a tool-change or `M0` wait nothing moves, so it is paused at once and continue is refused until `job.resume`; before the stream starts the job parks before streaming. A Probe Z job's `job.pause` (DF82) is the same feed hold, paused at `Hold:0`; `job.resume` sends `~` and the probe goes on; Stop still resets. A homing job cannot be held (GRBL ignores `!` while homing): `job.pause` fails `job.notPausable` ("Homing can't be paused; use Stop (it resets the controller)"). A hold DFYOM did not send (the machine's hold button, its safety door) pauses the job the same way and resumes the same way ([External holds](#external-holds-df82)). | Every source                        |
| **Jog cancel** (`run.machine.jogCancel`)      | `0x85`: ends every queued jog.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          | Every source                        |
| **Reset (immediate)** (`run.machine.reset`)   | `0x18` at once. During motion GRBL raises `ALARM:3` (position lost: home again).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        | Every source                        |

- **A job never claims paused while the machine moves** (DF82, [commands.md](../architecture/commands.md#pausing-a-job)): a refused or failed `job.pause` leaves the job `running`. The status bar's job list offers no Pause for a homing job; for a held Probe Z job it offers Resume. The machine toolbar's Resume resumes the held run job, or a Probe Z job this window started when it is held without a held run (a Probe Z without a project has no job list to resume it from); a Probe Z started elsewhere (an agent, another window) is resumed where it was started or stopped with Stop. While the hold decelerates (`Hold:1`) the badge says "Holding…" and Resume is disabled (a cycle start before `Hold:0` would be lost). A hold from the machine's button or safety door is resumed the same way; while the door is open Resume is disabled ([External holds](#external-holds-df82)). While held, the probe's reply timeout waits on (the sender restarts a command's timeout after a `Hold` report).
- **Stopping is never refused and never confirmed** ([ui.md](../conventions/ui.md#confirmations)): stop, hold, jog cancel and reset are allowed for every source on every connection, skip the command queue (`urgent`) and need no plan, no homing and no reservation.
- **Reset:** GRBL keeps G54 over a reset (EEPROM) and loses the position only when the reset interrupts motion (`ALARM:3`); after any position alarm DFYOM marks the machine **not homed**, which blocks runs until `$H` ([run-v0.1.md](run-v0.1.md#implementation-task-39)). A reset never restarts a program.
- **Critical alarms** (`ALARM:1` hard limit, `ALARM:2` soft limit): GRBL answers nothing until a reset; DFYOM refuses every other command until then and shows the alarm with the next step (reset, then home; wording: [run-machine.md § Machine readiness](run-machine.md#machine-readiness-m3), M3).

### 2. Who may command a real connection (Q50)

The permission policy ([commands.md](../architecture/commands.md#dispatcher-pipeline) step 5, `src/core/commands/permission.ts`) decides per command and source. **M1.**

| Command                                                                                                                                             | UI (a person at the app) | Agents, CLI, automation, system                                          |
| --------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------ | ------------------------------------------------------------------------ |
| Reading: `run.status.get`, `run.settings.check`, `run.ports.scan`, `job.get`, `job.list`, `job.wait`; plan and export commands                      | yes                      | yes                                                                      |
| Stop paths: `job.pause`, `job.abort`, `run.machine.jogCancel`, `run.machine.reset`                                                                  | yes                      | yes                                                                      |
| `run.connection.open { target: 'serial' }`; `run.connection.close` of a real connection                                                             | yes                      | **no** (`permission.denied`)                                             |
| Motion and machine state: `run.machine.home`, `.unlock`, `.jog`, `run.workZero.set`, `run.job.start`, `run.job.continue`, `job.resume` of a run job | yes                      | **no** (`permission.denied`)                                             |
| Probing and overrides: `run.machine.probeZ` (M4), `run.override.set` – `reset` included (M6)                                                        | yes                      | **no** (`permission.denied`)                                             |
| Anything on the virtual machine                                                                                                                     | yes                      | yes (unchanged, [grbl.md](../architecture/grbl.md#transport-and-sender)) |

- Deny by default: a command the table does not name, a connection still opening, an unknown target or a process without a machine port counts as real.
- `job.resume` is not a machine command, but resuming a held run is motion: before resuming a job whose command is a machine command, the dispatcher asks the policy with that command (`run.job.start`).
- The refusal says why: `permission.denied`, `data: { command, source, target }`, message "agent sources may not run run.machine.jog on a real machine; the user runs it from the app". The exit criterion's agent variant ends at `plan.export`; the user runs it from the app.
- **Later** (not in hardening): agent-started real runs, each confirmed in the app by the user, with a watchdog that holds the run when the agent stops polling.

### 4. Before a real run streams

Checked by `run.job.start` (main) and again by the host at `jobStart` ([run-v0.1.md § Run job](run-v0.1.md#run-job)); any failure refuses the start before a byte is sent.

1. The plan is `finalized` or `inUse` ([run-machine.md amendment of decision 5](run-machine.md#amendments-to-run-v01md)). **M1.**
2. The controller's `$$` matches the connection's machine copy in every mapped setting and has homing enabled ([run-machine.md § Settings check](run-machine.md#settings-check)); else `run.state`, rule `settingsMismatch`. **M1.**
3. Idle, homed in this connection (not after an unexpected controller reset: M2), the work zero re-read (`$#`) and unchanged since the check, the soft-limit check passed (existing; covered on the serial path in M2).
4. The connection is reserved for the job from its checks to its stream (existing).

### 6. Lost connection, disconnect and reconnect

A lost USB link **cannot be made safe by DFYOM**: GRBL keeps executing what is in its buffers (up to 15 planned motion blocks and 128 bytes of lines: seconds of cutting, more for long moves) with the spindle on, then stops with the spindle still on (no `M5` arrives).

- DFYOM fails the job with `machine.connection`, closes the connection (no automatic reconnect: the controller's state is unknown) and says so: "Connection to the machine lost. It may still be moving and the spindle may still be on: use the emergency stop." (the real-target failure dialog and the navigator: [run-machine.md § Lost connection](run-machine.md#lost-connection-m2), M2).
- **Reconnect = reset:** opening the port resets most Arduino-based GRBL boards (DTR); otherwise the handshake sends `0x18` when no banner comes. Either way buffered motion ends and GRBL starts locked (`$22=1`): the new connection is **not homed** and must home before a run.
- **Disconnect = reset:** closing a real connection on purpose (`run.connection.close`, app quit) sends `0x18` before closing the port, also when Idle, so no queued jog or line runs on after DFYOM let go. A running job is stopped first (hold, then reset), as on the virtual machine. **M1.**
- App quit during a run asks first, then stops the run (existing, [run-v0.1.md](run-v0.1.md#implementation-task-312-run-mode-ui)).

### 7. What DFYOM never does on a real machine

- Write GRBL settings (`$x=`), send raw gCode or `$` lines (no MDI console, Q52), restart a program at an arbitrary line, or reconnect on its own.
- Stream a program it did not export, in the same job, from a finalized plan at the live work zero.
- Change a plan's machine copy to match the controller silently ([library.md](../architecture/library.md#grbl--import)).

### Testing the rules

Without hardware: the sender and the host over a loopback serial stream against the GRBL emulator in its GRBL-exact silent-homing mode ([run-machine.md § Testing](run-machine.md#testing)); the permission table per source (`permission.test.ts`); fault injection (lost port, silent controller, hard limit mid-run, probe fail) with M8 ([run-machine.md § Fault injection](run-machine.md#fault-injection-m8)). With hardware: the manual checklist of [testing.md](../conventions/testing.md) (hardening 1.3) before X1.
