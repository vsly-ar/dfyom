v0.4 builds the **feature model** of [features.md](features.md) and its first two kinds: the **hole** feature (simple, counterbore, countersink, sizes from fastener tables) and the **Clones** feature (one face, no rotation). Countersinks need a cut DFYOM does not have yet, so v0.4 adds the **chamfer operation** on circular edges and the **chamfer mill** tool type first ([features.md rule](features.md#feature-vs-operation): a feature never cuts on its own). This doc owns what v0.4 adds or bounds; the feature model itself (owned operations, ids by role, order, Apply, undo, persistence) stays in [features.md](features.md) and is linked, not repeated.

## Hole feature

Status: implemented: `simple` and `counterbore` (F3, [§ Implementation (F3)](#implementation-f3)), `countersink` (F4, [§ Implementation (F4)](#implementation-f4)).

A hole feature is one round hole with an optional counterbore or countersink at its mouth, placed by `[u, v]` and an anchor on a [face target](design-v0.2.md#face-targets-generalised-on), like a drilling.

### Parameters

| Parameter         | Kind   | Default                                       | Rule                                                                                                                                                                                                                                      |
| ----------------- | ------ | --------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `type`            | –      | `simple`                                      | `simple`, `counterbore`, `countersink`, `recessedCountersink` (hardening H1: reuses `cb*` / `cs*`, [hole-slots-and-round-corners.md](hole-slots-and-round-corners.md#recessed-countersink-type))                                          |
| `fastener`        | –      | none                                          | Optional table key (`M3`); sets the defaults below when chosen, never afterwards on its own                                                                                                                                               |
| `purpose`         | –      | `clearance`                                   | `clearance` or `tapDrill`; `tapDrill` only with `type: simple`                                                                                                                                                                            |
| `fit`             | –      | `normal`                                      | `close`, `normal`, `loose` (ISO 273); `clearance` only                                                                                                                                                                                    |
| `diameter`        | length | from the table, else 6 mm / 1/4″              | > 0                                                                                                                                                                                                                                       |
| `bottom`, `depth` | –      | `through`                                     | As [drilling](design.md#drilling): `through`, `flat`, `drillPoint`; `depth` from the face                                                                                                                                                 |
| `cbDiameter`      | length | table head Ø + clearance (counterbore)        | `counterbore` only; > `diameter`                                                                                                                                                                                                          |
| `cbDepth`         | length | head height + `headSink`                      | `counterbore` only; 0 < `cbDepth` < `depth` (through: < the stock extent along −n)                                                                                                                                                        |
| `csDiameter`      | length | table head Ø + 2 × `headSink`                 | `countersink` only; > `diameter`                                                                                                                                                                                                          |
| `csAngle`         | angle  | head angle from the table (90° ISO), else 90° | `countersink` only; 60°–120°                                                                                                                                                                                                              |
| `csMethod`        | –      | `chamfer`                                     | `countersink` only: `chamfer` (a chamfer mill) or `stepped` (terraces cut by the hole's own end mill, [§ Stepped countersink](#stepped-countersink-f7-d41))                                                                               |
| `csStepdown`      | length | 1 mm / 1/32″                                  | `stepped` only; ≥ 0.1 mm; the terrace height at most                                                                                                                                                                                      |
| `headSink`        | length | 0.2 mm / 0.008″                               | ≥ 0; how far the head sits below the face; only used when the defaults are filled (a new `headSink` alone moves `cbDepth` / `csDiameter` while they still equal the table's value)                                                        |
| `slotLength`      | length | 0                                             | ≥ 0; a slotted (long) hole's travel between its end centres, 0 = round (hardening H2, [hole-slots-and-round-corners.md](hole-slots-and-round-corners.md#slotted-holes-df119)); not with `drillPoint`, `tapDrill` or a stepped countersink |
| `rotation`        | angle  | 0°                                            | The slot's direction, CCW from +u; only with `slotLength` > 0 (H2)                                                                                                                                                                        |
| `center`, anchor  | –      | required                                      | `[u, v]` in the face frame, [anchor](design-v0.2.md#placement-anchors) `center`                                                                                                                                                           |

Choosing a `fastener`, `purpose` or `fit` refills `diameter`, `cbDiameter`, `cbDepth`, `csDiameter` and `csAngle` in the same command (one undo step); editing a size by hand clears `fastener` to "custom" only for that size's read-out ("M3 · counterbore Ø 7 (custom)"). Every size is a quantity and may be an expression, as operation parameters are.

### Expansion

The [expansion](features.md#expansion-and-owned-operations) per type (role → operation, in design order):

| `type`                | Owned operations                                                                                                                                                                                                                                    |
| --------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `simple`              | `drill`: drilling (`diameter`, `bottom`, `depth`) on the feature's face                                                                                                                                                                             |
| `counterbore`         | `counterbore`: circular pocket (`cbDiameter`, depth `cbDepth`) on the face; `drill`: drilling `on` `<id>_counterbore.floor`, depth `depth − cbDepth` (or `through`)                                                                                 |
| `countersink`         | `drill`: drilling on the face; `countersink`: [chamfer operation](#chamfer-operation-v04-circular-edges) on the mouth of `<id>_drill` with `width = (csDiameter − diameter) / 2` (D45), `angle = csAngle` (`stepped`: also `stepdown = csStepdown`) |
| `recessedCountersink` | `counterbore` (the recess) as above; `drill` on its floor as above; `countersink` as above but `on` `<id>_counterbore.floor`, chamfer mill only ([H1](hole-slots-and-round-corners.md#implementation-h1))                                           |

With `slotLength` > 0 every type expands as above with the bores as Round rectangle **pockets** (`drill`: (`slotLength` + `diameter`) × `diameter`, through or a flat floor; `counterbore`: (`slotLength` + `cbDiameter`) × `cbDiameter`) and the countersink as an [edge chamfer](edge-chamfers.md) on the `drill` pocket's outline ([H2](hole-slots-and-round-corners.md#implementation-h2)).

Ids follow [A3](features.md#expansion-and-owned-operations) (`hole1_drill`, `hole1_counterbore`, `hole1_countersink`). Changing `type` keeps the `drill` role and its tool lock; a disappearing role removes its operation (or fails with `design.referenced`).

#### Tolerances of derived sizes (hardening B5)

Owned operations whose size is derived from several hole fields get their tolerance from what the machine actually controls, not from interval arithmetic over every field ([quantities.md § Tolerance](../architecture/quantities.md#tolerance) is for formulas the user writes). Programs cut nominal sizes, so these tolerances only change surface limits (`….z.min/max`) and what the inspectors show; the goldens are unchanged.

- **Countersink width.** The chamfer mill sets the outer diameter at the face by its depth, from the nominal edge; the drill's own diameter tolerance does not move that circle. So `width` takes **`csDiameter`'s explicit tolerance halved** (`Ø12 ±0.1` → width `±0.05`; notation kept); `diameter`'s tolerance is not combined. An untoleranced `csDiameter` leaves the width untoleranced (the general tolerance applies; it is not in the expansion context).
- **Drill below a blind counterbore: absolute bottom.** Decision: the hole's `depth` (and its tolerance) is the bottom's distance from the hole's face, as drawn on a print; the counterbore floor's tolerance must not stack onto it, because both are cut to nominal levels from the same zero. The drill is placed on `<id>_counterbore.floor`, so its segment `depth − cbDepth` gets the deviations that make the floor's interval plus the segment's equal the hole depth's: upper `depth.upper − cbDepth.upper`, lower `depth.lower − cbDepth.lower` (an untoleranced `cbDepth` counts as 0/0). When `cbDepth`'s band is wider than `depth`'s (the two would cross), the segment gets a zero band at their midpoint and the bottom's surface limits follow the counterbore's band: the narrowest the floor reference allows. An untoleranced hole `depth` leaves the segment untoleranced, as before. Alternative not taken: tightening by interval arithmetic of `depth − cbDepth` (it widens the band by `cbDepth`'s, the stack-up the decision avoids).

### Counterbore tool

Status: implemented (X1 follow-up "plan order v2").

- **One end mill for a counterbored hole.** The `counterbore` role's [auto choice](design-v0.2.md#auto-choice) takes the `drill` role's tool whenever that tool fits the counterbore (before keeping its own; change reason `followsHole`), and runs whenever the drill role's does; `design.operation.tool.set` on the drill role writes the same tool to an unlocked counterbore it fits (one undo step), as the [stepped countersink](#stepped-countersink-f7-d41) does. A drill bit never fits a pocket, so a hole made with a drill keeps a counterbore end mill of its own; a tool set on the counterbore itself locks it and is kept.
- **Why.** A counterbore is a small bore (about twice the hole's Ø, a few mm deep): boring it with the hole's end mill costs a few more helix turns, seconds per hole, while each tool change on a manual GRBL machine is a stop, a tool swap and a Z re-zero. The rule is local to the feature, so a choice never depends on unrelated operations or on the order of Applies. A general "prefer a tool already used in the part" rule was not taken: it would put large pockets on the smallest end mill (cycle time grows roughly with area / DC) and make choices history-dependent. The remaining tool changes are the machining order's job ([plan-v0.4.md § Machining order v2](plan-v0.4.md#machining-order-v2)).
- **Code and tests.** `tool-commands.ts` (`leaderOf`, `leadersFirst`, `toolFollowers`, shared with F7's stepped chamfer); `counterbore-tool.test.ts`.

### Fastener table

Status: implemented (F2). A built-in, read-only table in core ([`src/core/design/fastener/data.ts`](../../src/core/design/fastener/data.ts), every row citing its sources as [feeds-speeds.md](../architecture/feeds-speeds.md) requires; values ported from cnc-code's hole helper and re-checked, D30 Q7, relicensed by the author). Plain numbers in mm. Columns per size:

| Column                       | Source                                                                      |
| ---------------------------- | --------------------------------------------------------------------------- |
| Clearance close/normal/loose | ISO 273:1979 fine / medium / coarse series                                  |
| Tap drill (coarse thread)    | ISO 2306:1972 (6H; = DIN 336) / ISO 261:1998 pitch (e.g. M3 × 0.5 → 2.5 mm) |
| Socket head Ø and height     | ISO 4762:2004 dk max, k max (= d)                                           |
| Counterbore Ø                | DIN 974-1:2008 series 1 for ISO 4762                                        |
| Countersunk head Ø and angle | ISO 10642:2004 dk theoretical max, 90° (M3 up); ISO 7046-1:2011 below M3    |

The values live in `data.ts` only (not repeated here). The ISO and DIN texts are paywalled: values are those of the standards' dimension tables as reproduced in catalogues and handbooks, cross-checked against the cnc-code port; DIN 974-1 was checked against secondary charts only, and each of its values exceeds the ISO 4762 dk max (by 0.5 mm at M1.6 and M2, at least 1 mm from M2.5). A test lint requires a source for every column, sizes growing with the screw size in every column, and holes that fit their screw (tap drill ≈ d − P, d < close < normal < loose, counterbore > head Ø). The hole defaults use the table so: `cbDiameter` = the counterbore Ø, `cbDepth` = k + `headSink`, `csDiameter` = countersunk dk + 2 × `headSink`, `csAngle` = 90°.

v0.4 sizes: ISO metric M1.6, M2, M2.5, M3, M4, M5, M6, M8, M10, M12 ([Q29](../plans/v0.4.md#questions-for-the-user), M1.6 added by D34; ISO 10642 starts at M3, so the countersunk head values below M3 come from ISO 7046-1, with that source on the row); inch (#4–1/2″, ASME B18.3, 82°) after v0.4. The table version is not stored ([features.md § Persistence](features.md#persistence-high-level)). Query (app scope, no project needed): `design.fastener.list { standard?, size? }` returns `{ rows, sources }` (each row with its source keys, `sources` the cited standards); `size` is the folded `get` and an unknown size is `input.malformed` (rule `unknownSize`). Agents choose sizes the same way the inspector does.

### Stepped countersink (F7, D41)

Status: implemented ([§ Implementation (F7)](#implementation-f7)). User request (D41): an option, never the default, to cut a countersink with **the same end mill that makes the hole**: a rough countersink for when swapping to a chamfer mill is not worth it and the screw head hides the cone anyway.

- **Shape.** With the cone depth h = (`csDiameter` − `diameter`) / 2 / tan(`csAngle` / 2), the cone is cut as N = ⌈h / `csStepdown`⌉ **terraces** of equal height t = h / N. Terrace k (1…N) is a cylinder from depth (k − 1)·t to k·t of radius r<sub>k</sub> = `csDiameter` / 2 − (k − 1)·t·tan(`csAngle` / 2): its **top edge**, the stock corner the terrace above leaves, lies on the cone. The cut therefore contains the whole cone, so the seated head rests on the N step corners (and the hole's mouth) and **never stands proud**; the cut goes past the cone by at most one terrace (t along the axis, t·tan(α / 2) across), hidden under the head. The last floor is at h, where the cone meets the hole. (Terraces whose floor corners lay on the cone would leave stock inside it and lift the head by up to t.)
- **Tool.** A flat end mill smaller than the hole (DC < `diameter`, the upper bound of [helical boring](design.md#drilling)), reaching h below the face. Any end mill that bores the hole fits.
- **One tool, no tool change.** The hole is then bored by that end mill too. The drill role's auto choice takes only tools that also fit the stepped countersink (never a drill); the countersink role's auto choice is the drill role's tool whenever it fits (before keeping its own); `design.operation.tool.set` on the drill role writes the same tool to an unlocked stepped countersink in the same command (one undo step). Setting a tool on the countersink itself (locked), or locking a drill on the drill role, is an explicit choice: the countersink then picks its own end mill and the plan changes tools, as for a chamfer-mill countersink.
- **Model: a chamfer cut differently, not a new operation.** The owned `countersink` operation stays a [chamfer](#chamfer-operation-v04-circular-edges) with an optional `stepdown` (present = stepped). The design intent (the cone for the head), the edge, order, Clones pairing and `dfm.chamferTooDeep` are the chamfer's unchanged; only the tool type and the toolpath differ. The method is a design field, not a plan strategy, because tools are chosen in Design (a plan `entry` cannot turn a chamfer mill into an end mill); Plan resolves the chamfer's `entry` to `stepped` ([plan-v0.4.md § Stepped chamfer](plan-v0.4.md#stepped-chamfer-f7)). A new operation kind would repeat validation, geometry, Clones, order and plan wiring for one toolpath.
- **Note.** Info `dfm.countersinkStepped` on `<id>_countersink` (`parameter` `csMethod`): params `{ stepdown, terraces, feature }` (stepdown = t, mm): the cone is stepped and cut past by up to t, hidden under the head.
- **Rules.** `csStepdown` ≥ 0.1 mm (`range`, `min`); `csMethod` / `csStepdown` with another type is `notForType`; `csStepdown` with `csMethod: chamfer` is `notForMethod`. `csStepdown` alone switches to `stepped`.

## Chamfer operation (v0.4: circular edges)

A chamfer operation cuts a conical bevel at the **mouth** of an earlier round operation. In v0.4 it is used by countersink holes and may be added on its own to any drilling, circular pocket or `inside` profile of a circle (an edge break on a dowel hole or a through opening; [X2](#implementation-x2)).

**Sized by width (D45, user, 2026-11-22).** A chamfer's size is its **width**: the horizontal leg of the bevel at the face, from the edge to the chamfer's rim, the way drawings give it ("1.5 × 45°" is 1.5 mm wide at 90° included). The edge already has a diameter, so a chamfer diameter is not a useful input; it is shown as a derived value. The **depth** is the alternative input (some drawings dimension it): entering it stores the width it gives through the angle. The width is what is stored, so a chamfer keeps its width when the edge's diameter changes (a machinist's expectation) and when its angle changes (the depth follows).

| Parameter  | Kind   | Default              | Rule                                                                                                                           |
| ---------- | ------ | -------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `edgeOf`   | –      | required             | Id of an earlier drilling, or pocket or `inside` profile with a `circle` shape; the edge is its mouth on that operation's `on` |
| `width`    | length | 0.5 mm (inch: 1/64″) | > 0 (rule `positive`); the bevel's width at the face. Diameter at the face = edge Ø + 2 × `width` (derived, shown read-only)   |
| `angle`    | angle  | 90°                  | Included angle, 60°–120°                                                                                                       |
| `stepdown` | length | none                 | Present = stepped (F7): terraces by a flat end mill, ≥ 0.1 mm; set only by the hole's `csStepdown` in v0.4                     |

- **Depth** (not stored): `width / tan(angle / 2)`. A command or the inspector may give `depth` instead of `width` (never both: rule `notWithWidth`); the stored width is `depth × tan(angle / 2)` with the angle of the same command, kept to 1 µm (exact at 90°).
- **Removal region:** the cone frustum from the face plane (the chamfer's diameter, edge Ø + 2 × `width`) down to where it meets the edge's diameter, axis along −n, at the depth above. Surfaces: `chamfer1.cone` (display only, not a face target and not an expression name: it is not planar).
- **Order:** after its `edgeOf` operation (a reference, [design order](design.md#ordering-and-composition)).
- **Fit** (adds a row to [the fit table](design-v0.2.md#fit-when-a-tool-can-make-the-operation)): `chamferMill` with `angle` equal within 0.5°, `tipDiameter` < the edge's diameter, and either `diameter` ≥ the chamfer's diameter at the face (plunged at the centre) or a cutting edge long enough for the chamfer's slant height (contoured on **one ring**, [plan-v0.4.md](plan-v0.4.md#chamfer-toolpath)). A stepped chamfer ([F7](#stepped-countersink-f7-d41)) instead needs a `flatEndMill` with DC < the edge's diameter (rules `type`, `diameter`) reaching the chamfer depth. A chamfer whose slant is longer than every tool's cutting edge needs a larger tool (rule `slant`); several rings would be stepped clearing of the wedge, not a chamfer pass ([Implementation (C2)](#implementation-c2)).
- **DFM:** `dfm.chamferTooDeep` (cone below the edge operation's bottom or through a thin floor), `dfm.chamferNoTool` (no library tool fits the chamfer; as `dfm.holeNoTool`).
- **Commands:** `design.chamfer.add { partId, edgeOf, width?, depth?, angle?, name? }`, `design.chamfer.update { partId, operationId, edgeOf?, width?, depth?, angle?, name? }` (no `tool` or `generalTolerance` args, [Implementation (C2)](#implementation-c2)); a new `edgeOf` keeps the width. General loops (`edgeOf` a pocket or profile of any other shape, outside edges) are later ([H-E](#decisions)); drafted after spike S7 in [edge-chamfers.md](edge-chamfers.md) (draft).

## Clones in v0.4

[features.md § Clones](features.md#clones) owns the concept, properties, checks and commands. v0.4 builds it with these bounds:

- **First version (user, D30):** one face (sources on one face or on each other's surfaces), every instance keeps the source's orientation, stable numbering after skips.
- **Sources allowed:** hole features, pockets, drillings, chamfers, and profiles with side `inside` or `on`. Facing and `outside` profiles are refused (`clonesSourceKind`): repeating the part outline is "part copies", which the user ruled out (D30 Q3).
- **C3, C4, C6 as recommended** ([Q31](../plans/v0.4.md#questions-for-the-user)): clone instances follow the source operation's tool; removing Clones keeps the source; Clones are created from existing operations or a feature only ("Make Clones…" on a selection).
- **Rows:** `grid`, `offset`, `polar`, `arc`, `point` as drafted, plus the **`along`** row (positions at a spacing or a count along a named shape's path, [features.md § Properties](features.md#properties); [§ Implementation (F6)](#implementation-f6)).
- **Positions of instances** are values: the evaluated source position plus the row offset, rewritten on every regeneration; expressions stay on the source only.
- **Plan:** nothing Clones-specific ([features.md § Plan and cut order](features.md#plan-and-cut-order)).
- **Groups and Clones of Clones** came with hardening DF40: [features.md § Clones v2](features.md#clones-v2-groups-df40).

New tools (each one MCP tool, [llm-api.md](../architecture/llm-api.md)): `design.hole.add`, `design.hole.update`, `design.chamfer.add`, `design.chamfer.update`, `design.clones.add`, `design.clones.update`, `design.clones.preview`, `design.feature.remove`, `design.feature.move`, `design.feature.list`, `design.fastener.list`; `design.feature.get` is folded into `list` (filter by id) to save room. `library.tool.add`/`update` and the tool unions grow by the `chamferMill` fields. Rough size: 11–14 K characters of `tools/list`; the budget is **120 K** ([Q32](../plans/v0.4.md#questions-for-the-user) option A, task M1; measurements in [llm-api.md](../architecture/llm-api.md#implementation-task-310)).

Results carry `{ featureId, operationIds, warnings }` as [features.md § Commands](features.md#commands-sketch) says; `design.operation.update` / `.remove` / `.move` on an owned operation fail with `design.featureOwned` naming the feature (A4, A5).

## Persistence

As [features.md § Persistence](features.md#persistence-high-level): optional `part.features`, optional `featureId`/`featureRole` on operations, a `chamfer` operation kind and a `chamferMill` tool type added to the unions. All additive: existing projects load unchanged, **no `schemaVersion` change** (pre-alpha rule).

D45 changed the chamfer record in place: it stores `width` instead of `diameter`. The old field is **not** read (converting it needs the edge's diameter from another record of the part: not a trivial schema change), so a project saved with a chamfer (a standalone one or a countersink's) before D45 no longer loads and is reset after the user confirms, as the [pre-alpha exception](../conventions/error-handling/migrations.md#pre-alpha-exception-no-data-preservation-yet) allows; no migration, no `schemaVersion` change.

**One ring (the open fit question, settled):** a chamfer is cut in one ring, and only by a tool whose cutting edge covers the slant (equivalently D − d ≤ DC − dt). A V-bit's flank meets a matching chamfer cone along a line, so one ring at full depth sweeps the whole wedge. With a shorter edge, rings from the inside out drag the shank through uncut stock, and rings from the outside in leave V ridges between them; both need radial stepping too, which is clearing a triangular wedge, a different strategy kept for later. A chamfer too large for every tool gets `dfm.toolUnfit` / `dfm.chamferNoTool` (rule `slant`) and needs a larger chamfer mill.

## Tabs relocate off free sides (TB1)

Decided D40 (2026-11-22): the lid's board is 255 × 200, so along X the outline nearly fills it and the slot runs off the stock on the left and right sides, while the front and back keep stock beyond the slot. A tab on a free side holds nothing. Amends [design-v0.3.md § Tabs on shapes](design-v0.3.md#tabs-on-shapes) and the v0.1 count rule ([design.md](design.md), first tab at the middle of the front wall), for every through profile of a closed loop (v0.1 rectangles and circles too).

- **Holds.** A point at distance `s` along the loop holds when both ends of the slot's cross-section there lie inside the stock face rectangle (the local stock of the operation's face; within 10⁻⁶ mm): there is stock beyond the cut. This is the threshold of `dfm.slotLeavesStock` / `dfm.slotOpensStock` (stock margin ≥ slot width), so the rules agree; no extra web is asked for. That stock must also belong to the strip along a **held side**: a stock side is **free** when the slot runs off it (the loop's exact bounds plus the slot's outward reach pass the face edge), and the ray from the slot's outer end along the loop's outward normal must leave the rectangle through a side that is not free (`inside` cuts hold on their slug and skip this). So a loose remnant at a corner between two free sides holds nothing, and with every side free nothing holds. The slot's cross-section is `[0, slotWidth]` outwards for `outside`, inwards for `inside`, `± slotWidth / 2` for `on`. A tab **holds** when every point of its span (centre ± `tabs.width` / 2, sampled every 0.25 mm and at both ends) holds. Only the stock rectangle counts: other cuts in the frame are not considered (no workholding model).
- **`tabs.count` (automatic spacing).** The count rule places the tabs first (unchanged: evenly from half a spacing after the start point; v0.1 contours from the middle of the front wall). Tabs that hold stay where they are. Each tab that does not, in index order, moves to the nearest position on the loop where it holds and does not overlap a tab already placed (centres at least `tabs.width` apart, as `tabsOverlap`); candidates lie every 0.25 mm along the loop; of two equally near ones the one further along the loop wins. So even spacing is kept wherever the stock allows, and the result is deterministic. Moved tabs keep their count; tab ids stay "tab order from the start point" ([§ Surfaces](design-v0.3.md#surfaces)).
- **Not enough room.** A tab that finds no such position stays at its count-rule position (holding nothing), so the number of tabs and their surface ids never change with the stock; `dfm.tabsNoHold` says how many hold and suggests that count. When no point of the loop holds at all, nothing moves (the outside slot's `dfm.slotLeavesStock` already names that case; `dfm.tabsNoHold` covers the others).
- **`tabs.positions` (free-form).** Never moved. Each entered tab that does not hold is listed by `dfm.tabsNoHold`.
- **One resolution.** Geometry evaluation (tab bands, tab surfaces), the toolpath generators (the tool lifts over the same bands; a v0.1 profile whose tabs moved starts in the middle of the largest gap between tabs), the DFM checks and the viewport's tab markers all use the same resolved centres (`resolveProfileTabs` in `core/geometry/tab-hold.ts`). Dragging a marker of a count-rule profile writes the resolved positions as `tabs.positions`, as before.

| Code                | When                                                                                                                                                                                                                                    | Severity |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------- |
| `dfm.tabsRelocated` | `tabs.count`: some tabs moved off sides where the slot leaves no stock beyond the cut; `params`: `moved`, `count`, `positions` (resolved centres, mm along the loop)                                                                    | info     |
| `dfm.tabsNoHold`    | Tabs that hold nothing: `tabs.count` with fewer holding positions than tabs (`params.held`, `count`; suggestion: at most `held`), or entered `tabs.positions` over a free side (`params.indices`); not when `dfm.slotLeavesStock` fires | warning  |

Why (best practice): Fusion 360 and VCarve space automatic tabs by count or distance and leave relocation to the user (dragging tabs); neither checks the stock. DFYOM knows the stock rectangle, so it can do that step for the automatic case, the way a machinist would: keep the even spacing, slide only the tabs that would hold nothing to the nearest side that still has stock, and never touch tabs the user placed by hand – those get a warning instead.

## Implementation (X2)

The v0.4 golden path through the UI (`e2e/golden-path-v0.4.e2e.ts`, [testing.md § End-to-end](../conventions/testing.md#end-to-end)) exports X1's golden program byte for byte. What it added or fixed:

- **Chamfer on a through opening.** The exit criteria had no standalone chamfer step (X1 covered only countersinks), and the lid's only round opening that is not a hole is the Ø 22 cutout, an `inside` profile (a pocket must end above the stock bottom). An inside profile of a circle leaves a circular mouth exactly like a circle pocket, so `chamferEdge` takes it ([§ Chamfer operation](#chamfer-operation-v04-circular-edges)); still circular edges only, as Q28 bounds v0.4. One helper, `circularEdgeDiameter` (`operation.ts`), replaces the four copies of the rule (commands, validation, plan grouping, geometry input); the renderer's `chamfer-view.ts` mirrors it on DTOs. `dfm.chamferTooDeep` reads an inside profile as through (`geometry/dfm.ts`), and the plan's freeing rule does not count a chamfer on a profile's own edge as freed by it ([plan-v0.4.md § Machining order v2](plan-v0.4.md#machining-order-v2)). X1 and X2 both add the chamfer (1.5 mm × 45°: `width` 1.5 at 90°, Ø 25 at the face; since D45 entered as the width, the same stored geometry and program; the default 0.5 mm is 0.5 mm deep, where the 12 mm mill's effective diameter is too small for its plywood feed, `feeds.chipLoadHigh`). The golden program changed for that addition only: the cutout is cut with Flat 6 before the chamfer mill's run (its chamfer follows it), so Flat 6 runs twice: 3 tool changes instead of 2.
- **Head defaults on thin stock.** A custom 6 mm through hole on the 6 mm board turned Counterbore with a 6 mm deep counterbore, which the core refuses (`aboveStockBottom`); the refusal sat at a field the inspector did not show yet, so the click did nothing. `headDefaults` now keeps a through hole's head within half the material below its face (`stockBelow`), and an error at a field the hole inspector does not show is placed at the choice that caused it (`HoleInspector.tsx`).

Open items (not built in v0.4): edge chamfers along general loops and outside edges (S7, next milestone); `dwell` for plunged chamfers. Feature recalculation and the Clones follow hook no longer cost a surface table and a full part parse per command (hardening P5, [shapes.md § Design commands (P5)](../architecture/shapes.md#design-commands-p5)).
