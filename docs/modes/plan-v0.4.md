## Chamfer toolpath

Input: the chamfer's axis point (the edge centre in the face frame), the edge diameter d, the chamfer diameter D (edge Ø + 2 × width, D45), the included angle α, the face Z; the tool's DC, tip diameter dt and angle. A V-bit's cutting cone of half-angle α/2 touches the chamfer cone along its whole slant only when the angles match (the fit rule, [design-v0.4.md § Chamfer operation](design-v0.4.md#chamfer-operation-v04-circular-edges)).

- **Plunge** (DC ≥ D and dt ≤ d): rapid to the centre at the clearance height, feed down at `plungeRate` to the Z where the tool's cone has diameter D at the face (tip Z = face − (D − dt) / 2 / tan(α / 2)), short dwell optional (strategy `dwell`, default 0), rapid out. The hole below lets the tip pass through the edge diameter without cutting.
- **Contour** (DC < D): the tool axis runs one circle of radius r so the cutting cone meets the chamfer from d to D. With slant height s = (D − d) / 2 / sin(α / 2) and usable cutting length l of the tool's cone, the fit rule guarantees s ≤ l, so one ring at full depth cuts it (several rings would be stepped clearing, later). Entry: a ramp along the first circle from the hole side (inside the edge diameter, which is already cut), climb direction, arcs as `G2`/`G3` ([plan-v0.3.md T-B](plan-v0.3.md#decisions)); exit: lift on a tangent arc into the hole.
- **Order checks:** a chamfer must cut after its `edgeOf` operation in the same setup ([order checks](plan-v0.1.md#plan-operations-and-order)); `plan.order` blocks the reverse.
- **Strategy parameters:** `entry` (`plunge`, `contour`, `auto` = P-C), `dwell`, `rampAngle` (contour); nothing else. A finishing pass is not offered (one ring cuts to size). As built ([Implementation (T1)](#implementation-t1)): `auto` is the default (no stored value), `dwell` is later.

### Stepped chamfer (F7)

A chamfer with a `stepdown` (the stepped countersink, [design-v0.4.md § Stepped countersink](design-v0.4.md#stepped-countersink-f7-d41), D41) is cut by a **flat end mill** as terraces; Plan resolves its `entry` to `stepped` (a stored `plunge` or `contour` is `strategy.entry` `stepped`), and `rampAngle` applies.

- **Terraces:** N = ⌈h / stepdown⌉ of height t = h / N (h the chamfer depth), terrace k a circle of radius r<sub>k</sub> = D / 2 − (k − 1)·t·tan(α / 2) at depth k·t, top to bottom, so every top step corner lies on the cone.
- **Rings per terrace** (tool radius R): the outermost has its axis at r<sub>k</sub> − R; inner rings (spacing ≤ DC / 2, equal) until the innermost, at most d / 2 + 0.4·DC, reaches into the hole. Usually one ring: an end mill that bores the hole has DC > d / 2.
- **Moves:** rapid to the first terrace's innermost ring start (−90°) at clearance and retract, feed down to the face at `plungeRate` (inside the hole); per terrace a **ramp along the innermost ring** from the level above to k·t (whole turns, at most `rampAngle`, never descending faster than `plungeRate`; a straight plunge below r = 0.1 mm), one full ring at k·t, then each outer ring after a radial feed outward; then a radial feed back in to the next terrace's innermost ring (cleared). After the last terrace, feed to the centre (the hole) and rapid out. Climb (counter-clockwise inside the hole), one pass of kind `rough`.
- **Checks:** tool type `flatEndMill`, DC < d (`plan.check` `diameter`), reach to h; the generator re-checks type, size and the terrace count (≤ 1000).
- **Feeds:** the end mill's helical-boring engagement `helix { ap }` with ap = t (the hole's helix uses the same tool), drilling's field list.
- **One tool:** the drilling and the chamfer get the same design tool ([design-v0.4.md § Stepped countersink](design-v0.4.md#stepped-countersink-f7-d41)), and no other tool comes between them: the default order puts a chamfer that shares its edge operation's tool **right after that operation** (ahead of the pockets of other tools), and rebuild moves a new or re-resolved one up behind it ([Order](#implementation-t1)); a Clones of stepped countersunk holes plans every bore, then every terrace set, as one tool block (D34). Only a user's own reorder of kept operations can still put a tool between them.

## Machining order v2

Status: implemented (X1 follow-up "plan order v2"). Amends the default order and the loose-piece check of [plan-v0.1.md § Plan operations and order](plan-v0.1.md#plan-operations-and-order); the dependency rules (`onBefore`, [`edgeBefore`](#implementation-t1)) are unchanged. X1 showed the v0.1 order (group by kind, then tool within a group) changing tools 5 times for the lid's 3 tools, and cutting the outline before the openings inside it. Standard CAM practice: cut tool by tool, and the cut that frees the part last.

| Rule                | Behaviour                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Freeing cut         | A **through profile** (side `inside` or `outside`, or `on` without a depth) frees the piece inside its shape. In the default order it comes after every plan operation of its face direction that lies inside it: another operation by its centre (a facing always), another profile by its centre when that profile's bounding box is smaller (two profiles never wait for each other). "Inside" is the loose-piece test (circle by radius, else bounding box; general shapes by their placed box, with the 2D port only). A chamfer on the profile's own edge (an inside circle profile, X2) is not inside it: it bevels the rim round the opening, and `edgeBefore` puts it after the profile anyway. A freeing dependency that would close a cycle with the hard ones is dropped.                                                                                                                                                                         |
| Release cut last    | Hardening DF57 (the agent's two-setup enclosure test cut the outline before the back rim rebate, so the rebate was cut on a part held only by tabs; the rebate's centre lay outside the outline's box, so the freeing rule above missed it). A **release profile** is a through profile that no other through profile of its face direction frees (by the rule above): the outermost one, which separates the part from the stock (the outline, not a cutout inside it). In the default order it frees **every** other plan operation of its face direction, wherever it lies, except the other release profiles (two outlines never wait for each other) and a chamfer on its own edge; so it comes last in its setup. Tabs or not: a release without tabs frees the part all the same. Inner cutouts keep the inside rule, so they still come before the outline but may share runs with other operations.                                                  |
| Fewest tool changes | The order is a sequence of **tool runs**. A run takes every operation of its tool as soon as it is ready (an extra operation joining the current run never makes the later runs longer), so only the tool of each next run is chosen: `defaultOrder` searches those choices for the fewest runs (depth first, memoised on the set of done operations; past 5000 runs explored it takes the first candidate). Candidates are tried in the order of their first ready operation (kind group: facing, drilling, pockets, chamfers, profiles; then design order), and the first minimal order found is kept, so the result is deterministic. An operation without a tool is a run of its own.                                                                                                                                                                                                                                                                     |
| Setup boundary      | Hardening DF65 (the user's real two-setup cut changed tools at the re-fixture although the bottom setup could start with the tool still in the spindle). `deriveSetups` orders the setups first, then each setup after the first with the **last tool of the setup before it** as the preferred first tool (`defaultOrder`'s `startTool`): when an order with the fewest runs can start with that tool, that one is taken, so the tool stays in the spindle across the re-fixture and the setup has one tool change fewer. It is a tie-break only: it never adds a run to the setup and never overrides a rule (dependencies, freeing cuts, the release cut last); when no minimal order starts with that tool, the order is unchanged. Only the first run is affected: the setup's last tool is not chosen to suit the next setup (the release cut usually fixes it anyway). Applies to the default order (`plan.create`); a rebuild keeps the user's order. |
| Within a run        | Kind group, then design order among the ready operations (drillings before pockets of the same tool, a drilling on a counterbore floor right after its counterbores, profiles last); a chamfer sharing its edge operation's tool (F7) right behind that operation. Clones stay tool by tool (D34): every instance shares its source operation's tool, so they join one run. A plan operation's passes already go roughing before finishing; there is no separate finishing operation to order.                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| Rebuild placement   | New plan operations are placed by group first (as before, so `repairOrder` sees them); once their tools are assigned, each moves to the position in its valid range that adds the fewest tool changes (`placeByTool`; ties: nearest its group position). The range: after its dependencies (a freeing profile also after the operations inside it), before the operations depending on it and before a freeing profile enclosing it, unless the user's order already cut that profile earlier. Kept operations keep the user's order; `keepWithEdge` (F7) runs after it.                                                                                                                                                                                                                                                                                                                                                                                      |
| Check               | `plan.loosePiece` (warning, rule `profileFirst`) looks at through profiles only (a blind groove frees nothing) and now also at a later profile inside one (the smaller-box rule above): a user order that cuts the outline before the cutout and vents inside it warns once per later plan operation. It stays a warning: tabs hold the part, and a user may order so on purpose. Since DF57 it also warns, rule `releaseFirst`, for every later plan operation of the direction after a release profile ("Outline releases the part before Back rim rebate: the part is held only by its tabs").                                                                                                                                                                                                                                                                                                                                                             |
| Tool choice         | Not a Plan rule: the counterbore of a hole takes the hole's end mill when it fits ([design-v0.4.md § Counterbore tool](design-v0.4.md#counterbore-tool)), so a counterbored hole needs no second end mill. Tools are otherwise unchanged (largest that fits, [design-v0.2.md § Auto choice](design-v0.2.md#auto-choice)); the order absorbs the rest.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |

Code: `src/core/plan/order.ts` (`defaultOrder` with `startTool`, `freeingDependencies`, `releaseProfiles`, `placeByTool`, `orderFindings`), `setups.ts` and `build.ts` pass the 2D port. The lid of X1 had 2 tool changes for 3 tools: Flat 3 (countersink holes, counterbores, holes below them, vents) → chamfer mill (countersinks) → Flat 6 (cutout, outline). With X2's chamfer on the cutout's edge (it follows the cutout) the fewest runs are Flat 3 → Flat 6 (cutout) → chamfer mill (countersinks, the cutout's chamfer) → Flat 6 (outline): **3 tool changes for 3 tools**, the only order with 4 runs. Tests: `order.test.ts` (fewest runs against the old grouping, the freeing profile, nested profiles, a chamfer on a cutout's edge, determinism, rebuild placement, the check; the release cut after a rebate outside the outline's box, DF57; the preferred first tool, DF65), `setups.test.ts` (a second setup starting with the first setup's last tool, DF65).

## Tool changes per setup (hardening DF66)

Status: implemented. The user asked to see a setup's tool changes in the Plan inspector and to reorder them by dragging (real cut, TG #242). A setup's machining order is a sequence of **tool runs** (consecutive plan operations with the same tool copy; [Machining order v2](#machining-order-v2)); each run starts with a tool change.

| Runs         | `toolRuns(operations)` (`src/core/plan/tool-runs.ts`): the setup's operations split where the tool copy changes; an operation without a tool is a run of its own. Each run: tool (snapshot id or none), its plan operations in order, the index of its first operation.                                                                                                                                                                                                                                                                                                                                                                                                                  |
| Tool changes | A setup's tool changes count every run, **the one at the setup start included** (the operator loads the first tool after re-fixturing), less one when the first run's tool is the last tool of the setup before it in machining order (`carriedTool`: it stays in the spindle across the re-fixture, DF65). | Reorder      | A run moves as a block: `plan.operation.move { count }` moves `count` consecutive plan operations starting at `planOperationId` (the run) to `toIndex` (the block's first position after the move), in one command and one undo step.
