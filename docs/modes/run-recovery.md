# Run: recovering from a lost connection, a crash or a power loss

Status: implemented (RC1–RC6, 2026-11-27; accepted 2026-11-27; hardening [DF129](../plans/hardening.md#intake-user-feedback-goes-here), the user's TG #413: "prepare for it: start/resume from a line, remember last confirmed (executed) gcode line number in memory (to suggest continuing from it), auto attempts to reconnect, also keeping current spindle coordinates in memory … suggest next actions to the user … think thru the UX of this "catastrophe" so it doesn't feel like one"; [Q158–Q160, Q167–Q173](#questions-for-the-user) take their recommendations, accepted by delegation D79; this reverses run.md § 7's "no restart at an arbitrary line" and "no reconnecting on its own" at the user's request) · Amends: [run.md § Safety](run.md#safety) § 6 and § 7 ([below](#safety-amendments)), [run-machine.md § Section resume](run-machine.md#section-resume-m5) (extended to any safe line) and [§ Lost connection](run-machine.md#lost-connection-m2), [run.md DF93](run.md#run-an-external-g-code-file-df93) (files may resume) · Uses: [run-goto.md](run-goto.md) (DF128) · GRBL facts: [grbl.md](../architecture/grbl.md) · Terms: [glossary.md](../glossary.md)

A run that ends without DFYOM wanting it to (the USB link drops, the controller restarts, DFYOM or the computer crashes, the power goes) should end in a calm checklist, not a red wall: what happened, where the machine was, what to check, and one button for the next step, until the job runs on from a safe place. DFYOM has not seen a disconnect yet; this doc prepares for it.

## Principles

1. **Nothing moves by itself.** DFYOM never homes, unlocks, jogs or resumes on its own. Reconnecting is allowed because it resets the controller, which _stops_ it ([§ Auto-reconnect](#auto-reconnect)).
2. **Say what is known, and how well.** Every number in the recovery panel says where it comes from: "last seen 0.2 s before the link dropped", "the controller confirmed up to line 4,812", "estimated". Never present an estimate as a fact.
3. **Err early.** When unsure where the cut stopped, resume earlier: re-cutting air costs seconds, skipping material ruins the part.
4. **One next step at a time,** in plain words, with the reason; the alternatives a click away.
5. **Leave and come back.** The record of the interrupted job survives closing the panel, reconnecting, quitting and a crash, until the user starts another run or dismisses it.

## What can go wrong, and how DFYOM notices

| Event                                                                                                  | What DFYOM sees                                                                                              | What the machine does                                                                                                                                                                                                                                  |
| ------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **USB link drops** (cable, connector, electrical noise from the spindle, a hub, the computer sleeping) | The port closes (`close` event) or stops answering (status watchdog, 2 s) ([run.md § 5](run.md#5-watchdogs)) | A controller powered by the machine keeps executing what it already received (planner and RX buffer: seconds of cutting), then stops **with the spindle still on**. A controller powered only by USB loses power: the steppers stop at once, mid-move. |
| **Controller restarts by itself** (power dip, noise)                                                   | A banner DFYOM did not cause ([grbl.md § Banner](../architecture/grbl.md#banner)); the link stays            | Reset: motion and spindle stop, the position is lost (`ALARM:3` or the start-up lock).                                                                                                                                                                 |
| **DFYOM's machine process exits** (a bug)                                                              | Host exit ([run.md § 5](run.md#5-watchdogs))                                                                 | As a dropped link: the OS closes the port; the controller runs out its buffer.                                                                                                                                                                         |
| **DFYOM or the computer crashes, or the computer loses power**                                         | Nothing at the time; at the next launch the [run journal](#what-dfyom-keeps) says a run never ended          | As a dropped link.                                                                                                                                                                                                                                     |
| **The machine loses power** (mains, the e-stop) and the controller with it                             | As a dropped link (USB-powered board: see the next row)                                                      | Everything stops; position lost.                                                                                                                                                                                                                       |
| **The machine loses power, the controller stays on USB power**                                         | Nothing: GRBL does not know the steppers are unpowered and reports progress as if it moved                   | Stops. DFYOM learns it only from the operator: Stop, then "The machine lost power" in the panel ([Q171](#questions-for-the-user)).                                                                                                                     |
| **Stop, alarm or error mid-run** (existing)                                                            | The run ends `stopped` or `failed` ([run-machine.md § Section resume](run-machine.md#section-resume-m5))     | Stopped; position kept after Stop, lost after a hard limit.                                                                                                                                                                                            |
| **An alarm or a reset after the run ended** (a limit switch hit while cleaning, DF134)                 | The alarm, then the reset's banner; no run job, so nothing is recorded: the record stays as the run ended    | Locked until `$H` or `$X`; G54 kept ([run-machine.md § After a hard limit](run-machine.md#after-a-hard-limit-df134))                                                                                                                                   |

**Prevention, built in with this work:** DFYOM keeps the computer awake while a run streams on a real connection (Electron `powerSaveBlocker` `prevent-app-suspension`; system sleep suspends USB and is a classic cause of mid-job disconnects), and the panel's "Why does this happen?" lists the usual causes (USB cable next to the spindle or VFD wires, no ferrite, an unpowered hub, a shared ground) without blaming.

## What DFYOM can know about where the job stopped

GRBL answers `ok` when a line is **in its planner**, not when it has run. Between "sent", "acknowledged" and "executing" there are up to 15 planned motion blocks and the 128-byte serial buffer ([grbl.md § Protocol subset](../architecture/grbl.md#protocol-subset)).

| Number                                     | Meaning                                                                                                                  | Trust                                                                                                                                                                                                                                            |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Sent** (`job.sent`)                      | Lines written to the port.                                                                                               | Exact. The **upper bound**: a powered controller can still parse and run every line it received, also the ones whose `ok` never came back.                                                                                                       |
| **Acknowledged** (`ok`s, `job.line − 1`)   | Lines GRBL took into its planner.                                                                                        | Exact, but not "executed": the confirmed line runs up to 15 blocks (an arc is many blocks) after its `ok`.                                                                                                                                       |
| **Executing (estimate)** (`job.executing`) | The line the machine was moving in at the last status report.                                                            | An estimate, exact in > 90 % of reports and never more than a line off on the emulator ([run.md DF84](run.md#gcode-panel-df84)); at most 0.2 s old (5 Hz). The **lower bound**: every line before it had finished.                               |
| **Reported executing** (`Ln:`)             | GRBL's own line number in the status.                                                                                    | Only on a controller built with `USE_LINE_NUMBERS` (`$I` option `N`) and with `N` words in the program. DFYOM sends no `N` words, so default GRBL never reports it; numbering lines when `$I` shows `N` is a later option, not part of this doc. |
| **Last position**                          | `MPos` (and `WCO`, so `WPos`), `FS` feed and rpm, `Ov` overrides, state, from the last status report.                    | Exact at its time (≤ 0.2 s before the loss). After that the machine may have moved on, up to the end of the last sent line.                                                                                                                      |
| **Modal state at any line**                | Units, distance mode, plane, feed mode, work offset, motion mode, feed, spindle (M3/M4/M5, S), coolant (M7/M8/M9), tool. | Exact, **derived from the program**: DFYOM parses the program from line 1 with the virtual machine's parser (`parseBlock`), the same subset the controller runs. The controller's own modal state is gone after the reset anyway.                |
| **Work offset G54**                        | Stored by GRBL in EEPROM.                                                                                                | Survives resets and power cycles. DFYOM keeps the value read at the start (`$#`) and compares it with the one read after reconnecting.                                                                                                           |

So "where it stopped" is a **range**: from the executing line at the last report (certainly reached) to the last sent line (possibly reached, when the controller kept power). The panel shows the range ("It was cutting around lines 4,797–4,812; the controller may have continued up to line 4,830") and suggests a resume point **before** it ([§ Choosing where to resume](#choosing-where-to-resume)).

**After reconnecting**, GRBL has reset: the machine position is unknown and, with homing enabled (DFYOM's real-machine rule, [run-machine.md § Settings check](run-machine.md#settings-check)), the controller is locked until homed ([run.md DF46](run.md#run-mode-presentation-df46) "Needs homing"). Homing restores machine coordinates; G54 from EEPROM then puts the work zero back where it was, **if** nothing moved the stock and no steps were lost. The panel asks the user to confirm that physically ([§ The recovery panel](#the-recovery-panel)).

## What DFYOM keeps

**In memory** (main, `MachineClient`), extending `RunStatus.lastRun` ([run-machine.md M5](run-machine.md#section-resume-m5)): an `interruption` record from the moment a run ends unintentionally. DF135 C2 adds `finished` (the plan operations the run finished: all for `done`, else those before the operation it stopped in, plus those a resumed run had finished) and `real` (a serial connection), from which Run marks operations already cut ([cut-state.md § Implementation (C2)](cut-state.md#implementation-c2)).

**On disk**, the **run journal** `<appData>/run-journal.json` ([persistence.md § Files and folders](../architecture/persistence.md#files-and-folders); one per app instance, since there is one machine connection per instance), so a crash or power loss of the computer loses at most a second ([Q159](#questions-for-the-user)):

| Field                    | Content                                                                                                                                                                                                                                                                                              |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `state`                  | `running` while a run streams; `interrupted` (with `reason`: `connectionLost`, `controllerReset`, `hostExit`, `machinePowerLost`, `appCrashed`), `stopped`, `failed` or `done` once it ends. A `running` journal at launch means the app or computer died.                                           |
| `job`                    | Kind (`plan` or `file`); for a plan: the project file path, project id, `planId`, `setupId`, `planHash` (as M5) and the operations in order; for a file: its path, size and SHA-256. Always: the **program's SHA-256** and line count, the section starts and the tool changes (line, number, name). |
| `machine`                | Target (`serial`), port path, the USB serial number and VID:PID when the OS reports them, the library machine id, the travel and homing corner from `$$`.                                                                                                                                            |
| `workZero`               | G54 read at the start (`$#`) and its last known value (a tool change re-zeroes Z).                                                                                                                                                                                                                   |
| `progress`               | `sent`, `acknowledged`, `executing` (estimate) and the time of each.                                                                                                                                                                                                                                 |
| `lastReport`             | Time, state, `MPos`, `WCO`, feed and rpm (`FS`), overrides, `Bf` when reported.                                                                                                                                                                                                                      |
| `position`               | The current tool (number, name) and operation (id, label) at the executing line, and the modal state there (for display when the program can no longer be read).                                                                                                                                     |
| `startedAt`, `updatedAt` | Times.                                                                                                                                                                                                                                                                                               |

- **Writes:** at the start, at every section start, tool change, pause, the end, and at most once a second in between (throttled from the 5 Hz status), each as write-to-temp, `fsync`, rename, so a crash leaves the previous complete journal. Main writes it (`src/main/persistence/run-journal.ts`); the host is not involved. Cost: a few hundred bytes per second.
- **Lifetime:** kept after the run ends; replaced by the next run's start; removed by "Dismiss" in the panel. A `done` journal is never offered for recovery.
- **The virtual machine** keeps the in-memory record (for practising, [§ Testing](#testing)) but writes no journal: no hardware to recover.
- **Unreadable journal** (truncated, from another version): discarded and logged at warn; pre-alpha, no migration ([migrations.md](../conventions/error-handling/migrations.md#pre-alpha-exception-no-data-preservation-yet)).

## Auto-reconnect

After a **lost real connection during a run** (port closed, status watchdog, host exit), DFYOM tries to connect again by itself ([Q158](#questions-for-the-user)):

- **Which port:** the same path, or the port with the same USB serial number (and VID:PID) when the OS gave it a new path (`/dev/cu.usbmodem1101` → `…1201` after a re-enumeration). Never another device.
- **When:** at once, then after 1, 2, 4 and 8 s, then every 10 s, for 2 minutes in all; a port that appears in the OS's list (scanned each second while waiting) is tried at once. Then the panel shows "Try again" and stops trying.
- **What a reconnect sends:** only what any connect sends: the handshake (opening the port resets most boards through DTR; otherwise `0x18`), `$$`, `$#`, `$G`, `$I` and status polls. **Never** `$H`, `$X`, a jog or a line of the program. The result is a connected, locked, not-homed machine waiting for the user.
- **Why this is safe, and even safer than waiting:** the reset that comes with every connect **stops** a controller that kept running its buffer and switches its spindle output off (a GRBL reset clears the spindle and coolant pins). The rule "no automatic reconnect" in [run.md § 6](run.md#6-lost-connection-disconnect-and-reconnect) is amended for this case only ([below](#safety-amendments)).
- **Not automatic:** at app launch from a journal (the panel offers "Connect to /dev/cu.usbmodem1101"; the user may have moved the machine, or be away), after a user's own disconnect, or when the controller restarted with the link intact (it is already connected). A setting "Reconnect automatically after a lost connection" (default on) turns it off.
- **The panel shows it** ("Reconnecting… attempt 3, next in 4 s", "Reconnect now", "Stop trying") in a polite live region; the assertive announcement is only the loss itself.

## The recovery panel

Where: the Run inspector's run section shows it in place of "Start run" whenever `lastRun.interruption` (or a journal at launch) exists, and the failure dialog of such a run is replaced by a short sheet ("The run was interrupted") that points to it, so the panel and the jog pad, Home and Probe Z are usable together. Every window shows it (the record belongs to the machine connection, [run.md DF80](run.md#run-without-a-project-df80)); windows without the project show it read-only with "Open project" ([§ Edge cases](#edge-cases)).

**Tone:** neutral surface, an info icon, no red except the one safety line while the machine may still be moving. Title: **"The run was interrupted"**, subtitle **"DFYOM kept where the job was. Follow the steps to continue."** A stepper with one open step, the finished ones ticked and collapsible, the next ones greyed with their titles visible (the user sees the way ahead).

### Step 1 · Make it safe (only while the machine may still be moving)

Shown when the link dropped during motion and the controller has not been reset yet (not reconnected): **"The machine may still be moving, and the spindle may still be on. If it is, press the emergency stop."** (the existing safety line, [run-machine.md M2](run-machine.md#lost-connection-m2)), with the reconnect status under it. Ticked by itself once DFYOM has reconnected (the reset stopped the controller: "Reconnected. The controller restarted, so it stopped moving and switched the spindle output off. A spindle switched by hand is still on: switch it off.") or by "The machine is stopped".

### Step 2 · What happened

Facts, each with its source:

- "**The USB connection dropped** at 14:32:07, 23 minutes into the run." (or "The controller restarted by itself", "DFYOM's machine connection stopped", "DFYOM was closed unexpectedly while a run was streaming (last saved 14:32:06)")
- "It was in **Pocket 2** (operation 3 of 7, tool 2: 6 mm flat end mill), about 62 % into the program."
- "Last seen at **X 120.400 Y 45.000 Z −3.200** (work) · X −291.900 Y −188.000 Z −91.300 (machine), feed 1800 mm/min, spindle 18,000 rpm, 0.2 s before the connection dropped."
- "The controller confirmed lines up to **4,812**; it was cutting around lines **4,797–4,812** and may have continued up to line 4,830." The gCode panel marks the range ([run.md DF84](run.md#gcode-panel-df84)), and the 3D view shows the tool's last seen position as a ghost marker with the remaining toolpath from the range on.

### Step 3 · Check the machine

A checklist the user ticks (not enforced, but the next step says when something was left unticked):

- "The bit is intact and tight in the collet." (if not: the resume waits at the tool anyway, and Z zero is set again there)
- "The stock has not moved (clamps, screws, tape)." Unticked → the work zero step asks to set X/Y again.
- "Chips are cleared and nothing is in the way."
- "Nobody moved the gantry by hand." (moving it does not matter before homing; listed so the user does not worry)

### Step 4 · Connect and home

"Connect" (when not connected), then **"Home the machine"** (the usual confirmation, [run.md § 3](run.md#3-confirmations-before-motion)), with the reason: "The controller restarted, so it no longer knows where the spindle is. Homing finds it again." A hard-limit or other alarm shows the alarm panel's steps first ([run-machine.md M3](run-machine.md#machine-readiness-m3)).

### Step 5 · Check the work zero

- "The controller kept the work zero: **X −412.300 Y −233.000 Z −88.100** (G54), the same as during the run." (or, in warning tone, "The work zero differs from the run's: X −410.000 now, −412.300 during the run. Set it back?" with "Restore the run's work zero", which writes the journal's G54 with `run.workZero.set`; confirmed.)
- **"Go to the last position, above the stock"**: a [Go to](run-goto.md) prefilled with the last seen X/Y at the safe height: the bit should hang right above the cut it was making. **"Go to the work zero"** the same for the zero corner. Both open the Go to dialog (preview, Enter), never move directly.
- If the bit was changed or slipped: Z is set again at the tool wait of the resume (Probe Z or "Set Z zero here"), so this step does not ask for it.
- If the stock moved (step 3 unticked): "Jog to the stock's zero corner and set X and Y zero" with the zero buttons; resuming after a moved stock is at the user's risk, and the step says so.

### Step 6 · Choose how to continue

Options as cards, the recommended one first and marked, each with what it costs:

| Option                                         | Text                                                                                                                             | Starts                                                                                |
| ---------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| **Resume near where it stopped** (recommended) | "From the start of pass 3 of Pocket 2 (line 4,705), just before the interrupted lines. Re-cuts about 40 s of air."               | The resume pre-flight at that [resume point](#choosing-where-to-resume)               |
| **Resume from the operation's start**          | "From the start of Pocket 2 (line 4,120). Re-cuts about 4 min of air: the safest choice if you are unsure the stock stayed put." | The pre-flight at the operation (as M5)                                               |
| **Choose a line…**                             | "Pick another resume point in the gCode panel."                                                                                  | The pre-flight's "Start at" set to "Line" ([§ Start from a line](#start-from-a-line)) |
| **Start the setup again**                      | "From the beginning; everything already cut is re-cut in air."                                                                   | The normal pre-flight                                                                 |
| **End here**                                   | "Keep the record and decide later." / "Dismiss" removes it.                                                                      | –                                                                                     |

The pre-flight then shows the generated lead-in (below) in the gCode panel and in the 3D view, the usual checks (soft limits over lead-in and remainder, the settings check, homed), and its primary button "Resume on the machine".

## Start from a line

The general feature behind resume, also usable without an interruption (testing a program's second half, skipping an operation already cut by another program). It lifts the "restart at an arbitrary line" exclusion of [run.md § 7](run.md#7-what-dfyom-never-does-on-a-real-machine) and Q52 for lines DFYOM can enter safely ([Q168](#questions-for-the-user)), and DF93's "no section resume for files" ([Q170](#questions-for-the-user)).

- **Where:** the pre-flight's **"Start at"** control: "Beginning" · "Operation…" (M5's select; for files, the tool changes and the program's own operation comments, e.g. Fusion's `(Pocket2)`) · "Line…" (a number field with the nearest resume points before and after it). In the gCode panel, a row's context menu "Start from here…" opens the pre-flight with that line (snapped to the nearest resume point at or before it, the snap shown).
- **Command:** `run.job.start` and `run.job.check` take `fromLine` (1-based line of the program as shown in the gCode panel) next to `from` (operation; one of the two). `run.job.check` returns the lead-in lines and the resume-point finding, so agents see the same preview; on a real connection the start stays UI only (Q50). Schema growth ≈ 0.1 K of `tools/list`.
- **Which program:** a plan's program re-exported at start must hash equal to the program the line refers to (the journal's program hash, or the panel's current program); otherwise line resume is refused ("The plan changed since the run: resume from an operation instead.") and M5's operation resume, which re-exports, is offered. A file must hash equal to the journal's ("The file changed since the run."). An edited plan therefore resumes per operation only, exactly as DF85 does today.

## Choosing where to resume

**Resume points** are lines where the tool can enter safely: computed once per program by `resumePoints(program)` (headless, with the modal-state parse).

| Kind                    | Rule                                                                                                                                                                                                                                                                                                                                       |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Operation start**     | A plan program's section/operation starts (M5); a file's tool-change markers and whole-line operation comments before a retract.                                                                                                                                                                                                           |
| **Pass start**          | The first feed move after a retract: a rapid (`G0`) that reaches the program's own rapid height (for plans the operation's retract or clearance height; for files the height the program rapids at between cuts), then X/Y rapids, then a plunge or ramp. Each level of a pocket, each depth pass and each tab-less profile lap starts so. |
| **Any line** (advanced) | Any line after the first motion, behind "Choose a line…" with findings (below) ([Q169](#questions-for-the-user)).                                                                                                                                                                                                                          |

**Findings for a chosen line** (warning tone in the pre-flight, the start allowed after reading them):

- **In material:** the line starts below the stock top (plans: from the in-process stock; files: below work Z 0 when the program faces from Z 0, else "below the program's rapid height"). The lead-in plunges there at the plunge feed: "The bit plunges straight into the cut at Z −3.2. Fine for an end mill that cuts at its centre; a V-bit or a drill-style plunge may not be."
- **Inside a ramp or helix:** the line belongs to a run of feed moves that change Z (a ramp, a helical entry): "This line is part of a helical entry; resuming here plunges straight down. Resume at its start (line 4,690) instead." with that button.
- **Inside an arc chain:** none needed: an arc is one line and the lead-in moves to its exact start point (I/J are relative to it, R arcs too), so resuming at an arc line is as safe as at a straight one. A resume never starts _within_ a line.
- **Across a tool change:** the line is after tool change n: the lead-in waits at that tool. A line before the last tool change of the run: "You resume with tool 1: change back to it and set its Z zero at the wait."
- **Incremental distance (`G91`) at the line:** allowed (the lead-in puts the tool exactly at the line's start point), with "This part of the program moves incrementally." for files.

**The suggestion** after an interruption: the **latest pass start at or before the lower bound** (the executing estimate at the last report, else the acknowledged line minus the planner's 15 blocks counted in planner blocks, as M5), never inside a ramp; if the operation has no pass starts (a single-pass profile), its operation start ([Q160](#questions-for-the-user)). After a Stop the same rule applies to `lastRun` (M5 keeps operation granularity unless the user picks "Resume near where it stopped").

## The lead-in

The resumed program = **lead-in + the program's lines from the resume line on, unchanged** (except that the first line gets its modal motion word when it relies on one: `X10 Y5` under modal `G2` becomes `G2 X10 Y5`, since GRBL cannot set `G2`/`G3` without axis words). For an operation start of a plan, M5's post-exported re-entry stays as it is; the lead-in below generalises it to any resume point, for plans and files, from the parsed modal state at the line:

1. `G90 G94 G17 G21|G20`, `G54` (units, distance, feed mode, plane, offset as at the line; a file's `G20` stays `G20`).
2. `M5`, then `G53 G0 Z<top>`: spindle off and straight up to the machine top (MPos Z −pull-off), whatever the work zero.
3. **Tool wait:** the tool-change marker and `M0` of the tool in effect at the line ("Tool 2: 6 mm flat end mill"), so the run waits in the tool-change dialog: check or change the bit, Probe Z or set Z zero, jog, Continue ([Q167](#questions-for-the-user)). DF69's touch-off spot applies when the tool run has one ([z-reference.md](z-reference.md#implementation-notes-df69)).
4. After the wait: units, distance, plane, feed mode, offset stated again (the post's post-`M0` restatement), `G53 G0 Z<top>`.
5. Coolant as at the line (`M7`/`M8`, when the program used it), then the spindle as at the line, `M3|M4 S<rpm>`, and the spin-up dwell `G4 P<s>` (the plan's spindle spin-up; files: 5 s, [Q172](#questions-for-the-user)). A hand-switched spindle (the machine has no PWM spindle): a program pause "Start the spindle at 18,000 rpm" instead.
6. `G0 X<x> Y<y>`: above the line's start point (the parsed position before the line) at the top.
7. `G0 Z<approach>`: down to the **approach height** above the start point: the program's own rapid height there (the operation's retract height for plans; for files the last `G0` Z of the program before the line), never below the start Z + 1 mm.
8. `G1 Z<start z> F<plunge>`: plunge at feed to the line's start Z (the plan operation's plunge feed; files: the last Z-only feed before the line, else half the feed in effect), skipped when the start Z is the approach height.
9. `F<feed>` in effect at the line (with `G1` when the line's motion is linear), then the program's lines.

The lead-in is shown as its own section in the gCode panel ("Lead-in", muted), drawn in the 3D view (rapids dashed), counted in progress, and checked against the travel with the rest (the top, the start point, the approach). Overrides restart at 100 % (a reset cleared them); the pre-flight says so when the run had them changed.

**Checked on the emulator** (the M5 standard): for resume points of the test part's program and of the DF93 sample files, the resumed program streamed through the virtual machine moves exactly as the full program from the resume line on (the end position of every motion line, work coordinates, within the text resolution), with the same modal state at the resume line.

## Edge cases

- **Interrupted at a tool-change or pause wait:** nothing of the program was in the controller; the suggestion is that tool change itself ("Resume at tool change 2").
- **Interrupted during the lead-in of a resume:** the record points at the original resume line again; the resume suggests the same point.
- **Interrupted during homing or a Probe Z job:** no run; no recovery panel, the usual lost-connection line ([run-machine.md M2](run-machine.md#lost-connection-m2)); no auto-reconnect (RC4 reconnects after a lost **run** only, [§ Implementation (RC4)](#implementation-rc4)).
- **A plan run, the project not open** (after a crash, the app starts without it): the panel says "The run was from 'Lid', plan 1, setup 1", with "Open project" (the journal's path; recovery of unsaved changes first, [persistence.md § Crash recovery](../architecture/persistence.md#crash-recovery)). Resuming needs the project; the facts, connect, home and Go to work without it.
- **The file moved or changed:** "The file is no longer at its path / changed since the run" with "Locate file…"; a file with another hash cannot resume by line.
- **Another machine or port:** a reconnect to a controller whose `$$` differs from the journal's machine is refused by the settings check as always; the panel says the run was on another machine.
- **A different tool in the collet than the one at the line:** the tool wait handles it.
- **Several interruptions:** the record keeps the latest; the gCode panel's range follows it.
- **The user starts a new run instead:** the journal is replaced; the panel is gone. Starting a run while a record exists asks once: "Discard the interrupted run's record?"

## Failure modes of the recovery itself

| Failure                                                                                                   | Handling                                                                                                                                                                                                                                                                                                                                                                                        |
| --------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| The estimate is late (the machine was further than estimated)                                             | Harmless: the suggestion is before the lower bound; the extra air cut is the cost.                                                                                                                                                                                                                                                                                                              |
| The estimate is early by more than the margin (should not happen)                                         | Still before the true position, since the suggestion is at or before the estimate; only a resume _after_ the upper bound could skip material, and DFYOM never suggests one.                                                                                                                                                                                                                     |
| Steps lost before the interruption (a crash into the stock)                                               | Undetectable by DFYOM; homing re-references the machine, but cuts made with lost steps are off. Step 3 asks to look at the cut; "Go to the last position" shows whether the bit lines up.                                                                                                                                                                                                       |
| The stock moved                                                                                           | Step 3 and 5: re-zero X/Y; the panel says resuming may leave a visible step.                                                                                                                                                                                                                                                                                                                    |
| The journal is a second old after a computer crash                                                        | The range is wider by what ran in that second; the suggestion uses the journal's lower bound, still earlier than the truth.                                                                                                                                                                                                                                                                     |
| The journal could not be written (disk full, permissions)                                                 | Logged at warn once per run, the run continues (a journal never blocks cutting); the in-memory record still works while the app lives.                                                                                                                                                                                                                                                          |
| Auto-reconnect finds the port but the controller does not answer                                          | Counted as a failed attempt; after the 2 minutes, "Try again" and the hint to power-cycle the controller.                                                                                                                                                                                                                                                                                       |
| Auto-reconnect connects to a controller in an alarm (e.g. hard limit tripped while it ran out its buffer) | The alarm panel's steps come first; the recovery steps wait.                                                                                                                                                                                                                                                                                                                                    |
| The machine lost power while the controller stayed on USB                                                 | DFYOM cannot tell (GRBL reports motion that did not happen). The operator presses Stop; the panel's "The machine lost power" marks the position lost (not homed) and opens recovery; DFYOM cannot know when the power went (the progress after it is fiction), so it suggests the operation start and the user may pick a line by where the cut visibly ends ([Q171](#questions-for-the-user)). |

## Safety amendments

When accepted, these change [run.md § Safety](run.md#safety):

- **§ 6:** "no automatic reconnect" becomes: after a lost real connection during a run, DFYOM reconnects automatically to the same device ([§ Auto-reconnect](#auto-reconnect)); a reconnect only resets and reads the controller and never moves it, homes or unlocks it. "Reconnect = reset" and "the new connection is not homed" stay.
- **§ 7:** "restart a program at an arbitrary line" becomes "start a program at a line without the generated lead-in": starting at a line is allowed from the app, with the lead-in, the soft-limit check over lead-in and remainder, and the pre-flight ([§ Start from a line](#start-from-a-line)). "Reconnect on its own" is removed (§ 6).
- **§ 2:** `fromLine` on `run.job.start` is a start: UI only on a real connection. Dismissing the record is a renderer action (no command, no agent tool); agents read the record in `run.status.get` (`lastRun.interruption`).
- **§ 5:** unchanged watchdogs; each now also writes the journal's `interrupted` reason.

## Agent API

No new tool. ## Questions for the user

Numbering continues after [run-goto.md](run-goto.md#questions-for-the-user)'s Q157; Q161–Q166 belong to [clones-mirror.md](clones-mirror.md#questions-for-the-user), so this doc jumps from Q160 to Q167. "Q158 ok" takes the recommendation; "all ok" takes every one.

1. **Q158 – Auto-reconnect.** (1) **Automatic after a lost connection during a run: same device (path or USB serial number), backoff for 2 minutes, reads only, never moves; not at launch; a setting turns it off.** (2) A "Reconnect" button only. (3) Off by default, a setting turns it on. _Recommendation: (1)._ A reconnect resets the controller, which stops a machine still running its buffer and switches the spindle output off; doing it within a second is safer than waiting for the user to find the button.
2. **Q159 – Where the record lives.** (1) **A run journal in the app data, written atomically at events and at most once a second.** (2) In the project's working folder. (3) Memory only. _Recommendation: (1)._ File runs have no project, a project may not reopen cleanly after a crash, and memory dies with the computer; once a second loses at most a second of progress, covered by erring early.
3. **Q160 – The suggested resume point.** (1) **The latest pass start before the earliest line that may still have been running; the operation start offered as "safest".** (2) Always the operation start (M5 as today). (3) The executing line itself. _Recommendation: (1)._ An operation can take many minutes of air cutting; a pass start is a clean entry (retracted, then plunge) seconds before the stop; (3) plunges inside the cut.
4. **Q167 – Tool wait in every lead-in.** (1) **Always wait at the tool (M5's rule), even when it did not change.** (2) Only when the tool changed or the user asks. (3) Never. _Recommendation: (1)._ After an interruption the bit may be broken, pulled out to clear chips or slipped; the wait is the natural place to look and re-zero Z, and costs one "Continue" click.
5. **Q168 – Start from a line as a general feature.** (1) **Yes: "Start at" in every pre-flight (beginning, operation, line), on plans whose program is unchanged and on files.** (2) Only inside recovery. _Recommendation: (1)._ The same lead-in serves both, and it is the feature senders like gSender offer; the safety comes from the lead-in and the findings, not from hiding it.
6. **Q169 – Lines that are not resume points.** (1) **Allowed behind "Choose a line…", with findings (in material, inside a ramp or helix) and the pre-flight.** (2) Only resume points (operation and pass starts). (3) Any line, no findings. _Recommendation: (1)._ Sometimes the user knows better (a file with odd structure); the findings say what the plunge will do.
7. **Q170 – Files resume too.** (1) **Yes, by line, with resume points found by the rules above; the file must hash equal.** (2) No (DF93 as today). _Recommendation: (1)._ A file from another CAM is exactly the run the user cannot regenerate in DFYOM; the parse gives the modal state either way.
8. **Q171 – Machine power lost, controller still on USB power.** (1) **"The machine lost power" in the panel after a Stop (and in the Position table's menu while idle): marks the position lost (home required) and opens recovery.** (2) Nothing special: the user resets and homes by hand. _Recommendation: (1)._ It is the one case DFYOM cannot detect, and without it the DRO shows a position that is wrong.
9. **Q172 – Spin-up dwell for files.** (1) **5 s, editable in the pre-flight's lead-in.** (2) The library machine's spindle spin-up (a new machine field). (3) None. _Recommendation: (1)_; a machine field can follow when DFYOM's own spin-up setting moves to the machine.
10. **Q173 – Practising.** (1) **"Simulate a lost connection" on the virtual machine, in the run section's menu.** (2) Tests only. _Recommendation: (1)._ The first real disconnect is the wrong time to see the panel for the first time.

## Implementation (RC1)

Record and journal, 2026-11-26. No recovery panel (RC5), no resume (RC2), no auto-reconnect (RC4) yet.

- **Where:** `RunRecorder` in [`src/core/run/journal.ts`](../../src/core/run/journal.ts) (headless) builds the record in main's `MachineClient` from the host's status, progress, phases and events; `RunJournalSchema` is the file's contract. Main writes it through the `RunJournalPort` ([`src/main/persistence/run-journal.ts`](../../src/main/persistence/run-journal.ts): `writeFileAtomic`, temp + fsync + rename + directory fsync; saves serialized, the latest winning when they queue up; a failed write logged once per run, never blocking it). The host only passes GRBL's `Ln:` (`job.reportedLine`, stripped from `RunStatus` like `ackedAtReport`) and posts a last status before `connectionLost`, so `sent` includes the lines written since the last throttled status.
- **Executing line:** `Ln:` when the controller reports it **and** the program's `N` words are unique and ascending (`Ln:` is the `N` number, not the line; a file may carry its own `N` words), mapped to the line; else DF84's estimate ([run.md](run.md#gcode-panel-df84)); else the acknowledged lines minus 16 (a full planner plus one, as M5). Never after the acknowledged lines, never going back; `progress.executingFrom` says which (`reported`, `estimate`, `planner`).
- **Modal state:** the state the executing line **starts in**, parsed forward once with the virtual machine's parser (motion, units, distance, feed, spindle and rpm, the last `T` word). Plane and coolant are added by RC2 (`stepModal` in `recovery.ts`). Tool: the last tool-change marker at or before the line; operation and section likewise.
- **Writes:** at the start (once the host accepted the job: a refused start writes nothing and keeps the last record), when the executing line enters another section, at a tool change, a program pause or a hold, at the end, and otherwise at most once a second from the status reports (`JournalThrottle`, Q159). The journal is only written on a real connection; the virtual machine keeps the in-memory record (`MachineClient.runRecord()`) only.
- **End:** the journal is kept with its final state (`done`, `stopped`, `failed`, `interrupted` + reason) as [§ What DFYOM keeps](#what-dfyom-keeps) says (a `done` one is never offered), not deleted; `discardRunJournal` is there for RC5's "Dismiss" and for an unreadable file. Reasons: `connectionLost` (the host's event, or a job ending with `machine.connection`), `hostExit` (the host exited unexpectedly), `controllerReset` (a banner DFYOM did not cause, or `machine.reset`), `appCrashed` (a `running` journal read by `loadRunJournal`; the app reads it at start and logs it, RC6 shows it). `machinePowerLost` comes with RC5's button. A Stop is `stopped` even after one of these events.
- **Upper bound after a host exit or a crash:** `sent` is the host's last status (≤ 0.1 s old) or the journal's last write (≤ 1 s); the controller may hold a few more lines. Harmless for the suggestion, which uses the lower bound.
- **Keeping awake:** Electron `powerSaveBlocker` `prevent-app-suspension` from the accepted start of a real run to its end, whatever the end (`keepAwake` in `src/main/machine/electron.ts`).
- **Format:** `format: 1`, the file's own (not project data: no `schemaVersion`); another format or an unreadable file is discarded with a warning (pre-alpha).
- **Deferred:** `RunStatus.lastRun.interruption` for agents and the UI to RC5 (its first reader; `lastRun` is plan-only today); the plan job's project path and id to RC6 ("Open project"); the file's own size and SHA-256 (the journal hashes the program as streamed, `programHash`); the USB serial number and VID:PID to RC4 (port matching); emulator `powerCycle` and loopback `unplug({ controllerRuns })` / `replug` to RC4, where reconnecting needs them (the RC1 test runs the unplugged emulator's buffer out by advancing it, which is `controllerRuns: true`). The journal is not wired in headless runs: real runs start only from the UI (Q50).
- **Tests:** [`journal.test.ts`](../../src/core/run/journal.test.ts) (the throttle, the executing line by source and `N` words, the modal state, the end states and reasons; on the loopback port: unplugged mid-job, the journal says `interrupted`/`connectionLost` with executing ≤ the line the emulator was in ≤ the line it stopped at after running out its buffer ≤ sent, the last report and modal state, writes ≥ 1 s apart, awake on and off; a host exit is `hostExit`; a normal end is `done`), [`run-journal.test.ts`](../../src/main/persistence/run-journal.test.ts) (temp + rename order, latest wins, a `faultFs` crash at write, fsync or rename keeps the previous journal, one warning per run, `running` reads as `appCrashed`, unreadable discarded).

## Implementation (RC2)

Resume points and the lead-in (core), 2026-11-27. No UI yet (RC3); the suggestion reaches the status with RC5's `lastRun.interruption`.

- **Where:** [`src/core/run/recovery.ts`](../../src/core/run/recovery.ts) (headless): `stepModal` (the virtual machine's parser plus the plane and the coolant; the run recorder's `ModalTracker` uses it, so the journal's modal state now has `plane` and `coolant` as RC1 deferred), `scanProgram` (one parse per program: per line its start and end point in work coordinates, an axis unknown until the program sets it absolutely or after a `G53` move, the tool in effect, the last `G0` Z, the last plunge feed), `resumePoints`, `resumeFindings`, `suggestResume`, `resumeProgram` (lead-in + remainder, sections shifted with a `Lead-in` section first) and `programHash` (SHA-256 of the lines joined with LF, Web Crypto, equal to main's journal hash). Run start path: `run.job.start`/`run.job.check { fromLine }` in [`job.ts`](../../src/core/run/job.ts).
- **Pass start:** the first feed move (G1–G3) after an X/Y rapid (programs rapid sideways only above the stock), or after a rapid back up to the height of the last X/Y rapid, whose start point is known; the program's first feed move too. A drill's peck retracts and a profile's tab ramps are therefore not pass starts, and a pass start is always the first line of its plunge, ramp or helix.
- **Operation start:** the first pass start at or after an operation boundary: a plan's operation lines (`operationLines` of the export), for a file every tool-change marker (also a first, loaded tool's without `M0`) and every whole-line comment between passes. The label is the last comment before the tool change (else the last one), DFYOM's own instruction comments (`Tool change to T…`, `Stop the spindle`, `Set spindle to …`) skipped, then `tool n: name`. A resume at a tool-change marker or its `M0` starts after them (the lead-in waits at that tool itself).
- **One rule for plans and files:** the approach height is the program's last `G0` Z before the line (the operation's retract height in a plan program), the plunge feed the last Z-only `G1` down before the line, else half the feed in effect: the program carries both, so the plan is not read for them. A start point at or above the rapid height is reached by the rapid and the plunge is left out; below it the approach is the rapid height but at least 1 mm above the start; a program with no `G0` Z before the line approaches 1 mm above the start (or above Z 0 when the start is below it). Spin-up: the post's 3 s for plans (`DEFAULT_SPIN_UP_SECONDS`), 5 s for files (Q172; editable in RC3's pre-flight). Hand-switched spindle: the plan machine copy's, for a file the connection's machine.
- **Lead-in additions:** a first comment line `(Resume at line n: lead-in)`, `M9` with the `M5` (coolant off while waiting at the tool), and the tool wait's marker for a file without tool changes names `Tool <T word, else 1>`. The motion word restatement covers any modal G0–G3 the first motion line relies on ([grbl.md § Resumed programs](../architecture/grbl.md#resumed-programs-hardening-df129)), so the lead-in ends with the distance mode and feed only (`G91 F10`).
- **Findings:** `inMaterial` when the start is below work Z 0 (plans and files; the in-process stock comes with RC3's preview), `ramp` (with `helix` when the run has an arc, and `from`, its first line) when the first motion line at the line is a feed move changing Z and not the first of such a run, `toolChange` (always: the lead-in waits at that tool; "you resume with tool 1" against the run's last tool needs the run record, RC5), `incremental` under `G91`.
- **Refusals:** `input.malformed` with path `fromLine`, rule `range` (outside the program) or `noStartPoint` (before the program's first absolute X, Y and Z, or after a `G53` move until Z is set again); rule `oneOf` for `from` with `fromLine`; rule `programChanged` (path `programHash`) when `programHash` names another program than the one exported or read now: "The plan changed since the run: resume from an operation instead." / "The file changed since the run." Without `programHash` the line refers to the program as it is now (the panel's current program). `run.state` when the controller's travel (`$130–$132`, needed for the machine top) is unknown.
- **Checks:** the soft limits of a start at a line are checked over the lead-in and the remainder as one program with the file check (`fileSoftLimits`: X/Y throughout, Z until the lead-in's tool wait, `G53` targets always), for plans too; the export's other machine warnings stay. `run.job.check { fromLine }` adds `resume { fromLine, programHash, leadIn, findings, before, after }` (the nearest resume points); `run.job.start` takes `programHash` from it (or the journal's). The job's progress counts the resumed program's lines; the status' operation lines are shifted (the operation holding the line starts after the lead-in). The journal of a resumed run hashes the resumed program; mapping its lines back to the original program ([§ Edge cases](#edge-cases), "interrupted during the lead-in") comes with RC5.
- **Agent API:** `fromLine` on both commands, `programHash` on `run.job.start`, `fromLine` without a minimum and `programHash` without a description to stay in the budget: `tools/list` 117,138 → 117,285 characters (+147, ≤ 0.15 K). On a real connection the start stays UI only (Q50), unchanged.
- **Tests:** [`recovery.test.ts`](../../src/core/run/recovery.test.ts): the modal state (plane, coolant, G53, units), the resume points and labels of the DF93 samples and the goldens (pocket, profile with ramps, helical pocket, multi-tool, inch with a hand spindle), helices and ramps found, in-material, `G91`, the suggestion, the lead-in's lines (mm and inch, coolant, `M4`, hand spindle, motion word), the refusals, the hash; on the virtual machine (homed, G54 set) **every resume point** of the four DF93 samples, four goldens and the geometry test part's program, and a line inside a helix: streamed to Idle without errors, every motion line from the resume line on ends where the full run's did (work coordinates, 2 µm). [`commands.test.ts`](../../src/core/run/commands.test.ts): `run.job.check`/`start { fromLine }` for a plan and a file on the virtual machine (lead-in with a tool wait, runs to the end, Idle), `programChanged`, `oneOf`, `range`.

## Implementation (RC4)

Auto-reconnect, 2026-11-27. The recovery panel came with [RC5](#implementation-rc5); the reconnect state also shows in the navigator.

- **Where:** [`src/core/run/host/reconnect.ts`](../../src/core/run/host/reconnect.ts) (headless): `matchPort` and `Reconnector` (the backoff, the port scan, the 2-minute limit; the attempt and the port list injected, timers a `TimerHost`). `MachineClient` ([`client.ts`](../../src/core/run/host/client.ts)) keeps the last connection opened (target, machine profile, USB identity) and starts an episode on a `connectionLost` event or an unexpected host exit **while a run job is current** (streaming, held, or waiting at a tool change or pause). Not: a connect that fails (so never at launch), the user's disconnect, a loss while idle, homing or probing (the edge case above is amended: no run, nothing to come back for), or with the setting off.
- **Matching:** the lost path, unless the OS reports another serial number there (another device took the path); else the port with the same USB serial number and, when both are known, the same VID:PID. Nothing listed: the attempt counts as failed without opening anything (the list is read before each attempt); no list from the OS: the path is tried. The USB identity is read once after a serial connect (a `listPorts` on the same host) into the connection and the journal's `machine.usb` (RC1's deferral).
- **Backoff:** attempts at 0, 1, 3, 7 and 15 s, then every 10 s: 15 attempts in the 2 minutes; the OS's list is scanned every second while waiting and a port that appears (absent in the last scan) is tried at once. At 2 minutes it gives up; an attempt still connecting then decides by itself. A successful reconnect becomes the connection to reopen next time (a re-enumerated device keeps its new path).
- **Reads only:** an attempt is a plain connect through the host's handshake: the banner after the DTR reset (`0x18` only when none comes), `$I`, `$$`, `$#`, `$G` and status polls (asserted byte for byte on the loopback port: `$I\n$$\n$#\n$G\n` plus `?`, and the emulator's position and Alarm unchanged afterwards). Nothing else runs after it: no unlock, no restored modes, no alignment, no resume. The controller comes back locked and not homed (`ALARM` start-up lock with `$22=1`).
- **Status:** `RunStatus.connection.reconnect { phase: waiting | connecting | reconnected | gaveUp, attempt, nextAt }` (`nextAt` epoch ms while waiting). `lost` stays while trying, also while an attempt connects (the safety line of step 1 keeps showing for a real machine and is not announced again per attempt). `reconnected` is kept until the next run, connect or disconnect; `gaveUp` until the next connect. The journal is not touched by reconnecting: it keeps the interruption RC1 wrote (`connectionLost`, `hostExit`) until the next run.
- **UI (minimal):** the navigator's `ReconnectStatus` at the end of the panel, a polite live region (only the loss itself is assertive): "Reconnecting… attempt n" with "Stop trying", "Reconnected — machine needs homing" while not homed, "Gave up after 2 min — reconnect manually"; neutral colours (the "Needs homing" look of DF46). "Stop trying" ends the episode (an attempt that connects afterwards is disconnected again, which resets); the user's own Connect also ends it. "Reconnect now" and the "next in 4 s" countdown come with RC5's panel (`nextAt` is in the status for it).
- **Setting:** "Reconnect automatically after a lost connection" (`autoReconnect`, default on) in Settings → Run ([ui.md § Settings](../conventions/ui.md#settings)); read at the loss.
- **Settings check after a reconnect:** the navigator's settings warning is cleared with the closed connection as before; a real run's start checks the controller's `$$` again ([run-machine.md § Settings check](run-machine.md#settings-check)), so a different controller behind the port cannot run.
- **Practising (Q173):** "Simulate a lost connection" in the navigator's connection section while a run streams on the virtual machine (RC5 may move it to the run section's menu; the navigator keeps it clear of RC3's pre-flight and gCode panel work). It sends the host action `simulateLostConnection`, which pulls the virtual transport's cable (`VirtualGrblTransport.unplug`): the sender sees a closed port and the connection is lost as a real one is. The simulated cable stays out 2.5 s (`SIMULATED_UNPLUG_MS`), so an attempt or two fail first. The virtual reconnect powers the emulator up where it stopped (`position`) with G54 kept (the target's new `workZero`, GRBL's EEPROM), never `prepare`, at the time scale it had. The virtual machine still writes no journal; its in-memory record says `interrupted`/`connectionLost`.
- **Renderer only:** `window.dfyom.run.reconnect('cancel' | 'simulate')` and `run.record()` (the run record, RC5's reader) over IPC; no command, no agent tool, `tools/list` unchanged. Agents see the state in `run.status.get` (`connection.reconnect`).
- **Fault hooks:** emulator `powerCycle()` and option `workOffset`, loopback `unplug({ controllerRuns })` and `replug({ afterMs, path })` with a serial number per loopback port ([grbl.md § Fault injection](../architecture/grbl.md#fault-injection)).
- **Tests:** [`reconnect.test.ts`](../../src/core/run/host/reconnect.test.ts): `matchPort` (path, new path by serial number, a taken path, VID:PID, no serial number); with fake timers the attempt times 0, 1, 3, 7, 15, 25 … 115 s and giving up at 120 s, a port's arrival tried at once, cancel; on the loopback port a run unplugged and replugged under a new path reconnects by itself (open at the new path, Alarm, not homed, G54 kept, the record `interrupted`/`connectionLost` with the USB identity) with exactly the handshake's bytes sent; gave up after 2 minutes without opening anything; "Stop trying"; no reconnect at launch, after a user disconnect, after a loss while idle or with the setting off; on the virtual machine "Simulate a lost connection" mid-run reconnects after the cable's 2.5 s, Alarm, not homed, G54 kept. [`protocol.test.ts`](../../src/core/run/grbl/emulator/protocol.test.ts): `powerCycle`. [`ReconnectStatus.test.tsx`](../../src/renderer/src/modes/run/ReconnectStatus.test.tsx) with axe. Hidden e2e [`run-reconnect.e2e.ts`](../../e2e/run-reconnect.e2e.ts): a file runs on the virtual machine, "Simulate a lost connection", the status pushes waiting → connecting (≥ 2 attempts) → reconnected, the navigator shows "Reconnected — machine needs homing", the toolbar "Needs homing", nothing moves, `run.record()` says `interrupted`/`connectionLost`, homing clears it.
