# Cut state: what is already cut, and planning new work on the cut part

Status: accepted, C1 implemented (accepted by delegation D84; **re-scoped by the user, TG #447**: the mark lives on design operations, independent of plans – Q193 and Q194 decided by the user, Q198–Q200 adjusted; hardening [DF135](../plans/hardening.md#intake-user-feedback-goes-here), the user's TG #442 after a successful real cut of "plan 2": "Seems like marking a cut as completed isn't implemented yet. Without cutting Pocket 2 again in the air in a new plan."; TG #447: "my initial idea was to be able to mark any operations as 'completed' or 'already cut' in the design mode, independently from the plans. DFYOM does not know what has been cut. A plan is a snapshot of the design and its program always cuts every operation from the raw stock. After a real cut the user wants to add work to the finished shape (a chamfer on an edge already cut, a pocket in Pocket 2's floor, a hole) and get a program that cuts **only the new work**, starting from the material that is really left. The same holds for a stock that arrives with something already in it (a pocket, a hole, a rebate): it is not a plain block, and the user wants to say so.

Today's nearest tool, **Disable** ([DF106](design.md#disabling-operations-and-features-df106)), does the wrong thing: it removes Pocket 2 as if it had never been designed, so its removal is gone from every later calculation, and every operation that builds on it (the new pocket `on` Pocket 2's floor, a chamfer on its edge) is switched off with it.

## Goals and not goals

- **Goal:** mark **design operations and features** as **already cut** in Design (the material is gone from the stock, whoever cut it); every plan keeps them in the machining order as removed material but generates no program for them; new work builds on them as usual.
- **Not goals (here):** a general 3D in-process stock for generation (the [model choice](#model-in-process-stock-from-cut-operations) keeps the existing 2D removal model); several physical workpieces of one design ([Q199](#questions-for-the-user)); crediting a partly cut operation ([Q197](#questions-for-the-user)).

## How other CAM handles it

Summary from their public docs and UI as we know them; not re-checked for this draft.

| Program        | What it offers                                                                                                                                                                                                                                                                      | Lesson for DFYOM                                                                                                                                   |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| Fusion         | A setup's stock can come **from the preceding setup** (the simulated in-process stock); adaptive and other strategies have **rest machining** from previous operations or setups; operations can be suppressed or protected from regeneration; post a selection of operations only. | The stock model is 3D simulation for 3D CAM. The workflow – new operations "from previous" and post only the new ones – is what the user asks for. |
| Carbide Create | No in-process stock: each toolpath has an enable checkbox and a **start depth**; to add work to a cut part you disable the done toolpaths and set start depths by hand.                                                                                                             | Disabling the done work is the common hobby workaround; DFYOM can do the start depth for the user from the cut operations.                         |
| Estlcam        | No stock model either; parts and their depths are set by hand (a start depth), the order and which parts to export are chosen per program.                                                                                                                                          | As above: the user carries the state in their head.                                                                                                |

DFYOM sits between: no 3D simulation for generation, but it already knows each operation's removal and its machining order ([DF61 material bands](plan-v0.2.md#material-left-for-later-cuts-df61)), so "already cut" can be one flag per design operation.

## Terms

| Term                 | Meaning                                                                                                                                                                                                                                    |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Already cut**      | A design operation or feature whose material is already gone from the stock (cut by a DFYOM program, by hand, or there when the stock arrived). Stored on the part; plans read it from their design copy. Glossary row: **Cut operation**. |
| **Cut operation**    | A plan operation all of whose design operations are already cut: locked, not in the program, still a removal for later operations.                                                                                                         |
| **In-process stock** | As in the [glossary](../glossary.md): here the material left after the already-cut operations.                                                                                                                                             |

## What is stored

- `PartDTO.alreadyCut?: string[]` – the top-level ids (plain operations and outermost features, as the [disabled list](design.md#disabling-operations-and-features-df106)) marked already cut, in design order; absent = none ([pre-alpha](../conventions/error-handling/migrations.md#pre-alpha-exception-no-data-preservation-yet): an optional field, no `schemaVersion` change, no migration). Ids of removed items leave the list after every design command (the disabled list's follow hook).
- **Derived, never stored:** the already-cut design operations (`alreadyCutOperations`, `src/core/design/already-cut.ts`): every operation of a listed unit (a feature's owned operations too), and the roughing pass of a cut operation (its material went first). **Dependants are not cut**: a pocket `on` a cut pocket's floor or a chamfer on its edge is new work. A plan operation is cut when it machines design operations and all of them are already cut (`cutTest`, `src/core/plan/cut.ts`); an alignment aid never is.
- **No date or author in C1.** "Who marked it" matters once Run marks ([Q196](#questions-for-the-user), C2), which adds it.

## Marking

**By hand** (Design): the row menu of a top-level row **Mark as already cut** / **Mark as not cut** (before Disable), one `design.part.update { alreadyCut }` and one undo step. The row stays in the list with its name muted and a check marker **Cut** ([ui.md](../conventions/ui.md#feature-rows-and-add)); everything else about it is unchanged: it is in the 3D model, its checks run, Chamfer and Make Clones… build on it.

**From Run** ([Q196](#questions-for-the-user), C2), using the run's own record ([run journal](run-recovery.md#what-dfyom-keeps): the job's plan, setup, `planHash` and operations in order, the acknowledged and executing lines), sets the same design mark for the design operations of the program's operations:

| Run ends                                                       | Marks                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `done` on a real machine, program unchanged (`planHash` equal) | Every design operation of the program, automatically; a toast "Marked 5 operations as already cut" with **Undo**.                                                                                                                                                                                                                                                                                                                                                                                 |
| `stopped` or `interrupted`                                     | None automatically. When the recovery panel is dismissed or a stopped run's sheet closes: "Mark the finished operations as already cut?" listing those whose last line was **executed** (before the executing estimate's lower bound, as [run-recovery.md](run-recovery.md#choosing-where-to-resume)). The operation in progress is never marked ([Q197](#questions-for-the-user)). Not offered while a resume is possible, since marking changes the program and line resume needs it unchanged. |
| The virtual machine, or a file run                             | None (practising; a file has no plan).                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| The plan changed since the export (`planHash` differs)         | None; the sheet says why and points to marking by hand.                                                                                                                                                                                                                                                                                                                                                                                                                                           |

**Plans:** the mark is a design change like any other ([plans are snapshots](plan-v0.1.md#plans-are-snapshots)): a `draft` plan follows on Apply; a `settledDesign`, `finalized` or `inUse` plan keeps its copy (and shows the design as changed) until rebuilt. A new plan starts with it.

## What a cut operation means in its plan

- **Locked.** Tool, feeds, strategy and order are read-only (`plan.status` refusal, rule `cut`, "Pocket 2 is already cut; mark it not cut in Design to change it"); a setup holding one is not split, merged or moved. Design edits reach it as usual ([§ Editing](#editing-an-already-cut-operation)).
- **Not in the program.** Export, the program's time, the tool runs and tool changes leave it out; a tool run with only cut operations disappears; a setup whose operations are all cut has no program (`plan.check`, rule `allCut`, "Top is cut: every operation is already cut"). Its toolpath is still generated (cached as today, never exported) because later calculations read it; the mark is not in the toolpath input hash, so marking regenerates nothing.
- **Still removed material.** It keeps its place in the machining order, so everything that reads earlier operations sees its removal unchanged: the [material bands](plan-v0.2.md#material-left-for-later-cuts-df61) (later passes start at its floor; partial coverage of pockets cut by area), through depths and openings, the [roughing rest](roughing.md), the [safe links' stock height field](safe-links.md#in-process-stock-height-field) (links dip into its cleared air; the link into the first uncut operation starts from the uncut one before it), the [Z reference](z-reference.md) flat patches (a cut facing's floor is a valid touch-off surface; the raw top it removed is not), and alignment points on [already-cut features](alignment.md#validity-already-cut-and-reachable).
- **Cut first.** Within a setup the cut operations count as machined before every uncut one (the physical truth: they are done), so a rebuild puts them first in their order (an `on` dependency still comes first). New work never goes into a setup before the last setup with cut operations: it gets a new setup at the end ([§ Setups](#setups-and-work-zero)); an uncut operation left in such a setup warns `plan.cutSetupOrder` ("Drilling 1 on Top is not cut, but Bottom is: cutting it needs the part flipped back").
- **Findings.** A cut operation keeps its errors (they block the removal later operations read) and drops its warnings and infos.
- **Display** ([Q200](#questions-for-the-user)). The row is muted with a check and **Cut**; its toolpath is hidden in the viewport unless **Show cut toolpaths** (the Toolpaths group, shown when the plan has cut operations) is on. The viewport's stock already shows the design's removal; slice C5 draws the in-process stock from the height map.

## Run (DF137)

Run shows and streams exactly the export (dogfood TG #454: Run drew the cut pocket's toolpath with no way to hide it). The program `run.job.check` and `run.job.start` stream is `exportPlan`'s, so a cut operation is never streamed, the gCode panel, Start at, the time and the tool waits are the export's, and a section resume at a cut operation is refused (`input.malformed`, rule `unknownOperation`). The run mode around it follows the same rule, from the plan's design copy (`cutTest`, as Plan):

- **Scene.** The toolpaths are linked over every operation (as the export links them), then the cut ones are left out: Run draws the lines Plan draws with **Show cut toolpaths** off. Run has no such switch; playback follows the program.
- **Tools.** The pre-flight's tool list, "Resume at" and the workholding guard's tool numbers (by first use in the program) skip cut operations.
- **Setups.** Run starts on the first setup with an uncut operation, and a run's next setup (the setup-change prompt, `run.job.start`'s `next`) skips setups cut in full, which have no program.

A plan that is not a draft keeps its copy of the mark (a snapshot, [§ What is stored](#what-is-stored)): Plan, Export and Run then all still cut the operation until the plan is rebuilt, so the three agree either way.

## Planning new work on the cut part

The user's flow: plan 2 was cut. In Design, Pocket 2 (and the facing) are marked already cut; then the user adds the pocket `on` Pocket 2's floor, the chamfer on its edge, a hole. A `draft` plan (plan 2 itself, or a new plan) follows: the new operations are placed after the cut ones; their toolpaths start from the material left: the pocket from Pocket 2's floor (its `on` level, and DF61's band for anything stacked), the hole's drilling cycle from the band's top, the chamfer at its edge's face; the links over Pocket 2 use its cleared air. Its export holds only the new operations. No "continue" copy of a plan is needed ([Q194](#questions-for-the-user)).

## Model: in-process stock from cut operations

[Q195](#questions-for-the-user). The choice is how later operations learn what the cut ones removed.

| Model                                                                                                                 | Exact?                                                                          | Cost                                                                                                                                                            | Covers the user's case                                          |
| --------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| **(1) Operation-level removals** (chosen): cut operations stay in the order as removals                               | Analytic regions and floors; partial coverage only for pockets (DF61)           | None new: bands, rest, links and Z reference already read earlier operations. Cut toolpaths are generated once and cached (the links field needs them today).   | Yes: a pocket on its floor, a chamfer on its edge, a hole in it |
| (2) Height map per setup: the [simulated cut](deviation.md#height-map-method) of the cut toolpaths as the start stock | Sampled (0.1–0.5 mm cells), credits any shape and partial passes                | Every generator would need a height-map input (none has one); the toolpath job depends on every earlier move; simulation per setup in the job (up to 4 M cells) | Yes, at a higher cost                                           |
| (3) Removed-region stack via the 2D ports: union of (region, floor) per cut operation                                 | Exact in 2D, more general than bands (partial coverage of facings and profiles) | A new model and its tests; bands would become its special case                                                                                                  | Yes                                                             |

(1) needs no new geometry; (2) is still useful for the **display** of the in-process stock and as the test oracle (`airCut`, `heightDifference` in `src/core/toolpath/testing/region-coverage.ts`); (3) is the follow-up when the bands' "partial coverage gives no band" leaves air passes over a cut operation the user notices.

**Performance:** (1) adds no work to a plan with no cut operations; with cut ones, their toolpaths are generated as before (cached by input hash, which the mark does not enter) and skipped at export. No new per-move cost.

## Setups and work zero

- **Same setup, part still clamped:** the new operations join the setup after its cut ones; the controller's G54 still holds; Run starts the setup's program as usual.
- **Part removed and re-clamped:** the setup-change prompt asks to re-zero as for any setup ([alignment.md](alignment.md)); alignment points on already-cut features (Pocket 2's walls) locate the part; the Z reference of the first tool run is a surface that still exists (the faced top or a cut floor, [z-reference.md](z-reference.md)), never the raw top a cut facing removed (`plan.zRefGone`, error).
- **Flipped part:** new operations of a direction whose setup comes before the last setup with cut operations go into a **new setup appended at the end** (e.g. Bottom · Top cut, then "Bottom 2" for the new bottom pocket): the part must be flipped back, and the DF61 bands already chain opposite-direction cuts of earlier setups. The safe links' field still starts flat at Z0 in each setup ([Q104](safe-links.md#open-questions-for-the-user)), the safe side.

## Editing an already-cut operation

([Q198](#questions-for-the-user), decided by the user's TG #447.) Editing is allowed and raises no finding: the mark describes the stock, so an edit **re-describes what is already gone** (the user may be fixing the design to match the part, or describing a stock that arrived with a pocket). The plan follows as for any design edit and still exports nothing for it.

- **C2:** an operation marked **by Run** warns when its geometry is edited afterwards (`plan.cutChanged`, warning: "Pocket 2 changed since the run cut it"), since the run's record says what the machine really removed. Marks set by hand never warn.
- **Removed from the design:** its id leaves the list; the plan no longer knows that material is gone (new work over it may cut air, never too little).
- **Disabled in Design:** out of the model as any disabled item; its mark stays and counts again when it is enabled.

## Agent API

`tools/list` was 118,418 of 120,000 chars; measured after C1: **118,539** (+121).

- `design.part.update { partId, alreadyCut: [ids] }` replaces the list (`[]` clears it; unknown ids `input.malformed`, rule `unknownItem`; an owned operation `insideFeature`, as `disabled`). No new tool.
- Read: `design.part.get` shows the list; `plan_get` marks each cut plan operation `alreadyCut: true` and leaves it out of the setup's time and tool runs; findings `plan.cutSetupOrder`, `plan.zRefGone` (results are not in `tools/list`).
- Run marks (C2) are UI only (as the run's end sheet); an agent marks by hand after `job.wait` returns `done`.

- **Plans are snapshots** of the mark: a draft follows, others show the design changed; `plan.duplicate` copies the plan's copy as it is. No plan-level mark, no continuing plan (TG #447).
- **The input hash** leaves the list out (the part is hashed with `alreadyCut` removed), so marking and clearing regenerate no toolpath; clearing restores the program byte-equal.
- **Not in C1:** the mark's date and author (C2 needs them; the marker says "Cut"), multi-select and an inspector switch (C3), the as-cut geometry (C4).
