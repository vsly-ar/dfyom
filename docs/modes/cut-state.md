# Cut state: what is already cut, and planning new work on the cut part

Status: accepted, C1–C5 and Q199's clear implemented (C3's multi-select marking with the Design navigator's multi-select, 2026-11-27; C4's follow-ups – hand marks, edge operations, engravings, through holes, the as-cut removal in C5 – accepted by delegation and implemented 2026-11-27; accepted by delegation D84; **re-scoped by the user, TG #447**: the mark lives on design operations, independent of plans – Q193 and Q194 decided by the user, Q198–Q200 adjusted; hardening [DF135](../plans/hardening.md#intake-user-feedback-goes-here), the user's TG #442 after a successful real cut of "plan 2": "Seems like marking a cut as completed isn't implemented yet. I want to add another operation to the resulting shape that respects existing geometry, e.g. a chamfer, another pocket in Pocket 2's floor. Without cutting Pocket 2 again in the air in a new plan."; TG #447: "my initial idea was to be able to mark any operations as 'completed' or 'already cut' in the design mode, independently from the plans. So that if my stock already has something that makes it not completely rectangular, I can specify it.") · Base: [design.md § Disabling operations and features (DF106)](design.md#disabling-operations-and-features-df106) (the list this one mirrors), [plan-v0.1.md § Plans are snapshots](plan-v0.1.md#plans-are-snapshots), [plan-v0.2.md § Material left for later cuts (DF61)](plan-v0.2.md#material-left-for-later-cuts-df61), [roughing.md](roughing.md) (rest by the roughing tool's reach, Q143), [safe-links.md § In-process stock height field](safe-links.md#in-process-stock-height-field), [z-reference.md](z-reference.md), [run-recovery.md § What DFYOM keeps](run-recovery.md#what-dfyom-keeps) (the run journal), [alignment.md § Validity: already cut and reachable](alignment.md#validity-already-cut-and-reachable), [deviation.md § Height map method](deviation.md#height-map-method) · Agent API budget: [llm-api.md](../architecture/llm-api.md) · Data rule: [migrations.md § Pre-alpha](../conventions/error-handling/migrations.md#pre-alpha-exception-no-data-preservation-yet) · Terms: [glossary.md](../glossary.md)

DFYOM does not know what has been cut. A plan is a snapshot of the design and its program always cuts every operation from the raw stock. After a real cut the user wants to add work to the finished shape (a chamfer on an edge already cut, a pocket in Pocket 2's floor, a hole) and get a program that cuts **only the new work**, starting from the material that is really left. The same holds for a stock that arrives with something already in it (a pocket, a hole, a rebate): it is not a plain block, and the user wants to say so.

Today's nearest tool, **Disable** ([DF106](design.md#disabling-operations-and-features-df106)), does the wrong thing: it removes Pocket 2 as if it had never been designed, so its removal is gone from every later calculation, and every operation that builds on it (the new pocket `on` Pocket 2's floor, a chamfer on its edge) is switched off with it.

## Goals and not goals

- **Goal:** mark **design operations and features** as **already cut** in Design (the material is gone from the stock, whoever cut it); every plan keeps them in the machining order as removed material but generates no program for them; new work builds on them as usual.
- **Not goals (here):** a general 3D in-process stock for generation (the [model choice](#model-in-process-stock-from-cut-operations) keeps the existing 2D removal model); several physical workpieces of one design ([Q199](#questions-for-the-user)); crediting a partly cut operation ([Q197](#questions-for-the-user)).

## How other CAM handles it

Summary from their public docs and UI as we know them; not re-checked for this draft.

| Program        | What it offers                                                                                                                                                                                                                                                                      | Lesson for DFYOM                                                                                                                                   |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| Fusion         | A setup's stock can come **from the preceding setup** (the simulated in-process stock); adaptive and other strategies have **rest machining** from previous operations or setups; operations can be suppressed or protected from regeneration; post a selection of operations only. | The stock model is 3D simulation for 3D CAM. The workflow – new operations "from previous" and post only the new ones – is what the user asks for. |
| Carbide Create | No in-process stock: each toolpath has an enable checkbox and a **start depth**; to add work to a cut part you disable the done toolpaths and set start depths by hand.                                                                                                             | Disabling the done work is the common hobby workaround; DFYOM can do the start depth for the user from the cut operations.                         |
| Estlcam        | No stock model either; parts and their depths are set by hand (a start depth), the order and which parts to export are chosen per program.                                                                                                                                          | As above: the user carries the state in their head.                                                                                                |

DFYOM sits between: no 3D simulation for generation, but it already knows each operation's removal and its machining order ([DF61 material bands](plan-v0.2.md#material-left-for-later-cuts-df61)), so "already cut" can be one flag per design operation.

## Terms

| Term                 | Meaning                                                                                                                                                                                                                                    |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Already cut**      | A design operation or feature whose material is already gone from the stock (cut by a DFYOM program, by hand, or there when the stock arrived). Stored on the part; plans read it from their design copy. Glossary row: **Cut operation**. |
| **Cut operation**    | A plan operation all of whose design operations are already cut: locked, not in the program, still a removal for later operations.                                                                                                         |
| **Recut**            | (C4) An operation a run marked already cut and edited since: cut again for the difference only, its as-cut version counting as removed material ([§ C4](#cutting-only-the-difference-c4)).                                                 |
| **In-process stock** | As in the [glossary](../glossary.md): here the material left after the already-cut operations.                                                                                                                                             |

## What is stored

- `PartDTO.alreadyCut?: string[]` – the top-level ids (plain operations and outermost features, as the [disabled list](design.md#disabling-operations-and-features-df106)) marked already cut, in design order; absent = none ([pre-alpha](../conventions/error-handling/migrations.md#pre-alpha-exception-no-data-preservation-yet): an optional field, no `schemaVersion` change, no migration). Ids of removed items leave the list after every design command (the disabled list's follow hook).
- **Derived, never stored:** the already-cut design operations (`alreadyCutOperations`, `src/core/design/already-cut.ts`): every operation of a listed unit (a feature's owned operations too), and the roughing pass of a cut operation (its material went first). **Dependants are not cut**: a pocket `on` a cut pocket's floor or a chamfer on its edge is new work. A plan operation is cut when it machines design operations and all of them are already cut (`cutTest`, `src/core/plan/cut.ts`); an alignment aid never is.
- `PartDTO.alreadyCutMarks?: Record<id, { by: 'hand' | 'run', at, fingerprint? }>` (C2) – who set each listed id's mark and when (ISO time, main's clock). A run mark also keeps the unit's **fingerprint** (`unitFingerprint`: a hash of the unit's features and operations without their names, taken from the run's plan's design copy), so an edit of what the run cut shows ([§ Editing](#editing-an-already-cut-operation)). A mark goes with its id (the same follow hook); a list written before C2 has none (read as by hand, no date). Optional, no `schemaVersion` change. Neither list enters the toolpath input hash.

## Marking

**By hand** (Design): the row menu of a top-level row **Mark as already cut** / **Mark as not cut** (before Disable), one `design.part.update { alreadyCut }` and one undo step; the same mark is the inspector's **Already cut** switch (C3) of a top-level operation or feature. The row stays in the list with its name muted and a check marker **Cut** ([ui.md](../conventions/ui.md#feature-rows-and-add)); everything else about it is unchanged: it is in the 3D model, its checks run, Chamfer and Make Clones… build on it.

**From Run** ([Q196](#questions-for-the-user), C2), using the run's own record (`lastRun`: the job's plan, setup, `planHash`, each operation's first line in the streamed program and where it ended – the record [run-recovery.md](run-recovery.md#what-dfyom-keeps) resumes from), sets the same design mark, **by run**, on the top-level units whose design operations the run's finished operations machined in full ([§ Implementation (C2)](#implementation-c2)):

| Run ends                                                       | Marks                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `done` on a real machine, program unchanged (`planHash` equal) | Every design operation of the program, automatically; the run section says "Marked 5 operations as already cut in Design." with their names and **Undo**.                                                                                                                                                                                                                                                                                                                                                                            |
| `stopped` or `interrupted`                                     | None automatically. Once no resume is pending (a stop: at once; an interruption: when the recovery panel is dismissed), the run section asks "Mark the 2 finished operations as already cut?" listing those that ended before the earliest operation the machine may still have been executing (the operation M5's resume starts at). The operation in progress is never marked ([Q197](#questions-for-the-user)). Not offered while the recovery panel waits, since marking changes the program and line resume needs it unchanged. |
| The virtual machine, or a file run                             | None (practising; a file has no plan).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| The plan changed since the export (`planHash` differs)         | None; the sheet says why and points to marking by hand.                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |

**Plans:** the mark is a design change like any other ([plans are snapshots](plan-v0.1.md#plans-are-snapshots)): a `draft` plan follows on Apply; a `settledDesign`, `finalized` or `inUse` plan keeps its copy (and shows the design as changed) until rebuilt. A new plan starts with it.

## What a cut operation means in its plan

- **Locked.** Tool, feeds, strategy and order are read-only (`plan.status` refusal, rule `cut`, "Pocket 2 is already cut; mark it not cut in Design to change it"); a setup holding one is not split, merged or moved. Design edits reach it as usual ([§ Editing](#editing-an-already-cut-operation)).
- **Not in the program.** Export, the program's time, the tool runs and tool changes leave it out; a tool run with only cut operations disappears; a setup whose operations are all cut has no program (`plan.check`, rule `allCut`, "Top is cut: every operation is already cut"). Its toolpath is still generated (cached as today, never exported) because later calculations read it; the mark is not in the toolpath input hash, so marking regenerates nothing.
- **Still removed material.** It keeps its place in the machining order, so everything that reads earlier operations sees its removal unchanged: the [material bands](plan-v0.2.md#material-left-for-later-cuts-df61) (later passes start at its floor; partial coverage of pockets cut by area), through depths and openings, the [roughing rest](roughing.md), the [safe links' stock height field](safe-links.md#in-process-stock-height-field) (links dip into its cleared air; the link into the first uncut operation starts from the uncut one before it), the [Z reference](z-reference.md) flat patches (a cut facing's floor is a valid touch-off surface; the raw top it removed is not), and alignment points on [already-cut features](alignment.md#validity-already-cut-and-reachable).
- **Cut first.** Within a setup the cut operations count as machined before every uncut one (the physical truth: they are done), so a rebuild puts them first in their order (an `on` dependency still comes first). New work never goes into a setup before the last setup with cut operations: it gets a new setup at the end ([§ Setups](#setups-and-work-zero)); an uncut operation left in such a setup warns `plan.cutSetupOrder` ("Drilling 1 on Top is not cut, but Bottom is: cutting it needs the part flipped back").
- **Findings.** A cut operation keeps its errors (they block the removal later operations read) and drops its warnings and infos.
- **Display** ([Q200](#questions-for-the-user)). The row is muted with a check and **Cut**; its toolpath is hidden in the viewport unless **Show cut toolpaths** (the Toolpaths group, shown when the plan has cut operations) is on. Plan and Run draw the **in-process stock** around the part: the blank with the cut operations' material gone ([§ In-process stock display (C5)](#in-process-stock-display-c5)).

## Run (DF137)

Run shows and streams exactly the export (dogfood TG #454: Run drew the cut pocket's toolpath with no way to hide it). The program `run.job.check` and `run.job.start` stream is `exportPlan`'s, so a cut operation is never streamed, the gCode panel, Start at, the time and the tool waits are the export's, and a section resume at a cut operation is refused (`input.malformed`, rule `unknownOperation`). The run mode around it follows the same rule, from the plan's design copy (`cutTest`, as Plan):

- **Scene.** The toolpaths are linked over every operation (as the export links them), then the cut ones are left out: Run draws the lines Plan draws with **Show cut toolpaths** off. Run has no such switch; playback follows the program.
- **Tools.** The pre-flight's tool list, "Resume at" and the workholding guard's tool numbers (by first use in the program) skip cut operations.
- **Setups.** Run starts on the first setup with an uncut operation, and a run's next setup (the setup-change prompt, `run.job.start`'s `next`) skips setups cut in full, which have no program.
- **Stock (C5).** The in-process stock as in Plan, always (no switch): [§ C5](#in-process-stock-display-c5).

A plan that is not a draft keeps its copy of the mark (a snapshot, [§ What is stored](#what-is-stored)): Plan, Export and Run then all still cut the operation until the plan is rebuilt, so the three agree either way.

## A new blank (Q199)

The marks describe the one stock of the design ([Q199](#questions-for-the-user)); cutting the design again on a new blank starts by clearing them.

- **Design: Clear cut marks** in the [part menu](../conventions/ui.md#part-menu-split-parts-s0) and the part row's context menu ("For a new blank: every operation is cut again. Undo brings the marks back."): one `design.part.update { alreadyCut: [] }`, which drops the marks' sources and dates too, one undo step, with the undo toast "Cleared 2 cut marks". Disabled with the reason "Nothing in this part is marked already cut." while there are none. Clearing **some** marks is the row menu's Mark as not cut (one row, or the multi-selection's Mark N as not cut, [§ Implementation (C3)](#implementation-c3)).
- **Run's pre-flight**, when every operation of the chosen setup is already cut (the plan's design copy, so the setup has no program): instead of Start at and the soft-limit check, a note "Everything in Top is marked already cut. Cutting a new blank? Clear the marks to cut it all again." with **Clear marks**; Start stays disabled ("Nothing to cut in Top: every operation is marked already cut."). Clear marks clears the part's marks in Design as above; a **draft** plan then follows at once (`project.apply`, as starting a run would) and the pre-flight checks the whole program. A plan that is **not a draft** keeps its copy ([§ Run](#run-df137)), so the note says "Plan 1 (Finalized) keeps its own copy of the marks: after clearing them, rebuild it in Plan (Settled design, then Rebuild)."; once cleared in Design, "The marks are cleared in Design. Plan 1 keeps its own copy until it is rebuilt in Plan …" without the button. A real machine runs only finalized plans, so the new blank of a finalized plan goes through Plan: the plan is a verified snapshot and Run does not rebuild it behind the user's back.
- **Agents:** `design.part.update { partId, alreadyCut: [] }` (no new tool, [§ Agent API](#agent-api)).

## Planning new work on the cut part

The user's flow: plan 2 was cut. In Design, Pocket 2 (and the facing) are marked already cut; then the user adds the pocket `on` Pocket 2's floor, the chamfer on its edge, a hole. A `draft` plan (plan 2 itself, or a new plan) follows: the new operations are placed after the cut ones; their toolpaths start from the material left: the pocket from Pocket 2's floor (its `on` level, and DF61's band for anything stacked), the hole's drilling cycle from the band's top, the chamfer at its edge's face; the links over Pocket 2 use its cleared air. Its export holds only the new operations. No "continue" copy of a plan is needed ([Q194](#questions-for-the-user)).

## Model: in-process stock from cut operations

[Q195](#questions-for-the-user). The choice is how later operations learn what the cut ones removed.

| Model                                                                                                                 | Exact?                                                                          | Cost                                                                                                                                                            | Covers the user's case                                          |
| --------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| **(1) Operation-level removals** (chosen): cut operations stay in the order as removals                               | Analytic regions and floors; partial coverage only for pockets (DF61)           | None new: bands, rest, links and Z reference already read earlier operations. Cut toolpaths are generated once and cached (the links field needs them today).   | Yes: a pocket on its floor, a chamfer on its edge, a hole in it |
| (2) Height map per setup: the [simulated cut](deviation.md#height-map-method) of the cut toolpaths as the start stock | Sampled (0.1–0.5 mm cells), credits any shape and partial passes                | Every generator would need a height-map input (none has one); the toolpath job depends on every earlier move; simulation per setup in the job (up to 4 M cells) | Yes, at a higher cost                                           |
| (3) Removed-region stack via the 2D ports: union of (region, floor) per cut operation                                 | Exact in 2D, more general than bands (partial coverage of facings and profiles) | A new model and its tests; bands would become its special case                                                                                                  | Yes                                                             |

(1) needs no new geometry; (2) is still useful for the **display** of the in-process stock and as the test oracle (`airCut`, `heightDifference` in `src/core/toolpath/testing/region-coverage.ts`); (3) is the follow-up when the bands' "partial coverage gives no band" leaves air passes over a cut operation the user notices.

**Performance:** (1) adds no work to a plan with no cut operations; with cut ones, their toolpaths are generated as before (cached by input hash, which the mark does not enter) and skipped at export. No new per-move cost.

## Setups and work zero

- **Same setup, part still clamped:** the new operations join the setup after its cut ones; the controller's G54 still holds; Run starts the setup's program as usual.
- **Part removed and re-clamped:** the setup-change prompt asks to re-zero as for any setup ([alignment.md](alignment.md)); alignment points on already-cut features (Pocket 2's walls) locate the part; the Z reference of the first tool run is a surface that still exists (the faced top or a cut floor, [z-reference.md](z-reference.md)), never the raw top a cut facing removed (`plan.zRefGone`, error).
- **Flipped part:** new operations of a direction whose setup comes before the last setup with cut operations go into a **new setup appended at the end** (e.g. Bottom · Top cut, then "Bottom 2" for the new bottom pocket): the part must be flipped back, and the DF61 bands already chain opposite-direction cuts of earlier setups. The safe links' field still starts flat at Z0 in each setup ([Q104](safe-links.md#open-questions-for-the-user)), the safe side.

## Editing an already-cut operation

([Q198](#questions-for-the-user), decided by the user's TG #447.) Editing is allowed and raises no finding: the mark describes the stock, so an edit **re-describes what is already gone** (the user may be fixing the design to match the part, or describing a stock that arrived with a pocket). The plan follows as for any design edit and still exports nothing for it.

- **C2:** an operation marked **by Run** warns when its geometry is edited afterwards (`plan.cutChanged`, warning: "Pocket 2 changed since the run cut it", kept on the cut operation like the other cut findings), since the run's record says what the machine really removed; Design's marker reads **Changed**, with the run's date in its tooltip. A rename does not warn; an edit back to what was cut clears the warning. Marks set by hand never warn.
- **C4:** the edited run-marked operation is **cut again for the difference**: the plan cuts only what the edit adds to what the run removed ([§ Cutting only the difference (C4)](#cutting-only-the-difference-c4)).
- **Removed from the design:** its id leaves the list; the plan no longer knows that material is gone (new work over it may cut air, never too little).
- **Disabled in Design:** out of the model as any disabled item; its mark stays and counts again when it is enabled.

## Cutting only the difference (C4)

Status: accepted by delegation (DF135 C4, decided with the implementation following this doc's model choice Q195 (1) and Q198 as revised). The user deepens or widens Pocket 2 after a run cut it; the plan should cut 6–8 mm (or the added ring), not the whole pocket again in the air, and never less than the edit asks for.

- **Which marks.** A **run** mark whose unit was edited since (`plan.cutChanged`) and that keeps the **as-cut geometry**. A hand mark still re-describes the stock (Q198: no finding, nothing cut). A run mark written before C4 has only the fingerprint: it stays cut and warns as in C2 ([pre-alpha](../conventions/error-handling/migrations.md#pre-alpha-exception-no-data-preservation-yet), no migration).
- **What is stored.** `CutMarkDTO.asCut?: OperationDTO[]` – the unit's design operations (a feature's owned ones too; roughing passes not, they remove nothing a finishing pass does not) as the run's plan's design copy had them, written with the run mark. Optional, no `schemaVersion` change.
- **Recut units** (`recutUnits`, derived): listed, run-marked with `asCut`, fingerprint changed. Their operations are **not already cut** (`alreadyCutOperations` leaves them out): the plan operation is unlocked, in the program, its tool run and time count, Run streams and draws it. `plan.cutChanged` stays a warning, "Pocket 2 changed since the run cut it: the plan cuts only the difference".
- **The as-cut removal** (`src/core/plan/as-cut.ts`). The stored operations, evaluated in the plan's part in place of the unit's current ones (the surfaces they stand on as the design is now), become **hidden removals** in the machining order just before the unit's first plan operation (same setup): the [material bands](plan-v0.2.md#material-left-for-later-cuts-df61), a pocket's partial coverage, through depths and openings read them like any earlier cut, and so do the [Z reference](z-reference.md)'s flat patches (its floor is no touch-off surface: the tool that cut it is not known; a surface it cut away is gone, so the touch-off spot is never in the old pocket). So a deepened pocket starts at the old floor (band top), a widened one cuts the added ring down to the old floor and the whole region only below it (partial coverage), a deepened blind profile starts at its old depth. An as-cut **drilling** clears its hole's full diameter disc down to its depth (not the tip cone; through holes not) – for as-cut drillings only, so no other plan changes. The removal counts for operations after it; earlier ones (an uncut operation in an earlier setup) do not see it: they cut more air, never less material.
- **Nothing below the cleared level.** When a recut pocket's partial coverage, an as-cut removal among it, is cleared down to its own floor (the widened pocket, the old one as deep), the whole-region pass at that floor is dropped: the uncovered part is cut down to the floor already, the rest is cleared to it (it would only re-trace the old floor in the air).
- **Safety.** The removal is the region the as-cut operation's design describes (a pocket's region inset by its floor fillet, a slot, a disc), never the toolpath's: what a run really left (finishing allowance, cusps) is no less. The safe links' stock height field does not read it (links stay higher over the old pocket: the safe side). Rapids into the old pocket follow DF61's band rules as for any stacked cut.
- **The input hash** takes the recut units' `asCut` (only when there are any: every other plan keeps its hashes), so a recut operation and everything after it regenerate when it starts or stops being recut.
- **Re-marked by the next run.** A run that finishes a recut unit marks it again (by run, the new date, fingerprint and `asCut`): `design.part.update { alreadyCut, cutByRun, recut: [ids] }` (the listed ids the run cut again; `finishedUnits` returns them with the new ones). By hand: Mark as not cut, then Mark as already cut (a hand mark).
- **Edits inside what was cut** (shallower, smaller, moved within it): the operation is recut but has nothing left to cut; its toolpath keeps the generators' one pass at the floor (in air). To re-describe the stock instead, mark it by hand.
- **What it covers:** the cuts the removal model already has – facings (a deeper facing starts at the old depth), pockets (deeper, wider, both), blind profiles (deeper), openings, and blind drillings (deeper, the same or a smaller Ø at the same centre).
- **Not in C4:** the as-cut removal in the safe links' field, as-cut named shapes (the shape as it is now is used, as in the fingerprint), crediting partly cut recut operations (Q197). Edge operations, engravings and through holes: [§ Edge operations, engravings and through holes](#edge-operations-engravings-and-through-holes-c4-follow-up); hand marks: [§ Hand marks](#hand-marks-keep-no-as-cut-geometry-c4-follow-up).

### Hand marks keep no as-cut geometry (C4 follow-up)

Status: accepted by delegation (DF135 C4 gaps, 2026-11-27). Could **Mark as already cut** by hand store the unit as it is when marked (`asCut`), so a later edit cuts the difference to it? **No**: a hand mark keeps re-describing the stock.

- **Why.** Q198 is the user's decision (TG #447): an edit of a hand-marked operation re-describes what is already gone ("if my stock already has something … I can specify it"). The common hand-mark flow is mark, then correct the dimensions to match the real part (or a stock that arrived with a pocket); a snapshot taken at marking time would turn that correction into a recut of a shape the user just said was wrong. A run mark knows what the machine removed (the run's plan copy); a hand mark knows only what the user says now.
- **To cut more on a hand-marked operation:** add the new work as its own operation (a pocket `on` its floor, a wider pocket around it: C1's bands and partial coverage count the marked one), or Mark as not cut and cut it in full. The same holds after a DFYOM program ran outside Run (a file run makes no run mark).
- **Later, if the user asks:** an explicit "Cut the difference from here" on a hand mark (the snapshot taken when asked, not when marked); not built.

### Edge operations, engravings and through holes (C4 follow-up)

Status: accepted by delegation (DF135 C4 gaps, 2026-11-27). A recut chamfer, Line (an engraving's grooves are Lines) or through hole cuts only the difference where the existing removal model expresses it exactly; otherwise it is cut in full again, as before (more air, never less material).

The recut operation's **as-cut twin** is its as-cut removal (`asCutRemovals`) of the same id. It counts only when it describes the same cut with less depth or width, compared field by field on the geometry: for a Line the same centrelines (placed shapes, `on` level, cell, face) and cutter (the design's tool), and the plan's tool has the cutter's shape (`isCutter`; another tool may be wider than the old groove: cut in full); for a circular chamfer the same edge (edge operation, axis, edge Ø, `on` level) and angle, neither stepped; for an edge chamfer the same edge (shape, side, depth, cell, chosen loops, tabs) and angle. The twin then gives the recut operation a **material top** (the plan's material band, `MaterialBand.top`, as for pockets and holes): the level down to which the run already cut along the cut's own surface. Nothing else reads it: other operations do not see these twins (their removal is no region), and the safe links' field does not either.

| Operation                                          | Material top from the twin                                | What the recut cuts                                                                                                                                                                                                                                                                     |
| -------------------------------------------------- | --------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Line, deeper** (V-bit, ball, flat, tapered ball) | `on` − the twin's shallowest depth along any of its lines | The depth passes from that level down: a pass nowhere below it is dropped (the last pass is always kept); the first kept pass starts with the floor already cut at that level, so its ramp-back (or plunge) begins there, in the old groove. Each kept pass takes at most one stepdown. |
| **Circular chamfer, larger**, contour              | `on` − the twin's depth                                   | The same ring (it depends on the edge Ø and the tip only), entered down to the old depth in the hole and old cone, then ramped from there to the new depth.                                                                                                                             |
| Circular chamfer, plunged                          | –                                                         | Unchanged: one plunge at the centre already meets only the added band.                                                                                                                                                                                                                  |
| **Edge chamfer, wider**, one ring (E1)             | `on` − the twin's depth                                   | Unchanged: the ring is the edge's air ring at the new depth; its cone meets only the added band.                                                                                                                                                                                        |
| **Edge chamfer, wider**, in levels (E4a)           | `on` − the twin's depth                                   | The levels' inner (rough) rings whose cone lies wholly in the old bevel are dropped; every bevel ring (it reaches the new width) is kept, with its corner lifts and its entry from the air ring.                                                                                        |
| Stepped chamfer (F7)                               | –                                                         | In full: the terraces of a new depth do not line up with the old ones.                                                                                                                                                                                                                  |
| **Through hole, larger**                           | –                                                         | Unchanged: a drill cycle or one helix at the new Ø through the full extent already meets only the ring around the old hole, and that ring runs the whole depth (nothing to drop). The same for a through profile that is not an opening (openings are in C4).                           |
| Surfacing, V-carving (3D)                          | –                                                         | No such operation kind exists yet (a facing is in C4). When they come, in full: their removal is a height field, not a region or a depth (Q195 (2)).                                                                                                                                    |

**Why it is safe** (each against the run's as-cut design, as the rest of C4):

- **Line:** a cutter whose radius never shrinks upwards (all four kinds) at the same XY with its tip higher than where the run's same cutter was lies inside the run's groove, so every dropped pass is in the air; the finished groove is set by the last pass, which is kept. The twin's shallowest depth is used for every line, so a groove that varies in depth is never credited deeper than it was anywhere. The groove counts as cut by the Line's cutter (the design's tool, which the plan ranks first); had the run's plan used a narrower tool than the design's, its groove is narrower and the first kept pass meets more than one stepdown – never a gouge (the finished groove is the last pass's).
- **Circular chamfer, contour:** the ring's tool axis is dt/2 inside the edge; its cone at tip depth z reaches z·tan(α/2) beyond the edge at the face, inside the old cone while z ≤ the old depth – for any tip Ø, so also when the run used another chamfer mill.
- **Edge chamfer levels:** the old bevel is every point whose distance to the edge's air is at most (d₁ − depth)·tan(α/2) (its design, as a DF61 region is a pocket's design, not its toolpath). A ring at offset o into the air (negative: into the material) and tip depth z lies inside it when its cone's reach at the face, z·tan(α_tool/2) + dt/2 − o, is at most the old width w₁ and, at the tip, dt/2 − o ≤ (d₁ − z)·tan(α/2) (both ends of the flank, so a tool angle within the angle tolerance of the chamfer's is covered).
- **Entries:** the first kept Line pass and the chamfer ring go down at the plunge rate (never a rapid) through air: the old groove, or the hole and old cone. A kept E4a ring keeps its entry from the level's air ring, across rings dropped because they lie in the old bevel.

**Edits inside what was cut** (a shallower Line, a smaller chamfer): as for pockets, the recut keeps one pass – a Line its last pass, a chamfer its ring – in the air.

## In-process stock display (C5)

Status: accepted by delegation (DF135 C5; the slice row's "height map of the cut toolpaths", decided with the implementation). The user sees the partly cut blank: the material the next cut really meets, apart from the toolpaths still to run.

- **What is drawn.** The raw blank less what the plan's **already-cut** operations (`cutTest` on the plan's design copy, every setup) remove, as a solid in the part frame, around the part. Cut operations come first in the machining order ([§ What a cut operation means](#what-a-cut-operation-means-in-its-plan): cut first), so this is the stock every uncut operation of every setup starts from: one solid per plan, the same in each setup.
- **The removal: the simulated cut of the cut toolpaths** – the [deviation](deviation.md#height-map-method) cut map (`simulateHeightmap`: real tool profiles, machining order, setups of one direction on one map), fed only the cut operations' own toolpaths (Q195 (2) for display, as [§ Model](#model-in-process-stock-from-cut-operations) planned). Not the 2D removal model: bands and regions have no partial passes and no tool shape, the toolpaths are what the machine cut.
- **The solid.** From the `+z` and `−z` maps (the bottom map read mirrored, `faceToFace`): per column the material between the bottom map's top and the top map's; top and bottom are smooth height fields on the cell centres (the outermost vertices on the stock's sides) joined by four side walls; a column with no material left is empty (a through cut shows no inner wall). Cell 0.5 mm, coarser above 150 000 cells per map (√(L·W / 150 000), in 0.05 mm steps).
- **When.** The plan has cut operations and each has a toolpath (cut toolpaths are generated with the plan, as before); while one is missing nothing is drawn (a raw blank would be wrong). A **stale** cut toolpath (new work on its floor changes its inputs) is drawn as last generated, as Plan draws outdated toolpaths.
- **Where it runs: in the window**, not the compute worker. The window already holds the toolpaths it draws, the display is derived from what one window shows ([workers.md](../architecture/workers.md#what-runs-on-a-worker): renderer-local work), and it is fast: the cut part of the core test (80 × 50 mm, a facing and a pocket, 160 × 100 cells) takes **13 ms** for map and solid (64 000 triangles). It runs after the toolpaths are read, off the render, and is cached by its input (cut toolpaths, stock, setups, zeros): a mode or setup switch, a selection or an edit that leaves the cut toolpaths alone reuses it. A renderer Web Worker is the next step if a plan's cut toolpaths ever take frames (none exists yet).
- **How it looks** ([ui.md § Plan mode](../conventions/ui.md#plan-mode-task-37)): a translucent `--vp-stock` solid (40 %, no depth write, offset over the part's own faces, never picked) around the opaque part: the part stays visible inside, the material still on it reads as a neutral haze, the cut pocket as clear; the toolpaths still to run are drawn over both as usual. Neutral, no accent.
- **Plan:** a **Show in-process stock** switch in the Toolpaths group under Show cut toolpaths (shown when the plan has cut operations, per window, **on** by default). **Run:** always drawn (Run has no switches, [§ Run](#run-df137)). The view summary says "In-process stock shown: the material left after 2 already-cut operations."
- **A recut operation's as-cut removal** (C4 follow-up, accepted by delegation 2026-11-27): it has no toolpath of its own, so its regions are stamped into the cut maps after the simulation – a facing's face, a pocket's region (inset by its floor fillet), a blind profile's slot and a blind hole's disc, each lowered to its floor, an opening's interior through (the regions C4 counts, `asCutRemovals`, in the ±z maps; a stamp only lowers). The old pocket then shows as cleared before the recut runs, and a recut unit with nothing else cut draws the stock too. An as-cut chamfer or Line has no region: its material shows as still there (the safe side).
- **Not in C5:** side setups' (±x, ±y) removal (the solid is a Z height field; their material shows as still there); as-cut chamfers and Lines; inner walls of through cuts; the in-process stock as an input to generation (Q195 (1) stays the model).

Choices made with the implementation:

- **Run marks only, with their geometry stored.** The fingerprint cannot be turned back into a shape, and the run's plan copy is gone once the plan is rebuilt, so the mark keeps the unit's operations (`asCut`); hand marks re-describe (Q198). Pre-C4 run marks keep C2's behaviour (pre-alpha, no migration).
- **Evaluated now, not then:** the as-cut operations are evaluated in the plan's part as it is (in place of the unit's current ones), so `on` surfaces and formulas resolve against today's design; a unit whose as-cut operations no longer evaluate is cut in full again (more air, never less material).
- **Placed before the unit, not before everything:** the removal counts from the unit's first plan operation on (C1's rule: cut work keeps its place in the order); an operation earlier in the order cuts more air, never less material.
- **The regions the design describes**, as for every DF61 removal (a pocket inset by its floor fillet); never the toolpath's sweep.
- **The dropped whole-region pass** only where an as-cut removal is part of the coverage (`PartialCover.asCut`): other partly cleared pockets cleared to their floor keep DF61's pass at the floor (it re-traces cleared floor too, but changing it would change existing programs, e.g. the v0.3 exit-criteria flow); every existing snapshot and golden stays byte-equal.
- **Undo after a run** takes back only the units the run added; a recut unit keeps its new mark (without any it would be cut in full again), Design's undo restores the old one.
- **Not in C4:** see [§ C4](#cutting-only-the-difference-c4) – the links' field, as-cut named shapes; edge operations, engravings and through holes in the follow-ups below.

Code: `src/core/plan/in-process-stock.ts` (`inProcessStockInput`: the cut operations' toolpaths per setup with their tools and zeros, `none` / `waiting` / `ready` with a cache key; `inProcessCell`; `inProcessStockMesh`: the ±z solid; `meshVolume`), renderer `modes/plan/useInProcessStock.ts` (reads the cut toolpaths, again after a generation; simulates and builds off the render; a small cache by key), `modes/plan/usePlanScene.ts` (with the zeros the plan reports, while the switch is on), `modes/run/useRunScene.ts` (always), `viewport/InProcessStockLayer.tsx` (drawn by `RunLayer` in the part frame, outside the setup frame; `RunScene.inProcessStock`), the Viewport's summary sentence and `data-in-process-stock` (the count, for tests), Plan's switch in `PlanNavigator.tsx` (`showInProcessStock` in the plan store). No command, schema, worker task or `tools/list` change. Tests: `plan/in-process-stock.test.ts` (only the cut operations, in order, the uncut new pocket left out and not waited for; waiting without a cut toolpath, a stale one drawn and flagged; the pocket floor and the faced top in the map; the solid's volume within 1 % of the faced block less the pocket; the cell budget; the bottom map mirrored and a column cut through empty; the raw block closed and wound outwards), `Setups.test.tsx` (the switch on by default, the scene's stock of one operation, off removes it; axe both ways), hidden e2e `cut-state.e2e.ts` (Plan: the switch, `data-in-process-stock="1"`, off and on again; Run: the same beside the program's lines; with `DFYOM_C5_DIR` the screenshots `c5-{plan,run}-{light,dark}.png`).

Choices made with the implementation:

- **One solid per plan**, not per setup: cut operations are first in the order, so every setup starts from all of them; the setup's frame only places its toolpaths.
- **The window, not the worker**, measured (13 ms); the deviation command's worker task stays for the agent-facing compare.
- **Stale cut toolpaths are drawn** (flagged `outdated` in the input, not dimmed): hiding the stock exactly when new work is added on a cut floor would hide it when the user needs it.
- **The zeros:** Plan passes the setups' work zeros from the plan's answer (those the toolpaths were made at); Run uses the core's own (`setupAlignment`, as its scene frame does).
- **Translucent over the opaque part** rather than replacing it: the finished shape and the material left are both visible, and drawing needs no boolean of part and stock.
