# Cut state: what is already cut, and planning new work on the cut part

Status: accepted (accepted by delegation D84, Q193–Q200 take their recommendations; hardening [DF135](../plans/hardening.md#intake-user-feedback-goes-here), the user's TG #442 after a successful real cut of "plan 2": "Seems like marking a cut as completed isn't implemented yet. I want to add another operation to the resulting shape that respects existing geometry, e.g. a chamfer, another pocket in Pocket 2's floor. Without cutting Pocket 2 again in the air in a new plan."; questions [Q193–Q200](#questions-for-the-user) open) · Base: [plan-v0.1.md § Plans are snapshots](plan-v0.1.md#plans-are-snapshots), [§ Plan status](plan-v0.1.md#plan-status), [plan-v0.2.md § Material left for later cuts (DF61)](plan-v0.2.md#material-left-for-later-cuts-df61), [plan-v0.4.md § Disabling in a plan (DF106)](plan-v0.4.md#disabling-in-a-plan-df106), [roughing.md](roughing.md) (rest by the roughing tool's reach, Q143), [safe-links.md § In-process stock height field](safe-links.md#in-process-stock-height-field), [z-reference.md](z-reference.md), [run-recovery.md § What DFYOM keeps](run-recovery.md#what-dfyom-keeps) (the run journal), [alignment.md § Validity: already cut and reachable](alignment.md#validity-already-cut-and-reachable), [deviation.md § Height map method](deviation.md#height-map-method) · Agent API budget: [llm-api.md](../architecture/llm-api.md) · Data rule: [migrations.md § Pre-alpha](../conventions/error-handling/migrations.md#pre-alpha-exception-no-data-preservation-yet) · Terms: [glossary.md](../glossary.md)

DFYOM does not know what has been cut. A plan is a snapshot of the design and its program always cuts every operation from the raw stock. After a real cut the user wants to add work to the finished shape (a chamfer on an edge already cut, a pocket in Pocket 2's floor, a hole) and get a program that cuts **only the new work**, starting from the material that is really left.

Today's nearest tool, **Disable in this plan** ([DF106](plan-v0.4.md#disabling-in-a-plan-df106)), does the wrong thing: it removes Pocket 2 from the plan as if it had never been designed, so its removal is gone from every later calculation, and every operation that builds on it (the new pocket `on` Pocket 2's floor, a chamfer on its edge) is switched off with it.

## Goals and not goals

- **Goal:** mark plan operations as **cut** (one operation, a setup, the whole plan), by hand and from Run when a run completes; a cut operation is locked, not in the program, and still counts as removed material for everything after it; a **continuing plan** takes the marks to new work on the same workpiece; edits to a cut operation in Design afterwards are caught.
- **Not goals (here):** a general 3D in-process stock for generation (the [model choice](#model-in-process-stock-from-cut-operations) keeps the existing 2D removal model); several physical workpieces per plan (one plan = one workpiece, [Q199](#questions-for-the-user)); crediting a partly cut operation ([Q197](#questions-for-the-user)).

## How other CAM handles it

Summary from their public docs and UI as we know them; not re-checked for this draft.

| Program        | What it offers                                                                                                                                                                                                                                                                      | Lesson for DFYOM                                                                                                                                   |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| Fusion         | A setup's stock can come **from the preceding setup** (the simulated in-process stock); adaptive and other strategies have **rest machining** from previous operations or setups; operations can be suppressed or protected from regeneration; post a selection of operations only. | The stock model is 3D simulation for 3D CAM. The workflow – new operations "from previous" and post only the new ones – is what the user asks for. |
| Carbide Create | No in-process stock: each toolpath has an enable checkbox and a **start depth**; to add work to a cut part you disable the done toolpaths and set start depths by hand.                                                                                                             | Disabling the done work is the common hobby workaround; DFYOM can do the start depth for the user from the cut operations.                         |
| Estlcam        | No stock model either; parts and their depths are set by hand (a start depth), the order and which parts to export are chosen per program.                                                                                                                                          | As above: the user carries the state in their head.                                                                                                |

DFYOM sits between: no 3D simulation for generation, but it already knows each operation's removal and its machining order ([DF61 material bands](plan-v0.2.md#material-left-for-later-cuts-df61)), so "already cut" can be one flag per operation.

## Terms

| Term                 | Meaning                                                                                                                                                                                                |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Cut** (mark)       | A plan operation whose material is already gone on the plan's workpiece. Stored per plan operation; locked; not in the program; still a removal for later operations. Glossary row: **Cut operation**. |
| **Continuing plan**  | A new plan for more work on the workpiece another plan cut: a copy of that plan with its cut marks, following the current design ([§ Continuing plan](#continuing-plan)).                              |
| **In-process stock** | As in the [glossary](../glossary.md): here the material left after the cut operations.                                                                                                                 |

## What is stored

- `PlanOperationDTO.cut?: { at, by: 'user' | 'run', hash, operations? }` – optional, absent = not cut ([pre-alpha](../conventions/error-handling/migrations.md#pre-alpha-exception-no-data-preservation-yet): no `schemaVersion` change, no migration). `at` the time, `by` who marked it, `hash` the hash of the plan operation's design operations **as cut** (the snapshot's DTOs, as the [stale indicators](plan-v0.1.md#plans-are-snapshots) hash them), `operations` (slice C3) the as-cut design operation DTOs themselves, so the plan can restore or keep them when the design changes.
- **Per operation, not per setup or plan.** "Mark setup as cut" and "Mark all as cut" set every operation's mark; a setup or plan is cut when all its operations are (derived, never stored).
- **Roughing and owned operations:** marking an operation cut also marks its roughing pass (`<id>_roughing`, [roughing.md](roughing.md)) – an owner cannot be cut without its roughing; unmarking a roughing pass unmarks its owner. Joined plan operations (drillings of one size, a feature's chamfers) are marked as one row, as they are one plan operation.

## Marking

**By hand** (Plan): the operation row menu **Mark as cut** / **Mark as not cut**; the setup row menu **Mark setup as cut**; the plan menu **Mark all as cut** and **Clear cut marks** (asks: "Clear the cut marks of 7 operations? Their material counts as uncut again and they return to the program."). Each is one command and one undo step, announced ("Pocket 2 is marked cut").

**From Run** ([Q196](#questions-for-the-user)), using the run's own record ([run journal](run-recovery.md#what-dfyom-keeps): the job's plan, setup, `planHash` and operations in order, the acknowledged and executing lines):

| Run ends                                                       | Marks                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| -------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `done` on a real machine, program unchanged (`planHash` equal) | Every operation of the program, automatically; a toast "Marked 5 operations of Top as cut" with **Undo**.                                                                                                                                                                                                                                                                                                                                                                                 |
| `stopped` or `interrupted`                                     | None automatically. When the recovery panel is dismissed or a stopped run's sheet closes: "Mark the finished operations as cut?" listing those whose last line was **executed** (before the executing estimate's lower bound, as [run-recovery.md](run-recovery.md#choosing-where-to-resume)). The operation in progress is never marked ([Q197](#questions-for-the-user)). Not offered while a resume is possible, since marking changes the program and line resume needs it unchanged. |
| The virtual machine, or a file run                             | None (practising; a file has no plan).                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| The plan changed since the export (`planHash` differs)         | None; the sheet says why and points to marking by hand.                                                                                                                                                                                                                                                                                                                                                                                                                                   |

**Statuses:** marking is allowed in every status but `archived`. It is a record about the workpiece, not a plan edit: an `inUse` or `finalized` plan takes it without stepping back.

## What a cut operation means in its plan

- **Locked.** Tool, feeds, strategy, order and Z reference are read-only (`plan.status`-like refusal, issue `plan.cut`, "Pocket 2 is cut; mark it not cut to change it"). Design edits reach it as usual (a `draft` follows the design) and are caught by [§ Editing a cut operation](#editing-a-cut-operation-afterwards).
- **Not in the program.** Export, run, the program's time, the tool runs and tool changes leave it out; a tool run with only cut operations disappears; a setup whose operations are all cut has no program ("Top is cut") and Run skips it. Its toolpath is still generated (cached as today, never exported) because later calculations read it.
- **Still removed material.** It keeps its place in the machining order, so everything that reads earlier operations sees its removal unchanged: the [material bands](plan-v0.2.md#material-left-for-later-cuts-df61) (later passes start at its floor; partial coverage of pockets cut by area), through depths and openings, the [roughing rest](roughing.md) (a cut roughing pass still clears for its owner), the [safe links' stock height field](safe-links.md#in-process-stock-height-field) (links dip into its cleared air), the [Z reference](z-reference.md) flat patches (a cut facing's floor is a valid touch-off surface; the raw top it removed is not), and alignment points on [already-cut features](alignment.md#validity-already-cut-and-reachable).
- **Cut first.** Within a setup the cut operations count as machined before every uncut one (the physical truth: they are done), so a continuing plan's order is cut operations in their original order, then the rest. A plan whose marks leave an uncut operation in a setup **before** a setup with cut operations warns `plan.cutSetupOrder` ("Drilling 1 on Top is not cut, but Bottom is: cutting it needs the part flipped back"); a continuing plan moves such operations into a new setup at the end ([§ Setups](#setups-and-work-zero)).
- **Display.** The row is muted with a check and "Cut 27 Nov" (by Run: "Cut by the run 27 Nov"); its toolpath is hidden in the viewport unless **Show cut toolpaths** is on; the inspector shows a banner with **Mark as not cut**. The viewport's stock shows the cut operations' removal as the part's current shape ([Q200](#questions-for-the-user)); slice C5 draws it from the height map.

## Continuing plan

The user's flow: plan 2 is cut (often `inUse`, so read-only); new work goes into a new plan.

- **Plan menu → Continue on the cut part…** (`plan.duplicate { planId, keepCut: true, name? }`): a deep copy of plan 2 with its setups (work zero, rotation, workholding, alignment points), tools, plan operations and **cut marks**, in status **`draft`**, so it follows the design: operations added in Design appear in it with a suggested tool after the cut ones ([auto-rebuild](plan-v0.1.md#plan-status)). Plain **Duplicate** (`keepCut` absent) clears the marks: a fresh blank.
- **Then in Design** the user adds the pocket `on` Pocket 2's floor, the chamfer on its edge, a hole; the continuing plan gets them as normal operations. Their toolpaths start from the material left: the pocket from Pocket 2's floor (its `on` level, and DF61's band for anything stacked), the hole's drilling cycle from the band's top, the chamfer at its edge's face; the links over Pocket 2 use its cleared air. Its export holds only the new operations.
- **Plan 2 stays as it was:** its marks record what it cut; re-running it on a new blank starts with **Clear cut marks** ([Q199](#questions-for-the-user)): the pre-flight of a plan whose setup is all cut says "Everything in Top is marked cut. Cutting a new blank? **Clear cut marks**".

## Model: in-process stock from cut operations

[Q195](#questions-for-the-user). The choice is how later operations learn what the cut ones removed.

| Model                                                                                                                 | Exact?                                                                          | Cost                                                                                                                                                            | Covers the user's case                                          |
| --------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| **(1) Operation-level removals** (recommended): cut operations stay in the order as removals                          | Analytic regions and floors; partial coverage only for pockets (DF61)           | None new: bands, rest, links and Z reference already read earlier operations. Cut toolpaths are generated once and cached (the links field needs them today).   | Yes: a pocket on its floor, a chamfer on its edge, a hole in it |
| (2) Height map per setup: the [simulated cut](deviation.md#height-map-method) of the cut toolpaths as the start stock | Sampled (0.1–0.5 mm cells), credits any shape and partial passes                | Every generator would need a height-map input (none has one); the toolpath job depends on every earlier move; simulation per setup in the job (up to 4 M cells) | Yes, at a higher cost                                           |
| (3) Removed-region stack via the 2D ports: union of (region, floor) per cut operation                                 | Exact in 2D, more general than bands (partial coverage of facings and profiles) | A new model and its tests; bands would become its special case                                                                                                  | Yes                                                             |

(1) needs no new geometry; (2) is still useful for the **display** of the in-process stock and as the test oracle (`airCut`, `heightDifference` in `src/core/toolpath/testing/region-coverage.ts`); (3) is the follow-up when the bands' "partial coverage gives no band" leaves air passes over a cut operation the user notices.

**Performance:** (1) adds no work to a plan with no cut operations; with cut ones, their toolpaths are generated as before (cached by input hash, so the continuing plan reuses them while the inputs are equal) and skipped at export. No new per-move cost.

## Setups and work zero

- **Per setup.** Marks are per operation; a setup is cut when all of its are. Work zero, alignment points and workholding are copied with the setup into the continuing plan.
- **Same setup, part still clamped:** the new operations join the setup after its cut ones; the controller's G54 still holds; Run starts the setup's program as usual.
- **Part removed and re-clamped:** the setup-change prompt asks to re-zero as for any setup ([alignment.md](alignment.md)); alignment points on already-cut features (Pocket 2's walls) locate the part; the Z reference of the first tool run is a surface that still exists (the faced top or a cut floor, [z-reference.md](z-reference.md)), never the raw top a cut facing removed (`plan.zRefGone`, error, slice C1).
- **Flipped part:** new operations of a direction whose setup comes before the last setup with cut operations go into a **new setup appended at the end** (e.g. Top · Bottom cut, then "Top 2" for the new top pocket): the part must be flipped back, and the DF61 bands already chain opposite-direction cuts of earlier setups. The safe links' field still starts flat at Z0 in each setup ([Q104](safe-links.md#open-questions-for-the-user)), the safe side.

## Editing a cut operation afterwards

The continuing plan is a `draft` and follows the design, so an edit of Pocket 2 reaches it. When a cut plan operation's design operations no longer hash equal to `cut.hash`:

- **Finding `plan.cutChanged`** (error: blocks export and run, because the part no longer matches the design and the plan would silently skip the change) on the operation: "Pocket 2 changed since it was cut (depth 6 → 8 mm): the part no longer matches the design." Params name the changed fields and whether the change **removes more** (deeper, larger) or **less** (shallower, smaller: the material is already gone).
- **Options** in the finding and the inspector banner ([Q198](#questions-for-the-user)):

| Option                             | Effect                                                                                                                                                                                | Slice |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----- |
| **Cut it again**                   | Mark not cut: the whole operation returns to the program (air passes over what was cut; safe).                                                                                        | C1    |
| **Keep as cut** (the part differs) | Accept: `cut.hash` takes the new value; the finding becomes the warning `plan.cutDiffers` naming the old values. For a change that removes less, or a cosmetic one.                   | C3    |
| **Restore as cut**                 | Put the as-cut operation (`cut.operations`) back into the design (one design command, one undo step).                                                                                 | C3    |
| **Cut only the difference**        | Removes more only: the as-cut operation becomes a hidden earlier removal for the edited one, so the bands start it at the as-cut floor and partial coverage cuts only the added area. | C4    |

- **Removed from the design:** a cut operation whose design operations are gone stays in the plan as a cut **ghost** from `cut.operations` (slice C3; it still counts as removed material, with the warning `plan.cutRemoved`); before C3 it is dropped as today and the finding says the plan no longer knows that material is gone (new work over it may cut air, never too little).
- **Disabled in Design or in the plan:** as removed (the material is still gone): the cut operation is kept, not parked.

## Agent API

Minimal; `tools/list` is at 118,418 of 120,000 chars.

- `plan.operation.cut { planId, planOperationIds?, setupId?, cut }` – marks (`cut: true`) or clears; no ids and no setup = the whole plan; `by: 'user'` (an agent's mark is the user's record too). One new tool `plan_operation_cut`, ≈ +0.25 K.
- `plan.duplicate { …, keepCut? }` – the continuing plan, ≈ +0.05 K.
- Read: `plan_get` lists each plan operation's `cut { at, by }` and the findings `plan.cutChanged`, `plan.cutSetupOrder`, `plan.zRefGone` (results are not in `tools/list`).
- Run marks are UI only (as the run's end sheet); an agent marks by hand after `job.wait` returns `done`.
- Total ≈ +0.3 K → about 118.7 K; measured in C1.

## Testing

- **Core, the user's case** (`plan/cut-state.test.ts`): a part with Facing 1 and Pocket 2 (40 × 30, 6 deep) on a 12 mm stock, plan 2 exported; mark all cut; continue (`keepCut`); add in Design a pocket `on` Pocket 2's floor (20 × 10, 3 deep), an edge chamfer on Pocket 2's top rim and a through hole in its floor. The continuing plan's program has no Facing 1 or Pocket 2 section and no tool run with only them; the new pocket's first level is Pocket 2's floor −stepdown; **air-cut oracle:** the height map of plan 2's program followed by the new program, every feed move of the new program cuts material except entries and links (`airCut` reports none over Pocket 2); the finished height map equals that of one plan with all operations (no material left, no overcut).
- **Marks:** setup and plan marking, roughing follows its owner, lock refusals, `inUse` takes marks, clear marks restores the program byte-equal; `plan.cutSetupOrder`; `plan.zRefGone` when the cut facing removed the raw top.
- **Edits:** a deeper Pocket 2 → `plan.cutChanged` (removes more), shallower → (removes less), export refused; "Cut it again" returns it.
- **Goldens:** every existing golden byte-equal (no plan has marks).
- **Run (C2):** loopback emulator: a run to `done` marks the program's operations; a stopped run offers the finished ones only; the virtual machine marks none.
- **UI:** row marker, menus, banner, the continue dialog; hidden e2e `cut-state.e2e.ts`: mark plan 2, continue, add a pocket in Design, export holds only it; screenshots `df135-cut-{light,dark}.png`.

## Questions for the user

Each with a recommendation; "Q193–Q200 ok" takes them all.

1. **Q193 – Where cut state lives.** (1) **On the plan's operations** (`cut` mark; the plan is one workpiece, its snapshot holds the as-cut geometry). (2) On the part in Design, so every plan sees it. (3) A separate workpiece record several plans point to. _Recommendation: (1)._ The plan already holds the setups, zero, tools and the geometry as it was cut; the design is the intent, not the physical piece, and (3) is a new concept for a case (many blanks of one plan) hobby work rarely has.
2. **Q194 – How new work picks it up.** (1) **"Continue on the cut part": a duplicate keeping the marks, in `draft`, following the design.** (2) `plan.create` with a "start from what plan N cut" option. (3) Edit plan 2 itself (back to `settledDesign`, rebuild). _Recommendation: (1)._ Two existing mechanisms (duplicate, draft follow) and one arg; plan 2 stays the record of what it cut, and an `inUse` plan cannot step back anyway.
3. **Q195 – The in-process stock model.** (1) **Operation-level removals: cut operations stay in the order and count through the existing bands, rest, links and Z reference.** (2) A height map per setup as the start stock for generation. (3) A removed-region stack through the 2D ports. _Recommendation: (1)_ now, the height map for display and tests (C5), (3) only if dogfood shows air passes the bands miss ([§ Model](#model-in-process-stock-from-cut-operations)).
4. **Q196 – Marking from Run.** (1) **Automatic on a real `done` run of an unchanged program, with Undo; after a stop or interruption offer the finished operations once no resume is pending; nothing on the virtual machine.** (2) Always ask at the end. (3) By hand only. _Recommendation: (1)._ A completed run is the strongest evidence there is; asking after every good run is friction, and marking during a pending resume would break line resume.
5. **Q197 – A partly cut operation.** (1) **Stays not cut; Run's resume or start from a line finishes it.** (2) Mark it cut and credit the executed passes from a height map. (3) Split it by finished passes. _Recommendation: (1)._ The recovery tools already finish an operation from a pass start; crediting part of one needs the height-map model and guesses about the last seconds.
6. **Q198 – Editing a cut operation.** (1) **Error `plan.cutChanged` with: cut it again, keep as cut, restore as cut, and (removes more) cut only the difference.** (2) Refuse design edits to cut operations. (3) Silently clear the mark. _Recommendation: (1)._ Design stays free (the user may be fixing the design to match the part), and nothing is skipped or re-cut without the user choosing; C1 ships "cut it again" alone.
7. **Q199 – Re-running a cut plan on a new blank.** (1) **Marks belong to the plan's one workpiece; the pre-flight of an all-cut setup offers "Clear cut marks".** (2) A history of runs per plan, marks per run. (3) A list of workpieces per plan. _Recommendation: (1)._ One click before a repeat cut; (2) and (3) are production features without a user asking.
8. **Q200 – How cut operations look in Plan.** (1) **Muted row with a check and the date, toolpath hidden by default ("Show cut toolpaths"), stock drawn with their removal.** (2) Hidden from the list (an "Already cut" group at the end). _Recommendation: (1)._ They keep their place in the order, which is what the bands use, and the user sees what the new work builds on.
