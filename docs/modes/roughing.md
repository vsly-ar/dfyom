# Roughing passes: a bigger tool clears the bulk, the operation's tool cleans the rest

Status: accepted; R1–R4 built (hardening DF122, the user's TG #401 "please plan attaching a roughing operation to most other operations and features that removes bulk of the material that's possible with a selected tool (minus a configurable margin) and main operation's tool only cleans what remains"; accepted 2026-11-26 by delegation D76: [Q139–Q146](#questions-for-the-user) take their recommendations) · Plan of record: [plans/hardening.md](../plans/hardening.md) DF122 · Generalises: [patterns.md § Roughing (DF108)](patterns.md#roughing-df108) (the pattern's `<id>_roughing` pocket and rest machining, built) · Builds on: [plan-v0.3.md § Pocket](plan-v0.3.md#pocket-offset-clearing-of-a-region) and [s4-offset-clearing.md](../research/s4-offset-clearing.md) (rest = region − opening), [plan-v0.1.md § Pass strategies](plan-v0.1.md#pass-strategies-v01) (finishing allowance, finish stepdown), [design-v0.2.md § Auto choice](design-v0.2.md#auto-choice) (tool field), [plan-v0.4.md § Machining order v2](plan-v0.4.md#machining-order-v2) (tool runs), [feeds-speeds.md § Finishing pass feed](../architecture/feeds-speeds.md#finishing-pass-feed-hardening-df74) (DF74) · UI: [inspector-layout.md](../conventions/inspector-layout.md) · Agent API budget: [llm-api.md](../architecture/llm-api.md) · Terms: [glossary.md](../glossary.md)

Today an operation's tool does all of its work. A pocket with R 1.5 corners gets a Ø 3 end mill (the auto choice ranks "leaves no rest material" first), and that Ø 3 then clears the whole pocket in small stepdowns and stepovers. A profile round an outline with tight inside corners is cut level by level with the same small tool. Patterns already solve this for their cells (DF108: an optional roughing pocket with a bigger tool, then the pattern's pocket cuts only the rest, −20 % on a 10 mm honeycomb). This doc makes that pass available to the operations that remove bulk material, with its own tool and a configurable margin on walls and floor.

## Goals

- **Faster programs for the same part:** the bulk goes with the biggest tool that fits (bigger stepdown, stepover and feed), the operation's tool cuts only what the bigger tool could not reach plus the margin.
- **Same part, same walls:** the operation's finishing pass, its tool and its feeds are unchanged; the finished geometry is identical with and without roughing.
- **Off by default, byte-equal goldens:** no program changes unless roughing is turned on.
- **One model** for patterns, pockets and profiles, so the pattern's DF108 code becomes the shared code, not a second copy.
- **Tiny agent API:** one field on existing tools; the roughing tool is set with the existing `design.operation.tool.*`.

## Which operations get a roughing pass

Decided per kind, by where the bulk is and whether a bigger tool can reach it ([Q139](#questions-for-the-user) picks the first version's set):

| Kind / feature                                      | Roughing | Why                                                                                                                                                                                                                                                                      |
| --------------------------------------------------- | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Pocket** (plain, any shape, blind or Through)     | yes      | The main case: area × depth of material, and the tool is often small because of the corners or a floor fillet. Rest = the corners and narrow necks the bigger tool cannot enter, plus the margin.                                                                        |
| **Pattern** (feature)                               | yes      | Built (DF108); moves onto this model with margins ([§ Patterns](#patterns)).                                                                                                                                                                                             |
| **Profile, `inside` / `outside`** (through or step) | yes      | Deep profiles with a small tool (tight inside corners of the outline) are cut level by level; a bigger tool takes the levels, the small tool the corners and its finishing pass. Needs path clipping to pay off ([§ Rest by the operation](#rest-by-the-operation), R3). |
| Profile, `on` (groove along a path)                 | no       | The groove is the tool's width (or `slotWidth`): no bulk beyond the slot, and a bigger tool would widen the groove.                                                                                                                                                      |
| Facing                                              | no       | Already the biggest tool and a thin layer; a separate floor finish is a different topic (finishing passes for facings, later).                                                                                                                                           |
| Drilling (drill or helix)                           | no       | A drill removes its hole in one plunge cycle; a helix bore's tool is already chosen to the bore. A large round opening is better a circle pocket, which gets roughing.                                                                                                   |
| Chamfer (circular or edge chamfer)                  | no       | A V-bit or chamfer mill takes a small triangle of material; there is no bulk and a flat tool cannot make the bevel.                                                                                                                                                      |
| Line, Engraving (feature)                           | no       | Centreline grooves whose width is the cutter's; clearing wide V-carve areas with a flat end mill first is a V-carve strategy of its own (later, with the carving work).                                                                                                  |
| Bolt hole (feature) recess / counterbore pockets    | later    | Owned pockets of a feature, usually Ø 8–20: the drill and end mill are close in size, so a roughing tool rarely pays. Comes when asked ([Q146](#questions-for-the-user)).                                                                                                |
| Clones (feature), split pieces                      | follow   | A Clones instance and a split piece repeat their source's operations, so they repeat its roughing too (R5).                                                                                                                                                              |

Pockets and profiles carry nearly all bulk volume of the parts DFYOM makes today, so "most operations" in volume is these two plus patterns.

## Model

**A roughing setting on the operation that owns a roughing operation** ([Q140](#questions-for-the-user)), the pattern's model generalised:

- **Setting:** `roughing?: { wall?: Quantity; floor?: Quantity }` on a pocket or an `inside`/`outside` profile, stored only when on (absent = off, so no existing record changes; no `schemaVersion` bump, pre-alpha rule). `wall` and `floor` are the **stock to leave** of the roughing pass (absent = the defaults below).
- **Owned operation:** while on, the operation owns **`<id>_roughing`** (`pocket1_roughing`), a design operation of the same kind with `roughing: true` (the DF108 flag, now set by any roughing owner) and `roughingOf: '<id>'`. Its `on`, shape, depth, Through, floor radius, side and tabs are the owner's, kept in sync by the owner's add/update and by recalculation (as a feature's owned operations and a chamfer's `on`); it is edited only through its owner, except its **tool field** (A4: own auto choice, lock, `design.operation.tool.*`). Turning roughing off or removing the owner removes it (one undo step).
- **Geometry:** it removes nothing of its own (its region is the owner's), its floor is no face target, material bands, through depths and construction surfaces ignore it (DF108).
- **Why an owned operation, not a second toolpath inside the owner's plan operation:** it gets everything an operation has for free: its own tool field and auto choice, its own plan operation with strategy, feeds and checks, its place in a tool run, its row in the navigator and the setup list, plan-only edits, labels and program comments ("Pocket 1 · roughing"). A second toolpath per plan operation would need a second tool per plan operation everywhere (tool changes, feeds, checks, Run's tool list).

### Tool: automatic, or the user's choice

[Q141](#questions-for-the-user). The roughing operation's tool field works as every tool field ([design-v0.2.md § Auto choice](design-v0.2.md#auto-choice)): **Auto** by default, locked by any user choice.

- **Fit** (`toolFit`, DF108's rules generalised): a flat or bull-nose end mill (bull nose with RE = the owner's floor radius, as pockets); it must enter the region somewhere (rule `width`; a profile: the slot or opening), and its Ø is at most **0.6 × the region's narrowest width** (rule `roughingWidth`; a profile: no width rule beyond the opening, an outside profile has none): a tool that only just fits clears a thin centre line and saves nothing. No corner rule; rest material is expected, so `dfm.restMaterial`, `dfm.cornerTooSmall`, `dfm.pocketNoToolFits` and `plan.restMaterial` are reported for the owner only.
- **Auto choice:** the **largest** fitting end mill, library first (the existing ranking minus "leaves no rest material", which roughing never meets), else the largest generalized tool of the standard series, as today.
- **No gain:** a roughing tool not larger than the owner's tool skips nothing; `dfm.roughingNoGain` (warning on the roughing operation, field `tool`: "The roughing tool (Ø 3) is not larger than the pocket's (Ø 3): the pocket still cuts everything. Choose a larger tool or turn Roughing off."). The DF108 "Later" note, now built in R1.

### Stock to leave: wall and floor

[Q142](#questions-for-the-user).

| Margin          | Default                                                                                                                                                         | Range                                                                                                                                                                               |
| --------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `wall` (radial) | the owner's resolved **finishing allowance** (0.2 mm / 0.008″, wood 0.5 mm / 0.02″; [plan-v0.1.md](plan-v0.1.md#pass-strategies-v01))                           | ≥ 0; ≥ the owner's finishing allowance (warning `plan.roughingWallThin` below it: the owner's finishing pass would cut the roughing's scallops at its allowance, not the allowance) |
| `floor` (axial) | **0** for pockets and profile steps (a flat end mill cuts the floor to size, as DF108); **0.5 mm / 0.02″** skin above the stock bottom for **through profiles** | ≥ 0; < the depth                                                                                                                                                                    |

- **Walls:** following the owner's allowance makes the owner's own clearing rings at that allowance cut air, so they are skipped and the owner's finishing ring takes the margin, as with DF108.
- **Floor:** with `floor` > 0 the roughing stops that much above the floor; the owner then clears its whole region at the levels below the roughing floor (nothing is cleared there) and only the rest above it. A cleaner floor from the finishing tool, at the cost of a full-area last level.
- **Through profiles keep a skin:** the roughing never cuts through, so nothing comes loose before the owner's tabs exist and the owner's tabs stay the only tabs. The owner cuts the skin and the walls with its tabs as today. Through pockets clear their whole region and leave no slug, so their roughing goes through (floor 0, DF108).
- **Where it lives:** in the design (the owner's `roughing`), because it is part of the operation's intent and the user edits it in the operation inspector. The roughing plan operation takes no `finishAllowance` / `finishStepdown` strategy keys (rule `notForRoughing`, `input.malformed`); its other pocket/profile keys (direction, entry, helix, ramp, breakthrough) work as usual. The pattern's DF108 roughing used the roughing operation's strategy `finishAllowance`; R1 moves that to the design margin with the same default, so its golden stays byte-equal.

## What the roughing operation cuts

- **Pocket:** offset clearing of every piece of the region its tool enters, down to `depth − floor`, leaving `wall` on the walls, **no finishing ring** (DF108). Pieces its tool cannot enter are skipped.
- **Profile:** the owner's slot passes with its own tool at the part-side distance R + `wall`, to `depth − floor` (through: to the skin), **no finishing pass and no tabs** (the skin holds through profiles; a step stops above the floor margin). Its slot is its own tool's width (`slotWidth` of the owner applies to the owner).
- Stepdown, stepover and feeds come from its own tool's cutting preset and the calculator, as any operation.

## Rest by the operation

[Q143](#questions-for-the-user), [Q144](#questions-for-the-user). The owner keeps its generator and skips what the roughing already removed, computed **from the roughing tool's reach**, not from a stock simulation:

- **Input (generalised `restAfter`):** when the owner's roughing comes earlier in the machining order, the owner's toolpath input carries `restAfter = { radius, cornerRadius, wall, floorDepth }` of the roughing's tool and margins (today `{ radius, cornerRadius, allowance }`; `floorDepth` = depth − floor). Without an earlier roughing (off, or the owner moved before it) nothing is skipped, as DF108.
- **Cleared region** (as DF108, plan-v0.3's rest = region − opening): `cleared` = the region shrunk by radius + wall and grown back by the flat radius (radius − corner radius); `inside` = `cleared` shrunk by the owner's tool radius (+ 0.01 mm). At levels **above `floorDepth`** the owner skips what lies in `inside`; at and below it nothing is skipped.
- **R1, ring skipping (built for patterns):** a node of the pocket's ring tree whose tool-centre region lies in `inside` is skipped with its children. Simple and safe, but a ring that touches one uncleared corner is kept whole, which is why DF108 saved about a fifth.
- **R3, path clipping** (built for pockets, [§ Implementation (R3)](#implementation-r3), which records where the build departs from this sketch: order per rest component, bridging instead of dropping short runs): each clearing ring or profile level pass is clipped to the **rest region** (the tool-centre positions whose disc is not wholly in `cleared`), keeping runs longer than a tool radius, joined by the existing linking (a feed link inside the cleared region where the straight link stays in it, else retract over the in-process stock, [safe-links.md](safe-links.md)). Each kept run enters at a corner of cleared air: a plunge or a short ramp into air, no helix (rule as the entry of an open region, [plan-v0.3.md](plan-v0.3.md#pocket-offset-clearing-of-a-region)). The finishing ring or pass is never clipped. Profiles need R3: their part-side level pass touches every inside corner of the outline, so without clipping they skip nothing.
- **Never cuts less than needed:** the cleared region is a lower bound of what the roughing removed (exact discs of its tool along its own rings, no credit for scallops between rings); a test oracle sweeps both toolpaths on a heightmap and checks that the finished region equals the owner's alone (no material left) and that the owner's moves in cleared air are only links and entries.
- **Why not a stock model:** an in-process stock heightmap (the cut map of [deviation.md](deviation.md), DF64's stock heights) would also credit facings and earlier operations, but it is sampled (0.1 mm cells), slower in the toolpath job, and makes every toolpath depend on every earlier one's moves; the reach rule is exact, cheap and keyed only on the roughing's tool and margins. The stock model stays the roadmap's "in-process stock across setups".

## Order and tool changes

[Q145](#questions-for-the-user).

- **Dependency:** an owner after its roughing, like `on` and `edgeOf` ([plan-v0.4.md](plan-v0.4.md#machining-order-v2)); the default order, rebuild placement and `repairOrder` keep it. Moving the owner before its roughing by hand is allowed (`plan.order` reports nothing): the owner then cuts everything, as DF108.
- **Tool runs across the setup:** machining order v2 already takes every ready operation of a tool into its run. So the Ø 8 roughs every pocket and profile of the setup in one run, then the Ø 3 cleans them all: one extra tool change per roughing tool, not per operation. The run order inside the setup is unchanged otherwise (facing, drilling, pockets, chamfers, lines, profiles; the roughing of a profile is a profile and runs with the profiles, before its owner).
- **Several setups:** the roughing is milled in its owner's setup (same `on`, same direction).

## Feeds

- **Roughing operation:** its tool's preset and the calculator, at its own stepover and stepdown, like any pocket/profile; no finishing pass, so no DF74 finishing feed.
- **Owner:** unchanged: its clearing rings at its feed, its finishing pass at the DF74 finishing feed. **Later:** the owner's rest runs engage at most the wall margin radially plus the corners, so radial chip thinning would allow a faster feed there (as DF74 for the finishing pass); measured after R3.
- **Time estimate:** the plan's time comes from the toolpaths, so it drops with the skipped or clipped moves; a plan with roughing shows both operations' times.

## Patterns

The pattern's `roughing: boolean` stays (DF108) and also takes the margins: `roughing: true | { wall?, floor? }`, the same object as the operations'. Its owned pocket `<id>_roughing` becomes an instance of this model (the owner is the pattern's pocket; `roughingOf: '<id>_pocket'`). Its tool rules, DFM and rest machining are the shared code. R1 keeps `pattern-honeycomb-roughing.nc` byte-equal; R3 (clipping) changes it, which is allowed (roughing on) and re-measured.

## Implementation (R1)

Built (hardening DF122, slice R1): pockets and patterns in core and plan, no UI (R2). Code: `src/core/design/roughing.ts` (the arg, `syncRoughing`, the refusal), `operation.ts` (`roughingIdOf`, `roughingOwnerId`), `plan/inputs.ts` (`roughingLeave`, `roughingBefore`), `toolpath/region-pocket.ts` (`RestAfter`, levels below the roughing floor), `geometry/dfm.ts` (`dfm.roughingNoGain`), `plan/evaluate.ts` (`plan.roughingWallThin`).

**Decided while building** (the doc above left them open or the code needed them):

- **Stored fields.** The owner's setting is stored as **`roughingPass: { wall?, floor? }`** on the pocket (the agent arg stays `roughing`): `roughing: true` already marks the roughing pocket itself (DF108), so one field name for both would make every reader test a type. The roughing pocket stores `roughing: true`, **`roughingOf`** (its owner) and **`leave`** (its owner's margins, only when one is set). The plan reads the margins from the roughing pocket, so pockets and patterns go through one path.
- **Patterns:** the feature stores `roughing: true | { wall?, floor? }` and copies the margins to its roughing pocket's `leave`; its `roughingOf` is derived from the role (`<feature>_pocket`), not stored, so existing pattern records stay byte-identical.
- **Arg:** `true` turns roughing on and **keeps margins already set** (defaults when it was off); an object replaces them (an absent margin is its default); `false` / `null` turn it off.
- **Place and life.** The roughing pocket sits **right before its owner** in the design list. `syncRoughing` is its only writer, run by `design.pocket.add` / `.update`, `design.operation.remove` (removing the owner removes it) and `design.operation.move` (it moves with the owner; an operation dropped between the two ends up before the roughing pocket). Each is one command, so one undo step.
- **Refusals:** a roughing pocket's geometry, removal and move are `design.featureOwned` (rule **`roughingOwned`**, `params.operationId` the owner); its name, general tolerance and tool stay its own (a custom name is kept, the default name follows a renamed owner). Roughing on a **Clones source** is refused (`design.featureOwned`, rule **`roughingNested`**) until R5, so a Clones span stays contiguous. Plan-only edits (`plan.design.operation.update`) take no `roughing`: it changes the design's operation list.
- **Fit:** a rectangle or circle roughing pocket (the analytic shapes, which have no shape measure) gets the same rules from its width (2 × the inscribed radius): `width`, then `roughingWidth` at 0.6 × it; no corner rule. The plan's own tool check skips the corner-radius rule for roughing pockets too (without it the plan replaced the Ø 8 by the owner's Ø 3).
- **Floor margin:** "at levels above `floorDepth`" reads **at or above the roughing's floor**: with floor 0 the roughing cut every level, including the last, so the owner skips there too (DF108's behaviour, goldens byte-equal); below a floor margin the owner cuts its whole ring tree. A roughing pocket with a floor margin stops that much above its floor, or above the material's bottom for a through owner (no breakthrough). The plan input carries `restAfter = { radius, cornerRadius, wall, floor }`, the toolpath input `{ radius, cornerRadius, wall, floorDepth }` once the depth is known.
- **Wall default:** the owner's resolved finishing allowance (its plan operation's strategy), the roughing pocket's own resolved allowance when the owner is not in the plan. The roughing's toolpath input takes the wall as its `finishAllowance`; `plan.operation.update` refuses `finishAllowance` / `finishStepdown` on a roughing pocket (`input.malformed`, rule **`notForRoughing`**; `null` stays allowed).
- **Results:** `design.pocket.add` returns the pocket's `operationId` only; the roughing pocket is in `design.operation.list` with `roughingOf`.

**Exit test** (`plan/pocket-roughing.test.ts`, golden **`pocket-roughing.nc`**): the doc's 60 × 40 pocket, 8 mm deep, R 1.5 corners, on the 80 × 50 × 12 walnut lid, with the plan fixture library plus a Flat 3 and a Flat 8: the owner takes the Ø 3 (its corners), the roughing the Ø 8 (the largest library end mill within 0.6 × 40 mm; with an empty library the auto choice is a generalized Ø 12, `design/roughing.test.ts`). The roughing runs first with a tool change; the program exports for GRBL and streams to Idle; the heightmap oracle over both toolpaths finds no leftover the Ø 3 reaches, no gouge, nothing below the floor. A second case (`{ wall: 0.1, floor: 1 }`) checks `plan.roughingWallThin`, `notForRoughing`, the roughing stopping at −7 and the owner reaching −8 with the oracle clean. Every existing golden is byte-equal, `pattern-honeycomb-roughing.nc` included.

**Measured:** without roughing the Ø 3 cuts 17,345 mm in 575 s (1,006 lines, the v0.1 rectangle generator); with roughing the Ø 8 cuts 2,571 mm in 38 s and the Ø 3 then 2,527 mm in 88 s: **126 s, −78 %** (370 lines). An open rectangle is the best case for ring skipping (the Ø 3 keeps its outer rings and the finishing pass); cells with many corners save less (DF108: −20 %).

**Agent API:** `tools/list` 115,956 → **116,417** chars (+461, 150 tools; `design_pocket_add` 2,311 → 2,587, `design_pocket_update` 983 → 1,042 with the sketch "As design.pocket.add roughing", `design_pattern_add` 3,134 → 3,293, `design_pattern_update` 1,672 → 1,639 with a sketch instead of the boolean). Over the ≈ 0.25 K estimate: the union `boolean | null | { wall, floor }` (strict, as the sketch test requires) costs about 0.13 K per full listing, and the pocket's description names the defaults; `plan.design.operation.update` (which repeats every pocket arg) does not take `roughing` (+0.3 K saved). 3.6 K headroom under 120 K.

**Known limits (later slices):** Clones instances do not repeat a source's roughing and a split piece keeps none (R5); profiles get roughing in R4; the Plan viewport does not shade the rest region yet ([§ Implementation (R2)](#implementation-r2), [§ Implementation (R3)](#implementation-r3)).

## Implementation (R3)

Built (hardening DF122, slice R3): rest clipping of pocket clearing rings, core only. Code: `src/core/toolpath/region-rest.ts` (`clipRing`, `segHits`, `restLinkClear`, `restArea`), `region-pocket.ts` (`restItems`, the rest level traversal, `REST_TOLERANCE`); test oracles `airCut` and `heightDifference` in `toolpath/testing/region-coverage.ts`. Levels below a floor margin and pockets without an earlier roughing take the unchanged code path, so every non-roughing golden is byte-equal.

**Decided while building:**

- **Exact clipping.** Each ring kept by R1's pruning is cut where its pieces (lines, arcs) cross the boundary of `inside` (the tool-centre positions whose disc lies in `cleared`). Each stretch between crossings is classified by its midpoint. A ring with no roughed stretch stays **whole**; otherwise it becomes **runs**, each starting where the ring leaves the roughed area and keeping the ring's direction (climb or conventional).
- **"Runs longer than a tool radius" read as bridging, not dropping.** Dropping a short run could leave material, so no run is dropped (only runs under 1 µm, which are 2D-library noise). Instead, a roughed **gap shorter than the owner's tool radius is bridged**: the tool runs on along the ring through that air instead of linking.
- **Air tolerance.** A position counts as roughed when its disc lies within **`REST_TOLERANCE` = 0.01 mm** of `cleared` (the coverage oracle's tolerance). DF108's skip test instead kept 0.01 mm _off_ `cleared`. Without this tolerance the owner's ring at the wall margin, which only grazes the roughed edge, was kept whole and cut air all round. With it, that ring keeps only its corner runs. The pruning of whole nodes uses the same `inside`.
- **Order: per rest component, innermost first.** The doc above said "joined by the existing linking" (the ring tree's post-order). That would still take the tool round the whole pocket on every ring: four corner runs per ring, linked at feed along the walls, cost about as much as the ring itself. Instead the items (runs and whole rings) are grouped by the piece of `roots − inside` they lie in, a **rest component** (a corner, a neck, a gap by an island). Components are taken nearest first. Within a component, items go by ring offset from the inside out (nearest first at equal offsets). This keeps the clearing invariant that the inner side of a run is already cut when it is cut, so engagement stays at most one step.
- **Links.** A straight feed link is used where every stretch of it lies in the roughed area (air), or in the component's tool-centre positions at offset ≥ the next item's offset (cut round already, as `linkInside`'s parent region). Otherwise the tool retracts, rapids and plunges ([safe-links.md](safe-links.md) phase 1 is unchanged; links inside an operation stay on the retract plane, SL-H).
- **Entries.** A run starts on the roughed boundary, so it is entered by a **plunge into air** at the plunge rate, with no helix or ramp. A whole leaf ring of the full tree (a neck or cell the roughing never entered) uses the pocket's own entry (helix, ramp or plunge, as without roughing), then its other rings are linked as before. A whole ring whose inner rings were pruned plunges at its node's deepest point when that point lies in the roughed area, then feeds onto the ring; otherwise it falls back to the blocked-link plunge of T-I.
- **Nothing to rest.** When the roughing reaches everything (S4's two islands with a Ø 8 and a Ø 3), the owner has no rest level and its finishing pass is the first cut. The finishing pass no longer assumes an earlier move.
- **Viewport rest shading** (the R3 row's "the plan viewport shades the owner's rest region") is left to the renderer work alongside R2. This slice is core only and exposes nothing new to the renderer.

**Tests** (`toolpath/region-pocket.test.ts`, "rest clipping (DF122 R3)"): the S4 corpus with a Ø 3 owner after a Ø 8 roughing (wall 0.2): a R 1.5 rectangle and a 40° triangle (corners), the dumbbell with a 6 mm neck, a rectangle with a square island and a round island 5 mm from the walls, and S4's two islands (nothing to rest). Every case is checked against these oracles:

- the path rules;
- the coverage oracle: no leftover, no gouge, nothing below the floor;
- **heights of roughing + rest equal to the Ø 3 alone within 0.02 mm** (`heightDifference`: 0 mm² on every case);
- **no plunge into material**;
- rest air (horizontal feed moves that remove nothing under the tool shrunk by 0.02 mm) at most 15 % of the air the Ø 3 alone would cut after the same roughing (measured 7 %, 12 %, 0.8 %, 8 %; what is left is links between runs, bridges and overlaps of the owner's own rings in narrow spots, which the Ø 3 alone has too);
- rest time under a quarter of the Ø 3 alone.

`clipRing` has its own unit test (lines and arcs, whole, empty, bridged).

**Goldens:** only the two roughing goldens change; every other golden is byte-equal.

- **`pocket-roughing.nc`** (370 → 343 lines): R1 kept only the Ø 3's ring at the wall margin here, entered at every level by a helix in the cleared middle (eight turns) and a link out to the ring. R3 cuts that ring's four corner runs, each entered by a plunge into the roughed air at its corner. The runs are joined by straight feed links along the walls, through air, so the tool still goes round the pocket at feed. The time saved is the helixes and the links from the middle. Low rapids for those links would save more, but they wait for safe-links phase 2. The Ø 3 drops from 2,527 mm in 88 s to **1,704 mm in 60 s**, and the plan from 126 s to **98 s**: **−28 s (−22 %) on R1, −83 % on the Ø 3 alone** (575 s). The plan test also checks the heights against the Ø 3 alone (identical), no plunge into material, and rest air under 10 % of the Ø 3 alone's after the roughing.
- **`pattern-honeycomb-roughing.nc`** (2,823 → 2,908 lines: more, shorter moves, as each hexagon's six corners are cut as runs with air entries): the Ø 2 drops from 4,965 mm in 213 s to **2,812 mm in 140 s**, and the plan (Ø 6 roughing 48 s) from 261 s to **188 s**: **−73 s (−28 %) on R1, −43 % on the Ø 2 alone** (328 s).

**Known limits:** links in air run at feed on the retract plane's rules (no low rapids inside an operation until safe-links phase 2). Between rest components the order is nearest first, so a run may engage more than a step where two components lie within a tool diameter across a narrow roughed band (not seen in the corpus). Profiles' level passes are clipped with the same code in R4.

Decisions (made under D76, the user can overturn any):

- **Model:** the profile gets the pocket's fields: `roughingPass { wall?, floor? }` on the owner, `roughing: true`, `roughingOf`, `leave` on `<id>_roughing`, which copies the owner's `on`, shape, side, slot width, depth, Through and tabs (the tabs for the record only: it cuts none). A groove (`side: on`) refuses roughing (`model.invariant`, rule `notForGroove`); switching an owner to `on` without a `roughing` arg turns its roughing off in the same update.
- **Skin (Q142):** a through profile's floor margin defaults to **0.5 mm / 0.508 mm (0.02″)**, and with tabs to **at least the tabs' thickness**, so the roughing stops at the tab tops, the tabs keep their full thickness and stay the owner's only tabs. A through skin must be > 0 (rule `floorRange`); a step profile's floor margin defaults to 0 as a pocket's. The inspector labels the field **Skin** with the placeholder "Auto · 0.5 mm" (or the tab thickness), "Leave on floor" otherwise.
- **The roughing's slot (deviation from § What the roughing operation cuts):** the roughing profile cuts at R + `wall` from the part, out to the owner's slot edge. A through owner's slot widens to its own tool + `wall` when that is wider (`roughingSlot`: max(slot, D + wall), into the offcut side, which is waste); a step keeps the owner's slot, so it never cuts outside the owner's region. Its tool fit is the slot rule (rule `width`, a tool wider than the slot), plus the opening rule for `inside`; no corner rule (flat end mill, rest expected).
- **Generators:** a roughing profile, and an owner with an earlier roughing, always take the region profile generator (also for analytic rectangle and circle profiles), so the R3 clipping applies; profiles without roughing keep their code path and goldens byte-equal. The roughing has level passes only (no finishing pass, no tabs) down to `depth − skin`.
- **Owner's rest levels (R3 code):** at levels the roughing cut, each side-pass ring is clipped to the rest, which is the band between the part and the roughing's near edge (R + `wall`) and its far edge, minus what the roughing's discs cleared, with `REST_TOLERANCE`. Items are taken group by group, nearest first. Runs are entered by a plunge into air (or an air link through `restLinkClear`), whole rings by the profile's ramp or a plunge. Levels below the skin are cut whole, with tabs, as before. The finishing pass is unchanged.
- **Exclusions:** the roughing profile removes nothing of its own and is left out of through/cutout and order logic (`isThroughGeometry`, `isThroughProfile`), solids, surfaces (no floor target, no tab tops), DFM profile checks and `leavesRest`; its through depth is its owner's. The stickout and reach checks treat it at full thickness (conservative).
- **UI:** the Profile inspector shows the Roughing accordion right after Tool, for `inside` / `outside` only, with the same fields as the pocket. The navigator nests the roughing row under the profile ("Profile 1, with roughing"; they move and remove as one; Make Clones hidden until R5). Its short inspector, the viewport (either selected draws both) and the Plan "rest" chip work as for pockets.
- **Floor icon (review fix):** the floor margin no longer uses the horizontal `thickness` glyph. A new **`floorAllowance`** field icon, the `allowance` drawing with the amber margin vertical on the floor, serves Leave on floor and Skin, in the Pocket, Pattern and Profile accordions and the short inspectors (the R2 notes above name the old icon).
