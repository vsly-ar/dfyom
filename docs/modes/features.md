## Feature vs operation

|                  | Operation (today)                                                                                                  | Feature (new)                                                                                                |
| ---------------- | ------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------ |
| What it is       | One cutting action: one removal region, its surfaces, one [tool field](design-v0.2.md#operation-tool)              | A named design element the user thinks in ("M5 counterbored hole", "bolt circle of 6"), stated by its result |
| Parameters       | Geometry of one cut (`shape`, `depth`, `diameter`, …)                                                              | Intent: hole type and size, fastener, Clones path rows, chamfer size, text and font                          |
| Makes geometry   | Directly (`part = stock − ∪ removal(op)`, [geometry.md](../architecture/geometry.md))                              | Never directly: it **generates** operations, and only they make geometry                                     |
| Downstream       | Geometry, DFM, auto tool choice, Plan, surface ids, references                                                     | Unchanged: all of them see the generated operations only                                                     |
| Examples (kinds) | `facing`, `pocket`, `drilling`, `profile`; later chamfer, engraving, V-carving ([candidates](#candidate-features)) | `hole` (simple, counterbore, countersink), `clones` (path rows), `edgeChamfer`, `text`, … (backlog)          |

**Rule:** a feature is a pure function of its parameters, its face target and the part's earlier state to an ordered list of operations (its **expansion**). It adds no geometry, tool or toolpath logic of its own; a feature that needs a new kind of cut first gets that **operation** (e.g. a chamfer operation and a chamfer-mill tool type before countersinks and edge chamfers).

## Expansion and owned operations

Assumptions A1–A6:

1. **A1 – Materialized, owned operations.** The expansion is stored: generated operations sit in the part's operation list like any other, each with `featureId` and `featureRole` (e.g. `hole1` / `counterbore`). They are the feature's **owned operations**. Geometry input, DFM, the auto tool choice, Apply, Plan and surface references therefore work on operations exactly as today. (Rejected: deriving the operations on every read, which would touch every consumer and give owned operations no place for their tool lock.)
2. **A2 – Regenerated in the same command.** `design.<featureKind>.add` / `.update` run the expansion inside the command (one undo step) and replace the owned operations by role. Expansion is cheap, deterministic and decides nothing on the user's behalf, so it is an **instant** reaction ([apply.md § Rules for new reactions](../architecture/apply.md#rules-for-new-reactions)); the auto tool choice of the owned operations still waits for Apply.
3. **A3 – Stable ids by role.** An owned operation's id is `<featureId>_<role>` (`hole1_drill`, `hole1_counterbore`); [Clones](#source-and-clone-instances) instances add the instance number (`clones1_3_hole1_drill`; instance 1 is the source). Underscores are valid in [expression names](../architecture/quantities.md#expressions-and-references), so surface ids stay `<operation id>.<role>` (`hole1_counterbore.floor`). A role that survives a parameter change keeps its id, so references, plan operations and tool locks survive; a role that disappears removes its operation and fails with `design.referenced` if a later operation references it, as [`design.operation.remove`](design.md#commands-and-queries-v01) does.
4. **A4 – Owned geometry is read-only.** The owned operations' geometric parameters are edited only through the feature. Each owned operation keeps the fields that are not part of the feature's definition: its **tool field** (pick, lock, unlock per operation), its `generalTolerance` and its display `name`; they survive regeneration by role. No per-field geometric overrides in the first version ([Q1](#questions-for-the-user)).
5. **A5 – No explode; owned operations live and die with their feature** (user, D26). Owned operations cannot be turned into plain operations, and `design.operation.remove` on one is refused; removing the feature removes them. An edit the feature does not offer means adding that option to the feature.
6. **A6 – One nesting level.** [Clones](#clones) nest their source: operations or one non-Clones feature (a bolt circle of counterbored holes); Clones of Clones are refused. Other features do not nest. (The parked [patterns](#patterns) would take the same rule.)

### Order and references

- A feature occupies one position in the [design order](design.md#ordering-and-composition); its owned operations are contiguous there, in the order its kind defines (counterbore: the counterbore pocket, then the hole `on` its floor). `design.operation.move` on an owned operation is refused; `design.feature.move` moves the block.
- The feature's `on` is a [face target](design-v0.2.md#face-targets-generalised-on) and its position is `[u, v]` in that [face frame](design-v0.2.md#face-frame) with a [placement anchor](design-v0.2.md#placement-anchors), like a pocket. Owned operations reference the feature's face and each other only; later operations may reference owned surfaces (`hole1_counterbore.floor.z`).
- Feature parameters are quantities and may be expressions over earlier surfaces, as operation parameters are.

### Validation and DFM

- Feature invariants are `model.invariant` on the feature's fields (counterbore diameter > hole diameter, counterbore depth < hole depth, Clones row count ≥ 1, instances inside the face). Check order: feature fields → expansion → the existing operation checks of [design.md § Implementation](design.md#implementation-task-25), with issue paths mapped back to the feature field where the expansion knows it.
- DFM warnings stay per owned operation (codes unchanged); the navigator rolls them up on the feature row, and the feature inspector shows them at the feature field that drives the parameter.

- **Seed:** an existing operation or feature (A6). Making a pattern from an existing one moves it into the pattern as instance 1 (one undo step).

## Clones

Accepted (D34, 2026-11-22; drafted from the user's definition, D30). The user's definition is the source of truth for this section. **Clones v1** (v0.4): one face and the source's orientation (C1, C5), stable numbering (C2), instances read-only and using the source operation's tool (C3), removing Clones keeps the source (C4), made only from existing operations or a feature (C6), and a source with several tools is planned tool by tool across all clones ([Plan and cut order](#plan-and-cut-order), D34); answers in [Open questions](#open-questions-clones). The definition:

> "I see clones as maybe creating a feature in dfyom from an existing feature or a set of operations (nesting them as a source that can be edited) to repeat (clone) them with a read-only operations. Number of clones, its positions (in a path) configured in the Clones feature's properties."

Clones are not [patterns](#patterns), which stay parked (D28). cnc-code's Clones are a different concept; only its path rows, skipping and cut order are borrowed (background only: the local research note `.continuous/research/2026-11-22-cnc-code-reuse.md` § 1, not in the repo).

### Source and clone instances

- **Source:** the Clones feature nests one existing feature (a counterbored hole) or a set of operations (a pocket plus the drilling on its floor). Creating Clones nests the source in the feature in one undo step: the source stays where its first operation was (gathered if scattered) and the instances follow right after it; source and instances are the feature's **span** in the [design order](#order-and-references), moved as one ([design-v0.4.md § Implementation (F5)](design-v0.4.md#implementation-f5)).
- **The source stays editable.** Source operations keep their ids and their own commands (`design.pocket.update`, …); a source feature is edited through that feature. The source is **instance 1**.
- **Clone instances** (instances 2…N) are owned operations of the Clones feature ([A1–A3](#expansion-and-owned-operations)), one per source operation per position, with ids `<clonesId>_<n>_<source operation id>` (`clones1_3_pocket2`, `clones1_3_hole1_drill`). D26 applies strictly: read-only, no Explode, never removed apart from their feature. Unlike A4, they have no tool field of their own: each uses its source operation's tool (pick, lock or unlock it on the source), so all clones of one source operation share one tool ([C3](#open-questions-clones)).
- **One face, one orientation (user, D30):** all source operations sit on one face target or on surfaces of each other (a drilling on the pocket floor); that face is the Clones feature's `on`, positions are in its [face frame](design-v0.2.md#face-frame), and every instance lands on that face (side) with the source's orientation. References inside the source map to the same instance's copies (clone 3's drilling is `on` clone 3's pocket floor); references to surfaces outside the source stay unchanged.
- **Nesting:** one level ([A6](#expansion-and-owned-operations)); Clones of Clones are refused.

### Properties

| Property | Meaning                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `rows`   | Ordered **path rows**. A reference point starts at the source (instance 1); each row places its positions from it and moves it to its own last position, so the next row continues there ("3 along u, then an arc of 5, then a 2 × 2 grid"). Kinds: `grid` (columns × rows cells with the reference point as the first cell, so `cols` · `rows` − 1 positions; spacing per direction, which may be 0 along a direction with a single cell, DF90), `offset` (`count` positions beyond the reference point, i.e. `count` clones; step `[du, dv]`), `polar` (`count` positions beyond it, angle and distance per step), `arc` (centre by radius and angle from the reference point, sweep ±360°, step angle; a full circle never repeats its start), `point` (absolute `[u, v]`, a jump). `along` (v0.4 F6, [Q30](../plans/v0.4.md#questions-for-the-user)): a named shape of one item (an open or closed path, or a primitive's outline) laid with its start point on the reference point and its shape frame on the face frame (orientation kept, no rotation or mirror); positions by arc length from that start point, from `start` (default 0) every `spacing` (as many as fit), or `count` spread evenly (an open path from `start` to its end; a closed loop once round, wrapping past its end); exactly one of `spacing` and `count`. The position at arc length 0 is the reference point itself and gets no number (like a full circle's closing point), so `count` 6 on a loop from 0 is the source plus 5 clones. The instances follow edits of the shape; the reference point ends at the last position. |
| count    | Derived, never entered: the rows' positions summed; the read-out shows "1 + 11 clones = 12 instances · 4 skipped". Limits: 100 positions per row, 20 rows and **100 instances per Clones feature** (source included; D36, [S6](../research/s6-clone-budgets.md#recommendation): plan creation and export are linear since [P4](../research/s6-clone-budgets.md#follow-up-p4), evaluation grows somewhat faster than the instances, 1000 is a target).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| `skip`   | Per row, position indices that make no clone; the reference point still walks through them, so a skipped one-position row is a shift. Instance 1 cannot be skipped. Numbering stays stable (user, D30): skipping 3 leaves 4–8 as 4–8, so ids, references, plan operations and tool locks survive.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| rotation | None in the first version: every instance keeps the source's orientation, also on `polar` and `arc` rows (user, D30). Rotating instances to follow the path (radial, like flange bolts) is a **later extension**, not specified here (it would build on v0.3 shape rotation, [S-E](design-v0.3.md#decisions)).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| `name`   | Default "Clones 1"; instance names default to "<source operation name> · <n>" ("Pocket 2 · 3").                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |

Row fields are quantities and may be expressions, as operation parameters are.

**Counts (DF90):** the kinds count differently, by design and unchanged (pre-alpha, but stored rows keep their meaning): a grid's `cols` × `rows` include the cell the row starts from, `offset`/`polar` `count` is the positions after it, and an `along` `count` spreads positions from arc length `start`, where one at length 0 is the start itself (no clone). The agent schema description and the inspector hints say this per kind.

### Editing the source

- A command that changes a source operation or the source feature re-runs the Clones expansion **in the same command** (one undo step, an instant reaction as in [A2](#expansion-and-owned-operations)); every instance follows. The pending key is the source field's own, so the instances' changes fold into it ([Apply](#apply-and-pending-changes)): "Pocket 2: depth" counts 1, not 12.
- Adding or removing source operations is `design.clones.update { source }`. Removing a source operation removes its instances; leaving the source empty is refused (remove the Clones feature instead).
- Removing the Clones feature removes its instances and keeps the source: it goes back into the design order, at the feature's position, as plain operations or its feature ([C4](#open-questions-clones)).

### Plan and cut order

- The expansion orders instances **operation by operation**: source operation A on every position in path order, then operation B on every position. With one shared tool per source operation, Plan's existing [default order](plan-v0.1.md#plan-operations-and-order) keeps them adjacent, so 8 counterbored holes cut as 8 counterbores, then 8 holes: **one tool change per source operation**, as for a single instance. A source with several tools (a counterbored hole: end mill, then drill) is planned **tool by tool across all clones** (D34; X1 asserts one tool change per distinct tool). Equal holes still share one plan operation. No Clones logic in Plan ([Q9](#questions-for-the-user)).
- Within one source operation, positions follow the path (an arc is cut round the arc); a shorter travel order is a later plan optimisation.

### Checks and DFM

- Feature invariants (`model.invariant`): at least one row, every row count ≥ 1, steps not 0 (a grid's `du`/`dv` only where it has more than one column/row), the limits above, the source on one face, no Clones of Clones.
- Every instance runs the existing operation checks; the navigator rolls them up on the Clones row.
- **Outside the stock:** instances are still generated; one warning on the Clones feature lists them (`dfm.cloneOutsideStock`: "3 clones lie outside the stock (7, 8 and 12): skip them or shorten a row"; checked on footprints since hardening B3: an instance is outside when its footprint reaches further past an edge of the stock face than the source's does, so a source that is open to an edge on purpose can be repeated along it). The footprint of the source is the area its operations cut in the face, in the face frame: a drilling's or a chamfer's outer circle, a pocket's or an inside profile's shape, an "on" or outside profile's shape grown by half or the whole slot width (an open path: its slot); facings have none. Folding the per-operation warnings they cause into it is not done yet.
- **Overlaps:** a position within 0.001 mm of another is dropped with one warning (`dfm.cloneDuplicate`; it keeps its number); instances whose footprints overlap (by more than touching) get an info note (`dfm.cloneOverlap`; exact for circles and rectangles, named and rotated shapes intersected in the 2D layer), since an overlap can be intended (a slot of overlapping pockets).
- **Size:** ≥ 50 owned operations get an info note (`dfm.clonesHeavy`): the part updates more slowly (S6).

As [Commands (sketch)](#commands-sketch-1): `design.clones.add { source: { featureId } | { operationIds }, rows }` and `design.clones.update { featureId, rows?, source?, name? }` (skips live in `rows`); the query `design.clones.preview` returns positions, instance numbers, skipped spots and warnings for a feature or a draft without changing the part (agents and the add flow). Shared: `design.feature.remove`, `.move`, `.list`, `.get`. Results carry `{ featureId, operationIds, warnings }`.

### UI (summary)

- **Navigator:** the Clones row (icon, name, "×12", rolled-up badge) nests **Source** (editable, normal rows) and **Clones** (read-only instances by number, collapsed by default).
- **Inspector:** a sortable list of path rows with an "Add row" menu (first values from the source footprint plus a gap), per-row fields with a dynamic illustration and the instance read-out. An instance shows read-only fields with "Clone 3 of Pocket 2", linking to the source.

While adding, the clones are ghosts until confirmed. Clicking an instance's surface selects it, a second click its Clones feature.

## Plan

- Plan sees **operations only**: the [design snapshot](plan-v0.1.md#plans-are-snapshots) copies the part, features included, but plan operations are built from operations as today. Equal holes from Clones group into one plan operation by the existing grouping key, and clones are cut tool by tool ([Plan and cut order](#plan-and-cut-order)).
- [Plan-only edits](plan-v0.2.md#plan-only-edits-and-the-snapshot-scene) work per owned operation (they edit the snapshot's operations); the feature in the snapshot is informational. A rebuild discards them as today.
- The plan navigator labels plan operations with their feature name ("Hole 1 · counterbore", grouped clone instances "Hole 1 · drill × 6") and the program comments each clone position (`(Clones 1 #3)`); no feature logic in Plan ([Q9](#questions-for-the-user), [plan-v0.4.md § Implementation (P1)](plan-v0.4.md#implementation-p1)).

## Apply and pending changes

- **Pending keys** ([apply.md § What is pending](../architecture/apply.md#what-is-pending)) for a feature are `(part, feature, field)` for its own fields and `(part, feature)` for add, remove and move; changes of its owned operations caused by the expansion fold into these keys, so changing a Clones row from 4 to 6 positions counts **1**, not 12. Owned-operation fields the user edits directly (tool unlock) keep their per-operation keys.
- **Refilled fields fold too:** a field a command refills from another one is no key of its own while the field that drove the refill is pending (`FeatureKindSpec.pendingFolds`). The hole's table sizes (`diameter`, `cbDiameter`, `cbDepth`, `csDiameter`, `csAngle`) fold into `fastener`, `purpose`, `fit`, `headSink` or `type` ([design-v0.4.md § Parameters](design-v0.4.md#parameters)), so choosing M4 counts **1**; a size typed by hand with no driver pending counts 1 on its own (X1).
- The [auto tool choice](design-v0.2.md#auto-choice) on Apply targets every unlocked owned operation of a feature with pending changes, plus new owned operations.
- The tooltip lists features by name ("Counterbore 1: diameter · Clones 1 added").

## Undo

One feature command is one undo step, the expansion included: add, update, remove (removes its owned operations), move. An adjust-panel session on a feature field is one [gesture](../architecture/commands.md#gestures-live-edits) as for operations. Undoing a feature update restores the owned operations by their inverse patches; the expansion is never re-run on undo or redo (handlers are not re-run, [commands.md](../architecture/commands.md#undo--redo)).

## Persistence (high level)

- The part record gains an optional `features: FeatureDTO[]`; every operation gains optional `featureId?` and `featureRole?`. A `FeatureDTO` is a union on `kind` with `{ id, kind, name, on, anchor?, generalTolerance?, …parameters }` (quantity DTOs as for operations). Absent fields mean "no features", so existing projects load unchanged; **no `schemaVersion` change** ([CLAUDE.md](../../CLAUDE.md) pre-alpha rule).
- Ids follow [design.md § Implementation](design.md#implementation-task-25): kind prefix + number (`hole1`, `clones1`, `chamfer1`, `text1`), default names "Hole 1", "Clones 1". Owned operation names default to "<feature name> · <role>" ("Hole 1 · counterbore").
- Consistency: an operation whose `featureId` names no feature, or a feature whose owned set differs from its expansion, makes the part `input.malformed` (corruption, never repaired silently). A fastener table version is not stored: chosen sizes are stored as values.

## Implementation (F1)

The feature model (A1–A6, order, Apply, undo, persistence) is built as this doc says; how and where, and what is left open for hole and Clones: [design-v0.4.md § Implementation (F1)](design-v0.4.md#implementation-f1). Where F1 settles details this doc leaves open:

- **Owned operation edits:** `design.<kind>.update` on an owned operation accepts only `name` and `generalTolerance` (A4); any geometric parameter, `design.operation.remove`, `.move` and `design.shape.convert` fail with `design.featureOwned`.
- **Roles and cut order:** a role is `<step>` or `<instance>_<step>`; expansions are step-major, which keeps the "operation by operation" order of [Plan and cut order](#plan-and-cut-order) in the stored data (tool by tool across all instances, D34).
- **`design.feature.get`** is folded into `design.feature.list { featureId }` (Q32 A).

## Relation to ADR 0019 and v0.3 shapes

- **Hole, counterbore and Clones of circles** need nothing from [ADR 0019](../decisions/0019-2d-geometry-library.md): they expand to v0.2 circles and drillings.
- **Edge chamfers along pockets and profiles of any shape, dogbone corner reliefs, text and engraving** need v0.3 shapes: offset loops of lines and arcs (CavalierContours) and, for text, glyph outlines turned into arcs like SVG Béziers (biarcs, ADR 0019 consequences). They follow v0.3.
- **New operations first:** countersink and edge chamfer need a chamfer operation and a chamfer mill / V-bit tool type ([library.md](../architecture/library.md#tool) lists them as later); text and engraving need the engraving / V-carving operations of [design.md § Carving and engraving](design.md#carving-and-engraving-later).

## Candidate features

## Questions for the user

Q1 and Q6 are answered (D26), Q8 (D28); Q2, Q4, Q5 and Q9 are settled by the accepted sections and Q29 (D34). Q3 and Q7 stay open with [Patterns](#patterns) (draft).

1. **Answered (D26):** read-only, no explode, removed only with their feature. Original question: owned operations read-only, or editable with per-field overrides? Recommendation was: read-only geometry, own tool field, tolerance and name per owned operation, plus Explode (A4, A5). Overrides that survive regeneration are hard to show and to reason about; add them later only for a concrete case.
2. **Store owned operations or derive them on read?** Recommendation: store them with `featureId` (A1), so every consumer stays unchanged.
3. **Pattern of features?** Recommendation: yes, one level (A6): a bolt circle of counterbored holes is the common case.
4. **Pending count per feature field?** Recommendation: yes (4 → 6 instances is "1 change").
5. **Fastener tables in the hole feature?** (Tables confirmed by D30 Q7; the v0.4 standards are asked as [Q29](../plans/v0.4.md#questions-for-the-user).) Recommendation: yes, a small built-in table (ISO metric M1.6–M12 socket head and flat head, inch #4–1/2″; clearance close / normal / loose; counterbore and countersink sizes), values copied into the feature and always editable; a fastener library later.
6. **Answered (D26):** the seed's chamfer, and a chamfer is an operation of its own (needs a chamfer operation and a chamfer-mill / V-bit tool type). Original question, "pattern with optional chamfers": a repeat pattern whose seed may carry a chamfer (assumed), or a decorative surface pattern (texture)? Recommendation: the former; decorative patterns would be a carving feature later.
7. **Converting existing operations:** pattern from an existing operation, yes; a general "group these operations into a custom feature" (user templates)? Recommendation: not now; user-defined features later.
8. **Answered (D28):** v0.3 Shapes first; hole features after it; patterns much later, after the user explains them. Original question, milestone: hole (counterbore) and patterns need nothing from v0.3. Recommendation: a small lane after v0.2 (or in v0.3 beside shapes); chamfers, text and engraving after v0.3 shapes and their operations.
9. **Feature names in Plan:** recommendation: label only, no plan logic per feature.
