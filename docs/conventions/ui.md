How the renderer looks and behaves: design tokens, components, layout, interaction, run-mode safety, accessibility, copy, testing. Rules are imperative. The user's answers to the open questions are recorded as [decisions](#decisions); concrete token values, the palette and the component looks come from the approved [design system](#design-system) (task 1.16).

## Decisions

Settled with the user (tasks 1.11 and 1.16); the sections below specify them.

1. **Theme:** follow the OS, with a Light / Dark / System setting ([tokens](#design-tokens)).
2. **Design system first:** tokens, palette and a components preview were defined in a separate step and approved by the user before any UI is built (task 1.16, [design system](#design-system)). Look: a strict, serious desktop CAD-style tool, not a web page ([decision 17](#decisions)).
3. **Colour scales:** Radix Colors (MIT) 12-step scales, adapted to the chosen palette.
4. **CSS:** CSS Modules + CSS custom properties.
5. **Icons:** own set only (B22, [D33](../plans/v0.3.md#confirmed-decisions), 2026-11-22; was Lucide (ISC) + own CNC icons) ([icons](#icons)).
6. **Renderer state:** Zustand (MIT) for per-window UI state (selection, mode, panels, pick mode); `useSyncExternalStore` over the document replica.
7. **i18n:** English only in v0.1, strings centralised in `messages/`, errors and warnings rendered from code + params, no library ([internationalization](#internationalization)).
8. **Typography:** system fonts at 13 px base with tabular numerals ([type](#type); 14 px before the design system).
9. **Control sizes:** 44 px in run mode, 28 px elsewhere ([sizes](#spacing-radii-sizes); 32 px before the design system).
10. **Viewport mouse:** selectable presets as a setting; default left-drag orbit, right-drag pan, wheel zoom to cursor; a Fusion 360-style preset and others where cheap ([selection and picking](#selection-and-picking)).
11. **Confirmations and run safety:** undo instead of confirm for document edits; a pre-flight dialog before every run, the virtual machine included; hold, stop and reset are never confirmed; `Escape` = feed hold while streaming; no single-key resume ([confirmations](#confirmations), [run safety](#run-mode-safety-ui)).
12. **Window chrome:** native title bar and native application menu.
13. **Panels:** `react-resizable-panels` (MIT).
14. **Testing:** Vitest + Testing Library + jsdom + axe-core for components, plus a dev-only gallery screen for manual review; the Playwright end-to-end tests cover the real app screens, not the gallery (decided 2026-11-21, [testing](#testing)).
15. **Outdated evaluation:** keep the last mesh, draw the edited operation's outline live, tint the mesh and show "Updating…" only after 300 ms ([evaluation status](#evaluation-status-pending-outdated-failed)).
16. **Reference autocomplete** in the quantity input (3.4): a simple list of valid references (earlier surfaces, tool parameters).
17. **Desktop look:** native title bar with the document name, then the app name and version (version added by the user 2026-11-21, B20; [app shell](#app-shell)), no logo or app name inside the window; toolbars, panels and a status bar; dense, not cramped.
18. **Accent Amber `#f5b700`, used sparingly:** on icons or parts of icons, selection, toggles and active states (switch, checkbox, segmented thumb, active mode); never a large fill. Accent icons use the saturated amber (`--accent-icon`) in both themes.
19. **No coloured primary button:** primary keeps the neutral surface and differs by a semibold label, a stronger outline and an amber icon; every primary button has an icon. Stop is the only filled control.
20. **Running is amber:** the running machine state takes the accent (play icon, a dot circling the badge edge), departing from IEC 60204-1 green on purpose; feed hold and warnings are orange; tool change is blue with an in-progress animation ([run safety](#run-mode-safety-ui)).
21. **Three severities:** soft warning (neutral, dismissible), hard warning (orange, not dismissible), error (red, impossible value, blocks Generate) ([warnings](#warnings-and-dfm)).
22. **Graphical fields:** every field has an illustration icon whose measured part is an amber line ([field](#field)).
23. **Mode switcher** is its own component, separate from tabs; it sits in the centre of the main toolbar (3.3b, [app shell](#app-shell)).
24. **Rich motion:** indicators slide, toolpaths draw in, selections pulse; every animation explains something and turns off with reduced motion ([motion](#motion)).
25. **Contrast by APCA:** colour contrast is checked with APCA Lc targets per role instead of WCAG 2 contrast ratios ([colour](#colour), [ADR 0017](../decisions/0017-apca-contrast-for-design-tokens.md)); red text has its own token and muted text a secondary role ([ADR 0018](../decisions/0018-danger-text-and-secondary-text-role.md)).
26. **Drag to reorder (D45, 2026-11-22):** ordered lists reorder by dragging a dotted grip in the row's action slot, with a drop indicator line, smooth motion and the move command's refusal when a drop is invalid; the ↑/↓ move buttons are gone, `Alt+↑/↓` stays and moves are announced politely ([reordering](#reordering-lists-d45)).
27. **Row actions in context menus (DF67, 2026-11-24):** a list row's actions open by right-click and by `Shift+F10` / the Menu key on the focused row (`ContextMenu`, `openContextMenu`), not from a "…" button on the row, so a row's name and status icons never move or hide on hover (the user: "prefer RMB menus overall in the app for consistency"). Applied to the plan setup panel, and since DF70 to every list row: the design operation list ([row menu](#feature-rows-and-add): its "…" and Remove buttons are gone, `Delete` removes a top-level row) the Shape Editor's [segment table](#shape-editor) (its "Actions for segment N" button on # is gone), and the Shapes dialog's [shape rows](#navigator-and-add) (DF70 follow-up: their hover Remove button is gone, the menu holds Remove; `Delete` still removes). **Discoverability** (DF70): a row with a menu lists `Shift+F10` in its `aria-keyshortcuts` and is described by one hidden hint per list, "Right-click or Shift+F10 for actions." (`aria-describedby`; the segment table's keys description says it instead, since its cells are the focus targets); there is no visible per-row hint – right-click is the desktop CAD convention, the hover tooltip stays the row's name, and a hint on every row would be noise. Panel menus stay buttons (the plan picker's "Plan actions", the Add menus); a row's single inline action that is its keyboard path stays too (a clone instance's Skip / Restore). Not yet moved (listed by the DF70 follow-up audit, always-visible inline buttons, not hover ones): the Shape inspector's item rows (grip and Remove), the Clones rows (grip and Remove), a Clones source's remove (×), the tab positions' Remove, the library cutting-data presets' Remove, the job indicator's Pause/Resume and Cancel, the start panel's Restore / Discard of a recoverable project, and a warning's dismiss (×).

## Design tokens

Tokens are **CSS custom properties** on `:root` in `tokens.css`, consumed by CSS Modules ([decision 4](#decisions)). Values come from the [design system](#design-system); this section fixes names and structure.

- **Semantic** tokens (below) are the only tokens components use. The design system sets them directly; Radix Colors scales ([decision 3](#decisions)) were the starting point for the neutrals and feedback hues, and primitives (`--gray-*`, …) are added to `tokens.css` only if a value is needed by several semantic tokens.
- A theme is a set of semantic values: light on `:root`, dark under `:root[data-theme='dark']` and under `prefers-color-scheme: dark` unless `data-theme='light'` is set; the setting offers Light / Dark / System, default System ([decision 1](#decisions)). Classes `.t-light` / `.t-dark` scope a theme to a subtree (the gallery).

Units: `rem` for type and spacing (so Electron zoom scales the UI), `px` only for hairlines (1 px borders). The viewport reads its colours with the `useTokens(ref, names)` / `useToken(ref, name)` hooks (`viewport/useTokens.ts`: `getComputedStyle` on the viewport element, so theme scopes apply; re-read on theme change), so there is one source of truth for three.js too.

Rules:

- Contrast is measured with **APCA** (APCA-W3 0.0.98G-4g), not WCAG 2 ratios ([decision 25](#decisions), [ADR 0017](../decisions/0017-apca-contrast-for-design-tokens.md)): the lightness contrast `Lc` of a foreground on its background (order matters; negative for light on dark) must reach the target of its role, in both themes ([accessibility](#accessibility)). Targets follow the APCA Bronze levels at the sizes and weights we use; our 10–13 px text is below Bronze's font minimums, so they are floors:

  | Role      | \|Lc\| ≥ | Used for                                                                                                                              |
  | --------- | -------- | ------------------------------------------------------------------------------------------------------------------------------------- |
  | read      | 75       | Text read for content at 11–13 px, regular (400): body, values, menus, error text                                                     |
  | secondary | 60       | Secondary text at 11–13 px (`--text-muted`): labels, hints, notes, ids, descriptions under a title, read-only values; never body copy |
  | label     | 60       | Text at 10–13 px, medium/bold (500–600): button labels, chips, badges, tooltips                                                       |
  | spot      | 30       | Non-content text: placeholders, unit suffixes, metadata, disabled (`--text-faint`)                                                    |
  | icon      | 45       | Outline pictograms with fine detail (1.5 px stroke, 12–16 px)                                                                         |
  | mark      | 30       | 1–2 px control outlines, focus ring, solid indicators ≥ 5.5 px                                                                        |

  Heading-size text (≥ 24 px bold) would take Lc 45; no token pair is used only at that size. The pairs and their roles are listed in `src/renderer/src/ui/tokens.test.ts` (`PAIRS`), which computes them from `tokens.css`; every pair meets its target in both themes (values adjusted 2026-11-21, [design system](#design-system)). Text people must read as body copy uses `--text`, not `--text-muted`. Red text uses `--danger-text` (read / label); `--danger` pairs are marks and icons. Viewport lines (feature edges on part, hover and outdated surfaces; stock, toolpaths (feed, rapid, plunge), tool, axes and the error marker on `--bg-viewport`) take the mark target; the grid and surface tints are quiet area fills with no target.

- Colour never carries meaning alone: every status also has a label or icon (and shape for machine states).
- Safety colours follow the IEC 60204-1 indicator meanings (red = emergency/alarm, orange/amber = abnormal/attention, blue = action required, grey = neutral/off) with one deliberate exception: running uses the amber accent instead of green ([decision 20](#decisions)).
- The accent appears as a line, an icon part, a thumb or a check, never as a large fill; `--accent-calm*` from the page is for proposal callouts in docs only.

### Spacing, radii, sizes

- Spacing on a 4 px grid: `--space-0-5` 0.125 rem, `--space-1` 0.25 rem, `-2` 0.5, `-3` 0.75, `-4` 1, `-5` 1.25, `-6` 1.5, `-8` 2 rem. Component padding uses `-2`/`-3`; between panel sections `-4`.
- Radii: `--radius-xs` 3 px (chips inside controls), `--radius-sm` 5 px (inputs, buttons), `--radius-md` 7 px (popovers, cards), `--radius-lg` 10 px (dialogs), `--radius-full` (pills, status chips).
- Control heights: `--control-sm` 1.5 rem (dense tables), `--control-md` 1.75 rem (default, 28 px), `--control-lg` 2.75 rem (run-mode controls). Pointer targets are ≥ 24 × 24 px everywhere (WCAG 2.2 target size) and ≥ 44 × 44 px in run mode ([decision 9](#decisions)), which may be used on a shop touchscreen.

| ------------ | ----------------------------------------- | ------------ | --------------------------- |

### Motion

- Durations `--motion-instant` 80 ms (press), `--motion-fast` 120 ms (hover, colour), `--motion-base` 180 ms (popovers, panels, the field support area pulling out), `--motion-slow` 280 ms (dialogs, segmented thumb, camera view changes), `--motion-emphasis` 450 ms (selection pulse), `--motion-draw` 900 ms (toolpaths drawing in). Easing `--ease-standard` `cubic-bezier(0.2, 0, 0, 1)`, `--ease-emphasized` `cubic-bezier(0.2, 0.8, 0.2, 1)` for things that arrive, `--ease-exit` `cubic-bezier(0.4, 0, 1, 1)` for things that leave.
- `--delay-tooltip` 450 ms. `--delay-indicator` 300 ms: spinners, "Updating…" chips and progress for short work appear only after this delay, so fast work never flickers.
- Motion explains a change (where a panel came from, what moved, what is selected). Only ongoing processes loop: progress, the running badge's circling dot and the tool-change badge's swap icon and light sweep.
- `prefers-reduced-motion: reduce` (and the matching app setting, `data-motion='reduce'` on the root) sets every duration to 0 and replaces camera animations with cuts; progress bars and the moving indicator stay, without animation of their own beyond the value change. Looping indicators render a static fallback via `useReducedMotion()` (the running badge drops its circling dot, the tool-change badge its sweep).

## Components

### Radix wrapping pattern

Per [ADR 0012](../decisions/0012-radix-primitives-own-styles.md): Radix primitives, copied-in wrappers in the shadcn/ui style (we own the code; no shadcn dependency), our tokens.

- Only `src/renderer/src/ui/` imports Radix (`radix-ui` package); an ESLint `no-restricted-imports` rule enforces it like the other [layer boundaries](../decisions/0015-eslint-with-typescript6-api.md). Mode screens use `ui/` components.
- Each wrapper exposes a **small, typed API**: our variants (`variant: 'default' | 'primary' | 'ghost' | 'danger'`, `size: 'sm' | 'md' | 'lg'`) as props, rendered as `data-variant` / `data-size` attributes and styled in the CSS module. No `className` overrides from screens except layout (margin, grid placement) through a `className` prop that the wrapper appends.
- Style interaction states with Radix's data attributes (`[data-state='open']`, `[data-highlighted]`, `[data-disabled]`) and `:focus-visible`, never with JS-computed classes.
- Keep Radix's accessibility behaviour (focus trap, roving focus, `aria-*`); never re-implement it. Keep `asChild` where composition needs it (e.g. a `Tooltip` around an `IconButton`).
- Portals render into `document.body` by default, which inherits the root's `data-theme`; inside a `ThemeScope` (`.t-light` / `.t-dark`) they render into the scope, so they keep its theme.
- CSS module classes are read with brackets (`styles['button']`): the renderer keeps `noPropertyAccessFromIndexSignature`.
- Every icon-only control has an accessible name (`aria-label`) and a tooltip with the same text plus its shortcut.
- **A pressed trigger keeps its tooltip down** (DF48, UX audit #24): `Tooltip` stays closed after its trigger is pressed (pointer down, `Enter`, `Space`) until the pointer re-enters it or focus leaves it for another control (not for the menu or dialog it opened), so a tooltip never covers an open menu or reappears when focus returns from it.
- `Dialog` takes `size` `sm` (340 px, confirmations), `md` (420 px, the default) or `lg` (560 px: reports with a list beside a picture, the SVG import report).
- Header comment of every wrapper links back to this doc.
- **Dialog actions live in the footer** (dogfood re-report of DF12): a `Dialog`'s outcome buttons – Cancel or Done and its one primary action ("Create part", "Create plan", "Save as variant") – go in its `footer`, primary last at the end edge, never at the end of the body. The footer stays pinned to the dialog's bottom edge (`position: sticky`) while a tall body scrolls, so the primary action is always visible. Actions that act on part of the body ("Save to library", "Open library") may stay beside it.
- **Inspector drafts follow the same rule** (DF47, UX audit #5): a draft held in the inspector until it is committed (the [Clones draft](#clones)) ends in a footer bar pinned to the inspector's bottom edge, styled as a dialog footer (top border, `--bg-chrome`), with Cancel first and the primary last at the end edge. The body above it scrolls on its own, so the footer never covers a field and is always visible.

### Field

The `Field` component (3.3, quantity behaviour in 3.4) is a grid: label column (illustration + label), a lock column, the input, and a support area under the input.

- **Illustration** (`--icon-xl` 28 px, viewBox 20, 1 px grey drawing): draws the feature and makes the measured part itself one amber line (1.4 px, butt caps, on the same centreline as the drawing; 1.6 px while focused). No dimension arrows. Length runs end to end along the slot, width across its middle, depth the wall, the stock's length, width and thickness an edge of an oblique block ([DF11](#stock-dialog-df11df13)), stepdown the riser, corner radius the arc, chamfer the face, feed the travel line. The icon keeps full colour (`--text-muted` drawing, `--accent-icon` line) and saturation whether the field is focused or not (decided by the user 2026-11-21, was 35 % at rest); focus only thickens the amber line. Read-only and disabled fields stay fully desaturated at reduced opacity. The drawing meets the APCA icon target on `--bg-app` and `--bg-chrome` (`tokens.test.ts`).
- **One illustration per meaning, per panel** (DF25, user's dogfood finding): within one inspector or form no two fields that measure different things share an illustration. Positions have their own (`positionX`, `positionY`: a point with its amber offset from the origin), as do diameter, rotation, floor radius, slot width, tab width/thickness, breakthrough, counterbore and countersink sizes, head sink, flute length, stickout, overall length, shank, tip diameter, spindle speed, plunge rate, stepover, allowance, finish stepdown, chip break, clearance and retract heights (dashed planes), arc tolerance and the [Clones](#clones) row fields (DF47: columns and rows as a row or column of instance squares, the step along u or v between two squares, a count as three squares on a span, a polar direction and distance, an arc's radius, centre angle, sweep and step angle, an along row's path, start offset and spacing; drawn as rounded squares for instances, the source solid, copies dashed) (`ui/icons/field/FieldIcon.tsx`, `FIELD_ICON_NAMES`). Deliberate repeats, where the fields are one quantity in several roles: a minimum/maximum pair (spindle speed in the machine form), per-axis rows of one quantity (machine travel, feed, acceleration, steps per mm use length/width/depth for X/Y/Z), and the tab position rows (`tabs`).
- **Row alignment** (DF27): the illustration and the lock are centred on the control's height (`--control-md`), so row 1 is never taller than the input and the support area always tucks under the input; a field with a support area lets its label span both rows, so a wrapped label never pushes the support area down.
- **Lock** sits between label and input, outside the input; pressed, the other recommendations follow this value.
- **Lock rule** (the user's; accepted 2026-11-21, implemented in task 3.14): a lock appears only on a field that has a recommendation (auto) mode, while that mode is on; it means "use this value as a starting point, the other recommendations adjust to it". Without a recommendation, or with it off, the lock is **hidden** (not disabled): `Field` renders it only when the `lock` prop is given. It is **disabled** when its value is invalid, contradicts a limit, or makes the calculation impossible: `lock.disabledReason` makes it `aria-disabled` (stays focusable, a click does nothing), with the reason as its tooltip and as visible text in the support area (a lock-icon note), linked by `aria-describedby`. A toggle button with `aria-pressed` and a constant name ("Lock Spindle speed"; `lock.name`, default "Lock <label>"). Typing a value never presses the lock. Only plan mode's feeds fields have a recommendation mode ([plan-v0.1.md § Locks and auto mode](../modes/plan-v0.1.md#locks-and-auto-mode)); stickout (a tool default, not a recommendation), read-only fields and design fields (DFM suggests fixes, nothing recommends one value from others) have no lock, also on the [design system](ui-design-system.html) page.
- **Adjust panel** (DF9, decided by the user 2026-11-22; replaced the pencil inside the input): focusing a value field opens its adjust panel while the input keeps focus, so typing goes on in the input. The panel holds the step size (.001–100), −/+ around the value, the recommended value ("Use …") where there is one and, on a field with a pick hook, the [pick toggle](#selection-and-picking). It sits under the field, below the support area and aligned to the input's end, always below (never flipped over the field), and closes when focus leaves the field and the panel, on Escape, on a valid Enter (done editing) and after "Use …"; a click in the input reopens it. While open it covers what lies under it, and a press on it never reaches that: Enter, Escape or Tab clear the way. A pointer press in the panel never takes focus from the input. A field with nothing to adjust (read-only, `dense`) opens nothing. Nothing is drawn inside the input box any more (no pencil, no pick button), so Tab goes from field to field; the amber "fix available" pencil went with it (the recommended value shows in the panel, DFM fixes in the support area).
- **Adjust panel, keyboard and screen readers:** the input is a `combobox` with `aria-haspopup="dialog"`, `aria-expanded` and, while the panel shows, `aria-controls` naming it (a non-modal `dialog` named "Adjust Width"). While the [reference list](#quantity-and-expression-input) is open it takes the panel's place and the combobox points at that listbox. The panel's controls are out of the Tab order: `⌘↓` / `Ctrl+↓` (or a plain `↓` when the text cannot step and there are no references to list) moves focus to its first control, arrow keys, Home and End move between its controls, Escape closes it and returns focus to the input, Tab leaves for the next field and Shift+Tab goes back to the input. Escape in the input closes an open panel first (cancelling a live session, [below](#quantity-and-expression-input)); the next Escape reverts the typed text as before. In pick mode Escape cancels the pick first.
- **Support area:** one group under the input that looks pulled out from under it (no top corners, inset from the input's rounding, a small shadow from the input, slides in with `--motion-base`). It holds the echo ([quantity input](#quantity-and-expression-input)), the highest-severity status with its fix button ("Use 3.00": a warning's fix shows a check, a fix that adds something a plus, e.g. "Add to library"; `FieldMessage.fix.icon`; a fix may have one plain alternative action beside it, `FieldMessage.alternative`, e.g. "Use wexme 1/4″ 1F (6.22 mm)" with "Add to library" (DF42): then both buttons sit on their own row under the text, wrapping, and a long label wraps inside its button), and further notes collapsed ("1 dismissed · Show"). Its background follows the severity ([warnings](#warnings-and-dfm)). Read-only fields show it dimmed with a dashed border.
- **Support area collapse** (decided by the user 2026-11-21): when the echo goes away on blur and a pointer is pressed (the click that moved focus), the echo stays until the pointer is released and its click has been dispatched (`Field/pointerRelease.ts`), so the click lands on what was under the pointer at pointerdown. Then the echo, or the whole support area if it held only the echo, collapses in height with `--motion-base` and `--ease-standard` (Web Animations); with reduced motion it goes at once. Leaving with the keyboard collapses it right away (animated).
- Narrow panels: the input column narrows before the label column; below 260 px a fix button wraps under the text (a lone dismiss icon stays at the text's end). Field lists in a container (`container-type: inline-size`) narrower than 20 rem put the label above the input, the lock and input on the next row; without a lock the input and its support area start at the label's edge, not indented by an empty lock column (UX audit, 2026-11-22) (decided in 3.6: in the 16 rem navigator and the 20 rem inspector the 124 px label column left the input no room; approved by the user 2026-11-21, on the [design system](ui-design-system.html) page).

### Mode switching

- Modes are a three-way `ModeSwitcher` (its own component, [decision 23](#decisions)) in the centre of the main toolbar, `Ctrl/Cmd+1/2/3`. The mode is per window (Zustand UI store).
- Switching is instant and never blocked: jobs, evaluation and a run keep going. Each mode keeps its own selection and camera.
- A mode without its input shows an `EmptyState` instead of disabled controls: Plan without a part ("Design a part first", button to Design). Run needs no project (hardening DF80, [run.md § Run without a project](../modes/run.md#run-without-a-project-df80)): without a plan its navigator offers "No plan (manual control)" with a library machine (hardening DF31, [run.md](../modes/run.md#connect-without-a-plan-df31)); without a project it is manual control only (a "Machine" select, no Plan select), and the inspector's run section is the `EmptyState` "Open a project to run a plan" with "Open project". Connection, homing, jog, work zero, Probe Z, overrides, Reset and the DRO work as with a project. Plan with a part but no plan shows the [Plan start card](#plan-start-df29) over the view.
- **Side panels follow the mode** (DF30, user's dogfood finding): the toolbar, viewport and dialogs switch at once; the navigator's and inspector's content slides out toward its window edge (`--motion-fast`, `--ease-exit`, 1.5 rem and fading) and the new mode's content slides in from there (`--motion-base`, `--ease-emphasized`). Under reduced motion the content swaps at once (the tokens are 0, so no slide phase is set). `shell/useModePanels.ts`.
- **Side panels per mode** (DF30): each mode remembers whether its navigator and inspector are shown; the panel toggles (buttons, View menu) write it for the current mode (`sidePanels` in the [settings](#settings), so it is kept for the next start), and switching to a mode opens or closes the panels to its state when its content comes in. A mode never toggled shows both. The narrow window's inspector overlay is not a panel: it starts closed in every mode as before. Dragging a panel shut is a layout change, not a per-mode choice.
- Agents never switch the user's mode or steal focus; their edits appear in place ([undo](#undo-and-redo)).

### Project files

New / Open / Save in the window (task 3.6; `shell/project/`, shared by every mode). The window calls the app-scope commands agents call (`project.create`, `project.open`, `project.save`, `project.recovery.*`); only the native file dialogs (`window.dfyom.files`; also the gCode export's `chooseExport`, [plan mode](#plan-mode-task-37)) and the window choice (`window.dfyom.window.openProject`, below) are window plumbing.

Under them a "Machine" section (DF80): "Connect, home and jog the machine without a project." and "Go to Run", which switches the window to Run mode, so the machine is reachable from the first screen without creating a project.
- **New / Open go to a new window when the window has a project** (decided by the user 2026-11-21, replacing the 3.6 "replace the window's project"): an empty window (no project) is reused; a window with a project keeps it, so nothing is closed and nothing asks about unsaved changes. The window runs every opening command (`project.create`, `project.open`, `project.recovery.resolve` with `restore`) through `window.dfyom.window.openProject`, window plumbing in main (`src/main/ipc.ts`, decision logic `src/main/window-open.ts`) that picks the window, runs the command through that window's session (the same command and result as `call`) and adds `window: 'this' | 'other' | 'new'` to the reply's value:
  - a file already open in a window (this one or another) is not opened twice: that window comes to the front (`other`; `this` when it is the asking window) – the [lock](../architecture/persistence.md#lock) would refuse a second open in this instance anyway, and `project.open` answers an open file with its key (`alreadyOpen`);
  - otherwise the asking window when it has no project (`this`), else a new window (`new`). The new window is created hidden, bound to the project by the command, and shown only once the command succeeded; a refused command (recovery, lock, error) closes it unseen and the asking window shows the answer as before (recovery prompt, foreign lock, error dialog), so "Restore" and "Try again" route the same way. Discarding recovered changes binds no project and runs in the asking window.
  - The new window opens in front, cascaded 22 px right and down from the asking window with its size, back to the work area's top-left corner when it would leave the display (`cascadeBounds`; a window without a source window starts from the [remembered window](#remembered-window-state-and-dialog-folders), else the default size, centred). Window state is per window: mode, selection, camera, plan choice and dialogs start fresh (design mode); panel layout comes from the [settings](#settings) like any new window.
  - **No window open** (macOS, after closing the last one): File → New project… / Open project… open an empty window (its start panel offers both); the other menu items need a window and do nothing. The Dock icon opens an empty window too (`activate`).
  - Agents address projects, not windows: an agent's `project.open` / `project.create` / `project.recovery.resolve` that starts a project runtime gets a new window bound to it (cascaded the same way; an empty window is not reused, so an agent never takes over the window the user is in); a project already open (`alreadyOpen`) gets no second window. The CLI's headless entry has no windows ([llm-api.md](../architecture/llm-api.md#processes-and-hosting)).
  - **Opening from Finder (hardening U5):** the packaged app declares `.dfyom` as its document type ([packaging.md](packaging.md#file-association)), so a double-click, "Open With" or a file dropped on the Dock icon opens it; so does a launch with file paths in its arguments (`DFYOM.app/Contents/MacOS/DFYOM a.dfyom`). Main (`src/main/open-file.ts`, Electron-free and unit-tested; wiring in `src/main/index.ts`) collects the paths from macOS `open-file` (queued until the app is ready, so a file that launched the app opens in the first window instead of beside it), the first launch's arguments and a second launch's arguments, and hands each to one project window (`window.dfyom.window.onOpenFile`), which runs **File → Open's own path** with it (`files.openFile`: the same window choice, the recovery prompt, the foreign lock with "Retry in 2 min", the incompatible-project prompt and error dialogs; Open closes nothing, so nothing asks about unsaved changes). The window: the last focused project window when it has no project, else any project window without one, else the last focused project window (its Open puts the file into a new, cascaded window, or brings the window already showing it to the front), else a new empty window. A window takes its files one after the other, so several files from one Finder selection each get their own window. The Library and licences windows never take a file. Only paths ending in `.dfyom` are taken from arguments (flags and the value of `--data-dir` are skipped; relative paths resolve against the launching process's folder).
  - **One app instance per data folder:** a second launch on the same data folder ([persistence.md](../architecture/persistence.md#files-and-folders)) hands its arguments to the running instance and quits (`app.requestSingleInstanceLock`, which Electron keys by the `userData` folder; the running one gets `second-instance`); without a file path the running instance brings its last project window to the front, or opens an empty window when none is open. A launch with another `--data-dir` is an independent instance as before (the end-to-end tests run side by side this way), and the development build without `--data-dir` (`npm run dev`) takes no lock, so it never hands itself to an installed DFYOM on the same folder. The headless CLI (`dfyom mcp`, `dfyom <name>`) is not an app instance and is not affected ([llm-api.md](../architecture/llm-api.md#processes-and-hosting)).
- **Save** writes to the project file; an untitled project goes to **Save as**: the native save dialog (default name from the project, `.dfyom` added), then `project.save { target, confirm: true }` – the OS dialog already asked before replacing a file. The replica takes the new file from the save's outcome (`filePath`).
- **Recovery prompt:** `project.open` answering `persist.recovery` opens "Restore unsaved changes?" with "Restore changes" (primary) and "Discard changes" (danger, confirmed): `project.recovery.resolve`.
- **Foreign lock:** `persist.locked` opens "The project is open elsewhere" with the error, "Try again", and "Retry in 2 min" (a countdown, then it opens again by itself): a lock of a stopped instance on another computer can be taken over after 2 minutes ([persistence.md](../architecture/persistence.md#lock)).
- **Incompatible project (pre-alpha, hardening B6):** `project.open` failing with incompatible data ([persistence.md § Open](../architecture/persistence.md#open)) opens "This project can't be opened": it was saved by an earlier pre-alpha version whose data no longer loads, and pre-alpha versions don't upgrade projects; the `ErrorMessage` shows what failed. "Cancel" and "Discard and start fresh" (danger), which asks again ("Discard the content of “file”?": the file is replaced by an empty project of the same name, for good) before `project.open { file, reset: true }`.
- Other failures show the `ErrorMessage` in a dialog ("The project could not be opened / saved / created").

## Shell state

### Document replica

`state/replica.ts`, the read side of [commands.md project state](../architecture/commands.md#project-state):

- At start and whenever main pushes `project.bound` (the window's bound runtime changed: bound, closed, reopened), the window takes a snapshot (`window.dfyom.project.snapshot()`: key, document, revision, the action-log `seq` it includes, file, unsaved flag), then applies the `project.onEvent` patch stream in `seq` order. Events that arrive while a snapshot is on its way wait and are applied after it (those it already includes are skipped).
- A gap in `seq` or a patch that does not apply starts a new snapshot (resync). Main subscribes to the log before it pushes `bound`, so a snapshot taken after the push misses nothing.
- Unsaved changes: revision ≠ the revision of the last successful `project.save` event (the snapshot's `dirty` flag seeds it). Undo and redo are commits, so they count as changes, as in the host.
- The UI reads it with `useSyncExternalStore` (`useReplica()`), never edits it, and sends every change as a command (`window.dfyom.call`). Undo/redo names come from `history.list` after each revision; jobs from `job.list` on job events, polled every 500 ms while one runs (progress ticks are not in the action log), one read per window shared by the status bar and the Apply button (`createJobsFeed`), nothing while no job runs. Run mode follows the run job with `job.get` every 250 ms while it runs; the machine status itself is pushed (`window.dfyom.run.onStatus`), only when it changed. An idle window does no work: no polling, no viewport frames ([idle cost](../research/2026-11-23-idle-cost.md)).

### Remembered window state and dialog folders

What main remembers between runs without a setting (B18, B19; user requests 2026-11-21): `<appData>/app-state.json` (`src/main/settings/app-state.ts`), main-only (never pushed to windows, not reachable by agents), written atomically and debounced 500 ms, flushed on quit. A missing, unreadable or invalid file starts empty (a bad field falls back alone), like the [settings](#settings): no confirmation, no migration.

- **Library window:** its own record (`libraryWindow`, same fields), used when it opens; it never cascades a project window ([ui-library-window.md](ui-library-window.md#implementation-task-l1)).
- **Last window:** the normal bounds (`getNormalBounds`) of the window last moved, resized, maximized, made full screen or closed, with its maximized and full-screen state (minimized is not remembered). One record, not one per window: windows are not reopened at launch (no session restore).
- **Where a new window starts** (`windowStart`, `src/main/window-state.ts`): opened from a window (the asking or focused one) → cascaded from it ([project files](#project-files)); else, with no other window open (launch, or the first window after closing all on macOS) → the remembered window as it was, maximized or full screen again when shown; else → cascaded from the remembered window, never maximized. Without a record: the default 1440 × 900, centred. A remembered window is first made visible (`visibleBounds`): on the display it overlaps most, no larger than its work area and moved inside it; when its display is gone, centred on the primary display.
- Maximize and full screen are applied when the window is shown, so hidden end-to-end runs (`DFYOM_HIDE_WINDOWS=1`) never show a window; restoring bounds alone does not show one.
- **Dialog folders:** each kind of file dialog (`DialogKind`: `project` for Open, Save as and the quit's Save all; `gcode-export`; `reference-import` for the R3 reference import; `svg-import` for the I1 SVG import) starts in the folder last chosen in a dialog of that kind (`defaultPath`; a save dialog gets the file name in it), if that folder still exists. A new dialog kind adds its key to `DIALOG_KINDS` and passes it to `showOpen` / `showSave` in `src/main/file-dialogs.ts`.

## Interaction

### Reordering lists (D45)

Ordered lists whose order the user sets – the design navigator's operation list (plain and feature rows), the Clones rows editor, the Shape Editor's item list and (hardening U3) the plan navigator's setups and each setup's plan operations – reorder by drag and drop (user, D45, 2026-11-22: replaces the ↑/↓ move buttons).

- **Grip:** a dotted grip (2 × 3 small dots, 1.6 px, `--text-muted`, `--text` on hover; cursor `grab`, `grabbing` while dragging) at the row's start, **before the row icon** (dogfood DF24; it sat in the action slot before Remove until then). It is 14 px wide and as tall as the row; a list with one row keeps the empty slot so icons line up. It is a pointer convenience, not a tab stop: its tooltip (`title`) is "Drag to reorder (Alt+↑/↓)". Rows that move with an outer feature (owned and nested rows) have none.
- **Plan lists** (hardening U3, 2026-11-23): setups and plan operations have the design list's grip in a start gutter before the row icon (shown with the row's actions; a setup's on its name line), the same small dots. A setup carries its operations with it. A plan operation drags **within its setup**; moving into a neighbouring setup of the same direction stays with `Alt+↑/↓` and the row menu's "Move to …" (a drop target across setups would need the setups' direction rules shown while dragging: not built). The row menus keep Move up / Move down. A drop the core refuses (`plan.order`) puts the row back with the shake and shows the refusal under the list, as the menu does. Read-only plans show no grip and reserve no gutter. Renders: `design/features/renders/hu3-plan-drag-{light,dark}.png` (`e2e/setups.e2e.ts` with `DFYOM_RENDERS=1`).
- **Auto-scroll** (hardening U3): while a row is dragged with the pointer within 32 px of the top or bottom edge of the list's scrolling container (the navigator, the inspector), the container scrolls, faster closer to the edge (up to 14 px a frame), and stops at its end or when the pointer leaves the band. The drop indicator and the lifted row follow the scroll. `edgeScrollSpeed` is pure and unit-tested.
- **Drag:** pressing the grip and moving 3 px lifts the row (`--shadow-2`, `--bg-raised`, follows the pointer vertically); a **drop indicator line** (2 px, `--accent`) marks the gap the row lands in, between whole rows only (a feature row with its children counts as one). Releasing drops: one move command (one undo step), exactly what the same number of `Alt+↑/↓` steps would give. Releasing over its own place, `Escape` or a cancelled pointer puts the row back.
- **Motion:** after a drop or an `Alt+↑/↓` step, rows glide from their old to their new places (`--motion-base`, `--ease-standard`, FLIP); the dropped row glides from where it was let go. Reduced motion: no glide.
- **Refusal:** where the outcome is known before the drop (the design list checks the reordered operations with the core's `checkReferences`), the indicator turns `--danger` with a `not-allowed` cursor and the reason shows under the list while hovering there. A refused drop (pre-checked or refused by the command) puts the row back with a short shake (none with reduced motion) and shows the **move command's refusal** under the list – the same text `Alt+↑/↓` gives ("Not moved: Pocket 2 uses facing1.floor, which has to come before it."). It stays until the next move.
- **Keyboard and screen readers:** `Alt+↑/↓` on the row moves it one step (unchanged); every move, by pointer or keys, is announced politely ("Moved Profile 1 to position 1 of 3."), refusals likewise.
- **As built:** `ui/Reorder` (`useReorder`: native pointer events, no dependency; `DragGrip`; `ReorderStatus`, the polite announcement and the visible refusal); `dropGap` / `dropIndex` are pure and unit-tested. The plan navigator's setups and plan operations use it since hardening U3 (`SetupList`: one `useReorder` for the setups, one per setup for its operations) and keep their move up / move down menu items and `Alt+↑/↓`.

### Quantity and expression input

Every dimensional field is a `QuantityInput` over the [quantity model](../architecture/quantities.md) (task 3.4). The parser, units, tolerance grammar and error codes are owned there; these are the UI rules.

- **Show what was entered.** The field shows the source as typed (`1/16"`, `D/2 ±0.01`). When unfocused and the source is in another unit than the project unit system or is an expression, the computed value follows in muted text at field precision (`1/16" · 1.588 mm`).
- **Echo the interpretation while typing,** when it adds something to the text. Below the field, a one-line preview states how the input is read: `= 1.588 mm`, `= 25.4 mm, upper +0.1, lower −0.05`, `= 3 mm (from pocket1.floor.z)`. This is the general answer to the ambiguous inputs in the plan's known issues (`+1/2` as a deviation pair, `D -1/2`): the echo shows the reading, and the field's hint for those rule ids offers the intended spelling.
- **Unit suffix:** the bare-number default unit is shown as a muted suffix inside the field; typing any accepted unit of the kind overrides it.
- **Validation timing:** parse on every change (debounced 150 ms) for the echo; show an error only on blur, on Enter, or after 600 ms without typing, never mid-word. The field keeps the raw text when invalid.
- **Commit (v0.2, D13, task P3; [apply.md § Field rule](../architecture/apply.md#field-rule)):** Enter commits a valid value as one command (one undo step) **and applies** (the deferred work of all pending changes: tool choice, draft plans, toolpaths); blur, Tab or a click away commit only; Escape reverts to the stored source. An invalid value never commits and Enter then applies nothing; the document and viewport keep the last valid value, and the field stays marked until fixed or reverted. Fields with local form state (stock setup, dialogs) commit only: they sit outside the shell's `ApplyScope`.
- **Optional fields (empty = unset):** a field whose value may be absent (min spindle speed, spindle power) is `optional`: emptying it (blank or only spaces) and committing commits _unset_ instead of an error, and an empty optional field is never marked. A required field (the default) treats empty text as invalid ("Enter a value."). The field says it is optional in a note under it ("Optional: …"), not in the input.
- **Errors in place:** `issues[].params.offset` underlines the position in the text; the message comes from the catalogue keyed by `rule` ([errors](#errors)); a `hint` param becomes a one-click fix button ("Use `1 1/2"`").
- **Steppers:** `↑`/`↓` step a plain literal by the field's step in the source's unit (`Shift` ×10, `Alt` ×0.1); disabled for expressions. No spinner buttons.
- **Tolerance:** typed in the same field. An untoleranced field shows the inherited general tolerance as muted text with its scope ("±0.1 mm from part").
- **Recommended range:** where a check or the calculator knows one, the field shows it as a hint ("recommended ≥ 3.2 mm") and a `Term`-style tooltip explains what it depends on and what it affects (principle §5); a [DFM suggestion](#warnings-and-dfm) offers "Apply".
- **Recommended value** (`recommended` prop): a single value the app derives for this field, such as a facing's depth down to the reference model ([reference-model.md § Facing depth](../modes/reference-model.md#facing-depth-from-the-reference-df4)): the adjust panel (opened on focus, DF9) shows "Recommended … · Use …", "Use" enabled while the stored value differs (the amber pencil cue went with the pencil). It never commits by itself.
- **References:** typing a letter offers an autocomplete list of valid references (surfaces of earlier operations, tool parameters) ([decision 16](#decisions)); a reference that becomes unknown later marks the field with `expression.reference`.
- **Precision:** display precision belongs to the field ([quantities.md](../architecture/quantities.md#value)); the decimal separator is always `.`.

Implementation (task 3.4): [`ui/QuantityInput/`](../../src/renderer/src/ui/QuantityInput/QuantityInput.tsx) renders a `Field` and reads the text only through the core (`quantityFromSource`, `parseLiteral`; pure helpers in `reading.ts`); messages and labels in [`messages/quantity.ts`](../../src/renderer/src/messages/quantity.ts). Props: kind, bare-number default unit (also the display unit), stored `Quantity`, `onCommit` (with `optional`, `onCommit(undefined)` for unset; the pair is the `QuantityCommitProps` union; a second argument `gesture` for adjust-panel steps), `onCancelGesture` (Escape after live steps), optional resolver, references, field rules (`validate`), precision, step, inherited tolerance, recommended value, pick hook (`onPick`, `picking`, `onPickCancel`). Refinements decided while building it:

- **Echo** shows only while focused and only for a reading that is not an error (a stale echo never sits next to an error). It shows only when it adds information (`echoAddsInformation` in `QuantityInput/reading.ts`, decided by the user 2026-11-21: "I enter 15 mm, why would I need to see '15.000 mm'?"): for an expression or reference, a fraction or mixed number, a unit other than the display unit, an asymmetric tolerance, or any text that is not a plain decimal. A plain decimal with no unit or the display unit's own spelling (`15`, `15 mm`, `15mm` in an mm field, `0.5 in` or `0.5"` in an inch field), also with a symmetric decimal tolerance (`10 ±0.05`), shows no echo; with an inherited tolerance it shows only that ("±0.100 mm from part"). Errors, their verified fixes and the other support items are unaffected. The inherited general tolerance is part of the echo ("= 1.588 mm · ±0.100 mm from part"), not shown at rest. Deviations show with their sign at field precision ("upper +0.100, lower −0.050"); a formula names its references ("(from pocket1.floor.z)").
- **Computed value at rest:** for an expression, or a literal whose written unit is not the display unit; the unit suffix hides when a unit is typed or the computed value shows.
- **Error marks** are drawn by a text overlay of the input (wavy `--danger` underline from `offset` to the next space; at the end of the text a short stub). A stored formula that no longer reads (reference gone) is marked at once, without typing.
- **Fixes** are verified with the core before they are offered, and applying one commits it. Known ambiguities get fixes: a trailing `+n/d` / `-n/d` that fails `order` ("“+1/2” reads as a tolerance (upper +1, lower +2)…", fix `10 + 1/2`, `D - 1/2`); Greek mu U+03BC (fix: micro sign); `hyphenatedMixedNumber` and `ambiguousDivision` hints (first variant).
- **Steppers** (`↑`/`↓` in the field) change the text only; Enter/blur commits. They replace the number between the core's nominal offsets, so unit and tolerance stay as typed (`1.50 ±0.05` → `1.60 ±0.05`; `1/16"` + 0.1 → `0.1625"`).
- **Adjust panel = live gesture** (decided 2026-11-21, D9, for the popover the [adjust panel](#field) replaced in DF9; replaced "closing commits once"): the panel's steps (step .001–100, −/+, recommended "Use …") update the whole app live – model, viewport, live outline, warnings and plan values follow every step – and the session is still **one undo step**. The first step starts a [gesture](../architecture/commands.md#gestures-live-edits) with a unique id (`newGestureId`; since DF9 a session starts with its first step, not when the panel opens, since the panel opens on every focus); each −/+ and "Use …" commits at once with that id (`onCommit(value, gesture)`; the caller passes it as `call(name, args, { gesture })`), and the dispatcher merges the steps into one history entry. Typing in the field ends the session (the next step starts a new one). Closing by focus leaving the field (or "Use …") keeps the value; nothing else is sent. **Escape** (in the panel, or in the input while the panel is open) cancels: without a step it only closes the panel; otherwise the field shows the opening value at once and calls `onCancelGesture(gesture)`, which command callers implement with `useCancelGesture` (`history.undo { gesture }`: reverts and discards the entry, so it cannot be redone). If the entry is no longer on top (someone committed after it), nothing is forced: the field keeps the value and notes "Kept the adjusted value: the project changed after it, so Escape could not revert it." If no step landed (every step's command was rejected, so the stored value never moved), the field just shows the opening value again, without that note. A field without `onCancelGesture` (local form state: stock setup, library dialogs) commits the opening value again instead. Typing in the field stays commit-on-Enter/blur. The panel's title hint names only what acts there ("Esc reverts"); `↑`/`↓` (`Shift` ×10, `Alt` ×0.1) step in the field, not in the panel, where arrows move between its controls (decided 2026-11-21). While steps are still landing (one IPC round trip each) the field shows the latest step and does not flick back to an older stored value.
- **Adjust panel and Apply** (v0.2, D13): steps stay live and pending; closing the panel does not apply, Cmd/Ctrl+Enter inside it does ([apply.md § Adjust panel](../architecture/apply.md#adjust-panel)).
- **Cost of a step** (measured on the exit-criteria project, 2026-11-21): a `design.pocket.update` step with the `plan.draftAutoRebuild` hook takes ~3.5 ms in the dispatcher and a `plan.operation.update` step ~0.4 ms, far below click intervals, so steps are not throttled. The heavy work is already coalesced: part evaluation has its 200 ms trailing debounce and aborts on a newer input ([workers.md](../architecture/workers.md#automatic-evaluation-after-design-edits)), and the renderer's per-revision re-reads (warnings, plan data, undo names) keep only the latest answer.
- **References:** the list opens while typing a name, or with `Ctrl+Space` (and `↓` when the text is not steppable); `↑`/`↓` move, `Enter` inserts, `Escape` closes the list without reverting. Options show the id and the human name.
- **Pick hook:** `onPick(insert)`; the pick toggle in the [adjust panel](#field) or `Alt+P` (a bare `P` would type into the field). `insert(reference)` puts the reference at the last caret/selection, refocuses the field and does not commit. While `picking`, the toggle is pressed and a second press (or `Alt+P`) calls `onPickCancel` (DF10).

### Errors

How an `AppError` reaching the UI boundary ([boundaries.md](../conventions/error-handling/boundaries.md#entry-points-ui-agent-cli-automation)) is shown:

| Situation                                    | Display                                                                                                                                           |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| `issues` with a `path` matching a field      | Inline in the field's support area (`--danger-text`, icon, `aria-invalid`, `aria-describedby`); focus moves to the first invalid field on submit. |
| `issues` without a matching field            | Summary at the top of the form/inspector.                                                                                                         |
| `severity` `info` (incl. `op.aborted`)       | Neutral toast or nothing; cancellation is never shown as a failure.                                                                               |
| `severity` `warn` / `error`, no field        | Inline banner in the panel that started the action, with `userMessage` and a retry button if `retryable`.                                         |
| `severity` `fatal`, `machine.*` during a run | Blocking dialog (run errors: [run safety](#run-mode-safety-ui)).                                                                                  |
| `command.conflict`                           | Not shown for UI sources (never rejected); for queued agent actions see the agent indicator.                                                      |

- Message text: the catalogue in `messages/` maps `code` (and issue `rule`) to a friendly sentence with `params` formatted in the project unit system; fallback is the registry's `userMessage` ([codes.ts](../../src/shared/errors/codes.ts)). The developer-facing `message` and the frames are only in an "Details" expander with a "Copy details" button (for bug reports).
- Every message says what happened, why if known, and what to do next.

### Selection and picking

- Click in the viewport selects the operation (or plan operation) owning the clicked surface; the navigator row and inspector follow. Selecting a row selects in the viewport. Hover highlights (`--vp-hover`) before click. `Escape` clears the selection. Multi-select is later.
- **Pick mode** for surface references (`on`, references in formulas): the field's pick button (a toggle: `aria-pressed`, a second press cancels, DF10; on a value field the toggle sits in its [adjust panel](#field); or `Alt+P` while focused; a bare `P` types) enters pick mode – crosshair cursor, eligible surfaces (horizontal surfaces of the stock and earlier operations, [design.md](../modes/design.md#positioning-v01)) highlighted, others dimmed, a banner "Pick a surface for _On_ · Esc to cancel". Click picks and returns focus to the field. A cancel (Escape, the pressed toggle, anything else that ends pick mode without a pick) is announced politely under the viewport: "Pick cancelled." The same field always offers a dropdown of the eligible surfaces, so picking never needs the mouse. v0.2: eligible faces of every direction for `on` ([face picking](#design-and-plan-controls-v02)).
- Picked and referenced surfaces are named by the operation name and the surface's role ("Pocket 1 floor", "Stock top"), **never their id** (DF43: the `on` dropdown read "Stock top · stock.top"). Where two surfaces would read the same (two operations renamed alike), the label adds the owner's place in the design order ("Pocket floor (operation 3)"); an id the part no longer has reads "Unknown operation". The id stays the option's value and is what a formula is written with: the formula completion list shows the reference name (`pocket1.floor.z`, the formula language) beside the readable label. The same applies to every visible text – selects, menus, toasts, warnings, refusals: items are named by their name, never their id (`itemName`, `surfaceLabel` and `dfmNames` in `modes/design/model.ts`); ids may appear only in tooltips and `data-*` attributes. Texts the core builds and the UI shows as they are follow the same rule, with the ids and paths kept in their structured data for agents: rebuild and library-update blocked reasons and the `stockFit` finding (`partIssueText` in `src/core/design/issue-text.ts`: "Pocket 1 depth: must end above the stock bottom"), progress labels of toolpath generation and export (`planOperationLabel`), and field keys in words ("Feed rate", "the shape's centre X").
- **Face selection (design mode, DF22):** a click on a stock face (`stock.top`, `stock.bottom`, `stock.side[0..3]`) selects that **face** instead of clearing the selection; `Alt`+click selects the face under the pointer when it is a [face target](../modes/design-v0.2.md#face-targets-generalised-on) of an operation (a floor or a tab top; a plain click there still selects the operation). The face stays selected (selected tint and amber outline on that one surface, its [face frame](../modes/design-v0.2.md#face-frame) axes drawn) until something else is selected, `Escape` or a click on empty space. Hovering the stock highlights the one stock face a click would select. The inspector shows "Face: Stock top" with its direction ("Facing up (+Z)"), its axes ("u → +X, v → +Y") and one button per operation kind ("Add facing here", …); Add → an operation (and Add → Hole) then creates it **on that face**: a pocket, drilling or hole uses it as `on`, a facing or profile (stock faces only) uses the stock face of the same direction, and the default values fit the face's rectangle and the material below it. Without a face selected, Add keeps its default (`on` the last top facing's floor, else `stock.top`). The new operation is selected (the face selection ends) so its fields can be edited at once. The empty part inspector says how to get there: "Select a face in the viewport (Alt+click for a floor) to add operations on it." The selection is stored as `face:<surface id>` in the design selection (one selection per mode, as before). Code: `modes/design/face-selection.ts` (pure), `FaceInspector`, `useAddOperation`; renders `design/features/renders/df22-face-{light,dark}.png` and `df20-measure-axis-{light,dark}.png` (`e2e/face-select.e2e.ts` with `DFYOM_RENDERS=1`).
- Camera: orbit, pan, zoom to cursor; a [view cube](ui-view-cube.md) at the top right (B25, task L2: 26 clickable regions, face views in the face frame, drag orbits; translucent until hovered, DF19) with "Fit" and a "Views" menu in a vertical floating toolbar to its right; keys `1`–`4` (Top, Front, Right, Iso), `Shift+1/2/3` (Bottom, Back, Left, by physical key) and `F` while the viewport has focus. Mouse mapping is a setting with presets ([decision 10](#decisions)):

  | Preset     | Orbit               | Pan                 | Zoom             |
  | ---------- | ------------------- | ------------------- | ---------------- |
  | Default    | Left-drag           | Right-drag          | Wheel, to cursor |
  | Fusion 360 | Shift + middle-drag | Middle-drag         | Wheel, to cursor |
  | Blender    | Middle-drag         | Shift + middle-drag | Wheel, to cursor |

  Left-click always selects (a click is a press and release without drag). Trackpad gestures (two-finger pan, pinch zoom) work in every preset. More presets only where they are a mapping table entry.

- The viewport is focusable (`tabindex=0`, labelled region); arrow keys orbit, `Shift`+arrows pan, `+`/`−` zoom.

### Shapes (v0.3)

Accepted with the v0.3 docs (D29, 2026-11-22); U1 (the Shapes group, the Shape Editor, the import dialog), U2 (the operation inspector for shapes, tab markers, the face-on editor) and U3 (snap and measure) are built, see [Implementation (U1)](#implementation-u1), [(U2)](#implementation-u2) and [(U3)](#implementation-u3) (tasks U1–U3, [plans/v0.3.md § 5](../plans/v0.3.md#5-shape-ui)). Behaviour lives in [design-v0.3.md](../modes/design-v0.3.md) (its [UI summary](../modes/design-v0.3.md#ui-summary) is the intent), the renderer's 2D port in [shapes.md § Where the 2D layer runs](../architecture/shapes.md#where-the-2d-layer-runs), and toolpath notes in [plan-v0.3.md](../modes/plan-v0.3.md). These are the UI rules.

**Visuals approved in L3 (D33).** The colours, handle and marker shapes and the motion below are made from existing tokens (no new token); the user approved them as built in review L3 ([plans/v0.3.md § 6](../plans/v0.3.md#6-ui-lane-d27)), with four changes: above 20 segments a path shows only the selected segment's handles (L3-7, [Shape Editor](#shape-editor)), the import's split choice is a dropdown (L3-10, [Navigator and Add](#navigator-and-add)), measure is `D` (Dimension) instead of `M` (L3-17, [Snap and measure](#snap-and-measure)), and the view cube's Fit/Views toolbar keeps a small gap below the cube (L3-22, [ui-view-cube.md](ui-view-cube.md#as-built-task-l2)).

**Rules for the whole Shape UI:**

- **Numbers first:** every handle, marker and snap edits a quantity that is also a field in the inspector. The field is the keyboard and screen-reader path; the canvas is the pointer convenience, as with the view cube. A value given as an expression locks its handle (drawn disabled, tooltip "Remove the formula to drag."), as the [anchor picker](#design-and-plan-controls-v02) does.
- **One drag is one [gesture](../architecture/commands.md#gestures-live-edits):** the outline follows the pointer every frame from the renderer's 2D port. Gesture steps (`design.shape.item.update`, or the operation's update) go out at most every 100 ms and on release, so the drag is one undo step. `Escape` during a drag cancels it (`history.undo { gesture }`). A press that stays within the 4 px click distance commits nothing.
- **Drawing style:** a CAD drawing, not an illustration. Loops are 1.5 px `--vp-edge` lines, a pocket region has a quiet `--vp-removal` tint with its holes (islands) left untinted, and open paths are bare lines. The selected item gets the amber outline (`--vp-selected`). The accent never fills an area.
- **Both themes:** overlays read their colours through `useTokens`, so they follow the theme and add no values of their own.
- **Motion:** handles fade in over `--motion-fast`. A snap pulls the point in over `--motion-instant` and pulses its glyph once (`--motion-emphasis`). Entering the Shape Editor animates the camera to the flat view (`--motion-slow`, like a named view). Reduced motion turns all of these into cuts, and nothing loops.

#### Shape Editor

Selecting a shape row, or adding a shape, opens the Shape Editor: the inspector shows the shape and the viewport switches to its flat view. Clearing the selection returns the camera to its previous view.

- **Flat view:** orthographic and face-on to the face of the first operation that uses the shape, seen from outside that face ([S-D](../modes/design-v0.3.md#placing-a-shape-on-a-face)). Muted context sits behind the shape: the stock face outline (dashed `--vp-stock`), the [reference section](#snap-and-measure) while the reference is shown, and the face-frame axes. A shape no operation uses is shown in its own frame on the grid. Orbit is off; pan and zoom work as usual. A chip at the viewport's top left names the view ("Shape · Top face" or "Shape frame"), and so does the view summary ("View: Shape 1 on Top face, flat").
- **Inspector** (`ShapeInspector`) shows the name, then the **item list** (`ShapeItemList`). Each row has:
  - the item's `op` as a `SegmentedControl` (Add, Subtract, Intersect), read-only Add on the first row
  - the kind icon and a short label ("Rectangle 40 × 20")
  - the drag grip (and `Alt+↑/↓`, [reordering](#reordering-lists-d45)) and remove, as in the operation list; remove is always shown and is a tab stop, and `Delete` or `Backspace` on the row removes the item (not the last one), keeping focus on the row now in its place (hardening U2)

  Under the list are the selected item's `Field`s with illustrations. Each commit is one `design.shape.item.update`, and its issues show at their field (`shapes.<id>.items.<n>.<param>`). A summary from `design.shape.get` ends the group: area, bounding box and smallest inside radius.

- **Segment table** (`SegmentTable`) for a path item: a dense grid (`--control-sm`) with a row per segment. **Row menu** (DF70, [decision 27](#decisions)): right-click anywhere on a row, or `Shift+F10` / the Menu key on one of its cells, opens "Actions for segment 3" – Move segment 3 up (`Alt+↑`), Move segment 3 down (`Alt+↓`), Remove segment 3 (`Delete`; disabled for a path's only segment); the row is selected (its handles highlight) and focus returns to the cell the keys opened it from, or the row's # cell after a right-click. The # cell is plain text (until DF70 a button opening the same menu); the grid's keys description ends "Right-click a row, or press Shift+F10 on a cell, for the row's actions." The app has no native text menu in fields, so a right-click on a cell's field opens the row menu too.
  - Columns: #, type (`Select`: Line, Arc, Tangent arc), end X and Y, radius, CW/CCW, large arc, and the fillet at the end vertex. A cell that does not apply to the type is empty, not disabled.
  - Above the table: the start point and "Closed" (`Switch`). "Add segment" inserts after the selected row; a row's context menu moves or removes it.
  - Keyboard: arrows move between cells (grid roving focus); `Enter` starts editing a cell and `Enter` commits it; `Alt+↑/↓` moves a row; `Delete` on a row header removes the row, with an undo toast.
  - Every cell is a `QuantityInput`, so expressions, units and the echo work as in any field. The selected row and its segment's handles highlight each other.
- **Handles** (`ShapeHandles`) appear on the selected item only:
  - Many segments (L3-7, D33): on a path with more than 20 segments (an imported outline) only the selected segment's handles show, its start and end points and an arc's radius; without a selected segment none show, and a note at the view's bottom says "Click a segment, or a row of the segment table, to show its handles." A click on a segment of the selected path (any path, a 12 px target) selects its table row, which scrolls into view; the selected segment is drawn as a 3 px `--vp-selected` line.
  - Marks: points are 7 px squares, radii and sizes are 7 px diamonds on the edge they size, and centres are small crosses. The mark stays small, but its pointer target is ≥ 24 px.
  - Colours: neutral at rest (`--bg-raised` fill, `--vp-edge` outline), `--vp-hover` when hovered, amber while dragged.
  - Modifiers: `Shift` constrains the drag to 15° steps; `Alt` turns [snapping](#snap-and-measure) off for that drag.
  - While dragging, a chip beside the pointer shows the edited value in project units ("R 12.50 mm"), in `--text` on `--bg-raised` like the face-frame labels.
- **Live outline:** the renderer's 2D port redraws the resolved loops on every value change, before the mesh follows ([evaluation status](#evaluation-status-pending-outdated-failed)). In an invalid state (a crossing path, a fillet too large) the last valid outline stays, the offending segment is drawn in `--danger` with the error marker, and the error shows at its field. An unresolvable shape never looks valid.
- **Boolean items:** the selected item's own outline is drawn dashed over the resolved result, so a subtracted item reads as a cut-out. Other items show only through the result. "Show items" (`IconButton` with `aria-pressed`, per window, sends no command) draws every item's outline thinly.

`ShapePicker` (U2) replaces the pocket's and profile's shape kind control:

#### Tab markers

On a selected profile with tabs (U2), each tab is a marker on the loop: a bar across the slot as long as the tab is wide, neutral with a `--vp-edge` outline, amber while dragged. A small open circle with a direction tick marks the loop's **start point** and its counter-clockwise direction seen from outside.

- **Dragging** moves a marker along the loop to the nearest loop point (`pointAt`, `distance`). The first drag on a count-spaced profile turns the count into `tabs.positions` within the same gesture; the note then says "Positions entered by you." with "Space evenly", which clears them. A marker stops at its neighbour's edge, so a drag never makes `tabsOverlap`.
- **Keyboard path:** the Tabs group lists one `QuantityInput` per position ("Tab 1 at 32.0 mm from the start"), with "Add tab" and a remove action per row. On the canvas, a focused marker moves 1 mm per arrow key (0.1 mm with `Alt`, 10 mm with `Shift`), and each run of keys is one gesture. Its name is "Tab 2, 84.5 mm from the start", announced politely when it changes: on every key step and at the end of a drag (hardening U2, through the design viewport's polite announcement).

#### Import report

`ImportReportDialog` (U1) is a `Dialog` opened after `design.shape.import`, built from its `report` ([design-v0.3.md § SVG import](../modes/design-v0.3.md#svg-import)):

- **Options step:** names the file ("File: drawing.svg", full path as tooltip, DF48) above Unit and Shapes.
- **Title and summary:** "Imported Shape 1" or "Imported 3 shapes". The report is a wide dialog (`size="lg"`, DF48), so fact labels stay on one line. The summary line gives the size, where it came from, and the shapes and loops created: "120.0 × 80.0 mm, from the file's width and height", or "Unitless: 96 px per inch assumed".
- **Facts** in a two-column list (label, value, tabular numerals): elements imported (by kind in words, "2 paths", DF48); elements skipped, by kind (text, images, clip paths); curves fitted with arcs (count, largest deviation "≤ 0.010 mm"); corners kept at cusps; micro corners merged; loops repaired.
  - What changed the drawing (skipped, repaired) is a soft warning with the "i" icon; the rest are plain facts.
  - Nothing in the report is an error; a refused file shows its `ErrorMessage` instead.
- **Assigned note** (DF49): when the import came from an operation's shape picker, one line above the facts says which operation now uses which shape, or that it could not.
- **Preview and actions:** a mini flat outline of the result, then "Edit shape" (primary, selects the first shape; with several shapes it names it, "Edit outline", DF48) and "Close". The import is undone like any edit ("Undo Import SVG").
- **Later access:** while the window is open, the shape inspector reopens the last report ("Import report"). Reports are not persisted.

#### Snap and measure

Bounded, and the first item cut if v0.3 runs long (U3, [Q23](../modes/design-v0.3.md#answered-questions)). Without U3, handles and markers work unsnapped.

- **Snap targets** while dragging handles and tab markers: grid ([Snap grid](#settings) setting), shape points (ends, centres, midpoints), stock edges and corners, and the **reference section**, computed in the worker.
- **Snap glyph** at the active target: a square for ends and corners, a circle for centres, a triangle for midpoints, a cross for grid points, plus a label chip ("Midpoint", "Stock corner", "Reference"). The glyph is `--vp-edge` with the hover tint; the shapes tell targets apart, so colour carries no meaning alone.
- **Snap values:** a snap writes the number in the user's units and format ([design-v0.3.md § Measure and snap](../modes/design-v0.3.md#measure-and-snap)). Holding `Alt` turns snapping off for one drag; the "Snap" toolbar toggle (`IconButton`, `aria-pressed`, per window) turns it off until pressed again.
- **Reference section:** while a reference is shown, the Shape Editor's floating toolbar has "Section depth" (`QuantityInput`). The section is a thin `--vp-edge` line at the ghost's opacity, never in the accent.
- **Measure** (`MeasureTool`): the main toolbar's "Measure" (its "Tools" group, DF19; not in Run), or `D` (Dimension; `M` until the user changed it in L3, D33) while the viewport has focus. Click two points (snapping applies), or a point and an edge. A dimension line with ticks shows the distance in a chip in project units, and the chip's tooltip adds ΔX, ΔY, ΔZ. Nothing is stored. With two points set, the next click (on the part or on empty space) only clears them, and the click after starts a new measurement (DF21); `Escape` clears the points first and ends the tool only when none are set; the button ends it at once. After the first point, holding `Shift` locks the line to the part-frame axis (X, Y or Z) closest to the pointer's direction on screen (DF20; an axis pointing at the camera, short on screen, is never chosen): the second point is the axis point nearest the pointer ray (or, when a vertex snap is active, the snapped point projected onto the axis), a thin dashed guide in that axis colour (`--vp-axis-x/y/z`) runs through the first point, and the banner names the axis ("Along X"). Keyboard path: the viewport's live summary repeats the result ("Distance 42.00 mm"), and the inspector fields give exact positions.

#### Implementation (U3)

Code: core `geometry/snap.ts` (the pure snap engine, moved from the renderer in hardening A6 so agents rank targets the same way; `viewport/snap.ts` re-exports it) and `geometry/measure.ts` (`measureBetween`, `angleAt`), `viewport/` (`SnapGlyph`, `MeasureTool` with `Dimension2d` and `MeasureChip`, `Measure3d`, snapping and measuring in `ShapeView`, the tab drag's scale in `TabMarkers`), `modes/design/` (`useReferenceSection`, `sectionMatrix` and `middleDepth` in `reference-view.ts`, `snapAlong` in `tabs-model.ts`) and core (`design/mesh-section.ts`, worker task `reference.section`, [workers.md](../architecture/workers.md#what-runs-on-a-worker)). How it differs from the rules above, or settles what they left open:

- **Snap engine** (`snapPoint`): candidates within `SNAP_PX` = 8 screen px (so the reach in mm follows the zoom); the best priority wins, then the nearest: ends and stock corners, then centres, midpoints, edges (stock edges and the reference section), then the grid. A handle's own start point is excluded, so a drag does not stick where it began. `Shift` (15° steps) and `Alt` drag freely, as does the "Snap" toggle off.
- **Snap values.** A snap to a shape point, stock edge or corner or the grid is exact: the handle's value is written to 0.1 µm in the field's unit (`SNAP_STEP_MM`), so a 1/16 in grid point reads `0.0625"` and not a pixel-rounded number. A reference snap keeps the pixel rounding of free drags, since the mesh's vertices are not design values.
- **"Snap" toggle** is a `ToolbarButton` with `aria-pressed` in the Shape Editor's toolbar, per window (`snapOn` in the ui store, on at start), and also governs tab markers and the viewport's measure. The [Snap grid](#settings) setting is two lengths, one for mm and one for inch projects (`snapGrid: { mm, inch }`, 1 mm and 1/16 in).
- **Glyphs:** square for ends and corners, circle for centres, triangle for midpoints, cross for grid points, an hourglass (two ticks across the line) for stock edges and the reference. One pulse on each new target (`--motion-emphasis`, none with reduced motion), then still. Label chip beside it. In the 3D measure a mesh vertex is labelled "Vertex".
- **Reference section** in the face-on editor: the first shown reference whose mesh is loaded, cut by the face plane `Section depth` below the face (a `QuantityInput` under the toolbar, per window, `sectionDepth` in the ui store). Its default is the middle of the reference's placed box along the face normal, measured from the face (mid-wall of an enclosure fitted to the stock). The cut runs in the worker (`reference.section`, the mesh kept there per path, ~45 ms at 1 M triangles); the editor keeps the last answer while a new one is on its way. The section is drawn as thin `--vp-edge` lines at 55 % and is a snap edge.
- **Tab markers** snap to the loop's corners and side middles, else to the grid _along the loop_ (a tab's position is a distance from the start point), with the glyph at the marker.
- **Measure in the Shape Editor:** the toolbar's "Measure" (`D`). Clicks pick the first and second point (snapped like a handle), a third starts again; a drag still pans; the line follows the pointer until the second click. The dimension is a thin line with end ticks and the chip beside its middle, the chip's tooltip and the live summary give the components along the face axes ("Distance 111.80 mm (ΔX 100.00 mm, ΔY 50.00 mm)."). `Escape` ends the measure before it leaves the editor; handles do not drag while measuring.
- **Measure in the 3D viewport:** "Measure" in the main toolbar (not in Run; in the view toolbar until DF19) and `D` on the region. Clicks raycast the part and the shown references (the ghost stays unpickable for selection; the measure raycasts meshes tagged `userData.measure`), snapping to the hit triangle's vertices and the stock corners within 8 px. The dimension line draws on top, the chip shows the distance with ΔX, ΔY, ΔZ on a second line in project units (drei's `Html` overlays render outside the app's providers, so no tooltip there); the measure button sat in the view toolbar until DF19 moved it to the main toolbar (`measuring` in the ui store, so the toolbar and the viewport share it; the Viewport keeps its own state when no `measuring` prop is passed); a drag still orbits; selection clicks are off while measuring; pick mode wins over it.
- **Review fixes (U3):** in a narrow inspector (a container query on the table, below 34rem) the segment table puts each segment on two lines (type, end X, end Y; radius, direction, large arc, fillet; # spans both) with smaller mono numbers, so 4 integer digits and 3 decimals show without horizontal scroll; wider inspectors keep one line. A shape row's "Used by n" fades while the row's actions show (hover, focus, selected) instead of running under the delete button.
- **Not built:** point-to-edge distances (the rules mention them; point to point covered the review cases), and snapping in the 3D viewport beyond the measure tool (the viewport has no other drags).
- **Headless (hardening A6):** `design.measure` gives agents the same snap and measure without the UI: snap candidates near a part-frame point (mesh vertices, stock corners, part zero, hole and face centres, the nearest feature edge) ranked by `SNAP_PRIORITY` within a radius in mm instead of `SNAP_PX`, and distances (with ΔX, ΔY, ΔZ) or angles between points ([llm-api.md § A6](../architecture/llm-api.md#a6-designmeasure-headless-snap-and-measure)). The viewport's behaviour is unchanged.

#### Section illustration

A dimensioned-looking **section** of the feature, drawn from the entered values (principle 5), above the size fields of the hole and the chamfer inspector.

- **What it draws:** the cut through the axis at true proportions (one uniform scale fitted to the inspector width, about 120 px high): the face line, the stock below it (to its bottom for a through hole, else fading out under the deepest point), the bore, the counterbore step or the countersink cone, the drill point when chosen.
- **Stock beyond the drawing fades out (D45, user, 2026-11-22):** where the stock runs on outside the drawing (under a blind hole, a deep bore cut short, the stock under a chamfered pocket's floor) the drawing fades into the box's background with a gradient (`--bg-field`, so it follows the light and dark themes) instead of ending on a zigzag break line; the bottom face is then not drawn. The fade starts below the deepest drawn feature, so the bottom, the drill point and the cone stay crisp, and the measured parts are drawn over it. A break line stays only for a drawing **split** to show a far part at scale (a small, deep hole drawn in two pieces to show its bottom); none of the v0.4 sections draws one yet. With a fastener chosen, the screw's head and shank silhouette in `--text-faint` dashes shows how it sits (head sink, clearance) – a picture of the fit, not geometry.
- **Field style, larger:** drawing in `--text-muted` 1 px lines, the cut material in a quiet hatch of `--vp-edge`, no fills in the accent. The **focused field's measured part is the amber line** ([field](#field) rule: no dimension arrows), and its value sits beside it in a small chip (`--text` on `--bg-raised`). Hovering a part of the drawing highlights its field's label (`--vp-hover`), and clicking it focuses that field.
- **Values:** resolved quantities (an expression draws its current value). While a value is invalid the last valid drawing stays and the offending part is drawn in `--danger` with the error marker, as the [Shape Editor's live outline](#shape-editor). Changes morph over `--motion-base` (a cut with reduced motion).
- **Reusable as a `sketch` view:** the drawing is a pure function of the values (`holeSection(values, units) → primitives`, unit-tested) rendered by one component (`SketchView`) that takes primitives and the highlighted part, with no knowledge of `Field` or the inspector. The later Field info views spec (D30 Q11, [plans/v0.4.md § Not in v0.4](../plans/v0.4.md#not-in-v04-and-why)) can host it as its first `sketch` view without changes; the chamfer's section uses the same component.
- **Accessibility:** `role="img"` with a label built from the values ("Section: Ø 3.4 mm through; counterbore Ø 6.5 mm, 3.2 mm deep; M3 head 0.2 mm below the face."); not a live region (the fields announce their own changes).

#### Clone path in the viewport

While the Clones feature (or one of its rows) is selected, and during the draft:

- **Path:** the reference chain as a thin `--vp-edge` line from the source through every position in instance-number order (a grid row by row, as numbered: 1, 2, 3, 4 in a 2 × 2 grid, D45 fix; where a grid's reference point ends elsewhere – its zigzag-last cell – the line goes on to it, so the next row starts on the line; straight between `offset`, `grid` and `point` positions; along the arc for `arc`; along the shape for `along`), with an arc's centre as a small cross and its construction arc dashed. The **focused row's segment is amber**, the rest neutral.
- **Positions:** a marker per position (7 px, the [handle](#shape-editor) look: neutral at rest, `--vp-hover` hovered) with its **instance number** in a small chip (`--text` on `--bg-raised`); the source is "1" with a ring. Numbers hide where markers sit closer than 24 px on screen and show on hover. Positions outside the stock get the warning triangle beside the number.
- **Skipped positions** draw the source's footprint as a dashed `--vp-edge` ghost at the reference ghost's opacity, the number muted. Draft ghosts are the same, solid-lined.
- **Click to skip:** with the Clones feature selected, a click on a marker (a ≥ 24 px target) toggles its skip (`design.clones.update`, one undo step, announced "Clone 4 skipped." / "Clone 4 restored."); the source marker is not a target ("The source can't be skipped." as its tooltip). Hover shows a chip "Clone 4 · click to skip" or "Skipped · click to restore".
- **Keyboard:** from the focused viewport, `Tab` cycles the markers in number order (out of the app's tab order, as tab markers); each is named "Clone 4 at u 9.00 mm, v 15.59 mm" (", skipped"), and `Space` toggles its skip.

#### Accessibility (feature UI)

- **Names:** a feature row is named "Hole 1, M3 counterbore, 2 operations, 1 warning, collapsed"; an owned row "Hole 1 · counterbore, edited through Hole 1"; an instance row "Clone 4, skipped". Read-only fields are `aria-readonly` with the reason in `aria-describedby`.
- **Non-pointer paths:** every viewport action has a navigator or inspector path: selection steps (breadcrumb), skipping (instance rows, the Skip button, the row's Skipped chips), edge picking (the Edge select), the section illustration's click-to-focus (the fields themselves).

### Viewport (task 3.5)

`src/renderer/src/viewport/` exports `Viewport`, the one react-three-fiber canvas ([ADR 0010](../decisions/0010-react-three-fiber-viewport.md)); the shell (3.3b) mounts it in its viewport slot and keeps it alive across modes. Dependencies, exact versions: `three` 0.187.0, `@react-three/fiber` 9.8.2, `@react-three/drei` 10.7.9 (camera controls: `camera-controls`), all MIT; drei's transitive dependencies are MIT, ISC, BSD-3-Clause and Apache-2.0, all GPL-3.0-compatible ([ADR 0014](../decisions/0014-gpl-3-or-later-license.md)).

- **Props-driven, no document access.** In: `mesh` (`PartEvaluation` or any `{ positions, indices, triangleSurface, surfaces }`; `null` before the first evaluation), `stock` box, `status`, `selectedOperation`, `pick` (`{ eligible, field }`), `mousePreset`, optional `summary`; v0.2: `frame` (face-frame axes `{ origin, u, v, length, labels }`) and `anchor` (`{ at, u, v }`), and in pick mode a normal glyph per eligible surface (`surfaceGlyphs`); `ghosts` (task R3: `{ id, positions, matrix, box }` per visible reference, [reference ghost](#reference-ghost-v02)). Out: `onSelect(target | null)`, `onHover`, `onPick(target)`, `onPickCancel()`, where a target is `{ surface, operation }` and the operation is the surface id's prefix (`stock` for stock surfaces). Which surfaces are eligible is the caller's business.
- **Scene:** the part mesh (one geometry per evaluation, [geometry.md](../architecture/geometry.md#worker-and-renderer)) with `--vp-edge` feature edges, the stock as a dashed `--vp-stock` outline, a grid under it (10 mm, major 50 mm), axes at the part origin. Perspective camera, 30° vertical field of view, Z up; the first mesh or stock is framed from Iso, later evaluations keep the user's camera. `frameloop="demand"`: nothing renders while nothing changes.
- **Colours:** base `--vp-part`; selected operation 25 % `--vp-selected` plus an amber outline (the accent is never a large fill); hover shows `--vp-hover` on every surface of the hovered surface's operation (what a click would select); pick mode tints eligible surfaces 12 %, the hovered eligible one 40 %, with the outline, and dims the rest 60 % towards `--bg-viewport`; `pending` (after 300 ms) and `failed` replace the base with `--vp-outdated`. Mixing ratios live in `colours.ts` (`MIX`).
- **Input:** mouse presets map onto camera-controls' button actions per press (so Shift selects the Fusion 360 / Blender action). Wheel events, in every preset: a mouse wheel dollies to the cursor, a two-finger trackpad scroll pans (content follows the fingers, like a drag), a pinch (macOS sends it as a wheel event with `ctrlKey`, as is Ctrl + wheel) dollies to the cursor. `classifyWheel` (`viewport/wheel.ts`) tells them apart per event, first match wins: `ctrlKey` → zoom; line or page `deltaMode` → zoom; within 120 ms of a pan → pan (rest of the gesture and its momentum); non-zero `deltaX` or fractional `deltaY` → pan (so Shift + wheel pans sideways); Chromium's `wheelDeltaY` equal to −3 × `deltaY` and not a multiple of 120 → pan; otherwise zoom. `Viewport` classifies in a capture-phase listener and sets camera-controls' `mouseButtons.wheel` (`TRUCK` or `DOLLY`) before its own listener runs; camera-controls would turn a `ctrlKey` wheel into a field-of-view zoom, so a pinch is re-sent without `ctrlKey` and dollies like the wheel. No setting: the mapping is the same in every preset. A click is a press and release within 4 px; a click on empty space clears the selection. Keys act while the region (or its toolbar) has focus; arrows only on the region itself, since the toolbar uses them for roving focus. In pick mode `Escape` is caught on the document, so it cancels while focus stays in the field. Camera moves animate unless motion is reduced.
- **Accessibility:** a `region` named "3D viewport", `tabindex=0`, described by a hidden text summary (default "Part with 3 operations.", the shell may pass a richer one) and the key list. The view toolbar is the `Toolbar` from `ui/` with Fit (`fit` icon) and the Views menu (`iso` icon; every named view with its shortcut, and "Setup view" in Plan and Run); the canvas cube is a pointer convenience. The summary ends with the current view ("View: Front", "View: custom"), announced politely when it changes ([ui-view-cube.md](ui-view-cube.md#as-built-task-l2)). Optional prop `insetRight` (px covered by the narrow-window inspector overlay) moves the cube and its toolbar beside it.
- **Run scene (task 3.12):** optional prop `run: { lines, done, tool } | null` (`RunScene`; `null` outside run mode). `lines` are the plan's toolpaths flattened to segments (`toolpathLines`: arcs in 3° chords, drill cycles down at feed and up as a rapid), drawn feeds `--vp-feed` and rapids `--vp-rapid`; segments before `done` fade 70 % towards `--bg-viewport` (`DONE_DIM`). `tool` (the status' `wpos`) places the tool marker (`--vp-tool` cone with its tip at the tool tip); the work zero is a ring at the WCS origin. Optional `frame` (v0.2 task E2): the setup's WCS in the part frame (`setupFrame`); the layer (toolpaths, tool marker, work zero) is drawn through it as a group matrix and the framing bounds are placed with it, so a bottom or side setup lands on the part; absent for an unrotated top setup, whose WCS is the part frame ([plan-v0.1.md](../modes/plan-v0.1.md)). Run mode passes the chosen setup's frame and toolpaths; Plan mode passes its window's setup's (F6). Optional `envelope` (DF33, [run.md](../modes/run.md#machine-coordinates-and-the-homing-corner-df33)): the machine travel `[−travel, 0]` minus the G54, i.e. in work coordinates, drawn as a box outline (`--vp-grid-major`) with a home marker (a small ring at the homing position) through the same frame; it widens the framing bounds. Run mode passes it from `RunStatus.envelope` while connected. Toolpaths widen the framing bounds. `useRunScene(mode)` (`modes/run/`) fetches the chosen plan's toolpaths (`plan.toolpath.get` per plan operation, again when a run starts; with every toolpath current, the lowered links of `plan.warning.list`, read when the setup is shown, applied, DF64 L3, so the drawn path is the program's) and computes `done` by following `wpos` forward along the segments (`advancePlayback`, 0.1 mm tolerance, never backwards).

### Undo and redo

- Undo/redo buttons in the main toolbar and `Ctrl/Cmd+Z`, `Ctrl/Cmd+Shift+Z` (also `Ctrl+Y` on Windows/Linux) dispatch `history.undo` / `history.redo` ([commands.md](../architecture/commands.md#undo--redo)). While focus is in a text field, the shortcuts act on the text, not the history.
- A field's adjust-panel session is one undo step, however many steps it committed live ([Quantity input](#quantity-and-expression-input)).
- v0.2 (D13): an Apply is its own undo step; undoing it reverts the automatic changes and leaves the edits pending ([apply.md](../architecture/apply.md#baseline-and-undo)).
- Tooltips name the step: "Undo Add pocket (Pocket 2)". The history is shared by all sources; when the top step is not the user's own, the tooltip says whose ("Undo Add pocket – by agent").
- After undo/redo the affected item is selected and briefly highlighted (`--motion-slow`, none under reduced motion) so the user sees what changed.
- Removing something shows a toast "Removed Pocket 2 · Undo" instead of a confirmation ([confirmations](#confirmations)).
- **Where toasts show** (DF45, UX audit 2026-11-23 #4: the toast sat over the inspector and hid the Tool field and Tab thickness): bottom-centre over the 3D view, 16 px above its bottom edge, never over the navigator, the inspector or the status bar. `AppShell` places a `ToastAnchor` in the viewport region; `ToastRegion` portals its list into it (fixed bottom-right only where no anchor is mounted: the gallery and component tests). Beside the narrow window's inspector overlay it centres in the rest of the view, as the Plan start card. At most 420 px wide, and never wider than the view minus 32 px.
- **Toasts time out:** an undo toast closes by itself after 6 s (`ToastRegion`'s default). The timer pauses while the pointer is over the toast or focus is in it, and while the window is in the background (Radix; WCAG 2.2.1) and then runs on with the time left. A new toast replaces the one showing (one per mode, `removedToast`). `Escape` or the next undo dismisses it early. Undo stays available after it closes: the toolbar's Undo and `Ctrl/Cmd+Z` (`altText`).
- **Escape with a toast over a dialog** (hardening U1): one `Escape` closes the open modal dialog (`Dialog`, `ConfirmDialog`) and leaves the toast; the next one dismisses the toast. Radix makes a toast that appears over a dialog the highest dismissable layer, so the toast asks the innermost open modal dialog to close first when focus is inside it (`ui/Dialog/modal-stack.ts`); focus in the toast, or in a list portalled out of the dialog, keeps that layer's own `Escape`.
- Agent edits (source `agent`) briefly highlight the changed row with an agent badge, so the user notices changes they did not make (principle §1).

### Warnings and DFM

Warnings never block ([design.md](../modes/design.md#dfm-checks), [plan-v0.1.md](../modes/plan-v0.1.md#plan-record), [feeds-speeds.md](../architecture/feeds-speeds.md)).

- **Where:** next to the blamed parameter in the inspector (`parameter`), as a badge on the navigator row (`operation`), as a marker at the operation in the viewport, and in the warning list (status bar count).
- **Severity** ([decision 21](#decisions)):

  | Tier         | Meaning                                               | Look                                                                     | Dismiss                                |
  | ------------ | ----------------------------------------------------- | ------------------------------------------------------------------------ | -------------------------------------- |
  | Soft warning | Outside a recommendation; safe to ignore              | Neutral background, `--border-control` bar, "i" icon                     | `×`; collapses to "1 dismissed · Show" |
  | Hard warning | Likely bad result or risk (tool can't cut the radius) | `--warning-subtle` background, `--warning` triangle icon                 | No                                     |
  | Error        | Impossible value; blocks Generate                     | `--danger-subtle`, `--danger` icon, `--danger-text` text, `aria-invalid` | No; fixed or reverted                  |

  Core `info` maps to soft, `warning` to hard (the mapping per check code lives in the message catalogue). Warnings never block; only errors do. Counts (status bar "n errors, m warnings", navigator row badges) count errors and hard warnings only; soft findings are notes, shown in the lists but never counted as warnings (decided 2026-11-22: an "i" note such as "power check skipped" next to a "1" warning triangle read as a contradiction).

- **Plan errors** (3.7) use the error tier in lists too: `WarningList` items with tier `error` (`--danger-subtle`, circle icon, not dismissible).
- **Text:** re-rendered from `code` + `params` in the project unit system through the message catalogue; the core's English `message` (mm values) is the fallback. ### Confirmations

Policy ([decision 11](#decisions)): **undo instead of confirm** for document edits; confirm only what cannot be undone.

| Action                                                                                                                      | Confirmation                                                                                                                                          |
| --------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| Document edits incl. removing operations                                                                                    | None; undo toast.                                                                                                                                     |
| `plan.remove`, `design.part.remove` of a part with plans, library item delete, discard recovery, close with unsaved changes | `ConfirmDialog` naming the item and the consequence; the destructive button names the action ("Remove plan"), never "OK".                             |
| `run.job.start`                                                                                                             | Pre-flight dialog before every run, the virtual machine included: plan, machine copy, work zero, tools in order, soft-limit check result, time scale. |
| `run.machine.unlock` (`$X`)                                                                                                 | Confirm: "Position is not known until homed."                                                                                                         |
| Quit with unsaved changes or during a run                                                                                   | Native message boxes in main, in order (see below).                                                                                                   |
| Feed hold, stop, `run.machine.reset`                                                                                        | **Never** confirmed.                                                                                                                                  |

`ConfirmDialog` focuses the safe choice (Cancel) first, except the run pre-flight, which focuses "Start run" only after the checks pass.

**Quit** (menu, `Cmd+Q`, closing the last window on Windows/Linux; decided 2026-11-21): main asks in `before-quit`, before any window closes, with native message boxes (the question spans every window), each only if still needed when its turn comes. Logic and wording: `src/main/quit.ts`.

1. During a run: "A run is in progress" with Cancel / "Stop run and quit" ([run-v0.1.md](../modes/run-v0.1.md#implementation-task-312-run-mode-ui)).
2. Any open project with unsaved changes: one message box naming them ("Quit with unsaved changes in “Bracket”?", or "in 2 projects?" with the names listed), buttons "Save all" / "Quit without saving" / Cancel, Cancel focused and on `Escape`. "Save all" saves each project to its file through a main-process session; an untitled project gets the native save dialog on its window (default name from the project). A cancelled save dialog cancels the quit; a failed save shows "“name” could not be saved" with the error and cancels the quit. "Quit without saving" keeps the changes recoverable ([persistence.md](../architecture/persistence.md#crash-recovery)).

Cancel at any step leaves the app as it was (closing a window still asks for its project). Paths that skip `before-quit` never ask: `app.exit` after a failed start or a crash; the headless CLI/MCP entry has no windows and keeps closing projects recoverably.

### Jog, position and probing (DF88)

User feedback from the first real-machine session (hardening DF88). Replaces M3's "Step / Continuous" jog mode ([run-machine.md § Machine readiness](../modes/run-machine.md#machine-readiness-m3)).

- **One jog pad, click or hold** (`modes/run/JogPad.tsx`: the same component, with the same window step and feed (`useJogControls`), in the navigator, the tool-change dialog and the setup-change dialog; there is no jog mode any more): pressing a jog button (pointer, or `Space`/`Enter` on the focused button) starts a **hold delay** of 300 ms (`HOLD_DELAY_MS`, `modes/run/jog-press.ts`). Released before it ends → **one step** at the chosen step and jog feed (`run.machine.jog { by, feed }`). Still pressed when it ends → a **continuous jog** to the travel edge at the jog feed (`continuous: true`), cancelled on release with the jog cancel (`0x85`). A click never starts a continuous jog. Every other way a press ends (`pointercancel`, lost pointer capture, blur, the window losing focus or hiding, the pad turning disabled, unmounting) cancels a continuous jog, or drops a press still inside the delay without a step. One press at a time per pad.
- **Step picker** (`modes/run/JogStepPicker.tsx`): a group "Jog step" captioned "Step · mm" (or "in"), a 4 × 2 grid of 32 px cells: seven presets as a radio group (arrow keys move and choose, one tab stop) – mm: 0.1, 1, 5, 10, 20, 50, 100; inch projects: 0.001, 0.01, 0.05, 0.1, 0.25, 0.5, 1 (the usual inch ladder rather than converted mm values) – and, as the eighth cell, an inline **custom** field ("Custom jog step", placeholder "Custom", in the project unit) right in the grid: no dialog or popover. Committing a positive value up to 1000 mm (Enter or leaving the field) chooses it, and focusing it while it holds a valid value chooses it too; anything else marks the field invalid, shows "Above 0, at most 1000 mm" in the caption row (its right end, reserved, so nothing moves; the field's description) and keeps the previous step; `Escape` in the field restores its value. The chosen cell has the accent fill (the pad's one accent). The step is kept per window in mm (`jogStep`; default 10 mm, or 0.1 in in an inch project), so changing the project's unit never turns 10 mm into 10 in: a step that is no preset of the unit shows in the custom field.
- **Jog feed slider:** "Jog feed" with the value in mono on its right ("2000 mm/min"), a `Slider` from one step up to the machine's jog feed limit in steps of **100 mm/min** (5 in/min in inch projects). The limit is the lower of the machine's X and Y max feed rates (`$110`/`$111` in the library machine or the plan's copy), else 5000 mm/min. Default 2000 mm/min. Clicks and holds both use it for X and Y; Z jogs at the lower of it and the machine's Z max feed rate (`$112`). **Remembered per machine** in the app settings (`jogFeed`, keyed by the library machine id); without a known library machine, per window.
- **Pad polish:** the X/Y cross and Z column keep their 44 px cells, the pad centred in the panel with the axis letter in `--weight-medium` and the direction sign in mono; a button keeps an `--accent-subtle` fill and an accent outline while a continuous jog runs from it (`data-holding`, eased with `--motion-fast`, instant under reduced motion). Order: step picker, jog feed, pad, "Stop jog". Nothing appears or disappears, so the pad never moves (DF34).
- **Position table zeroes:** "Zero X Y Z" is gone. "Zero X/Y/Z" moved from the navigator into the inspector's Position table: a small ghost button **"0"** next to each axis letter (accessible name "Set X zero" / "Set Y zero" / "Set Z zero"; `run.workZero.set` for that axis), disabled with the work-zero gate (its reason as the button's description). The live G54 shows under the table. The setup-change dialog keeps its "Zero X/Y/Z" buttons (no Position table there); the tool-change dialog keeps "Set Z zero here".
- **Probing:** the navigator's former "Work zero" section, now only "Probe Z", is titled **"Probing"**; without a touch plate it says "Set the machine's touch plate thickness in the Library to probe Z."
- **Homing confirmation, "Don't ask again":** the real-machine "Home the machine?" confirmation ([run.md § 3](../modes/run.md#3-confirmations-before-motion)) has a checkbox "Don't ask again for this machine" (unchecked each time it opens). Confirming with it checked adds the library machine id to the app setting `skipHomeConfirm`; Home then homes that machine at once. Settings → "Homing confirmation" → "Ask again for every machine" clears the list (disabled while it is empty). Without a known library machine the checkbox is not offered.

#### Jog hotkeys

Run mode jogs from the keyboard too (`modes/run/useJogHotkeys.ts`, key maps in `modes/run/jog-keys.ts`), with the pad's click/hold rule: a key press shorter than the hold delay jogs one step; a key held past it jogs continuously until its `keyup` (`0x85`). Auto-repeated `keydown`s are ignored, and one key jogs at a time (another jog key while one is down is ignored). **`Escape` stops jogging** (jog cancel) whenever the machine jogs without a run job, and drops a key press still inside the delay; it is not prevented, so it still closes the top overlay.

The style is the app setting **Jog keys** (`jogKeys`):

| Style                         | X−        | X+        | Y−        | Y+        | Z−                | Z+              |
| ----------------------------- | --------- | --------- | --------- | --------- | ----------------- | --------------- |
| Videogame (WASD, the default) | `A`       | `D`       | `S`       | `W`       | `Shift`           | `Space`         |
| gSender                       | `Shift+←` | `Shift+→` | `Shift+↓` | `Shift+↑` | `Shift+Page Down` | `Shift+Page Up` |
| Arrow keys                    | `←`       | `→`       | `↓`       | `↑`       | `/`               | `'`             |
| Off                           | –         | –         | –         | –         | –                 | –               |

- **Custom** keys are backlog: the select shows "Custom (coming later)" disabled.
- The gSender style matches gSender's default jog shortcuts (`JOG_X_P` `shift+right`, `JOG_X_M` `shift+left`, `JOG_Y_P` `shift+up`, `JOG_Y_M` `shift+down`, `JOG_Z_P` `shift+pageup`, `JOG_Z_M` `shift+pagedown`; [Sienci-Labs/gsender, `src/app/src/features/Jogging/index.tsx`](https://github.com/Sienci-Labs/gsender/blob/a632b88fa010fce9e1a694e7e41b737f4402b6dd/src/app/src/features/Jogging/index.tsx#L804-L886)); gSender also stops a jog when one key of the combination is released, and so does DFYOM (`Shift` up ends the hold). The videogame and arrow-key styles match the physical key (`KeyboardEvent.code`: `KeyW`, `Slash`, `Quote` …), so they work on any layout.
- **Active** only in Run mode (the hook is mounted with the run mode's dialogs, so it works with the navigator or inspector hidden), while connected, with **no run job** (not at a tool change or a pause either), and the jog gate open (Idle or Jog). **Never while typing:** not in a text field, number or quantity field (the custom step included), text area, select or other text box (`isEditableTarget`, as the shell shortcuts). Not inside a dialog other than the setup-change prompt (a focused confirmation never jogs), and not with `Ctrl`, `Cmd` or `Alt` held (app shortcuts keep their keys). The arrow-key and gSender styles leave arrow and Page keys to a focused widget that owns them (slider, radio group, tabs, menus, lists, separators). Otherwise any focus works: a handled jog key is prevented, so in the videogame style `Space` on a focused button jogs Z+ instead of pressing it (`Enter` still presses it); a focused jog pad button keeps `Space` and `Enter` for itself (it jogs its own axis).
- The Keyboard shortcuts dialog lists the chosen style's keys in a "Run: jog" group.
- **Tests:** `jog-press.test.ts` (click vs hold with fake timers, abort, one press at a time), `jog-keys.test.tsx` (the styles, gSender's Shift release, modifiers, the focus rules, the shortcut list), `JogPad.test.tsx` (pad click/hold, Space/Enter, blur and disabling, presets and the inline custom step, inch presets, the hotkey hook: styles, typing, Escape, the active rule; axe), `RunMode.test.tsx` (jog feed per machine and the Z cap, WASD and Escape in the app, the zero buttons in the Position table, "Don't ask again" and its reset in Settings), `e2e/run-jog.e2e.ts` (on the virtual machine: click step, custom step, hold jog, WASD tap and hold, Escape, typing never jogs, zero per axis; renders `df88-jog` and `df88-position`, light and dark).

## Accessibility

Target: **WCAG 2.2 AA** for all non-3D UI, except that colour contrast (1.4.3, 1.4.6, 1.4.11) is measured with APCA ([colour](#colour)); the 3D viewport has a non-visual equivalent for every task.

- **Keyboard:** every action is reachable by keyboard; tab order follows the visual order; `F6`/`Shift+F6` cycle shell regions (main toolbar, navigator, viewport, inspector, status bar); `?` opens the shortcut list. Shortcuts never fire while typing in a field, except feed hold.
- **Focus:** visible `:focus-visible` ring (2 px `--focus`, 2 px offset, Lc ≥ 30 against both neighbours); focus returns to the trigger when a popover or dialog closes; never `outline: none` without a replacement.
- **Contrast:** as in [colour](#colour); checked by the token unit test and axe in component tests.
- **Reduced motion:** as in [motion](#motion); also an app setting independent of the OS.
- **Screen readers:**
  - Landmarks: `banner` (main toolbar), `navigation` (mode switcher, navigator), `main` (viewport region with an `aria-label` and a text summary: "Part with 4 operations, 2 warnings"), `complementary` (inspector), `contentinfo` (status bar).
  - The navigator list is the accessible way to select; picking always has the dropdown alternative.
  - Live regions: polite for evaluation status, job completion and toasts; assertive for alarms, run failures and tool-change waits.
  - Fields: label, unit, hint, recommended range and error wired with `aria-describedby`; `aria-invalid` when invalid.
  - Status chips and machine states expose their text, not just colour.
- **Zoom:** UI is in `rem`, so Electron zoom (`Ctrl/Cmd +/−`) scales it to 200 % without loss; panels scroll rather than clip.

## Copy and terminology

- Use [glossary](../glossary.md) terms exactly, never simplified replacements ("Feed hold", "Work zero", "Stepdown", not "Pause machine", "Origin", "Layer depth") (principle §5). New terms go to the glossary in the same change.
- Wrap terms in `Term`: dotted underline, tooltip with the one-line definition (seeded from the glossary) using real values where possible ("Stepdown: 1.5 mm per pass for this pocket"), and "Learn more" opening the wiki panel (wiki content: later; v0.1 shows the glossary entry).
- **British spelling** (DF47, UX audit #10) in every user-visible text and in the glossary: centre, centreline, colour, behaviour ("Centre X", "Centre angle"). It already dominated the messages and the docs; new prose follows it. Identifiers, API fields and CSS keep their spelling (`center`, `boxCenter`, `color`), since agents and code read them, not users.
- Sentence case everywhere; buttons are verbs with an object ("Add pocket", "Export gCode", "Start run"); no "OK" / "Yes".
- Messages: what happened, why, what to do; no blame, no exclamation marks, no codes in the main text (codes go to Details).
- An action that asks for more input before it acts ends in the ellipsis character "…" (U+2026: "New tool…", "Export gCode…"), never three dots; `messages/copy.test.ts` checks the catalogue and the native menu.
- Name a state by its glossary term, not a coined verb: "Set the plan status to settled design to edit …", not "Settle the design …".
- An empty optional field whose absence has a meaning shows that meaning as its placeholder in `--text-faint` (general tolerance: "None: lengths are exact"); emptying it clears the value.
- A list that is empty says how to create the first item; the editor beside it then stays empty instead of asking to select one (Library window).
- Values always with units in the project unit system; operations by name (`Pocket 2`). Ids (`pocket2`) are for agents: lists and rows never show them; an inspector header carries its item's id as a tooltip.
- Empty states teach the next step in one sentence plus one action.

## Internationalization

Decided for v0.1 ([decision 7](#decisions)): **English only, i18n-ready structure, no i18n library.**

- All user-facing strings live in `messages/` modules (per feature), never inline in JSX; sentences are whole template functions with typed params, never concatenated fragments.
- Error and warning text is derived from `code` + `rule` + `params` ([error handling decision 4](error-handling/README.md#decisions)), so a later locale needs only a new catalogue.
- Number formatting is locale-independent in v0.1 (`.` decimal, as the [parser](../architecture/quantities.md#literal-grammar-task-21)); `lang="en"` on the document.
- Layouts allow 30 % longer text (no fixed-width labels).

## Icons

Status: **approved in the L3 review** ([D33](../plans/v0.3.md#confirmed-decisions), 2026-11-22: B22-1 b, B22-2 a, B22-3 a, B22-4 a, B22-5 a, B22-6 a, B22-7 b). Sources, specimens and provenance: [design/icons/](../../design/icons/README.md).

Lucide is no longer used (B22-1 b; it was the generic set until v0.3).
- **Single source:** [`ui/icons/iconSet.ts`](../../src/renderer/src/ui/icons/iconSet.ts), plain data (paths, the accent part, provenance). The app renders it with `<Icon name>` ([`ui/icons/Icon.tsx`](../../src/renderer/src/ui/icons/Icon.tsx)); `design/icons/render.mjs` renders the specimens and SVG exports from the same file; `design/icons/b22/sync-page.mjs` writes the [design-system page](ui-design-system.html#icons)'s icon sheet (a test fails while it is out of date). The [dev gallery](#testing) shows the whole set by group.
- **Grid and stroke** (B22-2 a): a 16 px grid, `--icon-stroke` 1.35 px at 16 px, round caps and joins, rectangle corners `rx` 0.5–1.5, a 1.5 px margin, no fills except dots ≤ 1.8 px.
- **One accent part per concept icon,** the part that tells it apart: an operation's passes, a tool's cutting end, a drawing tool's handles, the setup's up face, the G of gCode, the run triangle. Generic actions and status glyphs have none.
- **Where amber shows** (B22-3 a): grey (`currentColor`) at rest; the accent part turns `--accent-icon` (with `--accent-icon-edge`) only while its control is active (pressed toggle, selected navigator or library row, the chosen option of a list, the current mode) and in a primary button. In a primary button an icon without an accent part turns amber whole ([decision 19](#decisions)). Disabled: the whole icon grey, no amber. Status icons take their status colour, never amber. Field illustrations keep their own rule ([field](#field): amber focused and unfocused).
- **Tool types** (B22-4 a): side views told apart by the amber tip (flat, bull nose, ball end mill, drill, chamfer mill: the V-bit drawing, wired with the type in v0.4 task C1, B22-6 a), always next to the tool's name: the tool field (16 px before the value), the tool picker (20 px per option) and the library window's tool rows.
- **Operations:** facing, pocket, profile, drilling; a profile cut `on` its line shows the groove (a bent slot, B22-5 a); tabs are a bridge on the cut line, drawn tall enough to read alone at 16 px (B22-7 b).
- **Sizes:** `--icon-sm` 14 px (inline, status bar), `--icon-md` 16 px (default: buttons, toolbars, rows), `--icon-lg` 20 px (run controls, the tool picker), `--icon-xl` 28 px (field illustrations, empty states); `<Icon size>` or the control's CSS sets it. Never below 14 px.
- **Views:** tools from the side; operations, drawing tools and UI from the front or top.
- **Accessibility:** icons are decorative (`aria-hidden`) by default; the control or the text beside it names them, and icon-only buttons have an accessible name and a tooltip (`IconButton`). An icon that carries meaning alone gets `label` (role `img` with that name).
- **New icons** are drawn to these rules in `iconSet.ts` (provenance `redraw`/`b22`/`approved`), never copied from another set.
