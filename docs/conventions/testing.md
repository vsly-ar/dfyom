| Virtual machine | GRBL emulator ([ADR 0013](../decisions/0013-grbl-first-controller.md))                                      | Simulated CNC controller + simulated devices; run-mode tests without hardware ([modes/run.md](../modes/run.md)).               |

## Commands

- `npm test` – all unit tests once; `npm run test:watch` – watch mode; `npm run perf` – performance budgets (e.g. [geometry](../architecture/geometry.md#performance-budgets-v01)).
- **Timeouts.** Vitest's 5 s default stays global. A genuinely heavy test (seeded property loops, heap checks, long multi-step UI flows, spawned processes) sets `{ timeout }` on its `it` or `describe` with a comment saying why; parallel `npm test` load can make a 1–2 s test take several times as long. Never raise a timeout to hide a slow or racy test.
- `npm run lint` – ESLint incl. layer import boundaries ([ADR 0015](../decisions/0015-eslint-with-typescript6-api.md)); `npm run lint:fix` applies safe fixes.
- `npm run format` / `npm run format:check` – Prettier (owns formatting; ESLint does not).
- `npm run check` – `typecheck` + `lint` + `format:check` + `test`. Run before committing.
- `npm run e2e` – builds the app (`electron-vite build`) and runs the Playwright-for-Electron tests ([app tests](#app-playwright-for-electron)); not part of `check`, CI runs it as its own job ([CI e2e job](#ci-e2e-job)). Run it after changes to main, preload, the renderer entry, workers or the build.
- **CI** ([`.github/workflows/ci.yml`](../../.github/workflows/ci.yml)) runs two jobs on every push and pull request to `main`, with Node from `.nvmrc`: `check` (`npm ci` + `npm run check`) and `e2e` (`npm run e2e` under a virtual display, [below](#ci-e2e-job)).

## End-to-end

- `exit-criteria.mcp.test.ts`: an MCP SDK client spawns `dfyom mcp` over stdio; also checks the run's MCP progress notifications, and that CI runs `npm run check` (the third criterion).
- `exit-criteria.batch.test.ts`: `dfyom batch`, one JSON line per call, answered line by line (so tool changes can be continued).

### App (Playwright for Electron)

`@playwright/test` with its `_electron` launcher drives the built app (`out/main/index.js`); no browsers are downloaded. Config: `playwright.config.ts` (tests `e2e/**/*.e2e.ts`, one worker, artifacts in `node_modules/.cache/playwright`). Vitest does not pick these files up (its globs are `src/**/*.test.*` and `scripts/**`); `tsconfig.node.json` type-checks them and ESLint lints them as usual.

- **Fixture** (`e2e/app.fixture.ts`): launches the app with a fresh temp `--data-dir`, which in the app also moves Electron's `userData` (Chromium profile) and the log folder ([persistence.md](../architecture/persistence.md#files-and-folders)), so a run never touches the developer's projects, library or logs; collects console errors and uncaught exceptions of every window from creation on; stubs the native message boxes (they would show on screen and cannot be driven), which answer the quit questions with their quit button unless a test picks another (`answerMessageBoxes`, `askedMessageBoxes`); closes the app (normal quit path) and deletes the folder.
- **Hidden windows.** The fixture sets `DFYOM_HIDE_WINDOWS=1`: the app never shows its windows (no background throttling, no Dock icon or focus on macOS), so a test run does not cover the screen; the app ignores it when packaged. `DFYOM_E2E_SHOW=1 npm run e2e` shows the windows for debugging. Tests drive the hidden window through Playwright as usual.
- **Smoke test, task 0.9** (`e2e/smoke.e2e.ts`): the first window opens and is shown, its title is `DFYOM`, `#root` has rendered content, no renderer errors, `userData` and the logs are in the temp folder; and, through the window's preload bridge (`window.dfyom.call`, as the UI calls it), a part with a pocket evaluates to `done`, which runs the production worker chunk (`out/main`) in the packaged layout. Selectors rely only on the title, `#root` and the bridge, so they survive UI rewrites; later UI tests query by role and label ([ui.md](ui.md#testing)). Extended with the UI shell (3.3b): the three modes switch (click and shortcuts), the theme setting applies (`data-theme`, body colour) and persists (`settings.json`), and closing an edited project's last window asks first. The native title carries the version, and the window bounds and the project dialog folder survive a restart (`app-state.json`, relaunch on the same data dir; [ui.md](ui.md#remembered-window-state-and-dialog-folders)). With the window choice for New / Open ([ui.md](ui.md#project-files)): New in a window with a project opens a new, cascaded (still hidden) window and asks nothing; opening a file a window already shows opens no second window; a refused open closes its new window unseen.
- **Exit criteria, task 3.11** (`e2e/exit-criteria.e2e.ts`, joins the design flow of 3.6, the plan UI of 3.7 and the run flow of 3.12): everything through the UI only (roles and labels), starting from the empty library of a fresh install: New project, a new 100 × 60 × 20 block, facing, pocket (corner radius, floor fillet), drilling, profile with tabs, "Part up to date" from the geometry worker; Plan: the machine added with "New machine…" from the empty state, Create plan (machining order checked), the tools added with "New tool…" per operation (flat, bull nose with the floor fillet's corner radius, drill) and assigned, the profile's tool picked in the tool picker, the drill's feeds entered as overrides, Generate toolpaths, Export gCode… (save dialog) with "No machine warnings." and the file's line count; Run: connect to the virtual machine at Max, home, jog to the middle of the table, set the work zero, start through the pre-flight dialog (tools in order), confirm every tool change and program pause, "Run complete" with lines done = total = the exported file's lines; `Ctrl/Cmd+S` (Save as), then the app is closed and launched again on the same data dir (`launchApp`) and the file opened: same operations and values, evaluated, the plan with its tools and the drill's feeds. The native file dialogs are stubbed in the main process (`app.evaluate` replaces `dialog.showSaveDialog` / `showOpenDialog`; the export dialog is told apart by its title). Fields are filled, committed with Enter and left (`blur`) before the next click, since a field's echo collapses on blur and would move the click target.
- **Setup panel, v0.2 task F6** (`e2e/setups.e2e.ts`): a part with a top facing and pocket and a bottom facing, and its plan, are built through the bridge (keeps the test on the panel; the whole flow through the UI is X2's, below); then through plan mode's UI: the two setups in machining order with direction, WCS corner and rotation, the nested operations, Alt+↓/↑ reorder, the setup inspector's 90° rotation, Generate toolpaths, and one program per setup from the panel's "Export Bottom gCode…" / "Export Top gCode…" (each file's `(Setup: …)` header checked). The export dialog stub answers the suggested file name.
- **v0.2 golden path, task X2** (`e2e/golden-path-v0.2.e2e.ts`, ≈ 28 s locally): the [v0.2 exit criteria](../plans/v0.2.md#exit-criteria) through the UI only, mirroring X1's headless flow from the empty library of a fresh install: a 255 × 185 × 40 hardwood board (Material class); the enclosure STL imported with "Import STL…" (open dialog stubbed, told apart by its title "Import reference"), read as mm, fitted with Height "Bottom", hidden and shown with the eye (row "hidden", the viewport's text summary); top: facing, a cavity on "Facing 1 floor" (picked in the `on` dropdown) placed by its front-left corner with the anchor picker (a size edit keeps the corner), a through profile with tabs; right side ("Stock right side"): two drill-point holes; bottom ("Stock bottom"): a recess; Enter applies every field but one, whose Tab commit waits for "Apply 1 change". Plan: a 300 mm Z machine from "New machine…" (the right setup stands the board on its end, no `plan.machine` warning), Create plan → setups Bottom, Right, Top with their operations; the tools with "New tool…" (Flat 12, Flat 6, Drill 6) or the tool picker; between them, back in Design, the library's Flat 12 picked in the profile's tool field ("Flat 12 · Ø 12": locked, "Chosen by you.") and applied with the Apply button, so the draft plan takes it from the design ("From the design's tool field.") while the cavity's tool is "Chosen in this plan."; the drill's feeds by hand (no calculator data for drills), the auto-chosen generalized drill matched ("Matches the design's 6 mm drill."); Plan status "Settled design", the recess deepened in "Part (plan copy)" ("Edited in plan"), a peck cycle; Generate toolpaths; "Export <setup> gCode…" per setup (the save dialog answers the suggested name; "No machine warnings.", the line count, the `(Setup: …)` header, each program only its setup's operations); Run at Max: home, jog, zero, Start run (pre-flight names "Bottom (1 of 3)" and the machine), each run's tool changes and pauses continued until "Run complete: <its program's lines> lines", then the setup-change dialog ("Setup change: setup n, <name>", the stock picture) and "Start setup n"; Save as, relaunch, Open: the reference at its fitted position, six operations, the cavity's anchor and position, the profile's locked Flat 12, the three setups with their tools and the plan-only edit.
- **Electron binary.** Electron 45 has no install script: `require('electron')` downloads the binary on first use (`npm run dev`, `npm run e2e`), so `allowScripts` needs no entry for it.
- **Traces and logs on failure.** Under `CI` (or `DFYOM_E2E_TRACE=1`) every launch records a Playwright trace (screenshots, DOM snapshots); a failed test keeps it as `trace.zip` in its output folder and attaches it to the HTML report, as long as the app still runs at the end of the test (a test that already closed it has none). A failed test also keeps the app's log folder (`logs/`) before the temp data dir is deleted. Open a trace with `npx playwright show-trace <trace.zip>`.

#### CI e2e job

The `e2e` job of [`ci.yml`](../../.github/workflows/ci.yml) runs `xvfb-run -a --server-args="-screen 0 1920x1080x24" npm run e2e` on `ubuntu-latest`, next to `check` and in parallel with it:

- **Electron binary.** Unlike `check`, it does not set `ELECTRON_SKIP_BINARY_DOWNLOAD`; the first launch downloads the binary through `@electron/get`, whose cache (`~/.cache/electron`, ≈ 120 MB) is kept with `actions/cache`, keyed on `package-lock.json`.
- **Linux.** The runner image already has Electron's libraries (`libnss3`, `libgbm1`, `libasound2t64`, …) and `xvfb`; the Chromium sandbox works without `--no-sandbox` or `chrome-sandbox` changes, so the job installs nothing. `xvfb-run` gives Electron a display although the windows stay hidden (`DFYOM_HIDE_WINDOWS=1`, set by the fixture). The virtual screen is 1920 × 1080: on xvfb's default 1280 × 1024 the 1440 × 900 window is clamped to the screen width and a second window cannot cascade (it goes back to the corner), which the smoke test's cascade check would see.
- **On failure** the job uploads the artifact `playwright-e2e` (7 days): the HTML report (`playwright-report/`, CI only) and the test output folders (`node_modules/.cache/playwright`: traces, app logs, error context). Download it with `gh run download <run> -n playwright-e2e`.
- **Time.** About 1 min for the job before X2 (build ≈ 3 s, tests ≈ 40–55 s); X2's golden path adds ≈ 28 s (the whole suite ≈ 70 s locally), 20 min timeout. The Linux runner is slower than a developer machine: a check that passes locally only because the app is fast can fail there (the first run found such a race in the exit-criteria test).

## Docs lint

`scripts/docs-lint.test.mjs` (part of `npm test`) enforces [documentation.md](documentation.md): every doc is reachable from the [index](../README.md) (directly, via a folder link such as `decisions/`, or via an indexed folder README), has a valid `Status:` line in its first lines and the same status as in the index map, and every relative link and `#anchor` resolves (GitHub heading slugs).
