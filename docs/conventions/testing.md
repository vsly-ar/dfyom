## Commands

- `npm test` – all unit tests once; `npm run test:watch` – watch mode; `npm run perf` – performance budgets (e.g. [geometry](../architecture/geometry.md#performance-budgets-v01)).
- **Timeouts.** `npm run check` must pass on a heavily loaded machine (load average ≈ 25–40, e.g. parallel Electron builds), where a test takes 3–6× as long as on an idle one (measured for backlog B17). Never raise a timeout to hide a slow or racy test: find real waits and races first.
  - **`node` project:** `testTimeout: 15_000` (`vitest.config.mts`): room for machine-wide stalls, not for slow tests ([Load-stable tests](#load-stable-tests)). A genuinely heavy test (seeded property loops, heap checks, long emulator streams, open/save rounds, spawned processes) sets `{ timeout: 60_000 }` (more for the spawned end-to-end flows) on its `it` or `describe` with a comment saying why and how long it takes alone.
  - **`ui` project:** `testTimeout: 30_000` for the whole project (`vitest.config.mts`), no per-test numbers: component tests are multi-step flows through the app in jsdom (1–2 s idle, up to ≈ 12 s under load). Testing Library's `findBy*` / `waitFor` wait up to 5 s (`asyncUtilTimeout` in `src/renderer/src/test/setup.ts`, instead of 1 s); don't pass shorter `{ timeout }`s.
- **Layout in jsdom.** jsdom has no layout engine, so a component test checks a layout rule (one column `minmax(0, 1fr)`, a row that scrolls, an option that starts at the edge) by reading the stylesheet with `cssRule(path, selector)` (`src/renderer/src/test/css.ts`); a hidden e2e capture shows the result.
- `npm run lint` – ESLint incl. layer import boundaries ([ADR 0015](../decisions/0015-eslint-with-typescript6-api.md)); `npm run lint:fix` applies safe fixes. It runs with an 8 GB Node heap: typed linting of every TypeScript project (app + spikes) peaked at ~4.5 GB on 2026-11-25, past Node's default limit.
- `npm run format` / `npm run format:check` – Prettier (owns formatting; ESLint does not).
- `npm run check` – `typecheck` + `lint` + `format:check` + `test`. Run before committing.
- **Vendored WASM** ([ADR 0019](../decisions/0019-2d-geometry-library.md#decision) decision 6): `scripts/build-cavalier-wasm.test.mjs` (in `check`) compares `vendor/cavalier-contours/cavalier_contours.wasm` with its recorded SHA-256, so CI needs no Rust toolchain. After changing `vendor/cavalier-contours/src/lib.rs` or the crate version run `npm run wasm:cavalier` (pinned Rust 1.100.0 via rustup plus `rustup target add wasm32-unknown-unknown --toolchain 1.100.0`; it rewrites the module and its checksum) and commit both; `npm run wasm:cavalier -- --check` rebuilds and only compares (reproducibility). Tests load the module with `src/core/geometry/2d/testing/node-wasm.ts`; the CLI tests get its path from the global setup (`DFYOM_TEST_REGION2D_WASM`).
- **2D port oracles** ([shapes.md](../architecture/shapes.md#2d-port)): offsets are checked with the offset oracle (every output point lies |d| from the input, tolerance 1e-6 mm: near-tangent joins deviate by ≈ |d|·1e-7) and the crossings count on loops flattened to 2 µm (`src/core/geometry/2d/testing/oracles.ts`); booleans by exact areas.
- `npm run e2e` – builds the app (`electron-vite build`) and runs the Playwright-for-Electron tests ([app tests](#app-playwright-for-electron)); not part of `check`, CI runs it as its own job ([CI e2e job](#ci-e2e-job)). Run it after changes to main, preload, the renderer entry, workers or the build.
- **CI** ([`.github/workflows/ci.yml`](../../.github/workflows/ci.yml)) runs two jobs on every push and pull request to `main`, with Node from `.nvmrc`: `check` (`npm ci` + `npm run check`) and `e2e` (`npm run e2e` under a virtual display, [below](#ci-e2e-job)).

## Load-stable tests

`npm run check` and the hidden e2e suite must pass while the machine is busy (measured with ten `yes` CPU hogs on a 10-core Mac plus other work: load average 60–100). Under that load a test takes 3–6× as long as idle, with outliers of 20–30× for a few seconds, so a test that is only "fast enough" fails at random. Rules (hardening P1–P3):

- **Find the race first.** A test that fails "under load" usually waits on a stale state or on wall time. Wait for the state the step produces, not for a state that was already true before it: after a jog, a report showing the jog's end position, not just `Idle` (`run/commands.test.ts`). No `sleep`; poll a condition (`waitFor`, bounded by wall time, never by a count of polls: a loaded machine stretches every poll) or use fake timers (`FakeTimers`, `host.test.ts`). So far every such race was a product bug: a stop during the start was lost, in the host and again in the run job ([run-v0.1.md](../modes/run-v0.1.md#review-of-39)); an open right after a close went to the machine host still exiting ([run-v0.1.md § Machine host and protocol](../modes/run-v0.1.md#machine-host-and-protocol)); a ±10 % override step was undone by the slider's pending debounce (`OverridesSection`). A test of such a race makes the slow side slow on purpose (a host whose exit comes late, fake timers advanced past the debounce) so it fails every time without the fix.
- **Make oracles cheap, not timeouts long.** Test-only checks must not be quadratic: distances to many segments go through `segmentGrid` (`src/core/geometry/2d/testing/oracles.ts`, exact, used by the SVG import oracle and region coverage); the heightmap's `stamp` works row by row without an allocation per cell, has a flat-end fast path and takes a cone's tangent once per stamp (`surfaceOf`, not a `Math.tan` per cell: that was 80 % of a chamfer sweep; same numbers, `oracles.test.ts`); the docs lint computes each target's headings once. Several independent heavy cases are separate `it`s (`stepped-chamfer.test.ts`), so one budget covers one sweep.
- **Don't wait on the disk's flush.** `fsync` latency is unbounded on a busy disk (up to 80 ms per call measured; flushes were 75–85 % of a project open even idle). Persistence flow tests (open, save, recover, lock races, `testHost`) use `testFs` (`src/main/persistence/fs.testing.ts`, the real file system with no-op flushes; `faultFs`/`jitterFs` default to it); `faultFs(…).calls` still checks that and where flushes happen, and `fs.test.ts` keeps a real flush on `nodeFs`.
- **Timeouts** stay as in [Commands](#commands): only an intrinsically heavy test sets its own, with why and the measured time in a comment. The `node` project's 15 s (instead of Vitest's 5 s) is for one thing the tests cannot fix: on a busy, swapping machine all workers froze for ≈ 5 s at once (the first test of six files at the same moment, 40–300 ms when not frozen). A test that needs more than a few seconds idle is still heavy and still gets its own budget.
- **e2e:** web-first assertions wait up to 15 s (`expect.timeout` in `playwright.config.ts`): many steps wait on UI state that follows main-process work (a library write, an evaluation), measured at over 5 s for a ≈ 0.2 s step under load. Waits stay on state, never on time.
- **e2e: wait for the effect, not the action's return.** `page.mouse.wheel` returns before the scroll it causes (the wheel's DOM event and the scroll can land frames apart): before reading a scroll position, wait until it moved (`gcode-panel.e2e.ts`). Count a dialog answered once it is gone, not by the click's result: a click that closes its window can still reject (`closeApp`, hardening P8). A command's UI effect can show before the command is done: the DRO follows the machine's status push, the command's action event (which re-renders the window) can come over 1 s later; `zeroXyz` waits for the window to have applied the zero commands' events, and `idleActivity` counts only after two animation frames (hardening P13).
- **Reproduce** with `for i in $(seq 10); do yes > /dev/null & done` and `npm run check` (or several `npx vitest run --reporter=json --outputFile=…` at once to find the next weakest test); kill the hogs afterwards (`pkill yes`).

### App (Playwright for Electron)

`@playwright/test` with its `_electron` launcher drives the built app (`out/main/index.js`); no browsers are downloaded. Config: `playwright.config.ts` (tests `e2e/**/*.e2e.ts`, one worker, artifacts in `node_modules/.cache/playwright`). Vitest does not pick these files up (its globs are `src/**/*.test.*` and `scripts/**`); `tsconfig.node.json` type-checks them and ESLint lints them as usual.

- **Fixture** (`e2e/app.fixture.ts`): launches the app with a fresh temp `--data-dir`, which in the app also moves Electron's `userData` (Chromium profile) and the log folder ([persistence.md](../architecture/persistence.md#files-and-folders)), so a run never touches the developer's projects, library or logs; collects console errors and uncaught exceptions of every window from creation on; stubs the native message boxes (they would show on screen and cannot be driven), which answer the quit questions with their quit button unless a test picks another (`answerMessageBoxes`, `askedMessageBoxes`); closes the app (normal quit path) and deletes the folder. The Library window's unsaved-draft prompt is in the window, not a native box, so the fixture's close (`closeApp`) answers it with Discard while the app quits: an unanswered prompt used to hang the worker's teardown (hardening B1, seen as "closing a project with no part hangs"); `library.e2e.ts` covers the quit prompt and closing with no part. A field kept behind a closed More row, accordion or tab (DF110) is shown with `revealField(scope, label)`, the reveal event a message's target uses ([inspector-layout.md § S3](inspector-layout.md#s3-implementation-notes)), never with ad-hoc clicks on "More (…)"; a closed accordion whose controls are not labelled fields (the split editor's Blanks: Split to fit…) opens with `openInspectorGroup(scope, title)`, a click on its header; Plan tabs open with `openInspectorTab(scope, name)` ([§ S4](inspector-layout.md#s4-implementation-notes)).
- **Hidden windows.** The fixture sets `DFYOM_HIDE_WINDOWS=1`: the app never shows its windows (no background throttling, no Dock icon or focus on macOS), so a test run does not cover the screen; packaged builds honour it too ([packaging.md](packaging.md#smoke-test): `npm run smoke:packaged` runs the smoke tests on the packaged app). `DFYOM_E2E_SHOW=1 npm run e2e` shows the windows for debugging. Tests drive the hidden window through Playwright as usual.
- **Smoke test, task 0.9** (`e2e/smoke.e2e.ts`): the first window opens and is shown, its title is `DFYOM`, `#root` has rendered content, no renderer errors, `userData` and the logs are in the temp folder, the log has "2D geometry loaded"; and, through the window's preload bridge (`window.dfyom.call`, as the UI calls it), a part with a pocket evaluates to `done`, which runs the production worker chunk (`out/main`) in the packaged layout. Selectors rely only on the title, `#root` and the bridge, so they survive UI rewrites; later UI tests query by role and label ([ui.md](ui.md#testing)). #### CI e2e job

The `e2e` job of [`ci.yml`](../../.github/workflows/ci.yml) runs `xvfb-run -a --server-args="-screen 0 1920x1080x24" npm run e2e` on `ubuntu-latest`, next to `check` and in parallel with it:

- **Electron binary.** Unlike `check`, it does not set `ELECTRON_SKIP_BINARY_DOWNLOAD`; the first launch downloads the binary through `@electron/get`, whose cache (`~/.cache/electron`, ≈ 120 MB) is kept with `actions/cache`, keyed on `package-lock.json`.
- **Linux.** The runner image already has Electron's libraries (`libnss3`, `libgbm1`, `libasound2t64`, …) and `xvfb`; the Chromium sandbox works without `--no-sandbox` or `chrome-sandbox` changes, so the job installs nothing. `xvfb-run` gives Electron a display although the windows stay hidden (`DFYOM_HIDE_WINDOWS=1`, set by the fixture). The virtual screen is 1920 × 1080: on xvfb's default 1280 × 1024 the 1440 × 900 window is clamped to the screen width and a second window cannot cascade (it goes back to the corner), which the smoke test's cascade check would see.
- **On failure** the job uploads the artifact `playwright-e2e` (7 days): the HTML report (`playwright-report/`, CI only) and the test output folders (`node_modules/.cache/playwright`: traces, app logs, error context). Download it with `gh run download <run> -n playwright-e2e`.
- **Time.** About 1 min for the job before X2 (build ≈ 3 s, tests ≈ 40–55 s); v0.2's X2 golden path adds ≈ 28 s, v0.3's ≈ 39 s, v0.4's ≈ 34 s, v0.4-llm-first's ≈ 45 s (the whole suite ≈ 2 min locally on a loaded machine), 20 min timeout. The Linux runner is slower than a developer machine: a check that passes locally only because the app is fast can fail there (the first run found such a race in the exit-criteria test).

## Real machine

Status: draft (hardening 1.3, 2026-11-25; for the user's review). Rules: [run.md § Safety](../modes/run.md#safety) · Lane: [run-machine.md](../modes/run-machine.md) · Protocol: [grbl.md](../architecture/grbl.md#transport-and-sender).

**In CI (no hardware).** The sender and the machine host talk to a `ControllerTransport` byte stream, the same interface for the emulator and `SerialTransport` ([grbl.md](../architecture/grbl.md#transport-and-sender)), so every run path is tested against the GRBL emulator: over the loopback serial port with handshake, `$$` check, silent homing, jog, probing and runs ([run-machine.md § Testing](../modes/run-machine.md#testing)); `SerialTransport` against `serialport`'s mock binding; the Q50 permission table per source; fault injection for a pulled cable, a silent controller, a hard limit mid-run, a probe miss, external holds and the door ([run-machine.md § Fault injection](../modes/run-machine.md#fault-injection-m8), [grbl.md](../architecture/grbl.md#fault-injection)); the app over `DFYOM_LOOPBACK_SERIAL=1` in e2e.

**Not in CI.** The OS serial driver and the board (reset on open, banner timing), the user's controller fork and its quirks (an unrequested banner after `$H`, DF87), the real `$$` values (`$31` below the usable spindle minimum, DF86), physical homing switches, the touch plate's electrical contact, the hardware e-stop (A2), missed steps, spindle and cutting physics, and the part's accuracy ([grbl.md § Not emulated](../architecture/grbl.md#not-emulated-in-v01)).

**When.** Before each release that changes the sender, the machine host, run commands or the run UI, and before X1 ([hardening § 7](../plans/hardening.md#7-acceptance)). The user runs it from the installed app; e-stop within reach, spindle off until the air cut is done, bit clear of the stock.
