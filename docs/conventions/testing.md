## Commands

- `npm test` – all unit tests once; `npm run test:watch` – watch mode; `npm run perf` – performance budgets (e.g. [geometry](../architecture/geometry.md#performance-budgets-v01)).
- **Timeouts.** `npm run check` must pass on a heavily loaded machine (load average ≈ 25–40, e.g. parallel Electron builds), where a test takes 3–6× as long as on an idle one (measured for backlog B17). Never raise a timeout to hide a slow or racy test: find real waits and races first.
  - **`node` project:** Vitest's 5 s default. A genuinely heavy test (seeded property loops, heap checks, long emulator streams, open/save rounds, spawned processes) sets `{ timeout: 60_000 }` (more for the spawned end-to-end flows) on its `it` or `describe` with a comment saying why and how long it takes alone.
  - **`ui` project:** `testTimeout: 30_000` for the whole project (`vitest.config.mts`), no per-test numbers: component tests are multi-step flows through the app in jsdom (1–2 s idle, up to ≈ 12 s under load). Testing Library's `findBy*` / `waitFor` wait up to 5 s (`asyncUtilTimeout` in `src/renderer/src/test/setup.ts`, instead of 1 s); don't pass shorter `{ timeout }`s.
- `npm run lint` – ESLint incl. layer import boundaries ([ADR 0015](../decisions/0015-eslint-with-typescript6-api.md)); `npm run lint:fix` applies safe fixes.
- `npm run format` / `npm run format:check` – Prettier (owns formatting; ESLint does not).
- `npm run check` – `typecheck` + `lint` + `format:check` + `test`. Run before committing.
- **Vendored WASM** ([ADR 0019](../decisions/0019-2d-geometry-library.md#decision) decision 6): `scripts/build-cavalier-wasm.test.mjs` (in `check`) compares `vendor/cavalier-contours/cavalier_contours.wasm` with its recorded SHA-256, so CI needs no Rust toolchain. After changing `vendor/cavalier-contours/src/lib.rs` or the crate version run `npm run wasm:cavalier` (pinned Rust 1.100.0 via rustup plus `rustup target add wasm32-unknown-unknown --toolchain 1.100.0`; it rewrites the module and its checksum) and commit both; `npm run wasm:cavalier -- --check` rebuilds and only compares (reproducibility). Tests load the module with `src/core/geometry/2d/testing/node-wasm.ts`; the CLI tests get its path from the global setup (`DFYOM_TEST_REGION2D_WASM`).
- **2D port oracles** ([shapes.md](../architecture/shapes.md#2d-port)): offsets are checked with the offset oracle (every output point lies |d| from the input, tolerance 1e-6 mm: near-tangent joins deviate by ≈ |d|·1e-7) and the crossings count on loops flattened to 2 µm (`src/core/geometry/2d/testing/oracles.ts`); booleans by exact areas.
- `npm run e2e` – builds the app (`electron-vite build`) and runs the Playwright-for-Electron tests ([app tests](#app-playwright-for-electron)); not part of `check`, CI runs it as its own job ([CI e2e job](#ci-e2e-job)). Run it after changes to main, preload, the renderer entry, workers or the build.
- **CI** ([`.github/workflows/ci.yml`](../../.github/workflows/ci.yml)) runs two jobs on every push and pull request to `main`, with Node from `.nvmrc`: `check` (`npm ci` + `npm run check`) and `e2e` (`npm run e2e` under a virtual display, [below](#ci-e2e-job)).

## Load-stable tests

`npm run check` and the hidden e2e suite must pass while the machine is busy (measured with ten `yes` CPU hogs on a 10-core Mac plus other work: load average 60–100). Under that load a test takes 3–6× as long as idle, with outliers of 20–30× for a few seconds, so a test that is only "fast enough" fails at random. Rules (hardening P1–P3):

- **Find the race first.** A test that fails "under load" usually waits on a stale state or on wall time. Wait for the state the step produces, not for a state that was already true before it: after a jog, a report showing the jog's end position, not just `Idle` (`run/commands.test.ts`). No `sleep`; poll a condition (`waitFor`) or use fake timers (`FakeTimers`, `host.test.ts`). The run-job race found this way was a product bug (a stop during the start's checks was lost, [run-v0.1.md](../modes/run-v0.1.md#review-of-39)).
- **Make oracles cheap, not timeouts long.** Test-only checks must not be quadratic: distances to many segments go through `segmentGrid` (`src/core/geometry/2d/testing/oracles.ts`, exact, used by the SVG import oracle and region coverage); the heightmap's `stamp` works row by row without an allocation per cell and has a flat-end fast path (same numbers); the docs lint computes each target's headings once. Several independent heavy cases are separate `it`s (`stepped-chamfer.test.ts`), so one budget covers one sweep.
- **Don't wait on the disk's flush.** `fsync` latency is unbounded on a busy disk (up to 80 ms per call measured; flushes were 75–85 % of a project open even idle). Persistence flow tests (open, save, recover, lock races, `testHost`) use `testFs` (`src/main/persistence/fs.testing.ts`, the real file system with no-op flushes; `faultFs`/`jitterFs` default to it); `faultFs(…).calls` still checks that and where flushes happen, and `fs.test.ts` keeps a real flush on `nodeFs`.
- **Timeouts** stay as in [Commands](#commands): only an intrinsically heavy test sets its own, with why and the measured time in a comment.
- **e2e:** web-first assertions wait up to 15 s (`expect.timeout` in `playwright.config.ts`): many steps wait on UI state that follows main-process work (a library write, an evaluation), measured at over 5 s for a ≈ 0.2 s step under load. Waits stay on state, never on time.
- **Reproduce** with `for i in $(seq 10); do yes > /dev/null & done` and `npm run check` (or several `npx vitest run --reporter=json --outputFile=…` at once to find the next weakest test); kill the hogs afterwards (`pkill yes`).

### App (Playwright for Electron)

`@playwright/test` with its `_electron` launcher drives the built app (`out/main/index.js`); no browsers are downloaded. Config: `playwright.config.ts` (tests `e2e/**/*.e2e.ts`, one worker, artifacts in `node_modules/.cache/playwright`). Vitest does not pick these files up (its globs are `src/**/*.test.*` and `scripts/**`); `tsconfig.node.json` type-checks them and ESLint lints them as usual.

- **Fixture** (`e2e/app.fixture.ts`): launches the app with a fresh temp `--data-dir`, which in the app also moves Electron's `userData` (Chromium profile) and the log folder ([persistence.md](../architecture/persistence.md#files-and-folders)), so a run never touches the developer's projects, library or logs; collects console errors and uncaught exceptions of every window from creation on; stubs the native message boxes (they would show on screen and cannot be driven), which answer the quit questions with their quit button unless a test picks another (`answerMessageBoxes`, `askedMessageBoxes`); closes the app (normal quit path) and deletes the folder.
- **Hidden windows.** The fixture sets `DFYOM_HIDE_WINDOWS=1`: the app never shows its windows (no background throttling, no Dock icon or focus on macOS), so a test run does not cover the screen; packaged builds honour it too ([packaging.md](packaging.md#smoke-test): `npm run smoke:packaged` runs the smoke tests on the packaged app). `DFYOM_E2E_SHOW=1 npm run e2e` shows the windows for debugging. Tests drive the hidden window through Playwright as usual.
- **Smoke test, task 0.9** (`e2e/smoke.e2e.ts`): the first window opens and is shown, its title is `DFYOM`, `#root` has rendered content, no renderer errors, `userData` and the logs are in the temp folder, the log has "2D geometry loaded"; and, through the window's preload bridge (`window.dfyom.call`, as the UI calls it), a part with a pocket evaluates to `done`, which runs the production worker chunk (`out/main`) in the packaged layout. Selectors rely only on the title, `#root` and the bridge, so they survive UI rewrites; later UI tests query by role and label ([ui.md](ui.md#testing)). Extended with the UI shell (3.3b): the three modes switch (click and shortcuts), the theme setting applies (`data-theme`, body colour) and persists (`settings.json`), and closing an edited project's last window asks first. The native title carries the version, and the window bounds and the project dialog folder survive a restart (`app-state.json`, relaunch on the same data dir; [ui.md](ui.md#remembered-window-state-and-dialog-folders)). With the window choice for New / Open ([ui.md](ui.md#project-files)): New in a window with a project opens a new, cascaded (still hidden) window and asks nothing; opening a file a window already shows opens no second window; a refused open closes its new window unseen.

A failed test also keeps the app's log folder (`logs/`) before the temp data dir is deleted. Open a trace with `npx playwright show-trace <trace.zip>`.

#### CI e2e job

The `e2e` job of [`ci.yml`](../../.github/workflows/ci.yml) runs `xvfb-run -a --server-args="-screen 0 1920x1080x24" npm run e2e` on `ubuntu-latest`, next to `check` and in parallel with it:

- **Electron binary.** Unlike `check`, it does not set `ELECTRON_SKIP_BINARY_DOWNLOAD`; the first launch downloads the binary through `@electron/get`, whose cache (`~/.cache/electron`, ≈ 120 MB) is kept with `actions/cache`, keyed on `package-lock.json`.
- **Linux.** The runner image already has Electron's libraries (`libnss3`, `libgbm1`, `libasound2t64`, …) and `xvfb`; the Chromium sandbox works without `--no-sandbox` or `chrome-sandbox` changes, so the job installs nothing. `xvfb-run` gives Electron a display although the windows stay hidden (`DFYOM_HIDE_WINDOWS=1`, set by the fixture). The virtual screen is 1920 × 1080: on xvfb's default 1280 × 1024 the 1440 × 900 window is clamped to the screen width and a second window cannot cascade (it goes back to the corner), which the smoke test's cascade check would see.
- **On failure** the job uploads the artifact `playwright-e2e` (7 days): the HTML report (`playwright-report/`, CI only) and the test output folders (`node_modules/.cache/playwright`: traces, app logs, error context). Download it with `gh run download <run> -n playwright-e2e`.
- **Time.** About 1 min for the job before X2 (build ≈ 3 s, tests ≈ 40–55 s); v0.2's X2 golden path adds ≈ 28 s, v0.3's ≈ 39 s, v0.4's ≈ 34 s (the whole suite ≈ 2 min locally on a loaded machine), 20 min timeout. The Linux runner is slower than a developer machine: a check that passes locally only because the app is fast can fail there (the first run found such a race in the exit-criteria test).
