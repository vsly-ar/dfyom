# P7: idle cost (CPU and memory while nothing happens)

Status: implemented (measurement report, 2026-11-23) · Task: P7 in [plans/hardening.md](../plans/hardening.md) · Specs touched: [run-v0.1.md § Host → main](../modes/run-v0.1.md#host--main), [ui.md § Document replica](../conventions/ui.md#document-replica)

The user's reason for asking: other CNC senders "always using resources like crazy" while idle were one reason to start DFYOM. This note measures DFYOM's idle cost, lists the idle work found and what was changed.

## Result

Idle DFYOM now costs **0.1–0.5 % of one core in total** in every state measured, including connected to the (virtual) machine. Before, connected and after a run it cost **about 12 %** (GPU process ≈ 6.4 %, renderer ≈ 5 %), because every 5 Hz status report redrew the 3D viewport even when nothing had changed. No other state had idle work worth removing.

## Method

- **App:** the built app (`npx electron-vite build`, app 0.3.90, Electron 45.3.3), launched by the e2e fixture (`e2e/app.fixture.ts`, isolated `--data-dir`), on an Apple M1 Pro (10 cores). A background app (gSender) used 100–275 % CPU throughout, so only DFYOM's own processes are measured, by PID.
- **States** (the v0.4 golden path's flow, `e2e/golden-path-v0.4.e2e.ts`, paused at five points): (a) no project, start screen; (b) the v0.4 enclosure lid in Design, part up to date; (c) Plan mode, toolpaths generated; (d) Run, connected to the virtual machine, homed, work zero set, idle (time scale Max, as in the golden path); (e) after the finished run, still connected, idle.
- **Per state:** 10 s to settle, then 60 s measured. CPU % = the CPU time each process used in the window (`ps -o time` before and after) ÷ wall time, so 100 % = one core. Memory = resident set size (`ps -o rss`) at the end of the window. The process list and types come from `app.getAppMetrics()`. Compute workers are `worker_threads` inside the main process (ADR 0016), so they are in "Main". In the same window the renderer counted WebGL `clear` calls (viewport frames) and draw calls.
- **Windows:** hidden test windows run with `backgroundThrottling: false`, and `document.visibilityState` was `visible`. A second pass showed the window but kept it invisible: opacity 0, ignores the mouse, `showInactive`, accessory activation policy, so it is never on screen and takes no focus. Both passes gave the same numbers (below), so hidden windows do not hide idle work here. Limitation: neither pass covers a window the user can actually see on a real display. The compositor of an opaque visible window may add a little more, but only when something draws, and idle nothing draws.
- **Runs:** 4 complete passes (before/after × hidden/invisible-shown), plus one discarded early pass whose own rAF counter added a 120 Hz loop. The per-state totals of the hidden and shown passes agree within ±0.4 percentage points.
- The measuring script was a scratch copy of the golden path with pauses. It is not kept in the repo. The guards below are the part that stays.

Per process, state (d), hidden pass, before → after:

| Process                        | CPU % before | CPU % after | RSS (MB)  |
| ------------------------------ | ------------ | ----------- | --------- |
| Main (incl. compute workers)   | 0.25         | 0.05        | ≈ 190–210 |
| GPU                            | 6.29         | 0.02        | ≈ 110     |

| Machine host (utility process) | 0.33         | 0.35        | ≈ 80      |
| Network service                | 0.00         | 0.00        | ≈ 41      |

Memory varies by ±80 MB between passes, mostly the renderer and main heap, which grow and shrink with GC. The fixes did not change it. Idle DFYOM holds ≈ 0.45–0.75 GB RSS in total. RSS counts shared pages in every process, so this is an upper bound.

The machine host's remaining ≈ 0.3 % is the GRBL status poll (`?` every 200 ms of clock time, [run-v0.1.md § Behaviour](../modes/run-v0.1.md#behaviour)). It is required while connected. When disconnected, the host process exits (`src/main/machine/serve.ts`), so nothing polls.

### Open (not changed)

- **Numeric time scales above 1× (virtual machine only).** The sender's status poll runs in clock time, so at 100× an idle virtual machine is polled ≈ 500 times per wall second inside the machine host. After I1, nothing more leaves the host. At `max` the clock already runs at real time while idle (`ScaledClock` `busy`). The golden path and the default (1×) are not affected. Running numeric scales at real time while idle would change virtual-time semantics, so it is left for when it matters.

## Guards

- `src/core/run/host/host.test.ts` › "an idle connection keeps polling but posts no unchanged status": 10 s of fake wall time idle, connected, gives no `status` message. A jog is posted at once. Verified red without the fix.
- `src/renderer/src/shell/hooks.test.ts`: one `job.list` read per poll for two readers, no reads for 60 s without a running job, and none after the last reader leaves.
- `e2e/run-manual.e2e.ts` (via `idleActivity` in `e2e/app.fixture.ts`): connected, homed and idle in the real app, the window draws **0 viewport frames** and receives **0 status pushes** in 2 s.
