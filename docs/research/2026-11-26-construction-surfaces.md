# Construction surfaces: references to surfaces a later cut removes

Status: draft (research and reproduction, 2026-11-26; hardening [DF118](../plans/hardening.md#intake-user-feedback-goes-here), user TG #369) · Design: [construction-surfaces.md](../modes/construction-surfaces.md) · Builds on: [design-v0.2.md § Surface table](../modes/design-v0.2.md#surface-table-per-direction), [geometry.md § Evaluation checks](../architecture/geometry.md#evaluation-checks)

Question: why does a reference to a pocket floor break when a later chamfer removes all of that floor, and how should a reference keep resolving? The user (TG #369, project clamps_40): "if I wouldn't leave a small rim inside the 'Pocket for M5', it would show an error that this reference surface for 'M5 long hole' and 'Chamfer 1' no longer exists (because it was later removed by the chamfer). I guess a virtual surface should remain to be referenced against. Probably as a product of just the operation 'Pocket for M5' against the surface it references. And up the dependency tree to the stock face."

## Summary

- **The model already does what the user asks.** A surface reference resolves through the analytic **surface table**, not through the mesh. `SurfaceTable.build` ([`surfaces.ts`](../../src/core/design/surfaces.ts)) gives each surface a level computed from its operation and the surface it stands on (`floor.level = on.level − depth`), back to a stock face. The slot's depth, the chamfer's level, the plan's toolpaths and the tolerances all come from that table. None of them changes when the floor is cut away.
- **Only one check uses the mesh.** `dfm.surfaceMissing` ([`checks.ts`](../../src/core/geometry/checks.ts) `surfaceMissing`) warns when no triangle of the evaluated part carries the referenced surface id. So it warns whenever a later cut consumes a surface, even when nothing is wrong. It also tells the user to "Pick another surface". Its text says "which the part no longer has", which reads like an error, and the user calls it one.
- **Root cause:** the check confuses "the finished part has none of this face left" with "this reference is broken". A reference to an id the table does not define cannot exist at evaluation time: `checkReferences` refuses it at command time (`design.referenced`), and the dependants of a disabled operation are switched off with it ([design.md § Disabling](../modes/design.md#disabling-operations-and-features-df106)).
- **Recommendation:** name the consumed surface a **construction surface**, keep resolving it as today, and replace `dfm.surfaceMissing` with a narrower check. If only the surface's own dependants cut it away (the chamfer, the slot), there is no warning. The `on` field shows a note instead. If an unrelated later operation cuts it away (a deeper facing erasing the floor a pocket was measured from), a `dfm.surfaceCutAway` warning names that operation and says the level still holds. See [construction-surfaces.md](../modes/construction-surfaces.md).

## Reproduction

Clamps_40 copy (unzipped into the session scratchpad; the original was not touched): stock 80 × 40.35 × 10.11 aluminium. The operations, in design order:

| Id (user's) | Name          | Kind    | `on`            | Size                                                            |
| ----------- | ------------- | ------- | --------------- | --------------------------------------------------------------- |
| facing1     | Facing top    | facing  | `stock.top`     | 0.3 mm                                                          |
| facing2     | Facing bottom | facing  | `stock.bottom`  | 0.3 mm                                                          |
| pocket2     | Pocket for M5 | pocket  | `facing2.floor` | rectangle 11.3 × 31 R 5.6, 2 mm deep (the recess)               |
| pocket1     | M5 long hole  | pocket  | `pocket2.floor` | rectangle 5.5 × 25 R 2.5, 7.8 mm deep (the slot)                |
| chamfer1    | Chamfer 1     | chamfer | `pocket2.floor` | edge of `pocket1`, width 5.7/2 = 2.85 mm, 90° (the countersink) |

The recess's half width is 5.65 mm. The slot's half width plus the chamfer is 2.75 + 2.85 = 5.6 mm. That leaves a **0.05 mm rim** of recess floor along each long side, which is the rim the user had to keep.

The same part was built through the design commands in a throwaway Vitest file in the scratchpad (not in the repo). It was evaluated with Manifold and the 2D port, with three chamfer widths:

| Chamfer width | Recess floor left                             | Evaluation warnings                                                                             |
| ------------- | --------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| 2.85 mm       | 0.05 mm rim along the sides                   | none                                                                                            |
| 2.95 mm       | the sides gone, slivers at the slot ends      | none                                                                                            |
| 3.2 mm        | none (the cone reaches past the recess walls) | `dfm.surfaceMissing` on the slot's `on` and on the chamfer's `on`, both naming the recess floor |

In every case the operations' levels, the slot's depth and the chamfer's level stay the same, because the surface table does not change. Only the warning appears. `design.warning.list` already merges it when the evaluation is current ([design.md § DFM warnings](../modes/design.md#dfm-warnings-task-28-wiring)). In the 3.2 mm case the two warnings tell the user to pick another surface, but no other surface means the same level.

## Where references are resolved today

| Consumer                                                               | Source of the level or surface                                           | Affected by consumption?                                                                              |
| ---------------------------------------------------------------------- | ------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------- |
| `on`, formulas (`pocket2.floor.z`), recalculation, `design.referenced` | `SurfaceTable` (analytic, exact rationals, tolerances) and `designGraph` | no                                                                                                    |
| Geometry (`onZ` per operation)                                         | `partGeometryInput` from the table                                       | no                                                                                                    |
| Plan: toolpath levels, hole depths, tool checks                        | `SurfaceTable.of`                                                        | no                                                                                                    |
| Plan: Z reference (touch-off surface)                                  | in-process stock patches ([z-reference.md](../modes/z-reference.md))     | already handled: a consumed floor is refused as `cutAway`, with a clear message                       |
| `dfm.surfaceMissing`                                                   | triangles of the evaluated part                                          | **yes: false warning**                                                                                |
| Pick mode glyphs, hover highlight of the `on` surface                  | triangles of the evaluated part (`surfaceGlyphs`)                        | **yes: a consumed surface cannot be picked or shown in the 3D view** (the `On` select still lists it) |
| `design.measure` `faceCentre`                                          | triangles                                                                | yes, correctly: there is no face to measure                                                           |

## How CAD and CAM tools handle it

- **The topological naming problem (CAD).** A history-based modeller references faces and edges of the _result_ of earlier features. When a later feature splits, merges or removes that face, the reference breaks or jumps to another face. FreeCAD documents it as the [topological naming problem](https://wiki.freecad.org/Topological_naming_problem). Its advice is to attach sketches and datum objects to the origin planes, or to datums offset from them, and not to generated faces ([Feature editing](https://wiki.freecad.org/Feature_editing)). Realthunder's algorithm, the basis of the FreeCAD 1.0 mitigation, tracks element names through each operation ([Topological Naming](https://github.com/realthunder/FreeCAD_assembly3/wiki/Topological-Naming)). Reports say dress-up features (chamfers, fillets) still break references ([Hackaday on FreeCAD 1.0](https://hackaday.com/2024/09/21/freecad-is-near-1-0)). The problem is old: [Capoyleas et al. 1996](https://www.cs.purdue.edu/cgvlab/www/resources/papers/Capoyleas-Computer_aided_design-1996-Generic_naming_in_generative.pdf) show an edge round in Pro/ENGINEER "jumping" to another edge on regeneration.
- **Onshape** stores _queries_ instead of entity ids, and re-evaluates them on each regeneration. An evaluated query (a transient id) is only valid right away. Queries such as `qCreatedBy(feature)` name entities by the feature that made them ([FeatureScript library](https://cad.onshape.com/FsDoc/library.html); [forum: transient vs tracking queries](https://forum.onshape.com/discussion/11010/fixing-a-query-so-it-doesnt-change)). Onshape users still report references to edges that a later chamfer or fillet consumed ([forum](https://forum.onshape.com/discussion/comment/108786)).
- **Fusion (CAD):** the usual practice is construction planes offset from the origin, so a sketch does not lose its plane when a face goes away. **Fusion CAM** measures every height from a named reference (Model top, Stock top, Hole top, or a Selection: "Incremental offset from a Point (vertex), Edge, or Face selected on the model"), plus an offset ([Top height](https://help.autodesk.com/cloudhelp/ENU/Fusion-CAM/files/MFG-REF-TOP-HEIGHT.htm)). The page does not say what happens when the selected face changes. The named references are levels, not faces.
- **What DFYOM already has:** its references are **semantic, not topological**. A surface id is `<operation id>.<role>`, and its level is a function of the design (operation × the surface it stands on, back to a stock face). That is the design-intent datum the CAD best practice builds by hand. DFYOM does not have the topological naming problem. It only has a check that looks for the face in the mesh.

## Options

| ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| **1. Construction surfaces, narrowed check (recommended).** Resolve as today. A consumed surface is a construction surface. Warn only when an operation that does not depend on it cuts it away | Fixes the user's case with no data change. Keeps a useful warning for an unrelated cut erasing a datum (the pocket's visible depth shrinks). Shows the surface in the UI | Needs the consumers of a surface: a slab intersection in the evaluation, only for surfaces that lost all triangles                                |
| 2. Drop `dfm.surfaceMissing`                                                                                                                                                                    | Smallest change                                                                                                                                                          | Loses the hint when a later facing or pocket erases the floor an unrelated pocket was measured from                                               |

Persistent or topological naming (track faces through the booleans)                                                                                                                          | Familiar from CAD                                                                                                                                                        | Solves a problem DFYOM does not have. Status quo: leave a rim, or re-point `on` to another surface                                                                                                                                 | –                                                                                                                                                                        | The user's complaint. A rim of 0.05 mm is a fake design change. Re-pointing changes the intent (the slot would no longer follow the recess depth) |
